# ヘルプと問題の報告

AoT を使っていて行き詰まったら、まず画面右上の **ヘルプ** メニューを開きます。いま見ている画面のマニュアル、
オンラインマニュアル全体、API ドキュメント、AoT の GitHub にすぐ移動できます。エラーが起きたら、エラー画面とシステムログから
情報を集め、AoT の GitHub にイシューとして報告します。AoT には最初からこの方法があり、今も最も基本となる手段です。

## この章を終えると { #goal }

- いま見ている画面の説明と API ドキュメントを自分で探せる
- エラーが起きたときに、必要な情報を集めて GitHub に報告できる

## 始める前に { #prepare }

- ログインできる AoT（[インストール](g01-install.md#check)）
- 問題を報告する場合は GitHub のアカウント

## 手順 { #steps }

### 1. ヘルプメニュー { #step-1 }

画面右上の **ヘルプ** をクリックすると、次の項目が表示されます。すべて新しいタブで開きます。

| 項目 | 開く場所 |
|---|---|
| **ヘルプ: <画面名>** | いま見ている画面を説明するマニュアルの節。説明がある画面でだけ表示されます |
| **オンラインマニュアル** | マニュアルのトップページ |
| **ユーザーガイド** | このガイドの最初のページ |
| **API情報** | マニュアルの API の説明ページ |
| **APIドキュメント** | この AoT に組み込まれている API の一覧画面（`/api`）。リクエストの形式と応答を直接確認できます |
| **AoT GitHub** | AoT のソースとイシュー掲示板 |
| **AoTホームページ** | AoT の紹介サイト |
| **プライバシーポリシー**、**利用規約** | 該当する文書 |

マニュアルは、画面の言語に合わせて韓国語・日本語・英語の版が開きます。

設定画面の項目名の横にある **?** マークをクリックすると、その項目だけを説明したマニュアルの節に移動します。

### 2. エラー画面から情報を集める { #step-2 }

画面を開く途中でエラーが起きると、**エラー 500: 内部サーバーエラー** の画面が表示されます。この画面には、AoT のバージョン、
データベースのバージョン、ボードの情報、エラーの完全なトレースが表示されます。

1. 画面に表示された情報をすべてコピーします。
2. **GitHubで新しいイシューを報告する** のリンクをクリックすると、AoT の GitHub のイシュー作成画面が開きます。
   同じ問題がすでに報告されていないかは、先に **GitHubの問題** のリンクで探しておきます。
3. コピーした情報を貼り付け、何をしていたときにエラーが起きたかを書いて送信します。

AoT は、エラーの情報を自分からどこにも送りません。報告するには、自分でイシューを投稿する必要があります。

!!! warning "投稿する前に秘密の情報を削除してください"
    GitHub のイシューは誰でも見られます。貼り付ける内容に API キー、パスワード、メールアドレス、現場の住所や
    IP アドレスが含まれている場合は、削除してから投稿してください。

### 3. システムログをダウンロードする { #step-3 }

エラー画面は出ないのに動作がおかしい場合は、ログを確認します。

1. **管理** → **システムログ** を開きます（画面のタイトルは **ログ表示**）。
2. ログの種類（デーモン、Web アプリなど）と最小レベルを選び、問題が起きた時刻の前後を確認します。
3. **ダウンロード** をクリックすると、選んだログがテキストファイル（最大 2000 行）として保存されます。このファイルをイシューに添付します。

AI を接続している場合は、ログ画面の **説明**、**原因を診断**、**解決方法は?** ボタンで、選んだ行の意味を
尋ねることもできます（[AI・MCP 接続](g12-ai-mcp.md)）。

### 4. バージョンと状態を確認する { #step-4 }

**管理** → **システム情報** で、**AoTバージョン**、デーモンの状態、ディスクの使用量を確認します。イシューを投稿するときは、
AoT のバージョンとインストール方法（Docker または直接インストール）をあわせて書いてください。同じ問題がすでに修正されたバージョンがあるかどうかを
判断するのに必要です。

### 5. API を使う { #step-5 }

ほかのプログラムから AoT の値を読んだり機器を操作したりするには、API を使います。

1. **ヘルプ** → **APIドキュメント** で、使えるリクエストを探します。**API情報** では、使い方の例と規則を説明しています。
2. リクエストするときは、ユーザーの API キーを `X-API-KEY` ヘッダーに入れます（`Authorization: Bearer <キー>` も使えます）。
3. ユーザーの API キーは、**管理** → **システム管理** → **ユーザー一覧** → ユーザーの編集 → **APIキー** で、**新しいキーを発行** の行に
   名前を入力して **生成** をクリックすると作成されます。キーは **作成したときに1回だけ** 表示されるので、すぐに安全な場所に書き留めておきます。

**APIキー管理** メニューはこれとは別のものです。そこは、天気サービスや地図サービスのように AoT が外部サービスに使う
キーを保管する場所で、ユーザーの API キーはユーザーの編集画面でだけ作成します。

## 確認 { #check }

**ヘルプ** メニューからオンラインマニュアルと API ドキュメントが開き、問題が起きたときに投稿する情報をどこで得られるかがわかれば完了です。

- 設定画面を1つ開き、**ヘルプ: <画面名>** がその画面の説明につながるか
- **管理** → **システムログ** でログをダウンロードできるか
- **管理** → **システム情報** で AoT のバージョンを見つけられるか

## 現場 A { #site-a }

現場 A では、管理担当者1人が問題をまとめて GitHub に投稿します。現場の人は、おかしな点に気づいたら画面を
キャプチャーして時刻を書き留め、担当者に渡します。担当者は、その時刻のデーモンのログをダウンロードしてイシューに添付します。

## 現場 B { #site-b }

現場 B は既存の制御設備とつながっているため、問題が AoT 側にあるのか既存の設備側にあるのかを、まず見分ける必要があります。出力のコマンドが
送られたかは **管理** → **監査ログ** で、AoT が値を受け取ったかは **ライブ測定** で先に確認してから、イシューを投稿します。

## うまくいかないとき { #trouble }

| 症状 | 確認すること |
|---|---|
| **ヘルプ: <画面名>** の項目がない | その画面には、個別に結び付けられた説明がありません。**オンラインマニュアル** で探してください |
| マニュアルが開かない | マニュアルはインターネット上の `aot-inc.github.io` にあります。インターネットに届くか、ファイアウォールの許可リストに入っているかを確認します（[ネットワーク接続](g03-network.md#step-4)） |
| API のリクエストが拒否される | `X-API-KEY` ヘッダーにユーザーの API キーを入れたか、そのキーの権限がリクエストに合っているかを確認します |
| ユーザーの API キーをなくした | もう一度表示することはできません。新しく作成し、以前のキーは削除してください |
