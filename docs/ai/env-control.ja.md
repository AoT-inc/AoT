# 環境制御自動化

AoTの`env_coordinator`(画面上は**統合環境制御**)は、1つの施設のすべてのアクチュエーター
— 換気窓、排気・吸気ファン、ヒーター、冷房機、噴霧器、遮光スクリーン、保温カーテン、
補光照明、CO₂インジェクター — を1つにまとめて協調させる3層制御システムです。

異なる2つの場所で決まる、2つのことがあります。この2つを混同するのが、もっとも
よくある混乱の原因です。

- **何を目指すか** — VPD・CO₂・DLIなど — は、その施設で育っている**区画**の
  ものです。区画に付いた栽培プログラムを通じて決まります。
- **どう到達するか** — どんな設備があるか、越えてはいけない線はどこか、
  目標をどれだけ強く追うか — は**この関数**のものです。

---

## 目標はどこで決まるか { #targets }

| 層 | 持っているもの | 編集する場所 |
|-------|------|-----------|
| プログラム(`GeoProgram`) | 参照計画: 生育ステージ、目標項目の語彙、目標カーブ、作物の光合成定数 | プログラムページ |
| 区画(`GeoPlot`) | 実際の計画: ステージ境界日と、この区画のステージごとの目標値 | 区画画面(ステージスケジュール) |
| env_coordinator | 到達方法: 設備構成、安全の上下限、優先順位、チューニング、緊急時の挙動 | Function設定 |

区画は選んだプログラムを**内在化**します。区画画面でステージの目標値を編集すると、
その区画のその項目だけが上書きされ、プログラム本体や同じプログラムを使う他の区画には
影響しません。欄を空にすると、その項目はプログラムの値に戻ります — そのため
「元に戻す」ボタンを別に用意していません。

意図した制約が2つあります。

- 区画は新しい目標**項目**を作れません。語彙はプログラムのもの(`target_defs`)
  なので、未知のキーは黙って無視されるのではなく拒否されます。
- **カーブ**が設定されている項目は、数値で上書きできません。カーブが優先され、
  区画画面ではその項目が読み取り専用として表示されます。

### コーディネーターが毎サイクル読み込むもの { #targets-read }

| 値 | 用途 |
|-------|------|
| VPD目標(数値またはカーブ) | 主制御目標 |
| CO₂目標(数値またはカーブ) | CO₂施用。ないときはCO₂制御は休止します |
| ステージの昼温度・夜温度・湿度 | 今サイクルの[推奨範囲](#stage-guide) |
| DLI目標・日別GDD目標 | 累積トラッカー |
| `T_base` | GDDの積算 |
| 区画の開始日 | 経過週数 — ステージ型のカーブはこれで進みます |
| 光合成定数(`A_max`, `K_L`, `K_C`, `T_opt`, `T_sigma`, `VPD_half`) | Big-Leafモデル、および`K_L`から導かれる光飽和点 |

目標項目と制御軸は、項目のキー名ではなく**測定値の種類と形**で結び付きます —
利用者が「室内CO₂」と名付けた項目でも、測定値がCO₂であればCO₂制御に届きます。
測定値を選んでいない項目はどの軸にも届かず、画面には*参考のみ*と表示されます。

### 区画がないとき { #targets-no-plot }

コーディネーターは**止まりません。** 区画がない、プログラムがない、まだ確認されて
いないAI下書きしかない、プログラムの種類が区画の種類と合っていない、あるいは今日に
該当するステージがない場合は、単に目標がないだけです — 制御は自分自身の推奨範囲の
中で動き続けます。これはすでに定義された挙動であり、栽培中の作物がない温室でも暖房は
必要だからです。

### 昼夜の温度と湿度が推奨範囲を決めます { #stage-guide }

第一目標は引き続きVPDです。ステージの**昼温度**・**夜温度**・**湿度**は目標ではなく、
VPDを暑すぎて湿った組み合わせや寒すぎて乾いた組み合わせで達成することを防ぐガイドです。
コーディネーターは毎サイクル、自分の推奨範囲を次のものに置き換えます。

| | 範囲 |
|---|---|
| 温度 | ステージの昼温度（施設の位置での日の出〜日没）または夜温度 **± 5 °C** |
| 湿度 | ステージの湿度 **± 10 %** |

- 幅は固定で、プログラムの設定ではありません — 栽培技術資料の多くは平均値だけを示し、
  昼夜の幅は書いていないためです。
- ステージにその値がない、または施設の位置が分からず日の出・日没が求められない場合、
  その項目は機能自身の推奨範囲を使います。
- ハード上下限（`Min/Max Temperature`、`Min/Max Humidity`）が最後に適用されます。
- 推奨範囲を読むところはすべて追従します: VPDを分けた温度・湿度、VPD目標がないときの
  中央値、予報補正、換気の温度上限。
- 実際に使った範囲は機能設定の区画の下に **ガイド範囲** として表示されます。

コーディネーターには**自分自身の終了日オプションはありません。**
栽培を続けるかどうかは区画が決めます。Functionに日付を持たせると、新しい作物を
植えたあともその日付のせいで施設が止まったままになることがあるためです。

### 制御の基準 — VPD直接 / 温度優先 { #control-basis }

既定は**VPD直接**です — 上のとおりVPDの目標を追い、温度・湿度はガイドです。高度な設定の
**制御の基準**を**温度優先**に変えると、コーディネーターごとに次のように動きます。

- **温度が第一の目標です。** ステージの昼間・夜間温度(施設位置の日の出・日の入り基準)を
  追います。
- **湿度の目標はVPDの目標から作ります** — その温度でVPDの目標になる湿度です(例: 24°Cで
  VPD 1.0なら約66%)。誘導範囲の外なら範囲の端で切ります。
- **VPDは境界です。** 目標より0.4 kPa低くなるか0.8 kPa高くなったときだけ戻す方向に押します。
- ステージに温度がなければ、**温度は追わず**、誘導範囲内に保つだけです。

VPDを直接追うと、同じ許容誤差が8°Cでは湿度±9%、35°Cでは±1.8%になり、低温では届かない
湿度を求めることもあります。温度優先にはこの差がありません。

どちらを選んでも、もう一方の「その基準だったら送ったはずの指令」を毎サイクル計算して記録します
(制御には使いません)。同じ施設で2つの方式を比べるためです。

### スコープ内に区画が2つ以上あるとき { #targets-reference-plot }

間作・混作は普通に起こることなので、コーディネーターは推測しません。施設・ベイの
スコープ内に区画が2つ以上あるときは、そのことを伝えて**これに従う**ボタンを
出します。同じ選択は、詳細設定の**基準区画**にも保存されます。指定した区画が
終了したりスコープの外に出たりしても、値は消えません — 画面が「指定した区画は
もうここにありません」と伝え、選択ルールをあらためて適用します。

> 区画に記録されるプログラムのバージョンは、*バージョン番号*を固定するだけで
> *内容*までは固定しません。プログラムを編集すると、進行中の区画の解釈も
> 変わります。

## VPD(飽差) { #vpd-vapor-pressure-deficit }

VPDは、植物の蒸散と吸水を左右するもっとも重要な指標です。

```
VPD = SVP × (1 - RH/100)
SVP = 0.6108 × exp(17.27T / (T + 237.3))  [kPa]
```

| 範囲 | 状態 | 推奨する作物ステージ |
|-------|--------|----------------------|
| < 0.4 kPa | 低すぎる — カビのリスク | — |
| 0.4–0.8 kPa | 適正 | 発芽期/定植初期 |
| 0.8–1.2 kPa | 適正 | 栄養生長期 |
| 1.2–1.8 kPa | 適正 | 開花・結実期 |
| > 1.8 kPa | 高すぎる — 水ストレス | — |

### 空気VPDと葉VPD — 目標を何と比べるか { #leaf-vpd }

蒸散を駆動するのは、葉の内部(**葉温**で飽和)と周りの空気との差です。上の式は**空気VPD** —
葉が気温と同じとみなした値です。葉VPDは

```
葉VPD = SVP(葉温) − RH/100 × SVP(気温)
```

葉が空気より冷たければ空気VPDより低く、暖かければ高くなります(25 °C・70 %: 空気0.95 kPa、
1.5 °C冷たい葉0.68 kPa)。作物にとって大事なのは葉VPDで、空気VPDは参考値です。ただし葉温は
ほとんど測られておらず、コーディネーターの効果モデル・温湿度への分解・ステージのガイドはすべて
空気VPDでできているため、**制御量は空気VPDのまま**にして目標だけを換算します。

詳細設定の**VPD目標の基準**で選びます:

| 設定 | 動作 |
|---|---|
| **空気VPD**(既定) | 目標を、フィルター後の温度・湿度から計算した空気VPDと比べます — これまでとまったく同じです。 |
| **葉VPD** | 目標は葉VPDです。サイクルごとに、測った葉温でその葉VPDになる空気VPDに換算します: `空気目標 = 葉目標 + SVP(気温) − SVP(葉温)`。25 °Cの空気で葉が1.5 °C冷たければ、葉目標0.80 kPaは空気VPD約1.07 kPaになります。許容誤差(kPa)は変わりません。 |

赤外線の葉温(群落温度)センサーがあり、目標が葉VPDの値(多くの作物指針はそう示します)の
ときに**葉VPD**を選んでください。センサーは**葉温センサー**に割り当てます。割り当てがなければ、
葉の設定はエラーを一度記録するだけで何もしません。

葉温は、新しく(屋内センサーと同様に自身の更新周期で判定)、物理範囲内で、一つの値に止まって
おらず(屋内温度と同じ[止まったセンサー](#l2-situationreport-evaluation)の窓)、**気温との差が
10 °C以内**のときだけ使います — それより大きければ、センサーは葉ではなく床・骨組み・空を見て
います。軽く平滑化します(0.3 °Cの揺れがそのままだと目標が約0.06 kPa動きます)。使えないときは
**そのサイクルは空気基準**で動き — 同じ数値を空気VPDの目標として使い — 切り替わるたびに一度ログを
残します。**葉温を固定オフセット(気温 − 1.5 °Cなど)で推定することはしません**: 日なたで気孔を
閉じた葉は空気より暖かく、晴れた夜の葉は冷たいので、固定オフセットは空気目標の名前を変えるだけ
です。葉が空気よりはるかに暖かく、飽和した空気でも目標まで下げられないときは、空気目標は
0.1 kPaで止まります。

空気基準でもセンサーを割り当てておく意味があります — [施設ウィジェット](../geo/facility-widget.md#b-environment)
に空気VPDと並んで葉VPDが表示され、記録されます。目標の段階を飛ばすサイクル(安全ゲート・運転
時間帯の外)は新たに判定せず、最後の判定が3周期(最低5分)より古くなるとウィジェットはそれを
表示しません。センサーを割り当てているか葉基準のとき、
コーディネーターは毎サイクル(デバッグに関係なく)チャンネル94(0 空気基準 · 1 葉基準 · 2 葉基準だが
使える葉温がなく空気)、95(葉VPD、kPa)、96(設定した葉目標)を記録します。葉基準ではVPD目標の
チャンネル(3)は換算後の空気目標です。ヘルスチェックは2で動いた分数を報告します — センサーを人が確認してください。AIツール(`get_control_state`とAI要約)も同じ組を`vpd.air_kpa`・`vpd.leaf_kpa`というラベルで伝え、葉の値は葉温を測っている間だけ存在します。

> **以前のバージョンで保存されたVPD値。** 入力の自動VPDチャンネル(*自動VPD*、葉温 = 気温 − 1.5 °C)
> と**AoT VPD**ファンクションは、*空気*の湿度を*葉*の飽和水蒸気圧に掛けていたため、冷たい葉の
> VPDを過大にしていました(上の例で0.68ではなく0.87 kPa)。現在は上の式を使うので、更新後は
> 保存値が約0.06〜0.4 kPa下がります。コーディネーターはこの値を制御に使ったことはありません。

## env_coordinatorの制御レイヤー { #env_coordinator-control-layers }

### L1 — EnvTarget(設定値) { #l1-envtarget-setpoint }

上で説明した目標を、このサイクルの設定値へと解決します。Methodに従う目標項目は、
区画の経過週数と施設のローカルタイムゾーンで評価されます。

### L2 — SituationReport(評価) { #l2-situationreport-evaluation }

現在の偏差、制限要因、傾向を評価します。

室内の温度・湿度・VPDは、まず**ノイズを除きます。** センサーの表示刻み(温度0.1°C、湿度1%)が上下するだけで窓が動かないようにするためです。
指数平滑を使いますが、元の値が温度0.5°C・湿度3%以上離れたら実際の変化とみなし、すぐに元の値に追従します。
**制御が使うVPDは常に、除去後の温度・湿度から計算した空気VPD**です。
センサーが自前のVPDチャンネルを持っていても制御には使いません — 葉温を見積もった値(気温 − 1.5°C)でVPDを出す装置があり、その値は目標と温度・湿度の分解が前提とする空気VPDより低く出るためです。
装置のVPDは、温度または湿度を失ってそれしか残らないときに限って代わりに使われ、両者の差は記録に残ります。
**安全ゲートとハード上下限は除去前の元の値で**判定します — 保護をフィルターの分だけ遅らせません。

**すべての読み取りに状態を付けます。** 制御が読む軸(室内の温度・湿度・CO₂・VPD・光量、屋外の温度・湿度・風速・降雨・日射)ごとに、センサーが返したものを`valid`(使える)、`stale`(鮮度の上限を超えた古い値)、`missing`(値がまったくない)、`outlier`(他のセンサーと大きくずれて平均から外れた)、`out_of_range`、`frozen`(下記)のいずれかに分け、軸の状態はその軸を支えるセンサーのうち最も良いものです。
**制御の動作が変わるのは最後の2つだけです。** あり得ない値(湿度102%超、温度が−40〜70°Cの外、CO₂が150〜10,000ppmの外など)は平均にも制御にも入りません — 湿度130%を報告するセンサーは値がないものとして扱います。
止まったセンサーも同じ形で外します。
湿度100〜102%は目盛り誤差なので100%に切って使い、日射計が夜に出す−5 W/m²以内の値は0として読みます。
それ以外の状態は記録するだけです。
軸に使えるセンサーが1台も残らないときは、[測定のない軸、装置のない軸](#actuators-missing)の規則に従います。
デバッグログがオンなら、軸ごとの状態を測定`sensor_status`のチャンネル80〜89(室内の温度・湿度・CO₂・VPD・光量、続いて屋外の温度・湿度・風速・降雨・日射)に、0 valid · 1 stale · 2 missing · 3 outlier · 4 out_of_range · 5 frozen として残します。
チャンネル90は制御VPDの出どころ(0 なし · 1 温度・湿度から計算 · 2 装置)、チャンネル91は装置のVPDから制御VPDを引いた値(kPa)です。

**値が動かなくなったセンサーは外します。** ミラー装置やゲートウェイが更新を止めても、読み取りごとに
現在時刻を付けて送り続けることがあります。すると鮮度チェックを通過し、数字ももっともらしいため —
温室が46°Cなのに30.7°Cと読み、窓を閉めてしまいます。そこでセンサーごと、温度・湿度・CO₂のそれぞれに
ついて、値がセンサーの刻み(0.05°C、0.1%、1ppm)以内でどれだけ同じままかを数えます。正常なセンサーなら
必ず変化したはずの時間より長く同じで、かつ*異なる*読み取りが6件以上届いていれば、そのセンサーは
あり得ない値と同じ扱いにして平均から除きます。

| 状況 | 変化がない時間 |
|------|----------------|
| 昼(屋外日射100W/m²超) — 温度・湿度 | 60分 |
| 夜だが30分以内に装置が動いた — 温度・湿度 | 2時間 |
| 静かな夜 — 温度・湿度 | 3時間 |
| CO₂ | 2時間 |

同じ軸に正常なセンサーが他にあれば、それらで制御を続けます。止まったセンサーが唯一のものだった場合、
その軸は測定できないものとして[測定のない軸、装置のない軸](#actuators-missing)の規則に従います(装置は今の位置を保持)。
**値が変わった瞬間に、そのセンサーはすぐ使われます。** 整数しか出さないセンサー(湿度センサーに多い)は
時間を3倍にします — 静かな夜には同じ整数が何時間も続き得るためです(実測で最長4.5時間)。湿度100%は
数えません。更新の合間に同じ読み取りを再配信する遅い装置も止まったとは見ません — 新しい読み取りだけを
数えます。カウントはメモリ上にあり、再起動すると最初から数え直します。切り替えは1回ずつログに残り、
ヘルスチェックがその軸を`frozen`として知らせます。

⚠ 周期ごとに点を書きながら実際に終始同じ値にとどまる装置は、止まったセンサーと区別できません —
代償はそのセンサー1台が平均から外れるだけです。「変化時のみ報告」する装置かどうかを示す装置別の設定は
ありません。

| 評価項目 | 説明 |
|----------------|-------------|
| 偏差 | `現在値 - 目標値` |
| 制限要因 | 光・CO₂・温度・水分(VPD)のうち、どれが光合成を妨げているか |
| 傾向 | 値が目標の方向へ動いているか |

VPD目標があり、VPDを測定できるとき、温度と湿度は*制約*に格下げされます — VPDを
分解して得られる範囲であり、越えてはいけない線です。この関数はサーモスタットではありません。温度または湿度を失ってVPDを計算できないときは、そのサイクルは温度・湿度の基準に退きます([測定のない軸、装置のない軸](#actuators-missing))。

[猛暑保護](#heat-protect)中は、そのモードが先頭に来ます — *猛暑保護*、段階2では*緊急*。

### L3 — Coordinator(アクチュエーター指令) { #l3-coordinator-actuator-command }

装置ごとに**位置形PI**で0〜100%の指令を出します。教科書どおりのPIとは3つの点で
異なります。

- **積分は累積誤差ではなく、その装置の「記憶された平衡開度(%)」**で、常に0〜100に
  収まります。偏差が小さいときは積分がそのまま残り、直前の開度を保ちます。
- **1つの装置が複数の軸に効くときは、偏差を1つにまとめます。** たとえば開口部は
  温度・湿度・CO₂のすべてに影響します。軸ごとの偏差を比例帯(許容誤差 × 6)で割って
  同じ尺度にそろえ、*優先度 × その装置がその軸に与える効果の大きさ*で重み付き平均
  します。
- **許容誤差の半分以内は休む区間(デッドゾーン)**です。その外ではデッドゾーンの分を
  差し引いた値を使うため、境界で指令が階段状に跳ねません。

```
e      = Σ(優先度 × 効果 × 偏差/比例帯) / Σ(優先度 × 効果)
e_eff  = e からデッドゾーン(許容誤差 × 0.5)を差し引いた値
I      = clamp(I + 0.2 × e_eff, 0, 100)          # 記憶された平衡開度
指令   = clamp(1.0 × e_eff × 100 + I, 0, 100)
```

- **確定の順序はコスト指数の順**です(安い装置から)。同じドメインの中では、後の装置は
  前の装置が生む効果を差し引いた残りの偏差だけを見ます — これが負荷分担です。
- **動かしても効かない装置は休みます。** 100%で動かしても比例帯の2.5%未満しか
  動かせない場合(たとえば室内外の差がほとんどない換気)や、パーキング対象(水がないときは[噴霧器すべて](#water-supply))の場合は、
  サイクルごとに安全位置までの距離を60%に縮めながら、ゆっくり安全位置へ向かいます。
  保温カーテンは例外で**その場に留めます** — 安全位置(開)へ戻すと、夜に室内外の差が
  小さくなった途端に保温が外れてしまいます。その場に留めるのは熱の需要がない夜だけで、
  保温が必要なら閉じます([夜の保温](#curtain-gap)、根拠 49)。判定にはヒステリシスがあります — 一度
  効くと判定した装置は、しきい値(2.5%)の半分を下回るまで「休み」に切り替わらないため、
  しきい値付近で揺れる効果によって窓が開閉を繰り返すことはありません(根拠「主作用」↔「勾配なし」)。
- **疑わしい装置はその位置にとどめます。** 送信の失敗が続く装置、または何時間も強く命令したのに反応がない窓は、いる位置に置いたまま新しい命令を受けず、負荷分担の台帳にも何も載せないため、同じドメインの残りがその分を引き継ぎます([疑わしいアクチュエーター](#actuators-suspected))。
- **VPD 直接モードでは、暖房機は温度範囲の上限より上では動きません。** このモードで暖房機が受ける要求は VPD だけで、日没後は昼の VPD 目標がゆっくり下がる一方、温度範囲は一度に下がります(22–32 → 12–22 °C)。そのため暖房出力は誘導範囲の上限の 1 °C 手前から直線的に絞られ、上限以上で 0 になり、1 サイクル 20 %p のスルーを待たずにすぐ下がります(根拠 17)。最低温度の限界(Min Temperature)は従来どおり優先され、温度が制御目標のときはこの上限をかけません。
- **まもなくパーキングされる窓は、それ以上開けません。** [夜間閉鎖](#settings-ventilation)が始まる前の45分間、換気窓とファンは閉じることはあっても、VPD・湿度・通常の温度要求で今の開度を超えて開くことはなく、積分もそれ以上積み上がりません(理由48)。温度・湿度のハード上下限、[猛暑保護](#heat-protect)、結露エスケープは、それでも開けます。
- **雨のときは窓が上限を守ります。** [降雨の段階制限](#safety-gates)の間は、側窓は 30 % を超えず、予報の小雨で留めた天窓は今の位置より開きません — VPD・湿度の要求、日射の最低開度、[朝の湿気抜き](#morning-purge)、[猛暑保護](#heat-protect)の段階 1 が何を求めても。積分も上限に留めるので、雨がやんだ瞬間に窓が跳ねません(根拠 52)。
- **日が差すと窓は最低開度を保ちます。** 屋外日射が200 W/m²以上で、室内が作物の温度線(温度目標 + 許容差 — VPD直接モードでもステージ温度 + 1 °Cを超えない)より高く、外が1 °Cを超えて暑くなければ、VPD・湿度の要求は超過に応じた15–80 %の最低開度より下に窓を閉められず、積分もそこに留まります(根拠51)。[日射の熱を逃がす](#solar-vent)を参照。
- **室内の値がなくても、晴れた日は窓を少し開けます。** 室内温度を失っても外気の値が実測で、日射があり、外気が12 °C以上で、外気 + 日射1 W/m²あたり0.02 °Cが作物線より高ければ、測定がないためその場にとどまるはずの窓をサイクルごとに5 %pずつ10–20 %まで開け、日が沈んだ後はその程度に開いた窓を同じ幅で閉め直します(根拠60)。[晴れた日に室内の値が途切れたとき](#solar-vent-blind)を参照。
- **「その場」は実際に出た開度を守ります。** ルールが窓をその場に置くとき(外気・室内の値なし、換気無益の判定直後、夜間閉鎖直前の45分、雨・風の値を失って「これ以上開けない」、開けても反応がない)、指令は直前に実際に出た開度を今回のサイクルの伝達比率(風向重み)で割った値です。直前の開度をそのまま出すと重みがサイクルごとにかけ直され、「その場」のはずの窓が少しずつ閉まりました — 記録されたある朝、根拠21のまま50分で20 → 16 → 13 → 12 → 7 → 0 %。
- **朝の日射では過湿な家を少し換気します。** 屋外日射が100 W/m²以上で、室内が過湿ゾーンにあり、露点が屋外より2 °C以上高ければ、家が温度目標の下限線より大きく低くない限り、窓を「外気が冷たすぎます」でパーキングする代わりに5〜15 %の最低開度を与えます(根拠54)。[湿気抜き](#morning-purge)を参照。
- **日中は保温カーテンを開けておきます。** 効果モデルはカーテンの熱交換しか知らず、光を遮ることは知らないため、施設位置の日の出から日の入りまでは開けておき、夜だけ判断します。
  寒波などの安全ゲートはこの規則より優先します。
  途中で止められるカーテンは、朝に一度にではなく段階的に開けます([保温カーテン — 夜のすき間と朝の段階開け](#curtain-gap))。
- **遮光スクリーンは光に従って動きます。** 熱負荷と蒸散を抑えるのに使ってよいかは、作物が受ける光を見て1か所で決め、往復しないように動きを絞り込みます([遮光スクリーンで暑さを抑える](#shade-heat))。
- **カーテン・遮光スクリーンは全閉か全開のどちらかです。** いまの側から反対側へ動くには指令が60%(開ける)または40%(閉じる)を越える必要があり、50%付近で端から端へ往復しません。
  記録と画面にも実際に送った0/100が残ります。
  例外は途中で止められる保温カーテンの夜のすき間と朝の段階開けだけで(3 · 6 · 10 · 30 · 60%)、このときも記録には実際に送った値が残ります。
- **押す向きが反転したら、続くかを見てから従います。** 換気窓のVPD効果は冷却と乾いた
  外気が競り合った合計なので、両者が近いと外気湿度の数%で向きがサイクルごとに変わります。
  新しい向きが10分以上(かつ2サイクル以上)続いたときだけ従い、それまではその場に留めます。
  室温が誘導上限に届いたときに加わる温度項も、超えた分に応じて**徐々に**重みを得ます —
  線の付近を上下しても換気窓が階段状に上下しないようにします。
- **側窓は風を受ける側を広く開けます。** 風を背にした側窓は指令の最小20%まで絞ります。
  風速0.5 m/s未満では適用せず、3 m/sまで風圧(風速²)に比例して徐々に強まります —
  弱く不安定な風向で側窓がサイクルごとに絞られたり戻ったりしないようにします。
- **目標を越えたまま固まりません。** デッドゾーンの中でも「減らすべき」側の偏差が3サイクル
  続くと、その装置は指令をサイクルごとに60%に縮めながら退きます。保温カーテン・遮光
  スクリーンも同じです — 効果が開度に比例するので、減らす側がそのまま効果を減らす側です。
- **積分の暴走防止。** 100%で頭打ちになると、はみ出した分を積分から戻し、0%で
  頭打ちになるとそのサイクルの積分を止めます。一方の端に張り付いたままなら、積分を
  実際の開度のほうへ寄せていきます。
- **変化速度の制限。** 1サイクルあたり最大20ポイントまで動きます。Actionに全ストローク
  時間があり、その装置が実際に動ける量のほうが小さいときはその値を使います。カーテン・
  遮光スクリーンは一動作で開閉するため対象外です。5%未満の指令は0として送ります。

**VPDモードの温度上限。** VPDを直接制御しているとき、温度は制御目標ではありません。
そのままでは暑くなっても換気窓を開ける力が働きません。そこで、次の判断時点の予想温度
(現在値 + 上昇率 × 周期)が推奨上限の1°C手前に届くと、換気装置に温度の項を加え、
超えた分だけ重みを大きくします。一度入った項は、予想温度がその線よりさらに0.5°C
下がるまで切れません — 線の上に留まる温度のせいで換気窓が「冷やす」と「休む」の間を
行き来しないようにするためです。**最高温度**のハード上限に届くと冷房機にもかけ、冷やす
方向と逆らう他の軸の項を外します。それでも偏差に比例するPIのままで、何も100%に
強制しません — 外気のほうが暑ければ、換気窓はむしろ閉じる方向へ動きます。

項が切れる線の下**1.5°Cは保持帯**です。この項で開けた窓はその位置にとどまり(さらに開ける
ことはでき、夜間閉鎖などのパーキングは引き続き優先します)、予想温度がその帯より下がって
はじめて閉じる方向へ動きます。これがないと、窓が1サイクルのうちに室温を数度変える施設で、
開ける → 項が切れる → 閉じる → また暑くなる → 開ける を約50分ごとに繰り返していました。

[猛暑保護](#heat-protect)が有効なら、上限は保護中でなくてもしきい値を超えません — 通常の
制御がしきい値のすぐ下から冷やし始め、それで足りないときだけ保護が出ます。保護中は温度が
その線より上にある間だけ上限がハードで、線より下では保護外と同じように退きます。

誘導上限は**目標温度 + 許容誤差を超えません。** 目標が25°C、許容誤差が1°Cなら、推奨上限が30°Cでも
温度の項は26°Cから働きます。以前は推奨上限の近くでしか項が立たず、目標より2〜5°C高いまま窓が
VPDだけを見て閉じていました。目標温度が分からないときは、従来どおり推奨上限を使います。

## アクチュエーターのドメイン { #domains }

負荷の分担は**ドメインの中で**起こり、ドメインの区切りは装置の見た目が似ているか
ではなく、**エネルギーの行き先が同じか**で決まります。設定画面もおおむね同じ
区切りですが、補光照明だけは例外で、スクリーンと同じ「光と遮光」で設定します。

| ドメイン | デバイス | 性質 |
|--------|---------|--------|
| 換気 | 開口部・排気ファン・吸気ファン | 室内を室外の方向へしか押し出せない。窓もファンも室外の値を越えて動かせず、ファンの効果は定格風量とサイクルの長さに従う |
| 冷暖房・加湿 | ヒーター、冷房機、フォガー | 外気とは無関係に直接加える/取り除く |
| スクリーン | 遮光スクリーン、保温カーテン | 出入りする放射を遮る |
| 補助 | CO₂インジェクター、補光照明、循環ファン | それぞれが自分の軸を持ち、負荷を分け合う相手がない。ただし開口部が開いていると入れたCO₂がすぐ抜けるため、開口部の平均開度**とファンが入れ替える空気**に応じて注入効果を低く見積もります(平均30%で0)。ファンは同じ尺度の開度に換算します — 毎時20回換気=窓全開、ファンが毎時6回に達すると0、開いた窓のせいでファンが力を出せない分は割り引きます。排気ファンと吸気ファンは大きいほうだけを数え、定格風量や施設容積が分からないファンは数えません。効果が小さくなりすぎるとインジェクターは休みます — 窓が閉まっていてもファンが回っていれば同じです |

ドメイン同士は互いの仕事を見ないため、ドメイン間の調整は効果の暗黙の積み上げでは
なく、**明示的なインターロック**([換気](#settings-ventilation)参照)で行います。

### 屋根換気口と側面換気口は挙動が違う { #vent-form }

どちらも`opening`アクチュエーターですが、施設図面は棟(屋根)窓と側窓を区別し、
効果モデルもそれを使います。

| 形状 | 室内が室外より暖かいとき | 室外が室内より暖かいとき |
|------|---------------------------|----------------------------|
| 屋根(棟) | 浮力が助ける — 同じ面積でもより多くの熱を逃がす | 逆転する — 暖かい外気は下りてきにくい |
| 側面 | 基準ケース | 直接流入し、そのまま加温になる |

図面に形状の指定がない場合は、天窓・側窓を区別せず同じモデルで動作します(補正なし)。

## Function設定 { #function-configuration }

AoT UIで`Function → 統合環境制御`に移動します。アクチュエーター自体は別途
登録するか([アクチュエーターの登録](#actuators)参照)、連携施設から自動的に
検出されます。

### 設定画面の読み方 { #settings-screen }

以下の表を読む前に知っておくとよいことが5つあります。

**画面の最上部にステータスヘッダーがあります。** 施設選択欄の下に、制御が今
何をしているかが表示されます — 追従している軸ごとの現在値と目標(VPD・温度・湿度・
CO₂・光量)、デバイスの種類ごとの状態(開口部、冷暖房、加湿、遮光…)、最後に判断して
からどれくらい経ったか。次の行は、この施設が軸ごとに実際に何を調整できるかを伝えます
— 両方向、上げるだけ、下げるだけ、見るだけ、センサーなし。その下の2行の要約は、
追従している区画・ステージと、現在適用中の目標を伝えます。動かせない状態はそれぞれ
別の文で示されます — この施設に連携された環境制御がない、制御がオフ(代わりにこの
施設を動かしている制御があればその名前まで)、このコーディネーター自身の基準時間を
超えて判断がない、まだ1サイクルも回っていない。施設を選ぶ前はヘッダーは空のままです
— 選択欄がすぐ上にあるからです。区画が2週間以内に終了する場合は、その旨の1行が
追加されます。

**設定はオプションの種類ではなく、4つの層に並んでいます。**

| 層 | 内容 | 表示 |
|-------|------|-------|
| 接続 | 施設、ベイ | 常に表示 |
| 取り決め | 温度/湿度の範囲、猛暑保護、CO₂許容誤差 | 常に表示 |
| 戦略 | 換気・冷暖房の連携、夜間閉鎖、噴霧の保護、遮光スクリーンと保温カーテンの使い方 | 常に表示(トグルまたは段階スケール) |
| チューニング | それ以外すべて | **[詳細]**の中、および折りたたまれた詳細設定グループの中 |

**中心となる設定は、その詳細を引き連れて動きます。** 誰も答えられない数値
(「緊急判定の倍率は3.0にすべきか4.0にすべきか?」)を尋ねる代わりに、答えられる
質問をして複数の値を一度に動かします — ロボット掃除機の静音/標準/強のような
やり方です。そうした操作は3つあります: 制御の性格、換気・冷暖房の連携、噴霧の
頻度です。**段階の名前そのものは保存されません** — 保存されるのは実際の値だけで、
今どの段階かはその値から逆算されます。どの段階とも一致しない場合は*カスタム*と
表示されます。

**範囲はハンドルが2つの帯として尋ねられます。** 温度と湿度には質問が1つだけ
あります — どの範囲で育てるか。ハンドルをドラッグすると、越えてはいけない線が固定の
余裕(±5°C、±5%RH)でいっしょに動きます。ドラッグしなければ、ハード上下限は出荷時の値
(5〜35°C、30〜90%)のままです。帯ではハード上下限を推奨範囲より狭くできないため、
「12~32°Cで育てるが30°Cは絶対に超えない」という表現はできません — この組み合わせが、
ヒーターと冷房機を互いに逆らわせる設定です。[詳細]で数値を直接入力してそうなった
場合、保存したその場で知らせます — どの軸か、2つの範囲は何か、実際にはどの範囲の
内側でしか目標を立てないかまで。その軸の4つの値のいずれかを今回いっしょに保存した
ときに表示されます。そのうえでコーディネーターは推奨範囲をハード上下限の内側に
狭めて使い、そのことをログに残します。

**[詳細]スイッチ1つで、すべての数値欄が開きます。** 段階スケールごとにその
数値入力欄が併記され、詳細専用の行がすべて現れ、折りたたまれたグループも一度に
展開されます。このスイッチはブラウザ内だけのもので、保存される設定の一部ではない
ため、同じFunctionを2人が別の見え方で見ることはありません。親トグルがオフの
設定は無効化されるのではなく**非表示になります。** そのため保存済みの値は
そのまま送信され続け、トグルをオフ/オンしても消えません。

> 一部の設定は特定の条件下でのみ読まれます — カスタム駆動周期はプロファイルが
> *カスタム*のときだけ、夜間の時刻欄は夜間を固定時刻で判定しているときだけ
> 使われます。入力されているのに使われていない値がある場合、画面はそれを
> 知らせます。そうしないと、黙って何も起きないだけになってしまうからです。

### コマンド { #commands }

| コマンド | 効果 |
|---------|--------|
| アクチュエーターを再読み込み | Actionsテーブルとこのファンクション自身の設定を再読み込みし、アクチュエータープロファイルを再構築します — 再起動は不要です。 |
| 今すぐ実行 | 現在のセンサー値を使用して、協調サイクルを即座に1回実行します。緊急停止の保留が残っている間は無視され、残り秒数を応答で知らせます。 |
| 緊急停止 | すべてのアクチュエーターを安全時デフォルト位置に設定し、60秒間制御を一時停止します。 |

上の2つのコマンドのあとは、次のサイクルを1回だけ緊急として扱います — 換気窓が
駆動プロファイルの間隔を待たずに動くことがあります。

### 施設設定 { #settings-facility }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 連携施設 | (なし) | このコーディネーターが担当する施設。アクチュエーターとセンサーはここから取得します — 外皮、側面/屋根の換気口、カーテン、ファン、屋内外センサー。方位・面積・熱貫流率などのGISメタデータが各アクチュエータープロファイルに付与され、風向と施設の形状を計算に反映できます。これを設定しないと、残りの設定には対象がありません。 |
| ベイ範囲(任意) | (空) | このコーディネーターを1つのベイに限定します。そのベイの中のセンサー・アクチュエーターだけが使われ — どのベイにも属さない装置は除外され、施設全体を担当するコーディネーターの担当として残ります — 施設の容積・外皮・換気面積も、全ベイの幅の合計に対するそのベイの割合に応じて縮小されます(幅が分からないときは警告を残してベイの数で割ります)。空欄なら施設全体が対象です。複数のベイを独立して制御したい場合は、ベイごとにコーディネーターを作成します。空欄のままのコーディネーターは、同じ施設でベイを指定した別のコーディネーターがすでに担当しているベイを避けます — 1つの装置が2か所から指令を受けないようにするためです。連携施設のベイ一覧から選ぶ**ドロップダウン**です — 施設にもう存在しない保存済みの値は、黙って消されるのではなく印を付けて残されます。存在しないベイを指している間、このコーディネーターは施設全体に広げるのではなく**どの装置も担当しません**。 |
| 自動制御の対象デバイス | (除外なし) | 施設設定のすぐ下にある折りたたみの枠が、連携施設のアクチュエーターをすべてトグル付きで表示します。1つをオフにすると、その装置は自動制御から完全に外れます — 指令も出ず、安全ゲートもその装置を強制しません。修理中や手動で押さえている装置に必要な状態です。除外リストなので、あとから施設に追加した装置は最初から制御されます。オフにした装置がのちに施設から消えても、オフの状態はそのまま残ります。一覧を読み取れない場合は枠がそのことを伝え、保存済みの設定は空の値で上書きせずそのまま保ちます。 |

### 稼働時間 { #time-control }

トグルをオンにするまでは、それ以外の項目は表示されません。これは時間帯別の
制御ではなく**スイッチ**です。時間帯の外では、目標追従(L1〜L3)が**完全に**止まります
— 暖房・冷房も含みます。それでも保護は続きます。

- [事前安全ゲート](#pre-gate-checked-before-l1l3)(降雨・強風・低温緊急など)は
  毎サイクル評価され、作動すればその強制指令を送ります。強風の第1段階制限(根拠 55 —
  風上側と天窓を閉め、ほかは上限)も、[降雨の段階制限](#safety-gates)(根拠 52)も同じです — 閉じた天窓は閉じたまま、
  ほかの指令がない上限対象の側窓は閉じ(上限の下の位置を選ぶ PI がありません)、予報の雨で
  留めた天窓はその場のままです。
- 温度/湿度のハード上下限の**防ぐ側**もそのまま働きます。たとえば室内が最低温度を
  下回ると、開口部と保温カーテンを閉じ、冷房を止めます。ハード上下限はもともと装置を
  駆動しないため(暖房機を入れることはしません)、時間帯の外でも「停止」とぶつかりません。
  光量の上下限は補光灯を点ける駆動なので、時間帯の外では使いません。
- [猛暑保護](#heat-protect)もそのまま直接かかります — 窓は外の方が涼しいときだけ開け、
  日が出ていれば遮光、冷房機・循環扇はオン、暖房・噴霧はオフにします。
- 上の保護指令を受けなかった装置には、それぞれの終了時の動作を送ります。時刻は施設のローカルタイムで判定し、施設のタイムゾーンが
分からない場合はサーバーの時刻を使います。

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 時間帯制限を有効化 | オフ | 有効にすると、開始~終了の間だけ目標追従が動きます。 |
| 開始時刻(HH:MM) | 06:00 | コーディネーターが毎日いつから働き始めるか。 |
| 終了時刻(HH:MM) | 20:00 | いつ止まるか。終了時刻が開始時刻より早い場合は、日付をまたぐ時間帯として扱います。時間帯の外で各デバイスが何をするかは、そのデバイスのAction(時間制御ウィンドウ終了時)で設定します。 |
| 光周期メソッド | (なし) | 固定時刻の代わりに、日長カーブから時間帯を決めます。注意: 日長が短いと、コーディネーターもその時間しか動かないため、夜通し暖房されることはありません。 |
| 光周期基準時刻(HH:MM) | 12:00 | 太陽南中に相当する時刻 — 時間帯はこの時刻を中心に取られます。 |

### 目標と応答性 { #settings-target }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 温度範囲 | 12–32°C | 育てる範囲。上下限を超えると、間違った方向に働くものを止めます — 暑すぎるとき: 暖房を切り遮光スクリーンを閉じる。寒すぎるとき: 冷房を切り、開口部と保温カーテンを閉じる。どの装置も全開/全力にはしません。 |
| 猛暑保護 | オン | しきい値を超えると、目標より作物の高温ストレスを防ぐことを優先します — 遮光カーテンを閉め、暖房を止め、循環扇を回し、窓は外の方が涼しいときだけ開け、噴霧はまだ冷やせるときだけ使います([猛暑保護](#heat-protect))。 |
| 猛暑保護のしきい値 (°C) | 30 | 保護を始める室内の平均気温(20–45°C)。作物が耐えられる温度に設定してください。保護がオンのときだけ表示されます。 |
| 湿度範囲 | 40–85% | 湿度も同じ規則です — 湿りすぎるとき: 噴霧を切る。乾きすぎるとき: 排気ファンと吸気ファンをそろえて切る。 |
| CO₂許容誤差(ppm) | 100 | 目標からこの値の半分以内なら、CO₂の注入はそのままにします。この値は反応の強さの基準でもあり、6倍ずれると最大限に反応します([L3](#l3-coordinator-actuator-command))。目安: 50~150 ppm。 |
| 制御の性格 | 標準 | 目標をどれだけ強く追うか。1つの段階を選ぶと、サイクル周期・換気窓の駆動プロファイル・VPD許容誤差・2つの緊急しきい値がまとめて動きます。新規に追加したFunctionの出荷時の値は*標準*の段階そのもので、そのうちどれかをどの段階にもない値に手で変えると*カスタム*と表示され、[詳細]を見るよう促す一行が付きます。 |

[詳細]を開くと、各範囲帯の裏にある4つの数値(`推奨最小/最大温度`、
`最小/最大温度`、および湿度の対応する値)が表示され、猛暑保護は**解除幅**(°C、既定1.5、
0.5–5 — 気温がしきい値よりこの幅だけ低い状態が10分続いてから保護を終えます)と**最短継続**
(分、既定20、5–120)を、制御の性格はそのメンバーを表示します。

| メンバー | ゆったり | 標準 | 敏感に |
|--------|---------|----------|-----------|
| 周期(秒) | 600 | 120 | 60 |
| 換気窓駆動プロファイル | 緩慢(600秒) | 標準(180秒) | 敏感(60秒) |
| VPD許容誤差(kPa) | 0.15 | 0.1 | 0.05 |
| 緊急判定偏差しきい値(許容誤差の倍数) | 4.0 | 3.0 | 2.0 |
| 緊急判定変化率しきい値(°C / 10分) | 3.0 | 2.0 | 1.5 |

同じ場所にさらに2つのメンバーがありますが、これらは段階では**設定されません** —
同じ軸の上での微調整だからです。**カスタム駆動周期(秒)** — プロファイルが
*カスタム*のときだけ使われます — と、**緊急時の最小間隔(秒)**(既定60)で、
緊急時であっても2回の換気窓指令の間に空ける最小の間隔です。

駆動プロファイルが左右するのは、側面/屋根の換気窓が*動く*ことを許す頻度だけです。
センシングと計算は毎サイクル周期で常に実行され、カーテンや遮光スクリーンは
影響を受けません(一動作で開閉するため)。安全ゲートの強制指令(降雨・強風時の閉鎖など)は
この設定に関係なく**その装置にだけ**即座に送られ、強制を受けていない他の換気窓はこの
間隔を守ります。この間隔をまるごと飛ばす緊急は、室内温度が急変したときと、偏差が緊急
判定しきい値を超えたうえで**なお広がり続けている**ときと、[猛暑保護](#heat-protect)の
段階が上がったその1サイクルだけです — 目標から離れたまま留まっているだけ(保護が続いて
いるだけ)では緊急ではありません。

### 換気 { #settings-ventilation }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 換気と冷暖房の連携 | 高性能 | 換気と冷暖房が互いに邪魔しないようにします。3段階あり、下で説明します。 |
| 夜間は閉じておく | オフ | 夜間は換気窓を閉じ、暖房・冷房・除湿に負荷を任せます。閉じるのは開口部だけで、暖房・冷房・除湿はそのまま動き続けます。 |
| 強風しきい値(m/s) | 12 | 10分平均風速がこの値(測った突風は1.5倍)に達すると開口部をすべて閉じます。0.6倍(測った突風は0.9倍)からは風上側の窓と天窓を閉め、ほかは一部だけ開けます — [強風の二段階](#safety-gates)を参照。[詳細] |

**換気と冷暖房の連携**は、3つのトグルを一度に動かします。

| 段階 | 換気で助けられないときは開口部を閉じる | 換気で目標に届くときは冷暖房を休ませる | 冷暖房が動いている間は開口部を閉じたままにする |
|------|---|---|---|
| 高性能(既定) | オン | オフ | オフ |
| 標準 | オン | オン | オフ |
| 省エネ | オン | オン | オン |

- **換気で目標に届かないときは開口部を閉じる** — 換気は室内を室外の方向にしか
  引っ張れません。目標が外気の反対側にあるとき、開口部を開けば開くほど目標から
  遠ざかります。典型例は夜間の除湿で、外気が室内より湿っている場合です。これを
  オンにすると、開口部と排気・吸気ファンは、一晩中中途半端に開けておくのでは
  なく、閉じたままパーキングされます。
- **換気で目標に届くときは冷暖房を休ませる** — 外気がすでに目標を超えている
  とき、換気だけで到達でき、そこで冷暖房を一緒に動かすのは外気がタダでやって
  くれることに料金を払うようなものです。3つの条件がすべて成り立つ必要があります
  — 外気の値が許容誤差を超えて目標を上回っている、制御対象の変数の*すべて*が
  そうなっている、そして開口部にまだ余裕がある(直近サイクルの最大開度が90%
  未満)。外気が目標までの一部しか埋められないときは、冷暖房はその分を差し引いた
  残りの偏差だけ働きます。**15分**経っても目標に届かない場合は、すべてが暖房・
  冷房へ戻されます — 予測が外れたということです。降雨・風速の値が途絶えて開口部を
  それ以上開けられない間や、雨のため上限がかかっている間(根拠 52)は、この判定そのものがオフになります — それ以上開けられない
  窓の助けを当てにして冷暖房が引き下がってはいけないからです。
- **冷暖房が動いている間は開口部を閉じたままにする** — 稼働中の機器に逆らって
  換気すると、その熱や冷気をそのまま外へ捨てることになります。外気が目標に
  近づくのを助けてくれる季節であっても、この設定はその助けも一緒に捨てて
  しまいます。

稼働中の機器を検知するには**根拠**が必要で、その情報源は2つしかありません —
このコーディネーター自身がその機器に指令を出しているか、稼働すると値が上がる
測定値を信号として指定しているかです。室内温度は意図的に**使いません。** 日射の強い
昼間は冷房機がなくても室内が室外より涼しくなることがあり、「室内が室外より涼しければ
冷房が動いている」という判定は、余裕を持たせてもしばしば外れます。

| 項目(インターロックがオンのとき表示) | 既定値 | 説明 |
|-------|---------|-------------|
| 冷暖房の稼働検知信号 | (なし) | このコーディネーター自身が切り替えない機器にのみ必要です。稼働すると上がる測定値を選んでください — スマートプラグのワット数、クランプメーターの電流、補助接点のオン/オフなど。このコーディネーターが直接指令する機器なら空欄のままにしてください。 |
| 稼働判定のしきい値 | 0.5 | この値以上で、信号は稼働中とみなされます。オン/オフ接点なら0.5のままにしてください。ワット数や電流であれば、その機器の待機電力より上に設定してください。 |

信号自身に鮮度の上限がない場合、その信号自身の測定周期(×2、下限300秒)で
判定されます。期限切れの信号は*稼働していない*とみなされ、その旨が記録されます。

**夜間閉鎖**があるのは、夜になると湿度が上がり結露するためです — 夕方には
役に立っていた開口部が、朝には作物を濡らしたままにしてしまうことがあります。
そのサブ設定は、トグルがオンのときだけ現れます。

閉じておくほうがかえって危険になると、自分で解除します。温度・湿度のハード上下限を
超えたとき、そして**結露が迫っていて、換気がそれを和らげるとき**です。結露が迫るとは
室内温度と露点の差が2°C未満であること、和らげるとは外気を少し混ぜたときにその差が
広がることです。冷たく湿った外気は室内を冷やしてかえって結露を招くことがあるため、
外が乾いているというだけでは開けません。解除後は、差が3°Cまで回復するか換気が役に
立たなくなったときに再び閉じます。外気の値が分からなければ解除せず、値が*期限切れ*で最後のキャッシュで
判断している間も解除しません — 古い「外が乾いている」は開ける根拠にならず、パーキングが続けば窓は閉じます
(根拠19)。記録された一夜では、除湿で開いた窓が気象データの途絶後も3時間13〜25 %に留まりました。

結露からの脱出は**水蒸気圧の基準で厳しく**判定します。外気の露点が室内より 1.5°C 以上低く
(すでに開いていれば 0.75°C)、混ぜたときに露点余裕が 0.3°C 以上広がる必要があります。混ぜた空気が
暖かいだけで余裕がわずかに増えても開けません。解除後も窓は[過湿ゾーン](#humid-zone)の規則に従い、
最大 30 % までしか開きません(外気がほぼ同じ温度以上で露点が 3 °C 超えて低ければ、この上限は外れます)。暖房要求中や外気が室内より 8 °C 超えて冷たいときは開けません。室内が温度の基準線(温度が制御目標なら目標 + 許容誤差、VPD 直接モードなら誘導範囲の下端 — [過湿ゾーン](#humid-zone)と同じ線)以下で外気が 1 °C 超えて冷たいときも開けません — 温度が露点判断に優先します。
途中で止まれる保温カーテンがあればカーテンのすき間が先で、このエスケープはすき間を使い切った後にだけ働きます([保温カーテン — 夜のすき間と朝の段階開け](#curtain-gap))。

| 項目(夜間は閉じておくがオンのとき表示) | 既定値 | 説明 |
|-------|---------|-------------|
| 夜間の基準 | 日没~日の出 | 夜を日没から日の出までとするか、固定時刻で判定するか。 |
| 日没の何分前に閉じるか(分) | 0 | 日没のこの分数だけ前から閉じ始めます。負の値は無視されます — 日没後の遅延を取り除くのがこのオプションの目的だからです。 |
| 夜間の開始/終了(HH:MM) | 18:00 / 06:00 | 夜間を固定時刻で判定する場合にのみ使われます。 |

3つの保証が成り立ちます — **安全ゲートが優先します**(真夏の夜の熱でも換気窓は
開きます)、ハードな温度/湿度の上下限がパーキングを解除します、そして太陽時刻を
計算できる座標がない場合は何もパーキングされません。これとは別に、夜間閉鎖に
限らない4つ目の規則があります — 外気の値そのものが分からないとき(キャッシュが
空で、外気=室内と仮定した合成値しかないとき)は、その推測で通気口を開けることも
閉じることもせず、今の位置をそのまま保持します。このサイクルで換気の規則が下した
判定も、この保持が上書きします(ただし降雨・強風などの非常用安全ゲートはこの保持よりも優先され、閉じることがあります)。作り物の外気=室内の値を根拠に閉じてしまうと、気象データ
源が止まった際に真夏の日中でも通気口が閉じたままになりかねないためです。

**分からないことは「開けない」理由にしかなりません。** 外気の値がない間も、閉じる方向の動きが3つ
起こります — どれも欠けた値に頼らないからです。夜間閉鎖はそのまま閉じ(根拠19)、最後の実測の
降雨・強風による制限もそのまま掛かり(根拠52・55 — 上限を超えて開いた窓は上限まで下がります)、
日没後(晴天時日射が50 W/m²未満。施設の座標が必要です)に開度**10 %以下**の窓は0に閉じます
(根拠58。夜間閉鎖のオプションがなくても動きます)。降雨・風速の値だけを失って窓が「これ以上開けない」
になっているときも同じです(制御がなお開けたがる小さな窓が雨の夜をそのまま過ごしたことがありました)。それより大きく開いた窓はそのままで、昼に
「分からない」だけで閉じる窓はありません — 暑い日には被害になるからです。日没後の閉鎖は、温度・湿度の
ハード上限が換気を求めている間は見送りますが、記録された一夜ではまさにその隙間が問題でした。側窓が
除湿で25〜30 %開き(RH 91〜95 % > 上限90 %)、気象データが途絶えたあとも3時間13〜25 %に留まり、
雨が降り始めても見えませんでした。そこで外気の値(または降雨・風速の値)が**30分を超えて**ない場合、
夜にハード湿度上限(または夜間閉鎖を解く湿度・結露の脱出)のためだけに開いている窓を段階的に閉じます —
**10分サイクルごとに5 %p**ずつ0まで(根拠58、積分はコマンドに追従します。サイクルが短ければ幅も比例して
小さくなります)。半分にせず5 %pなのは、30 %の窓を半分にすると一度に15 %p下がり、0にも正確に届かない
ためです — 一定幅のほうが大きな窓にやさしく、0で終わります。30分以内の途絶は従来どおりです(気象台の値は
普段でも最大30分ほど欠けます)。温度のハード上限、極端な高温保護、昼間の開口には触れません。値が戻った
瞬間から通常の制御に戻り、残るラッチはありません。30分の時計は再起動をまたいで続きます(他のサイクル記憶と
一緒に保存され、サイクルが30分を超えてなかった記憶は破棄されます)。時刻は
施設のローカル
タイムゾーンで読み取られ、サーバーのものではありません。施設のポップアップでは、
このオプションでパーキングされたデバイスは*夜間のため閉じ、冷暖房で管理して
います*と表示され、*このデバイスが今できることは何もありません*とは区別されます。

**室内の値を失うのはその裏返しです。** 窓はその場にとどまりますが(根拠21、実際に出た開度のまま)、
晴れた日は外気と日射だけで決めた小さな開きを置き、日が沈むと閉め直します(根拠60 — [晴れた日に室内の
値が途切れたとき](#solar-vent-blind))。

**閉じる直前は、窓をそれ以上開けません。** パーキングが始まる前の45分間(日没 − *日没の何分前に閉じるか*、
または夜間の開始時刻)、換気窓とファンはコーディネーターが閉じることはできますが、VPD・湿度・通常の
温度要求で**今の開度を超えて開く**ことはありません。夕方は室内の湿度が上がり外気は乾いたままなので
「換気するとVPDが上がる」が窓を開けますが、10分後に夜間閉鎖がその窓をまた閉じます。記録されたある夕方には、
側窓が16:48〜17:49に12 → 91 %まで開き、18:42までに70 → 0 %で閉じました。
この往復は、モーターの移動、日暮れ直前の温度低下、苗に当たる冷たい空気という代償を払います。この区間では
開度を直前の値に留め、積分もそれ以上積み上がらないので、区間が終わる瞬間に飛び出しません。施設の
ポップアップには*今の開度のまま保ちます — まもなく夜間の閉鎖で換気窓が閉まります*(理由48)と出ます。
閉じる方向へ徐々に絞る傾斜は意図的に置いていません — 窓が本当に必要な施設を、パーキングより先に
無理に閉じてしまうからです。

パーキングを解く理由と暑さは、この保持も解きます。温度のハード上限(および温度上限のハード項)、
湿度のハード上限、[猛暑保護](#heat-protect)、上の結露エスケープです。雨・強風のゲートはそれでも窓を
閉じます。太陽時刻を計算できない場合、この区間はありません。45分は固定でオプションではありません。
ルールベースの制御(レガシー、物理モデルPI)に適用され、MPCには適用されません。

### 日射の熱を逃がす { #solar-vent }

日が差すハウスは窓を閉めると数分で暑くなります。日射が作物や床を温め、その熱が出ていく道は空気しか
ありません。ところが今の内外差だけで見ると、まさにそのとき換気は無駄か有害に見えます — 外のほうが
乾いているので「開けるとVPDが上がる」、内外の温度差が1 °C程度なので「換気の駆動力がない」(*勾配なし*、
根拠15)。その小さな差はたいていミストが空気を冷やして作ったものです。そして気化冷却は湿った空気を
入れ替えてこそ続きます — ミスト・換気・遮光はいっしょに使う手段です。湿度を守るために窓を閉めるのが
正しいのは、日射の熱負荷がないとき(夜・曇り・涼しい日)だけです。

そこで日がある間は窓に**最低開度**を設けます。

| 条件 | 値 |
|---|---|
| 日射 | 屋外日射200 W/m²以上(150未満で解除)。一時的に測れないときは快晴日射 × 直近30分の雲の具合、日射センサーがなければ快晴日射の半分、施設の位置が分からなければ判断しません |
| 暑い | 室内が*作物線*より高い — 温度が制御目標ならその目標 + 許容差、VPD直接モードでは導出温度目標 + 許容差と作物線の低いほう(下記)。その線より0.5 °C下がると解除 — ただし立ってから30分は温度では解除せず最小値に留まります(窓が1サイクルでハウスを冷やして解除し、閉じると日射がすぐ温め直して10分ごとに入切しないように) |
| 外のほうが暑くない | 外が室内より1 °Cを超えて暑くない(超えると換気が熱を入れます) |
| 最低開度 | 線のすぐ上で15 %、超過に応じて[猛暑保護](#heat-protect)のしきい値(保護オフなら**最高温度**)で80 %まで、日射で重み付け(200 W/m²で× 0.7、800 W/m²以上で× 1) |

VPD・湿度の要求はそれより下に窓を閉められません。その要求が守ろうとした湿度はミスト(冷やしながら
加湿)と[遮光スクリーン](#shade-heat)が受け持ちます。最低開度は積分にも掛かるので、規則が解けるとき
窓が一気に閉まらず、今の位置から制御が続きます(解けるときに最低開度を段階的に下げる方式は試して戻しました —
制御が下がっていく最低開度に逆らって窓を再び上げ、すぐ解除するより窓の上下が増えました)。保護しきい値の上では最低開度が最大値のままなので、
猛暑保護への引き継ぎに段差がありません。対象は天窓・側窓で、窓がないときだけファンです(ファンは
電気を使います)。施設ポップアップは*日射の熱を逃がすため開けています — 日が差し、温度目標を上回って
います*(根拠51)で、開始と終了にログを1行残します。

**「暑い」の線は作物の温度で引きます。** VPD直接モードの導出温度目標は、VPDを合わせるために動かした
温度です — 湿った朝はVPDを上げようと室温より上に立ち、室温につれて上がるので、その線では日射が閉じた
ハウスを温めている間ずっと「暑くない」になります(シミュレーション:夜通し閉じて湿ったハウスで最低開度が
90分遅れました)。そこでその目標は*作物線*を超えられません。作物線はステージの現在(昼)の温度 + 1 °C、
ステージ温度がなければガイド範囲の下端から幅の2/3の点(12〜32 °C → 25.3 °C — 範囲は昼夜を含むので
中央は昼の作物には低く、上端は保護しきい値より高い)で、保護しきい値 − 0.5 °Cを超えません(しきい値で
最低開度が80 %につながるように)。乾燥して導出目標が低いときは従来どおりそちらが線です。温度優先モードで
ステージ温度がなく目標が現在の室温に追従するときや、VPDを測れず退いたときも作物線を超えられません。

この区間では、ミストが冷やした空気のせいで*勾配なし*として休もうとする窓も最低開度に留まります。
効果モデルは変えません — 換気の温度効果に日射の熱を加えて数えるようにしてみたところ、シミュレーション
で窓がかえって**少なく**開きました(誤差は小さいのに重みだけ大きくなった温度項がVPDの要求を薄めます)。

最低開度より優先するもの: 降雨・強風ゲート、屋外不明(そのまま)、降雨・風速不明(これ以上開けない)、
夜間パーキングとその直前45分([根拠48](#settings-ventilation))、冷暖房連動、猛暑保護の「外のほうが暑い」
(根拠28)、温度・湿度のハード上下限、手動ロック、疑わしい装置。最低開度が勝つもの: VPD・湿度の要求、
*勾配なし*、換気無益、過湿域の開度上限、「開けても反応がない」。値は固定でオプションではありません。
ルールベース制御(従来・物理モデルPI)に適用され、MPCは適用しません。

#### 晴れた日に室内の値が途切れたとき { #solar-vent-blind }

上の最低開度は室内温度で決めます。室内センサーがすべて途切れると、判断できなくなった窓はその場に
とどまります(根拠21) — しかし晴れた朝にとどまることは、ハウスを閉め切っておくことです。記録された
ある途絶(07:29に室内ミラーセンサーがすべて途切れた)では、窓は夜の0 %のまま晴れて乾いた昼に入りました。
ある施設の側窓は外気19 °C・RH 25 %なのに09:03〜12:55閉じたままで、別の施設は日射656 W/m²で窓が
閉じていました。閉めたビニールハウスは日なたで外より15〜20 °C暑くなります。

そこで室内温度が分からず、外気の値が実測(外気 = 室内で埋めた代替値ではない)の間は、外の情報だけで
決めた小さな最低開度を置きます。

| 条件 | 値 |
|---|---|
| 日射 | 屋外日射200 W/m²以上(150を下回ると解除)。測定がなければ晴天日射 × 最近の雲、日射センサーがまったくなければ晴天日射の3/4(上の半分より大きくします — ここでは少なく見積もると晴れた日に閉めたハウスになり、多く見積もっても曇りの日に10 %開くだけです) |
| 外が寒くない | 外気12 °C以上 — 暖地性の苗で低温障害が始まるあたり。室内温度が分からないまま、それより冷たい空気は入れません |
| 閉めたままなら暑いはず | 外気 + 日射1 W/m²あたり0.02 °Cが作物線(上と同じ)より高い。その線より0.5 °C下がると解除。単棟ビニールハウスは定常状態で外より日射1 W/m²あたり約0.033 °C暑くなりますが、作物の蒸散と床の熱容量が午前の上昇を遅らせます — 閉ループシミュレーターでは晴れた秋の日に閉めたハウスが09時0.011、14時0.020 °C/(W/m²)でした。午後の値ならシミュレーションのハウスが線を超えるときに一緒に超え、0.033だとまだ暖まっている途中のハウスを1時間早く「暑い」とします |
| 最低開度 | 線のすぐ上で10 %、[猛暑保護](#heat-protect)のしきい値で20 %まで。外気そのものがそのしきい値以上なら10 %のみ |

根拠21でその場にとどまるはずの窓にだけかけ、**10分サイクルごとに5 %p**ずつ開けます(サイクルが短ければ
幅も比例して小さくなり、最初の一歩は装置の最小開度以上なので0に戻されません)。すでにもっと開いている
窓はそのままです — 根拠がないという理由で閉める窓はありません。曇り・夕方の薄明はその場にとどまります。
日が沈んだ後(晴天日射50 W/m²未満、根拠58と同じ線)も室内が分からなければ、20 %以下に開いた窓を同じ幅で
閉め、それより大きく開いた窓は引き続きその場にとどまります — ただし[夜間閉鎖](#settings-ventilation)を有効にした施設では、日没からその窓も夜間閉鎖(根拠19)が先に閉めます。室内の値が戻れば、窓が立っている位置から
通常の制御が続きます(積分は開度に追従します)。施設ポップアップは*室内の値がないため日射を見て少し
開けました — 閉めたハウスは日なたですぐ暑くなります(日が沈むと再び閉めます)*(根拠60)で、開始と終了が
ログに残ります。

**外がとても暑いことは閉める理由になりません。** 室内温度が分からないまま外気が保護しきい値以上なら、
窓を閉めずに最も小さな最低開度に置きます。日なたで閉めたハウスは常に外より暑くなります。猛暑保護の
「外のほうが暑い」(根拠28)は、ミスト・遮光がハウスを外より涼しく保っていることを**測ってから**窓を
閉めますが、室内の値がなければその測定がありません。かといって大きく開ける根拠もありません — ミストが
動いていたならハウスは外より涼しいかもしれず、そのとき大きな換気は熱い空気を入れます。小さな開きは
ミストが生んだ湿気を逃がして蒸発冷却を続けさせる分です。

この最低開度より優先するもの: 上の日射の最低開度より優先するものすべてと、雨・風・霜の上限(根拠52・55・
56)。値は固定でオプションではありません。ルールベース制御(従来・物理モデルPI)に適用され、MPCは適用
しません。

### 冷暖房・加湿 { #settings-hvac }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 加湿にミニスプリンクラーを使う | オン | 湿式の噴霧器を加湿にも使います。同じノズルをかん水にも使っている場合はオフにしてください — かん水向けに口径を決めたスプリンクラーは、短い一噴きでも葉に水膜を残します。オフにすると、その噴霧器は自動環境制御から丸ごと外れます — 命令をいっさい送らないので、別のかん水制御がそのまま使えます。 |
| 日焼け・夜間保護を有効化 | オフ | 強い光の中での湿式噴霧を遮断し(水滴が太陽光をレンズのように集めて葉を焦がすことがあります)、任意で日没前も遮断します。極端な高温・乾燥のときは短いパルス1回が遮断を通ります — [短いパルス噴霧](#pulse-fog)を参照。噴霧の頻度設定とは独立しています。 |
| 夕暮れ前に湿式噴霧を止める | オン(詳細) | 湿式噴霧は光が弱まると減り、日没の90分前に止まります(日焼け・夜間保護がオンなら*日没前の噴霧停止時間*で) — [夕暮れの湿式噴霧](#wetting-fog-dusk)を参照。夕方も噴霧したいときはオフにします。 |
| 噴霧の頻度 | ひんぱんに | 噴霧をどれくらいの頻度で作動させるか — 1回の作動時間と、次の作動までの間隔。 |

噴霧バルブはほとんどの場合オン/オフしかできないため、流量を絞る手段はありません
— 調整できるのは、1回の作動がどれだけ続くかと、次までどれだけ待つかだけです。
この段階スケールが設定するのはそれです。

| 段階 | 1回の噴霧最大時間(秒) | 強制乾燥間隔(秒) |
|------|-----------------------|------------------------------|
| まれに | 5 | 1200 |
| ふつう | 10 | 900 |
| ひんぱんに | 20 | 600 |
| かなりひんぱんに | 30 | 450 |

日焼け保護は頻度とは**別の**判断です — 2つを分けておくことで、
「頻繁に噴霧しつつ強い日差しでは遮断する」という組み合わせを指定できます。

| 項目(保護がオンのとき表示) | 既定値 | 説明 |
|-------|---------|-------------|
| 日差しの強さによる噴霧調節 | 150–250 W/m² | ハンドルが2つの帯です。下の値より暗ければ噴霧は自由に作動し、上の値より明るければ停止し([極端な高温・乾燥の短いパルス](#pulse-fog)だけは例外)、その間では直線的に弱まります。この間隔があることで、雲が通過するたびに噴霧が入切を繰り返すのを防ぎます。**葉をぬらす噴霧にのみ適用されます** — 霧タイプの噴霧は強い日差しの中でも作動します。推定された*室内*光量が基準に使われるため、遮光スクリーンを閉じると遮断が緩和されます。光量の測定がまったくない場合は、太陽高度から求めた晴天時日射の概算が代わりに使われるので、光センサーのない施設でも保護が働きます。噴霧原水が既定値(地下水)の場合、実際には100–150 W/m²に下げて使います。 |
| 極端な高温・乾燥の短いパルス噴霧 | オン(詳細) | 遮断中でも、極端に暑い・乾燥していて濡れた葉が数分で乾く日は、短いパルス1回(10秒オン、15分以上オフ)を通します — [短いパルス噴霧](#pulse-fog)を参照。オフにすると遮断はそのまま保たれます。 |
| 日没前の噴霧を許可 | オン | オフにすると、夜通し葉を乾いたままにします。葉が濡れている時間が長いほど、灰色かび病やべと病のリスクが高まります。**「夕暮れ前に湿式噴霧を止める」がオフのときだけ読まれます** — オン(既定)なら、これに関係なく湿式噴霧はすでに日没前に止まります。 |
| 日没前の噴霧停止時間(分) | 120 | 日没の何分前に噴霧を止めるか。このモードでは*夕暮れ前に湿式噴霧を止める*も同じ時刻に始まります。遮断は翌朝の日の出まで続きます。設置場所の座標が分からない場合は日没を求められないため、夜間の遮断はかかりません。 |
| 噴霧原水 | 地下水(未処理) | 未処理の地下水は硬度が高く冷たいことが多く、乾く水滴がミネラルの跡を残したり、日の当たる葉を冷やしたりします。これが選ばれている間(既定値)は、遮断/解除のしきい値が自動的に下がります(最大でも150/100 W/m²まで)。 |

保護の有無にかかわらず、湿式噴霧器は連続変調ではなくパルス投与されます — 連続的な
変調では葉が乾く暇がないためです。1回の時間と間隔は噴霧の頻度スケールの値を使い
(出荷時の*ひんぱんに*: 1回最大20秒、乾燥間隔600秒)、値が空のときだけ30秒/180秒で
動きます。

湿式噴霧は**最高湿度**のハード上限より手前でも遮断されます。湿度がこのサイクルの湿度の
基準(VPD目標から分けた湿度、推奨範囲内)**+ 5%** を超えると遮断し、湿度が分からない
ときも遮断します。すでに湿った空気の中で葉をさらに濡らさないためです。霧タイプ
(高圧ミスト)は対象外です。[猛暑保護](#heat-protect)中は、この遮断は**厳しくなるだけ**です —
基準 + 5%、**最高湿度**、85%のうち最も低い値。湿式噴霧は保護の蒸発冷却器ではありません。
水が葉やトレイに落ち、それが乾くことで冷やすので、すでに湿った空気の中でさらにまくと
葉が長く濡れるだけです。

### 夕暮れの湿式噴霧 { #wetting-fog-dusk }

湿式噴霧器(葉をぬらす水滴で、霧タイプではありません)の水は空中で蒸発しません。水は葉や
トレイに落ち、それが乾くことで初めてなくなり、乾く速さは日差しが決めます。そのため夕方まで
噴霧を続けると、作物は濡れた葉のまま夜を迎えます — 葉が濡れている時間が長いほど、灰色かび病や
べと病のリスクが高まります。実測(トマトの温室、VPD目標1.0 kPa、日焼け・夜間保護オフ):
湿式噴霧器が12時から17時まで100%(理由1、VPD)で動き続け、その間に日射は150から
31 W/m²まで下がり、日没は17:54でした。上の日焼け・夜間保護は育苗モードにしかないため、
この設置を止めるものがありませんでした。

そこで湿式噴霧器は、一日の終わりに向けて抑えます(日焼け・夜間保護モードでも — 下記参照)。

| 条件 | 湿式噴霧器 |
|---|---|
| 屋外日射150 W/m²以上 | 制限なし |
| 50 – 150 W/m² | 比例して減らす — 100 W/m²で命令の半分、75 W/m²で4分の1 |
| 50 W/m²以下 | 停止 |
| 日没の90分前から翌日の出まで(日焼け・夜間保護モード:*日没前の噴霧停止時間*から — 既定120分) | 日射がいくつでも停止 |

日射は屋外の測定値です。測定がなければ、晴天時日射 × 最近の曇り具合(日射センサーがまったく
なければ晴天値の半分)を使います。日射も施設の位置も分からない場合は何も制限しません —
分からないことは加湿を止める理由になりません。

このルールは**減らすだけ**です。ハード上限の**後**に適用されるため、**最低湿度**の要求が湿式噴霧を
夕方に100%へ押し上げることはできません。夕方に不足する湿度は、換気と霧タイプの噴霧の役目です。
霧タイプ(高圧ミスト)は葉をぬらさないので対象外で、ドリップも同じです。安全ゲートは
このルールよりさらに後で優先されます。

スイッチは**夕暮れ前に湿式噴霧を止める**(詳細、既定でオン)です。値(150 → 50 W/m²、90分)は
オプションではなく固定です。

**日焼け・夜間保護モード(*日焼け・夜間保護を有効化*)もこのルールを受けます。** そのモードの
強い日差しの遮断と段階的な減少は[冷暖房・加湿](#settings-hvac)に書かれたとおりで、昼の明るい時間を
引き続き受け持ちます。このルールは弱い光・夕方・夜を受け持ちます。以前は保護が夕方に遮断を解き、日没後の
湿式噴霧を止めるものがなかったため、模擬の熱帯夜で作物は毎晩590分ほど濡れていました。このモードでの
違いは、夕方の停止が始まる時刻だけです。90分ではなく*日没前の噴霧停止時間*(既定120分)です。

このモードでの設定の組み合わせ:

| *夕暮れ前に湿式噴霧を止める* | *日没前の噴霧を許可* | 結果 |
|---|---|---|
| オン(既定) | オン(既定) | 湿式噴霧は日没前に止まり、弱い光で減ります |
| オン | オフ | 同じです — 両方が同じ時刻に止まるので変わりません |
| オフ | オン | 夕方の噴霧を許可します(このルールができる前の動作) |
| オフ | オフ | 従来の夕方遮断のみ — *日没前の噴霧停止時間*から日の出まで噴霧なし |

そのため*日没前の噴霧を許可*は、このルールをオフにしたときだけ読まれます。日焼け・夜間保護モードで
夕方の噴霧を続けたいときは*夕暮れ前に湿式噴霧を止める*をオフにしてください。施設ポップアップには
*光が弱まったため、濡らすタイプの噴霧を控えています — 葉が濡れたまま夜を越してしまいます*
(理由53)と出て、ログには制限の開始と終了のときに1行残ります。ルールベース制御に適用され、
MPCは適用しません。

### 極端な高温・乾燥の短いパルス噴霧 { #pulse-fog }

上の日焼け遮断と[夕暮れのルール](#wetting-fog-dusk)は、日差しが強い間と一日の終わりにかけて、湿式噴霧を
0 に抑えます。普通の日には正しい動きです。ところが極端な日には、湿式噴霧による加湿も冷却もまったく
できなくなります。閉ループ試験の熱帯夜の猛暑(室内42.5 °C、40 °C超が337分、VPDが帯に入っていた割合7 %)と
乾いたフェーン風(RH 15 %、VPD最大7 kPa)では、噴霧が一日中オフでした。この遮断は、地下水のミネラル分が
葉に残ることや水滴が日光を集めることを防ぐためのものでしたが、作物で実際に観察された懸念ではありません。
そのため、そうした日には**短いパルス1回**だけを通します。

パルスは、日焼け遮断がオンで、**かつ**下の行がすべて成り立つときだけ出ます。

| 条件 | 意味 |
|---|---|
| 暑い、または乾燥 | [猛暑保護](#heat-protect)が段階1か2、**または**室内VPDが3 kPa超 |
| 乾きやすい | 乾球 − 湿球が8 °C以上 — 濡れた葉が数分で乾く |
| 湿度 | 湿式噴霧の湿度ロックがかかっておらず、**最高湿度**と85 %を下回る |
| 水 | [ミスト用の水供給](#water-supply)が水ありと言っている(信号未選択は水ありとみなす) |
| 夕方ではない | [夕暮れのルール](#wetting-fog-dusk)(理由53)が始まる4時間より前で、夕方の遮断がかかっていない — **午後の終わり・夕方・夜のパルスはありません。** 最後のパルスの水が閉まっていく室内で蒸発し続け、夜の結露を早めるためです(閉ループ猛暑:余裕なし +5 %、4時間の余裕 +0.4 %の夜の濡れ時間) |
| 他のゲートなし | 雨(実測・予報)、強風段階2、寒波緊急、霜の注意・保護、室内・室外の値の欠落がない。強風段階1は窓の開きを抑えるだけなのでパルスは止めません |

パルス自体は**10秒オン、その後15分以上オフ**で、制御が加湿を求めているときだけ(命令5 %以上。求めがなければ
オフのまま)出ます。すべての湿式噴霧器がすでに使っているパルス投与([デバイス種別による自動変換](#actuators-adapters))に
そのまま乗ります。オン時間は10秒と*最大噴霧時間*の短いほう、オフ時間は15分と*強制乾燥間隔*の長いほうです。
15分の休止は、デバイスアダプターが10分ごとに作り直されて忘れてしまうため、コーディネーターが噴霧器ごとに自分で計ります。もっと短く・もっとまばらに噴霧するよう設定された噴霧器はその設定を守り、
オフ時間は条件が終わった後も続きます。時間や容量で出力を切れない噴霧器(PWM・値出力)はパルスを出さず、
遮断されたままです。霧タイプとドリップは関係せず、日焼け保護がなければ遮断自体がないので何も変わりません。

スイッチ:**極端な高温・乾燥の短いパルス噴霧**(詳細。日焼け保護とともに表示、既定オン)。オフにすると従来どおり
遮断がそのまま保たれます。値 — 10秒、15分、3 kPa、8 °C — はオプションではなく固定です。施設ポップアップには
*極端な高温・乾燥 — 日焼け遮断中でも短い噴霧を1回だけ許可します*(理由57)と出て、ログにはパルスが許可され始めたときと
止まったときに1行残ります。ルールベース制御に適用され、MPCは適用しません。

### ミスト用の水供給 { #water-supply }

水のない噴霧器はポンプを熱するだけで湿度を上げませんが、コーディネーターはタンクを見られません。
**ミスト用の水供給を確認** は、測定値を1つ — タンク水位(%)、配管圧力、流量スイッチ — 結び付け、
しきい値のどちら側が「水がある」かを決めます。

| 項目(確認をオンにすると表示) | 既定値 | 説明 |
|-------|---------|-------------|
| ミスト用の水供給を確認 | オフ | 下の信号が水なしを示している間、すべての噴霧器を止めます。オフなら水があるものとみなします — これまでと同じです。 |
| 水供給の信号 | — | 読む測定値。タンク水位・配管圧力・流量スイッチ。 |
| 水供給のしきい値 | 0.5 | 信号が使う単位のままです。オン/オフのスイッチ(0 または 1)は 0.5 のままにし、タンク水位は噴霧を続けたい最低水位に設定します。 |
| 信号が次のとき水があるとみなす | しきい値以上 | *以上*: 水位・圧力・流量 — 大きいほど水が多い。*以下*: 空のとき 1 になる空タンク警報スイッチ。 |

| 信号 | 水 | 噴霧器 |
|---|---|---|
| 確認オフ、または信号未選択 | あるとみなす | これまでどおり |
| 新しい値がしきい値の正しい側 | あり | これまでどおり |
| 新しい値がしきい値の誤った側 | **なし**(不足) | すべて停止 |
| 値がない、または古い | **なし**(不明) | すべて停止 |

確認をオンにしたのに信号を選んでいないときは、ログに1回知らせ、水はあるものとみなし続けます。

信号が分からないことも、あえて「水なし」と読みます。水があるか分からないままポンプを回す損失は、
噴霧器を数分休ませる損失より大きく、休止は信号が戻ったサイクルで終わるからです。鮮度はこの信号
自身の周期で判定します(冷暖房の稼働信号と同じ規則)。いったん「なし」になると、しきい値から
しきい値の5%分さらに戻るまで「あり」に戻しません — ポンプ運転で生じる圧力の揺れで毎サイクル
反転しないようにするためです。

水がない間は、猛暑かどうかに関係なく**すべての噴霧器**をパーキングし(*ミスト用の水がありません*、
理由41)、そのサイクルから 0 を出力します。どのエンジン(グレーボックスMPCを含む)が命令を出して
いても、手動ロックが掴んでいても、最終オーバーライドが 0 に切ります。猛暑保護も噴霧を止めている
場合は、*いまは噴霧で空気を冷やせません* より理由41が優先されます — 人がすべきこと(水を補充する)
が見えるようにするためです。保護も同じフラグを読みます。

切り替わるたびにログを1回残します(*水がないため噴霧器をすべて止めます* / *ミスト用の水供給が
戻りました*)。確認をオンにすると、チャンネル92に 1(あり)・2(不足)・3(信号なし・期限切れ)を、
デバッグの有無に関係なく毎サイクル記録し、ヘルスチェックは水がなくて噴霧器が止まった時間を分単位で
報告します — 0 でなければ、人がタンク・圧力・信号を確認する必要があります。

### 光と遮光 { #settings-light }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 遮光・補光の基準 | 0–800 W/m² | とどまるべき範囲ではなく、2本の基準線です。帯より暗ければ: 補光灯が点き、遮光スクリーンが開きます。明るければ: 遮光スクリーンが閉じます。帯の中では何も起きません。基準は**作物が実際に受ける光量**です — 屋外日射に被覆材と遮光スクリーンの透過率を反映した値です。 |
| 遮光カーテンで暑さを抑える | オン | 作物がその日に必要な光を受けられる間だけ遮光スクリーンを閉じ、暑さと水分ストレスを和らげます。オフにすると従来どおり VPD・温度の偏差だけで動きます。[遮光スクリーンで暑さを抑える](#shade-heat)を参照。 |
| 夜の結露に保温カーテンを少し開ける | オン | 夜に空気が露点に近づくと、窓より先に閉じた保温カーテンを 3 → 6 → 10 % 開けます — 逃げる熱が許す範囲だけ。途中で止められるカーテンモーターだけに使います。[保温カーテン — 夜のすき間と朝の段階開け](#curtain-gap)を参照。 |

どちらの端もオフにでき、オフの意味は両端で異なります — 下側のハンドルを0にすると
*補光しない*、上側のハンドルをオフにすると*遮光しない*です。施設に遮光スクリーンや
補光照明が登録されていない場合、画面は何もしないハンドルを出す代わりにその旨を
伝えます。

遮光側の基準線は、閉じたスクリーンの下の光量ではなく**スクリーンを開けたら**どれだけ
明るいかで判定します — そうしないと、閉じた瞬間に暗くなって判定が解け、次のサイクルで
また開いてしまいます。屋外の光量が分からない場合(室内センサーのみの設置)は、現在の
値で判定します。遮光が効いている間は、補光と開放を同時に強制しません。2本の基準線を
同時に満たせないとき — スクリーンを閉じると補光の基準線より暗くなる設定 — は遮光を
優先し、その矛盾をログに一度だけ書き出して、人が直せるようにします。

裏にある実際の値は**最小光量しきい値(補光)**(既定0)と**最大光量しきい値**
(既定800)で、どちらも[詳細]の下に表示されます。

関連する3つの値はこの画面には**ありません**。

- **遮光生地の透過率**は施設側の設定で、施設エディターの遮光カーテンの下に
  あります。室内の光センサーがないときにのみ使われ、そのときは屋外日射と
  開度から室内の光量を推定します。未設定または範囲外の値は0.50にフォール
  バックし、施設が遮光カーテンを*持たない*と宣言している場合は1.0が使われます。
  1画面だけ生地が異なる場合は、そのActionで個別に上書きできます。
- **被覆材の透過率**は外皮の資材から自動的に決まります(ガラス0.85・二重フィルム0.78・
  不織布0.50など)。遮光スクリーンがなくても屋根は常に光を減らすため、
  室内光量の推定にあわせて掛けています。そのため光量の上下限は**室内基準**です。同じ250でも、
  ガラス温室と不織布ハウスでは作物が受ける光が2倍近く違います。
- **光飽和点**は遮光しきい値ではなく、プログラムにある作物の`K_L`から導かれます。
  この2つを1つの値にすると、遮光しきい値を下げた途端に光合成モデルが「もう十分な
  光がある」と判断し、強い日射の下でも光制限を検出できなくなります。`K_L`がない場合は、
  システムの既定値600 W/m²が使われます。

### 遮光スクリーンで暑さを抑える { #shade-heat }

遮光スクリーンを閉じると二重に涼しくなります — 空気を温める日射が減り、作物の蒸散が減って空気が
乾きにくくなります。しかし光も奪い、光は効果モデルが量る量ではありません。任せておくと制御器は
遮光をただの冷房とみなします。そこで、スクリーンを熱・湿度の調整に使ってよいかは一か所
(`screen_policy`)で決め、制御器はその答えだけを読みます。判断は日が出ている間だけです(外の日射
150 W/m² から、100 を下回ると解除 — 極端な高温保護と同じ線。日射が分からなければ日の出~日の入り)。
することがないスクリーンは日が出ている間だけ開いた状態に戻ります — 夜はその場のままです。閉じた
スクリーンが作物の空への放射冷却を防ぐためです。

**光の三つの状態。** スクリーンを**閉じ切ったとき**作物が受ける光量と、今日の光(DLI)を見ます。今日の
光は、ここまでに受けた光に「日没まで閉じたままにした場合」残りの一日がもたらす光を足したものです —
施設位置の晴天日射に、直近30分の曇り具合・被覆材・スクリーンの布を掛けます。

| 状態 | いつ | スクリーンは |
|---|---|---|
| 光を守る | 閉じ切ると**最小光量しきい値**を下回るか、その日の光がプログラムの DLI 目標に届かない | 開けたままにします(*遮光カーテンを開けたままにしています*、根拠 44) |
| 光に余裕 | 閉じ切っても作物の光飽和点以上か、湿潤型ミストの日焼けロックがかかるほど明るい | 熱・VPD の調整に自由に使います(*暑さを抑えるため遮光カーテンを閉じています*、根拠 43) |
| その間 | 閉じると光合成は減るが、その日の光は足りる — DLI 目標や光量が分からないときもここ | より安い手段を使い切ってからだけ使います。窓・ファンがすべて 80 % 以上(または外が室内 − 1 °C より暖かい)**かつ**ミストを使い切った(噴霧器なし、水・日焼けロック・高温保護で止まっている、または 80 % 以上で運転)。それまでは開けたままです(根拠 44) |

使ってよいときは[温度上限](#l3-coordinator-actuator-command)の項もスクリーンを動かし、線を越えた後では
なく越える前に閉じます。暑く乾いた日の順序はこうなります: 窓 → (光に余裕の遮光) → ミスト →
(その間の遮光) → ファン → 冷房。この順序は上の「使い切ったか」の判定が作ります — コストでは作れ
ません。負荷分担はドメインごとに別なので、スクリーンにコストを付けてもミストを待たせられません。

**往復を減らす。** 遮光スクリーンは一度動くのに数分かかります。制御器が命じる移動はふるいにかけます。
動いた後は少なくとも15分(または全行程時間の3倍の長い方)そのまま、動けという要求が5分続いてから
動き、日がなければ閉じず、施設の現地日付で1日8回までしか動きません — その後はその日の残りの間、
制御器の要求はその場に留めます(*遮光カーテンをそのままにしています*、根拠 45、ログは一度)。日没後に
開けるのは回数に数えません。最大・最小光量しきい値、温度のハード限界、極端な高温保護、安全ゲート、
手動ロック、光を守る規則が命じた移動は常に通ります。

**誰が握るか。** 極端な高温保護がオンでスクリーンを閉じた(または見送った)ときは保護が主です —
この節の規則はかけません。保護も光の判断をここに問います — 段階1では光の状態が*光を守る*(最小光量
またはその日の DLI)なら閉じず、段階2またはしきい値より3°C以上高ければ関係なく閉じます。最大・最小光量しきい値と
温度のハード限界はこの節のすべてに優先します。

遮光スクリーンの効果モデルは布の透過率 τ を使います。スクリーンが遮るのは光の (1 − τ) だけで、開けると
VPD は温まる分から**増えた日射で作物が蒸散した水の分を引いた**だけ上がります — 温度だけが上がると見た
場合の約 60~80 % です。係数を手で合わせたスクリーン(`k_override`)はその値を新しい単位で読みます —
τ = 0.5 では半分として数えます。

光の状態は変わったときだけログに残します。ヘルスチェックは根拠 43~45 を*遮光・熱負荷*、*遮光・光を守る*、
*遮光・往復防止*と呼びます。

### 保温カーテン — 夜のすき間と朝の段階開け { #curtain-gap }

モーターが途中で止まれる保温カーテン — 位置で動き(ペアモーターや位置出力)全行程時間が分かる
カーテン — は開・閉だけでなく途中も使います。それ以外(リレーのカーテン、行程時間なし)は 0/100 の
ままです。通常の制御の命令はどちらでも 0/100 で、下の二つの動作だけが途中で止まります(停止点
0 · 3 · 6 · 10 · 30 · 60 · 100 %)。記録される値がそのまま送られる値です。

**夜の保温 — すべての保温カーテン。** 夜、ハウスが熱を守る必要があればカーテンを閉じます: 室内が目標温度の
下の線(温度が制御目標なら目標 − 許容誤差、VPD 直接モードなら誘導範囲 — VPD から導いた温度目標は線に使いません)+ 2 °C より低いとき、または外がその下の線より寒いとき、あるいは室内の空気が露点の 3 °C 以内に近づいたときです(露の需要: 開いた
カーテンの下の作物は夜空へ冷えて空気より先に濡れます。シミュレーションでは同じ夏の夕方が、カーテンが閉じると
夜の濡れ173分、*勾配なし*で開いたまま残ると433分でした。露の需要では室内が目標の上の線を超えたときだけ冷やす
必要とみなし、余裕が 4 °C を超えて戻れば解除します。雨の間や止んで1時間以内、または外のRHが95 %以上の間は雲が空への放射を遮るので露の需要は見ません)。**暖房が動いているときもそれが熱の需要です**: 直前のサイクルで暖房機が 0 超の指令を受け(止まってから30分まで)外が室内より寒ければ、室内が範囲の真ん中でもカーテンを閉じます — そうしないと暖房機が温めている間、開いたカーテンが熱を捨てます。暖房が動いている間は、室内が入った線よりかなり上でも解除しません。
判断は目標と外気温で行い、今の室内外の空気の温度差では行いません — 開いたカーテンの下の室内は外に追従するので、
その差が小さいのはカーテンが開いている*から*であり、閉じたカーテンは空気の温度差に現れない晴れた夜空への放射
損失も防ぎます。室内が目標の上の線の 1 °C 以内かそれより上(冷やす必要がある)、または外気が室内より暖かければ
通常の制御に任せます。閉じた後は、室内が入った線より 1 °C 上がり外も下の線より 1 °C 上がったとき、室内が目標の
上の線を越えたとき、または外が室内より 1 °C を超えて暖かくなったときに解除します(*夜間の熱を逃がさないよう
保温カーテンを閉めました*、根拠 49)。リレーのカーテンも閉じます。下の夜のすき間は閉じたカーテンをこれまでどおり
少し開け、**最低温度**・安全ゲート・日の出の開放は変わりません。

**夜のすき間 — 結露はカーテンが先。** 夜、カーテンが閉じていて(5 % 以下)室内の空気が露点の 2 °C 以内に
近づくと、カーテンを少し開けます: 3 %、次に 6 %、次に 10 %。各段階を15分保ち、その間に余裕が回復し
始めていないときだけ次の段階へ進みます(*夜の湿気を逃がすため保温カーテンを少し開けています*、根拠 46)。
余裕が 3 °C を超えて戻れば再び閉じます([過湿ゾーン](#humid-zone)と同じ線)。熱が先です: 暖房が強制されて
いる間(**最低温度**)や、暖房機がないのに室内が目標温度の下の線以下ならすき間は開けず、外が室内より 8 °C
以上寒いか暖房機が 80 % 以上で動いていれば最初の段階までにします。寒波ゲートと**最低温度**はこれらすべての
上でカーテンを閉じます。

窓の夜間結露エスケープ([換気](#settings-ventilation)を参照)はすき間を待ちます — すき間を開けられるところ
まで開けて15分置いても空気がまだ露点に近いときだけ許されます。途中で止まるカーテンがないか、このオプション
をオフにすると窓は従来どおりです。

**朝の段階開け。** 日が昇ると、夜通し閉じていたカーテンを一度に開けず 10、30、60、100 % と開けます —
カーテンの上の冷気が作物に降りてこないようにします。各段階は10分で、その段階の間に室内の低下が 1 °C 以内で、
まだ温度範囲の下端以上のときだけ次の段階へ進みます — 後の条件は最初の2時間だけです。暖房が範囲まで温められない日にカーテンを一日中閉じたままにしないためです(*朝の冷気で作物が冷えないよう…段階的に開けています*、
根拠 47)。室内と外の差が 5 °C 未満なら気にすべき冷気の層がないので、すぐに開けます。それ以外の昼の開放は
従来どおりです(根拠 22)。

#### 効果キャリブレーション { #settings-calibration }

| 項目 | 既定値 | 説明 |
|-------|---------|-------------|
| 効果エンジン | レガシー | `レガシー`: 内蔵のK_*定数(既定、安全)。`シャドウ`: グレーボックスモデルを記録目的だけで並行実行します — 制御は変わりません。MPCが制御していたら送ったはずの指令とその予測も記録します。`グレーボックス`: 物理モデルによる制御。毎サイクル、まずMPC(数ステップ先を見通す最適化)を試し、うまくいかなければ物理モデルのPI、次にレガシーへ戻ります。MPCはこれからの外気を次のように見ます。日射は、太陽の位置から計算した晴天時の日射に今の晴れ具合を掛けて見ます(施設の座標があればどの国でも)。外気の温度・湿度は、今の実測から**予報が示す変化分**だけ動かします。予報は、施設(気象タブ)に連携した Open-Meteo 時間別予報入力のファイルを受信してから2時間以内ならそれを使います — 施設の座標の予報なのでタイムゾーンは問いません。そうでなければ、気象庁(韓国)の短期予報が発表から6時間以内で施設と同じタイムゾーンのときにそれを使い、どちらもなければ今の値のままにします。予報の値そのものではなく変化分を使うのは、予報(広い格子の平均)とこの施設の気象計との差を消すためです。MPCもPIと**同じ判定**に従います — 夜間閉鎖、外気では目標に届かない換気、冷暖房運転中の開口部ロック、換気優先、温度が求める方向と逆の冷暖房、[過湿ゾーン](#humid-zone)(外気のほうが湿っていれば閉じ、開けてよい場合も最大30%)。これらの判定がかかった装置は、MPCが開けたり入れたりしません。MPCは窓とファンを**風量**で扱います(窓の面積、ファンの定格風量)。同じ換気量なら、室内のほうが暑いときは天窓から、外のほうが暑いときは側窓から開けます。ファンの風量が窓より大きければファンで換気し、窓は閉じておきます(窓が開くと壁のファンは空気を抜けません)。遮光カーテンと保温カーテンはMPCが動かさず、今の位置を予測に入れます — 保温カーテンを閉じると外皮からの熱損失が減ることも計算します。推奨の流れ: まずシャドウ、次にグレーボックス。集めたデータと成績は、アプリやデーモンを再起動しても引き継がれます(制御周期を変えたときや、1週間を超えて止まっていたときは最初から集め直します)。物理モデルは**シャドウで集めたデータで学習し、10サイクル先の予測が「今の値のまま」という単純な予測より良いときだけ**グレーボックス制御が有効になります。この比較は気象区分(暑い昼・穏やかな昼・日の出/日の入り・夜など)ごとに行い、標本が十分に集まったすべての区分で上回る必要があり、そうした区分が2つ以上必要です — それまではレガシーで動きます。モデルの物理式が変わる更新のあとは、この学習と検証を新しい式でやり直します。シャドウまたはグレーボックスを選んでいる間は、この並行計算が動き続けないとその学習は進みません — 3サイクル連続で失敗するとログに記録し、その後は60サイクルごとにもう一度記録します。止まっているのに気づかないままにならないようにするためです。[猛暑保護](#heat-protect)中のサイクルはレガシーで動きます(MPCはその規則を知りません)。負荷分担から外した[疑わしいアクチュエーター](#actuators-suspected)があるサイクルも同様で、室内の温度または湿度(CO₂目標があればCO₂も)を測定できないサイクルも同じです — MPCが作り出した値で最適化することになるためで、理由が変わったときと、続く間は1時間ごとにログに残ります。試験中以外は変更しないでください。 |

## アクチュエーターの登録 { #actuators }

連携施設の図面に描かれたアクチュエーターは自動的に検出されます。それ以外は
このFunctionに**環境制御**アクションを登録します — デバイス1台につき1回、この
アクションを追加してください。手動登録は、施設から検出されたリストとマージ
されます。

ペアド・アクチュエーターモジュールも自動で検出されますが、**連携施設に属するものだけ**
です。施設のスロットに割り当てられているか、施設の地図に配置されている必要があります。
どの施設も使っておらず地図にもないモジュール(試験用、割り当てがすべて終了した機器)や
他の施設に属するモジュールは無視されます。「自動制御の対象機器」でオフにした機器は、
どの経路で検出されてもオフのままです。ファンの定格風量は、アクチュエーターの
*風量*仕様またはファン金具の風量から読み取り、どちらもなければ既定値(排気・吸気ファンは3000 m³/h、循環ファンは1500 m³/h)を使います。

| `vol` / `volume`(容積式ポンプ) | 容積式 | `vol_ml = flow_lpm × on_sec / 60 × 1000` |
| `pwm` | PWM | duty = pct |
| `on_off`リレー | 時間比例 | `on_sec = cycle_sec × pct/100`。5%未満はOFF |
| それ以外 | 値 | 0~100%をそのまま渡す(DAC、ステッパーなど) |

| 指令(%) | on/offリレー(60秒周期) | PWM | 容積式ポンプ(1.5 L/min) |
|---:|---|---|---|
| 0 | OFF | duty 0 | OFF |
| 30 | 18秒間ON | duty 30 | 450 mL/周期 |
| 100 | 60秒間ON(連続) | duty 100 | 1,500 mL/周期 |

**スクリーン。** 遮光スクリーンと保温カーテンは、どのアダプターで駆動しても全開か全閉に動かします([L3](#l3-coordinator-actuator-command))。例外は位置で駆動するスクリーン — ペアモーターまたは位置出力で、全ストローク時間が分かっているものです。保温カーテンの夜のすき間と朝の段階開けは、そうしたスクリーンを途中で止め(3 · 6 · 10 · 30 · 60%、[保温カーテン — 夜のすき間と朝の段階開け](#curtain-gap)参照)、記録には実際に送った値がそのまま残ります。リレーやPWMのスクリーンは常に0/100です。

湿式噴霧器は、さらにパルス投与でラップされます — 1回の噴霧は最大作動時間で
打ち切られ、乾燥間隔が経過するまでは一切噴霧しません。[極端な高温・乾燥の短いパルス](#pulse-fog)
(理由57)1回は、このパルス投与をより厳しい上限 — 最大10秒オン、最低15分オフ(休止はコーディネーターが計る) — で使います。
乾燥間隔は、コーディネーターが設定と機器を読み直すとき(10分ごと、または再読み込み)にも引き継がれます —
噴霧した直後の噴霧器が、読み直しの直後にまた噴霧することはありません。乾燥間隔を短くすると新しい値が
最後の噴霧から直ちに適用され、長くすると現在の休止も延びます。コーディネーターを再起動すると間隔は最初から数えます。
乾燥間隔は2回の噴霧の*開始*どうしの間隔として扱います(サイクルの揺れ数秒を許容、最大で間隔の10分の1)—
そのため周期600秒・間隔600秒なら1サイクルおきではなく毎サイクル噴霧します。理由57のパルス後の15分休止にはこの許容はありません。

かんがいの流量は施設図面から集計されます — あるレイヤー下のすべてのエミッターが
そのアクチュエーターの`flow_lpm`に合算され、容積式アダプターがそれをそのまま
使います。フォールバックの順序は、アクチュエーターごとの流量、次に施設全体の
合計、それもなければ1.0 L/minです。

噴霧器の効果モデルは**別の**流量を使います — そのアクチュエーターのドリップ以外の
噴霧ノズルの流量だけを見て、フォールバックしません。投与量には根へ向かうドリップが
含まれますが、空気中へ蒸発する量には含まれないからです。そのため図面にノズル情報が
ない噴霧器は、施設全体の合計を引き継ぐのではなく、冷却・加湿の効果がまったくない
ものとして計算されます。

### 過湿ゾーンと反応しない窓 { #humid-zone }

空気が飽和に近いとき、VPD で換気を判断すると誤ります。VPD は温度に引きずられる量で、
外気のほうが暖かいと、水分がずっと多くても外気の VPD は高く出ます。すると「開ければ乾く」と
読んで湿った空気を入れてしまいます。そこで**室内の VPD が 0.3 kPa を下回る、または露点余裕
(温度 − 露点)が 2 °C より小さい**ときは、換気を水蒸気圧(露点)で判断します。ゾーンを出る
しきい値は VPD 0.4 kPa、余裕 3 °C です。

| 外気の露点 | 窓の動き | 画面の表示 |
|---|---|---|
| 室内より **8 °C 超えて冷たい**、または**室内が温度の基準線以下**か暖房要求中(最低温度の限界による強制暖房を含む)で、外気が 1 °C 超えて冷たい | 露点に関係なく開けず、**閉じる側**へ向かいます。温度が露点の判断に優先します — 開けて失う熱(冬の暖房中)が湿気を逃がす効果より大きいためです。例外: 下の[湿気抜き](#morning-purge) | 過湿 — 外気が冷たすぎます |
| 室内より 1.5 °C 以上低い(すでに開いていれば 0.75 °C) | 開けますが**最大 30 %** まで。湿気を逃がすのが目的です。例外: 下の*開度の上限を外す* | 過湿 — 開度を制限 |
| それより小さい、または高い | 開けず、**閉じる側**へ向かいます。窓では解消できません | 過湿 — 換気では解消できません |

- **温度の基準線**は、温度が制御目標なら目標 + 許容誤差、**VPD 直接モードなら誘導範囲の下端**です。このモードの誘導温度目標は
  いまの室温より常に先にあり(湿っているほど遠く)、それを基準にすると外気が 1 °C 冷たいだけで「外気が冷たすぎます」で
  閉じていました — 金堤(キムジェ)10 月 13 日 12:48〜15:59、室内 RH 82〜91 %、外気は気温がほぼ同じで露点が 3〜4 °C 低いのに、
  側窓は 6〜30 % のまま 2 回閉じられました。いまはこのモードでは、室内が誘導範囲の下端を下回るときだけ暖房要求と読みます
  ([湿気抜き](#morning-purge)の温度の下限と同じ線)。誘導目標から出た「暖房要求」はこの判断に使いません。最低温度の限界による強制暖房は従来どおり閉じます。
- 高温の非常時や温度上限の項が立っているときは、このゾーンを適用しません。暑くて湿った日の
  換気は湿度ではなく温度が求めます。
- ハードの湿度上限を超えたときは開度の上限を外します。ただし外気のほうが湿っていれば開けません。
- **開度の上限を外す。** 30 % の上限の意味は「開けて温度・VPD を合わせない」であり、「湿気を逃がす量を減らす」ではありません。
  外気が**ほぼ同じ温度以上**(室内 − 2 °C 以上)で、**露点が 3 °C 以上低い**(通常のしきい値 1.5 °C の 2 倍)ときは、開けるほど
  湿気がよく抜け熱の損失は増えないので、上限なしで開きます。いったん外れたあとは 3 °C・2 °C に緩み、境目で上限が出入りしません。
  外気がそれより冷たい、または乾いていなければ従来どおり 30 % です。
- 外気の値が分からないときは、このゾーンは判断しません(「外気の値なし」の規則が担当します)。
- 暖房・除湿の装置がない施設では、窓で解消できない過湿を解く手段がありません。画面はその事実を
  そのまま示します。

**開けても偏差が縮まらない窓は、それ以上開けません。** 効きの弱い窓(有効度 0.06 未満)が 10 % 以上
開いているのに 45 分間で偏差が 10 % も縮まらなければ、その位置に留めます。開けても室内が
変わらない間に「もっと開けろ」が積み上がり、窓がゆっくり 100 % へ上がる(ドリフト)のを防ぎます。
偏差が再び縮まれば再開します。効きの強い窓は対象外です — 日射が強まり偏差が広がるときは
さらに開ける必要があります。(効きの強い窓が何時間も全開なのにまったく反応がない場合は別の扱いです — [疑わしいアクチュエーター](#actuators-suspected)を参照。)

**小さな VPD の差では窓を動かしません。** 換気無益の判定は、外気が室内と違うというしきい値を
許容誤差(既定 0.1 kPa)ではなく **0.25 kPa** にします。RH 1〜2 %p のセンサーノイズに収まる差では
開けません。

**無益の判定はしきい値で反転せず、開いている窓はすぐには削られません。** 新たに無益になるには差がしきい値の
60 %(0.15 kPa)を下回る必要があり、無益から抜けるにはしきい値(0.25 kPa)まで回復する必要があります。
開いている窓は、無益の判定が **20 分** 続くまでその位置に留め、その後で閉じる側へ減衰させます。
閉じていた窓はすぐにパーキングします。

**外気の温湿度は 10 分の移動平均で判断します。** 数時間ごとに変わる整数単位の値で判定が
反転しないようにします。降雨・風速などの安全ゲートは平均しない生の値を見ます。

### 過湿な朝の湿気抜き { #morning-purge }

晴れた朝は、上の表の「外気が冷たすぎます」の行が、日射が無料の熱で家を温め、外気のほうが乾いているのに、
RH 90 % 以上のまま何時間も窓を閉じたままにすることがあります(灰色かび病のリスク)。栄養(ヨンヤン)、10月10日:
07:00〜09:30 に日射が家を 9.5 → 22.9 °C まで温める間、RH 91 % のまま窓は 0 % でした。そこで日射が家を温めている間は、
窓をパーキングする代わりに **5〜15 % の小さな最低開度**(根拠 54)を与えます。

| 条件 | 値 |
|---|---|
| 日射 | 屋外日射 100 W/m² 以上(70 未満で解除) — [日射の熱を逃がす](#solar-vent)と同じ値 |
| 過湿 | 室内が上の過湿ゾーン内(入る・出るしきい値も同じ) |
| 外が乾いている | 室内の露点が屋外より 2 °C 以上高い(すでに抜いていれば 1 °C) — 水蒸気圧で判断するので、暖かくて VPD は高くても水分の多い外気は対象外 |
| 熱損失が小さい | 室内が温度目標の下限線(目標 − 許容誤差)より 1 °C 以内の下。3 °C 下までは家が温まっている最中(サイクル間で測った 0.5 °C/h 超)のみ。それより下、最低温度のハード限界による強制暖房中、外気が室内より 15 °C 超えて冷たいとき、下限線より下で 1 °C/h より速く冷えているときは行わない |
| 開度 | 5 % に最大 10 % を加算 — RH が 85 % を超えた分と日射(しきい値の上 400 W/m² で最大)に応じて増える。下限線より 1 °C 超えて低いときは 5 % のみ |

湿気抜きは窓をその開度まで**引き上げるだけ**で、VPD や温度を追ってそれ以上は開けません(それは制御器と日射の熱の規則の役目です)。
積分もそこに留まるので、解除時に窓が一気に閉まることはありません。室内が過湿ゾーンを出る、日射が弱まる、外気がもう乾いていない、
家が冷えるといずれかで解除されます。優先される判定: 降雨・風速ゲート、[降雨の段階制限](#safety-gates)(根拠 52 — 湿気抜きは窓を雨の上限より上げません: 閉じた天窓は閉じたまま、上限のかかった側窓は 30 % 以下のまま)、屋外値なし、降雨・風速の喪失、夜間パーキングとその直前 45 分、
冷暖房連動、極端な高温保護の「外が暑い」。「外気が冷たすぎます」・「勾配なし」・換気無益に勝ち、日射の熱の最低開度(根拠 51)のほうが大きければそちらの表示が残ります。
ポップアップは「夜の間にこもった湿気を逃がすため少し開けている — 日が当たり、外の空気のほうが乾いている」で、開始と終了はログに 1 行ずつ残ります。
値は固定でオプションではありません。ルールベースの制御(Legacy と物理モデル PI)に適用され、MPC は適用しません。

### 結露しやすい夜の循環ファン { #night-dew-fan }

熱帯夜は屋外の露点が室内より高いまま残り、窓を開けると湿気が抜けるのではなく入ってきます。ハウスは閉じたまま
空気は飽和に近く、作物は朝まで濡れたままです — 閉ループ `heatwave_tropical_night`(3日間、夜のRH 90 %以上)では
夜1148分が濡れていました。葉は風のない空気で最も長く濡れます: 厚い境界層が蒸発を遅らせ、葉が空気より冷えて
露が付きます。空気を動かすと境界層が薄くなり、葉が早く乾いて露も付きにくくなります。ハウス内の湿気を抜くのでは
なく、**葉が濡れている時間を短くする**手段です。

**循環ファン**が登録されていて**詳細オプション「夜露の循環扇（試験）」がオン**のとき（**既定はオフ**）、次の二つが同時に成り立つとファンを**100 %**(根拠59)で回します:

| 条件 | 値 |
|---|---|
| 夜 | 施設の位置の日没〜日の出。位置が不明なら何もしません |
| 露点の余裕が小さい | 室温 − 露点が **2 °C** 未満。**3 °C** で解除、ただし運転開始から30分は止めません。[過湿ゾーン](#humid-zone)・夜の[カーテン隙間](#curtain-gap)と同じしきい値です |

15分入り・15分切りのデューティではなく連続です: 効果は空気が動いている時間に比例し(ファンが止まると境界層は数分で
再び厚くなります)、デューティは5〜10分周期をまたぐ別の記憶が必要で、循環ファンは最も安い装置であり、この規則は
余裕が小さいときだけ働くためです。循環ファンのない施設は変わりません。[極端な高温保護](#heat-protect)と空間センサーが
見つけたホットスポットはそれぞれの根拠(1)でファンを100 %にし、霜対策([霜](#frost)、根拠56)も100 %にします — そちらが
常に優先です。ポップアップには *循環ファン稼働 — 夜の空気が露点に近く、空気を動かすと葉が濡れている時間が短くなります*
と表示され(翻訳)、ファンの開始・停止時にログが1行残ります。しきい値は固定でオプションではありません(オン・オフのスイッチだけがオプションです)。

**既定がオフの理由。** 仮想の循環ファンを付けた閉ループ `heatwave_tropical_night` では、この規則で夜の濡れ時間は変わらず(918分)、ファン電力が17 %、被覆の結露が80分増えただけでした — 熱帯夜の閉め切ったハウスは空気を動かすだけでは葉を露点より上に保てません。試験用に残してあり、下の健康点検の夜露・霜の時間はこのオプションと無関係に数えます。

ヘルスチェック(`check_env_coordinator_health`)は室内の温湿度センサーから、期間の**夜の結露分**(夜で室内RH ≥ 95 % または
露点の余裕1 °C未満)と**室内0 °C以下の分**も、霜の注意・保護の分の横に出します。夜の結露が夜の4分の1以上(かつ60分以上)、
室内の霜が15分以上、霜保護が60分以上のとき、施設への提案を1行加えます — *除湿機・保温カーテン・暖房の検討*(循環ファンや
暖房機がなければその旨も)。施設側の事柄なので終了コードの不具合には数えません。

### 測定のない軸、装置のない軸 { #actuators-missing }

施設ごとに備えている装置は違います。測定はできても動かす手段がない軸、逆に動かせても
測定する手段がない軸は、どちらも普通の構成です。コーディネーターはその組み合わせを
見て、自分で動き方を変えます。

| 状況 | コーディネーターがすること |
|------|----------------------|
| 測定はできるが、その軸を動かす装置がない | その値は**参考値**です。制御対象から外れ(外気の値があれば、その軸の目標を外気の値に置き換えます)、光合成の判定や他の軸の計算にはそのまま使われます。目標から外れたままなら、施設のポップアップが*動かせる装置がありません*と伝えます。 |
| 片方向しかない(ヒーターはあるが冷房機はない) | 正常です。その方向の要求が来れば働き、逆方向なら0%で休みます。 |
| 装置はあるが、その軸を測定できない | その装置が動かす別の軸を測定できれば、その軸で制御を続けます(たとえば湿度は測れないが温度は測れる開口部)。動かす軸を**1つも**測定できないときだけ、**その場にとどまります** — 実際に出た開度のままなので、風向重みが少しずつ閉めることはありません。偏差が分からないのに動かすのは根拠なく設備を使うことであり、閉じることも開けることも1つの判断だからです。唯一の例外は晴れた日の換気です — 閉じた窓をそのままにすること自体がハウスを暑くするからです: [晴れた日に室内の値が途切れたとき](#solar-vent-blind)(根拠60)。 |
| 室内の温度・湿度を測定できない | その軸はまるごと制御から外れます。ない値を0と作り出すことはしません — そうすると「室内0°C」と読まれ、暖房が全開になります。葉をぬらす噴霧は、湿度が分からない間は遮断されます。VPD目標があるのに湿度を失うと、温度・湿度からはVPDも計算できません。センサーが自前のVPDを出していればそれが代わりを務め、なければそのサイクルは温度・湿度の基準に退きます — 窓・暖房・冷房は温度で動き続け、ログの抜けた項目に*vpd*がその説明とともに残ります。 |

関数設定のいちばん上にある**調整可能**の行が、この組み合わせを軸ごとに一語で示します
(温度・湿度・VPD・CO₂・光量)。装置の構成と直近のサイクルで測った値からコーディネーターが
計算したもので、語にマウスを重ねると、その軸を動かす装置の名前が表示されます。

| 表示 | 意味 |
|------|------|
| 両方向 | 測定でき、上げる装置と下げる装置の両方があります。 |
| 上げるのみ / 下げるのみ | 測定でき、片方向の装置だけがあります。 |
| 見るだけ | 測定はできますが、動かす装置がありません(参考値)。 |
| センサーなし | その軸を直接動かす装置はありますが、測定できません。 |

装置もセンサーもない軸は表示しません。開口部がCO₂を少し下げるような、**副次的な効果
だけ**で動く軸も、センサーがなければ表示しません。VPDは温度と湿度の両方の装置を
合わせて見ます — 加湿の噴霧はVPDを下げ、換気は外気が乾いていればVPDを上げます。
この行は今のところ**表示専用**で、制御は上の表の規則どおりに動きます。

**安全ゲートも同じ規則です。** 室内の値が途絶えると、ゲートはその事実に名前を付けて
画面とログに残しますが、**強制指令は作りません。** すべての装置を安全時デフォルト
位置へ動かすこと(開口部は閉じ、スクリーンは開く)は、根拠がないという理由で
設備を動かすことになるためです。外気の値が途絶えたときと同じ判断であり、制御を
まるごと止めることもしません。CO₂や光量のように、まだ測定できる軸は制御を続けます。

降雨・強風のように**外気だけで判断できる危険は、そのまま防ぎます。** 逆に、高温緊急・
低温緊急は室内温度が分からないときは判定しません — これらのゲートはすべての装置を
一方向へ動かすため、根拠が確かなときだけ作動するべきだからです。

食い違った組み合わせはヘルスチェックも知らせます:

```bash
python3 -m aot.scripts.check_env_coordinator_health
```

目標はあるのに測定がない場合、目標はあるのに装置がない場合、装置はあるのにその装置が
動かす軸を1つも測定できない場合を**設定チェック**に報告します。測定だけがあり、目標も
装置もない軸は報告しません — それこそが参考値だからです。

### 疑わしいアクチュエーター { #actuators-suspected }

失敗し続ける、または何もしていないように見える装置に命令を積み続けてはいけません —
積分がワインドアップし、コーディネーターが「担っている」と*信じている*分が負荷分担の台帳に
残って、ほかの装置の働きが減ります。そのため**疑わしい**アクチュエーターは負荷分担から外し、
その位置にとどめます。

疑わしくなる経路は2つです。

| 経路 | 条件 |
|---|---|
| 送信の失敗が続く | 5サイクル連続で失敗し、**かつ**最初の失敗から4分以上。1回でも成功すれば数え直します。数週間にわたって散発した失敗は対象外です(学習の重みに使う累計回数は別の数値で、ここでは読みません)。 |
| 強く命令したのに反応がない(換気装置のみ) | 上の*開けても偏差が減らない窓*と同じ判定を、反対の帯に適用します。モデルが**効果が明確**とする(有効度0.06以上)換気装置が直前の命令**80%以上**で、外気の値が分かっているのに、**2時間のあいだ偏差が10%も縮まらず**、**かつ**いま命令している換気効果の80%以上をこの装置が単独で担い(複数の窓が全開なのに改善しない場合、原因は窓1つではなく共通です — 開ループのセンサー・センサー故障・能力不足)、**かつ**ほかの換気装置が残るとき。この経路で外せるのはドメインごとに同時に1台で、次は6時間後です。 |

疑わしい間、その装置は*この装置は故障の疑いがあります*(理由42)と表示され、命令は最後の位置の
まま、**送信せず**、積分はそのまま、台帳には何も載せません — 同じドメインの残りがその分を
引き継ぎます。安全ゲート・ハード上下限・猛暑保護はこの理由ではないため、その装置にも届きます。
グレーボックスを選んでいても、疑わしい装置があるサイクルはレガシーで動きます(MPCはこの規則を
知りません)。

**30分**後に自動で解除され、再試行します。解除の直後は、送信が2回連続(5回ではなく)失敗すると
すぐ戻り、1回成功すれば試験は終わります。保存しないため、再起動するとすべての疑いが解けます。

疑わしくなったとき、解けたときに1回ずつログに残ります(変化したときだけ、理由付き)。チャンネル93には
保留中の台数を残し(1台でもある間と、終わったときの0を1回)、ヘルスチェックは保留した分数・装置・
サイクル数を報告します — そこに出たら、人がその装置を確認してください。チャンネル73(*信頼度の低い
アクチュエーター*、デバッグ時のみ)は別の数値です — 学習の重みに従うもので、装置を制御から外す
根拠ではありません。

### 安全時デフォルト位置 { #actuators-safe-default }

各アクチュエーターには、安全ゲートが作動したとき、緊急停止時、または外部からの
`force_safe_state()`呼び出し時に移動する安全な位置があります。この位置はデバイスの
種類に従います — 保温カーテンと遮光スクリーンは100%でパーキングし、それ以外は
0(オフ)です。施設図面から検出されたアクチュエーターでも、アクションで登録した
ものでも同じです。

## Method(設定値カーブ) { #methods-setpoint-curves }

Methodは、設定値が時間とともにどう変わるかを定義します。Methodは**この
Functionではなく、プログラム側の目標項目**に付けられます — カーブが設定された
項目は区画画面で*カーブに従う*と表示され、数値で上書きできません。

- **Daily** — 時刻(HH:MM)ごとの設定値
- **Duration** — 開始からの経過時間ごとの設定値
- **Daily Bezier** — なめらかな日周カーブ
- **Repeating** — 繰り返しパターン

生育週で進行するカーブは、区画の開始日から評価され、施設のローカルタイム
ゾーンの深夜0時に読み取られ、区画画面や区画の日誌が使うのと同じ経過週数から
計算されます。

**作物ステージスケジュールの例(トマト):**

| 日数 | VPD目標 | CO₂目標 |
|-----|-----------|-----------|
| 播種~7日目 | 0.6 kPa | 800 ppm |
| 8~21日目 | 0.8 kPa | 900 ppm |
| 22~42日目 | 1.0 kPa | 1000 ppm |
| 43日目~ | 1.3 kPa | 1000 ppm |

`SEED:`から始まるMethodはシードプリセットで、読み取り専用です。編集する前に
プリセットを複製してください。

## 猛暑保護 { #heat-protect }

作物が長くは耐えられない温度を超えると、目標が変わります — 設定値を追うことより、作物の
高温・水分ストレスを防ぐことが先になります。それを担うのが**猛暑保護**です。既定で有効で、
作物ごとに違うため、しきい値は[目標と応答性](#settings-target)の設定です(既定30°C)。

**いつ始まり、いつ終わるか。** フィルター済みの室内**平均**温度で判定します — いちばん
暑いセンサーで測ると、30°Cでは頻繁に作動しすぎます。

| 段階 | 開始 | 解除 |
|---|---|---|
| 1 — 保護 | 室内がしきい値以上の状態が3分続く、または次の判断時点の予想温度(現在値 + 上昇率 × 周期)がしきい値より1°C以上高いとき | 室内がしきい値より解除幅(既定1.5°C)以上低い状態が10分続き、**かつ**最短継続(既定20分)が過ぎたとき |
| 2 — 深刻 | **最高温度**のハード上限を超えたとき(暖房を切り遮光スクリーンを閉じる、あのラッチ) | ハード上限が解除されたとき — その後は段階1の規則 |

室内の値が途絶えると、保護を新たには始めません。すでに作動中なら最大30分維持し(遮光は
そのまま、暖房は切ったまま、噴霧は止め、窓はその場)、その後解除します。[霜](#frost)とは
同時に作動しません — 霜の段階が作動している間、猛暑保護は解除され、始まりません。

**何をするか** — 上の行が下の行に優先します。

1. 降雨・強風による閉鎖が引き続き優先です。安全ゲートが閉じた窓は閉じたままです。
2. 外気の値が分からなければ、窓とファンはその場にとどまります。
3. 窓とファンは**外が室内より1°C以上涼しいときだけ**開け、外が室内より暑くなるまでその
   許可を保ちます。開けてよい間は、夜間は閉じておく・冷暖房連動・「換気しても効果がない」・
   「開けても反応がない」がその窓を閉じません。外のほうが暑ければ閉じる方向へ動きます
   (*猛暑 — 外の方が暑いため窓を閉めています*)。直前のサイクルで霧タイプの噴霧が動いて
   いれば15%は開けておきます — ファンがあればファン、なければ窓 — 湿気が抜けないと噴霧が
   冷やし続けられないからです。開けてよい窓は風向きの重み付けで絞りません。
4. 温度が先です。[温度上限](#l3-coordinator-actuator-command)の線(しきい値 − 1°C)より上では
   項がハードになり、窓を閉じようとするVPD・湿度の項を外します。線より下では通常の制御と
   同じようにその場にとどまるか退きます。温度・湿度を直接制御しているときも — 温度優先の
   基準、または湿度(したがってVPD)の値を失って温度・湿度に退いた場合 — 温度目標の上に
   この線をかけます。その目標はしきい値より高いことがあるからです(段階の温度がなければ推奨
   上限)。温度の優先度も2.0以上に上げます。
5. 噴霧は、水があり([ミスト用の水供給](#water-supply) — 信号を選んでいなければあるものとみなします)、空気がまだ水を受け取れ(乾球 − 湿球が4°C以上、2.5°Cを下回ると停止)、
   湿度が85%未満のとき(80%を下回ると再び許可)だけ使います。湿度が分からなければ止めます
   (*猛暑 — 今は噴霧で空気を冷やせません*)。冷却器として使うのは霧タイプ(高圧)の噴霧だけ
   です — ハードな温度の項がそれを動かします。湿式(下向き散水)は通常の制御と湿度の遮断に
   そのまま従い、保護はその遮断を厳しくするだけです。水が空中で蒸発せず葉やトレイに落ちる
   ため、冷却のために動かすと大半が流れ落ち、葉が夜まで濡れます。上の三つの条件はすべての
   噴霧器を止めます。日焼け・夕方の噴霧ロックは引き続き優先しますが、[短いパルス噴霧](#pulse-fog)の1回だけは例外です。
6. 日が出ていれば(外の日射150 W/m²から、100を下回ると解除)遮光スクリーンを閉じます。
   段階1では閉じたスクリーンの下の光量が**最小光量しきい値**以上で、その日の光が許すときだけ
   ([遮光スクリーンで暑さを抑える](#shade-heat)の*光を守る*でないとき)、段階2またはしきい値より3°C以上高ければそれに関係なく閉じます。一度閉じたスクリーンは
   日が出ている間そのままで、その間スクリーンは保護が握ります。
7. 暖房を切り、循環扇を回し、冷房機は段階1ではハードな温度の項に従い、段階2では100%で
   動かします。段階2では、開けてよい(外の方が涼しい)窓と吸排気ファンも100%です — モデルの
   推定ではなく能力のすべてを使い、**最低湿度**によるファン停止より優先します。*換気で目標に
   届くときは冷暖房を休ませる*は停止します。

保護中は、グレーボックスを選んでいてもそのサイクルはレガシーで動きます — MPCはこの規則を
知りません。段階が上がることは**1回だけ**緊急扱いです — 窓の駆動周期をそのサイクルだけ
飛ばします。L1~L3を飛ばすサイクル(雨・風のゲート、稼働時間外)でも保護はそのまま
かかります: 窓100%・15%・0%、噴霧オフ、冷房機・循環扇100%、暖房オフ、遮光 — ゲートが
指令した装置には触れません。

毎サイクル、段階(チャンネル75: 0/1/2)と判断(チャンネル76、ビットマスク: 窓を開けてよい ·
外の方が暑い · 噴霧可 · 蒸発の余力不足 · 湿度が高い · 水がない · 遮光 · 最小光量のため遮光を
保留 · 室内の値の途絶)を記録します — デバッグログの設定とは関係ありません。ヘルスチェック
(`check_env_coordinator_health`)が作動時間(分)と段階の切り替えを数えます。1時間に1回を
超えて切り替わるなら、温度がしきい値付近にとどまっているということです。段階2に入ると
猛暑警報メールを送ります(1日最大1回)。しきい値が最高温度以上ならログで1回知らせます。

以前の*高温緊急*ゲート(外気 ≥ 45°C かつ 室内 ≥ 35°C → 窓を全開)に代わるものです。その
条件ではほとんど常に外のほうが暑く、窓を全開にすると温室がさらに熱くなりました。そして作物が
実際に苦しむ30–35°Cの範囲では一度も作動しませんでした。

## 安全ゲート { #safety-gates }

安全機構はL1~L3の協調アルゴリズムの外側で動きます — 毎サイクルL1~L3の前に
確認するPre-Gateと、L3の結果を送信前にサニティチェックするPost-Gateです。
一度作動すると、Pre-Gateは最後に作動してから最低300秒はアクティブなままです
(急速なオン/オフの繰り返しを防ぐため)。ゲートが解除されると、ゲートが動かした装置は
**ゲートが置いた位置から**平衡を探し直します。ゲート前の平衡開度へすぐ戻ることは
しません — その間に条件が変わっている可能性があるためです。ゲートの強制指令は駆動周期を
待たずに直ちに送られ、ゲートが立っている間は毎サイクル送り直されます。ゲートが強制
しなかった装置は通常の駆動周期をそのまま守ります — 1つの装置にゲートが立っていても、
施設の残りが速くなることはありません。

### Pre-Gate(L1~L3の前に確認) { #pre-gate-checked-before-l1l3 }

| ゲート | 発動条件 | 動作 |
|------|--------------------|--------|
| 降雨(実測) | 雨量計・気象観測所が ≥ 0.5 mm/hr(固定、利用者は設定不可)を報告し、風のない小雨では**ない**とき(下記) | 側面/屋根の換気窓を閉じ、L1~L3 を飛ばします。カーテン・スクリーンは屋内側の設備のため、そのままにします。 |
| 降雨(段階制限) | **予報モデル**(Open-Meteo・韓国気象庁短期予報・NASA POWER)の降水、または風のない小雨の実測 | すべては閉じません — 下記[降雨: 実測と予報](#safety-gates)を参照。制御は動き続けます(根拠 52)。 |
| 強風(第2段階) | 10分平均風速 ≥ **強風しきい値**(既定12 m/s)、または測った突風 ≥ その1.5倍(18 m/s) | 風向に関係なく開口部をすべて閉じ、L1~L3 を飛ばします。 |
| 強風(第1段階) | 10分平均 ≥ しきい値の0.6倍(7.2 m/s)、または測った突風 ≥ 0.9倍(10.8 m/s) | すべては閉じません — 下の[強風の二段階](#safety-gates)を参照。制御は動き続けます(根拠 55)。 |
| 低温緊急 | 外気温 ≤ −5°C **かつ** 室内温度 ≤ 5°C(両方とも固定)。解除はどちらかが2°C以上上がったとき | 開口部を閉じ、保温カーテンを閉じ、ヒーターを100%に強制します。 |
| 霜注意 / 霜保護 | 有効室内 ≤ 4°C / ≤ 2°C — [霜](#frost)を参照 | 注意: カーテンを閉じ、開口部はそれ以上開けない。保護: 開口部・カーテンを閉じ、ヒーターと循環ファンを100%、噴霧・CO₂・冷房を止め、L1~L3を飛ばす。根拠 56。 |
| 低温を判定できない | 室内温度が分からない | 緊急ゲートは**作動しません** — すべての装置を一方向へ動かす措置なので、根拠が確かなときだけ作動します。 |
| 室内の値の途絶 | 室内の温度・湿度が届かない(センサーごとの鮮度ルールで判定 — 別の120秒タイマーはありません) | **何も強制しません。** 偏差を測れないため、その軸は制御から外れ、根拠を失った装置はその場にとどまります。測定できる軸(CO₂・光量)は制御を続け、値が戻ればすぐに再開します(300秒の保持なし)。 |
| 屋外の雨・風の途絶 | 届いていた降雨・風速の値が届かなくなった(センサーごとの鮮度ルールで判定 — 別の300秒タイマーはありません)。もともと無いセンサーは対象外です。最後の値は再起動をまたぐ(直近30分以内の記憶)ので、すでに途絶えたセンサーが再起動後に「もともと無いセンサー」と読まれることはありません。 | 最後の値が雨・強風なら、降雨・強風ゲートが新しい値が届くまで開口部を**閉じたまま**にします。そうでなければ開口部はその場に留まるか閉じることはあっても、**それ以上は開きません** — 古い「雨なし」は開ける根拠になりません。例外:**最高温度**のハード上限を超えている間は開けられます。遮光スクリーンとその他の装置は通常制御を続けます。 |
| 噴霧遮断 | 強い光、または日没前の遮断時間帯で、日焼け・夜間保護がオンのとき | 湿式噴霧器だけをロックします。局所的なロックであり、施設全体を止めず、300秒間保持されることもありません。 極端な高温・乾燥のときは短いパルス1回が通ります(理由57、[短いパルス噴霧](#pulse-fog))。 |

**降雨: 実測と予報。** 予報モデルの1時間降水量は「その格子でその時間に雨が降る*かも*
しれない」であり、「いま窓から雨が吹き込んでいる」ではありません。そこでゲートはまず降雨値の
出どころを見ます。ドライバーが自らモデルだと宣言している入力(`data_origin: model` —
Open-Meteo・韓国気象庁短期予報・NASA POWER)は予報で、それ以外と**判定できなかったものは実測**
(より厳しい側)として扱います。

**降雨の入力が複数あっても平均しません。** 新しい値を出した実測入力が一つでもあれば、
メイン・バックアップの優先度にかかわらず実測だけを使い、その**最大値**を使います(0/1 感雨器の
1 と雨量計の 0 は「0.5」ではなく雨です)。予報の降水は新しい実測が一つもないときだけ使い、
そのときは予報として扱います。以前は雨量計 0 と優先度表示のない Open-Meteo 1.2 が 0.6 に
平均されて実測の雨と読まれ、正午に開口部がすべて閉じていました。雨を報告していた雨量計が
途絶えても予報は引き継ぎません — ゲートは雨量計の最後の値で閉じたまま、雨量計が戻るのを
待ちます(最後の値が 0 だった雨量計はすぐに予報へ引き継ぎます)。

**降雨値はすべて1時間あたりの mm(mm/h)です。** チャンネルごとにゲートの前で換算します:
15分積算(韓国気象庁 `rn_15m`、`rain_15m`・`15-min` のような名前)は4倍、10分積算は6倍、
Open-Meteo・韓国気象庁短期予報の1時間降水量はそのまま、NASA POWER の日合計は24で割り、
インチ単位は mm に換算します。0/1 感雨器は 0/1 のままです。区間が分からないチャンネルは
そのまま使い、1時間より長い実測の積算は小さくしません — どちらも閉じる側にしか誤りません。

| 降雨値 | 天窓(形態が分からない開口部を含む) | 側窓 |
|---|---|---|
| 予報 0.1 以上 1.0 mm/h 未満 | **30 %** まで(それより開いていれば 30 % まで閉じる) | 通常制御 |
| 予報 1.0 mm/h 以上(しきい値がより高ければその値) | 閉じる | **30 %** まで。風速 2 m/s 以上で風向が分かれば風上側の側窓は閉じる |
| 実測 0.5 以上 1.0 mm/h 未満、今回測った風速 2 m/s 未満 | 閉じる | **30 %** まで |
| 実測のそれ以外(1.0 以上 — 0/1 感雨器の 1 を含む —、風速 2 m/s 以上、風速センサーなし、値の途絶) | 閉じる | 閉じる — 上の降雨ゲートのまま |

一度かかった制限は30分たつまで一段階下がりません — 1時間予報が 0.9/1.0 mm を行き来したり、
にわか雨が途切れてまた降り出したりしても、天窓が開け閉めを繰り返しません。制限はコーディネーター
の中でかけるので記憶(積分)が上限に巻き上がらず、最後にもう一度切ります。[猛暑保護](#heat-protect)
は側窓を上限までしか使えず、雨で閉じた天窓は開けられません。30 % の上限は猛暑保護の段階 2
でも保たれます。値が途絶えても規則は
続きます — 途絶えた実測降雨はすべて閉じ、途絶えた予報は制限を保ったまま「それ以上開けない」を
加えます。運転時間帯の外では上限の下のどこに置くかを決める PI がないため、ほかの指令がない
上限対象の窓は閉じます。

**強風の二段階。** 以前はしきい値ひとつで、1サイクルで開口部をすべて閉じ、次のサイクルでまた
開けていました。10~12 m/s で吹き続けるフェーンでは1日に何度も全閉と全開を繰り返し、晴れた午後には
1サイクルで室内が10 °C 跳ね上がりました。今は**強風しきい値**が二段階の基準で、ほかの数字はすべて
その倍数です。

| 段階 | 入る値 | 風上側の開口部(風向 ±60°以内) | そのほかの天窓(形の分からない開口部を含む) | そのほかの側窓 |
|---|---|---|---|---|
| 1 | 平均 ≥ 0.6倍(7.2 m/s)または突風 ≥ 0.9倍(10.8 m/s) | 閉じる | **30 %** まで。開口部の方位か風向が分からなければ閉じる | **50 %** まで |
| 2 | 平均 ≥ 1倍(12 m/s)または突風 ≥ 1.5倍(18 m/s) | 閉じる | 閉じる | 閉じる |

段階にはすぐ入ります。抜けるのは、その段階に入ってからの**直近20分の値の平均**(10分平均風速と
測った突風のそれぞれ)がその段階に入る値の**0.85倍**未満になったときで、一度に一段階ずつ下がります
— 収まっていく嵐は 2 → 1 → なし と進みます。通常の10分周期なら値は3つで、最も早い引き下げは段階に
入ってから30分後です。抜ける値の上に一度跳ねた値は平均に混ざるだけで、時計を数え直しません(以前の
「20分続けて」は 10.2 m/s 付近を行き来するフェーンで時計が何度も数え直され、晴れた日に開口部が80分
すべて閉じていました)。その段階に**入る**値を再び超えると20分を最初から数えます。風速の値が途絶えて
いる間は数えず、平均の窓も空にします(古い「穏やか」は開ける根拠になりません)。

**暑いと第2段階が短くなります。** 室内が[猛暑保護](#heat-protect)のしきい値以上か、保護がすでに
作動していれば、第2段階の根拠が消えた最初のサイクル — 10分平均がしきい値未満で、測った突風(突風
センサーがあれば)が1.5倍未満 — にすぐ第1段階へ下げます。風上側の窓と天窓は閉じたまま、ほかは
第1段階の上限までだけ開けます。第2段階の風が戻れば、ただちにすべて閉じます。風速・突風の値が
途絶えているときと、猛暑保護を切った設置では行いません。第1段階 → なしにはこの近道はありません。
突風はセンサーが測るときだけ使います:屋外センサーに測定項目**突風**のチャンネルを結び付けて
ください([センサーの役割](../geo/facility.ja.md#sensor-roles))。複数あれば最も強い値です。なければ
突風を**推定しません** — 第1段階の平均0.6倍は、よくある突風係数1.5を仮定した突風0.9倍と同じ位置に
すでにあり、推定の突風で真昼に開口部をすべて閉じてはいけないからです。第2段階の突風の値(1.5倍)も同じ係数に
従います — 気象台の突風は10分間の最大値なので、1.25倍(15 m/s)にしたところ平均10 m/s のフェーンでは
抜ける値の下に戻れず、シミュレーションで晴れた一日じゅう開口部が閉じたままでした。開口部の方位は、その装置を
結び付けた地図の図形から求めます。方位のない開口部は一度だけ記録され(「側窓の方位角が未設定 —
風向別に閉じられない」)、風向センサーが結び付いていれば健全性チェックが一覧を出します。第1段階の
上限は降雨の上限と同じように働きます — コーディネーターの中でかけて記憶(積分)を上限に留め、最後に
もう一度切るので[猛暑保護](#heat-protect)も上限までしか開けず、運転時間帯の外でほかの指令が
なければ閉じます。雨と風が同じ窓に上限をかけたときは低いほうが勝ちます。第2段階は全面ゲートなので、
高温保護は開け直せません(高温は上のとおり第2段階を短くするだけです)。

**値の途絶は緊急事態ではなく制約です。** 室内の値の途絶と屋外の雨・風の途絶は、
どちらも強制指令を作らず、300秒の保持もかけません。この2つだけが作動しているときは
L1~L3が通常どおり実行されます。根拠がないという理由で設備を動かさないという規則で
あり、動かすかどうかはコーディネーターが軸ごとに判断します。

**高温のゲートはありません。** 高温は、利用者が決めたしきい値で[猛暑保護](#heat-protect)が
担います。降雨・低温のしきい値はコードに固定されています — **強風**だけが
Functionのオプションとして公開されています。複数のゲートが同時に作動する
こともあり(例: 降雨+強風)、その場合は方向にかかわらず開口部は無条件に
閉じます。1つの開口部をめぐってゲートと猛暑保護の判断が食い違うときは、ゲートが
勝ちます — 降雨・強風は、猛暑保護が開けようとしてもその開口部を閉じたままにし、
遮光スクリーン・冷房機・ファンはそのまま猛暑保護の指令を受けます。

**ゲートが作動したサイクルも、サイクルであることに変わりありません。** ゲートが
サイクルを早期に終わらせると、簡略化されたサマリーが書き込まれ、サイクルには
タイムスタンプが付きます — そのため施設ウィジェットは、コーディネーターが
応答不能になったと報告するのではなく、実際に何が起きたかを表示し続けます。この
簡略化されたサマリーにも、そのサイクルで実際に測った環境値はそのまま載ります —
ゲートが作動していてもセンサーは測り続けているからです。省かれるのはL1~L3が
作り出したはずの値(目標や偏差など)だけです。デバイスもゲートが強制したものだけで
なくすべて一覧に残ります — 触れていないデバイスには0%ではなく、指令自体が
記録されません。デバイスごとの最終指令の記録(チャンネル 100+)もゲートのサイクルで残ります —
ゲートの指令、猛暑保護の指令、それ以外のデバイスは直前の指令を根拠 12 として。そのため、
どの時刻に窓が閉じていても、ログで説明できます。ゲートのサイクルでも規則の記憶は進みます —
今日の光の積算、雲の比率、晴天日射、日射負荷換気の「日が出ている」ラッチ。そのため長いゲートが
解けた最初のサイクルが、ゲートが立った時刻のまま固まった値で判断することはありません。装置を
どうするかは引き続きゲートが決めます。

### 霜 { #frost }

上の低温緊急ゲートは、施設が凍りつく日(屋外 −5 °C **かつ** 室内 5 °C)のためのものです。作物はそれよりずっと前に傷みます。
晴れて風のない夜は、葉と被覆が空気より 2〜4 K 低くなり(放射冷却)、空気が 2〜4 °C の時点で葉はすでに 0 °C です。
閉ループ試験*遅霜*(晴れた昼 18 °C、続いて風のない晴れた夜 −4 °C)では緊急ゲートは一度も作動せず、作物は警報も対処も
ないまま約 390 分を氷点下で過ごしました。**霜**は、はるかに早く作動する 2 段階の保護で、主に**室内**温度(最も冷たいセンサー)で判断します。

| 段階 | 開始 | すること |
|---|---|---|
| 霜注意 | 有効室内 ≤ **4 °C** | 保温カーテンを閉め、開口部は**それ以上開けません**(閉じるのは可)。制御(L1~L3)は通常どおり動きます。根拠 56 で表示されます。 |
| 霜保護 | 有効室内 ≤ **2 °C** | 開口部・給排気ファン・保温カーテンを閉め、暖房 100 %、**循環ファン 100 %**(葉の上に溜まる冷気を混ぜる)、噴霧・CO₂・冷房を止めます。低温緊急と同様に L1~L3 を飛ばします。警報メールは 1 日 1 通。遮光スクリーンと補光灯には触れません。 |

*有効室内*は、放射冷却が見込まれるとき室内の値から 2 °C を引いた値です。放射冷却の条件は、屋外 ≤ 2 °C、風速 2 m/s 未満、
実測の雨なし、日が出ていない(測定、光センサーがなければ太陽位置から推定)ことです。制御器は雲量を受け取らないため、曇りの夜も
晴れとして扱います — 霜を見逃すほうが高くつき、誤って出した注意のコストは閉じたカーテン程度です。そのため、晴れて風のない
夜は室内 4 °C で霜保護が作動します。

**作物。** 霜は物理の線(氷は 0 °C 付近で生じる)なので固定ですが、利用者が決めた限界を**超えることはありません。** 保護線は 2 °C と
**最低温度 − 1 °C** の低いほうで、注意線は保護線 + 2 °C です。最低温度が 9 °C(トマトの育苗場)なら 4 / 2 °C のままです — 9 °C 未満は
霜ではなく低温で、最低温度の限界(根拠 33)が担当します。氷点を耐える作物で最低温度を 1 °C にしている場合は 2 / 0 °C になります。
別の設定項目はありません。

**行き来しないように。** 段階はすぐに始まり、室内がその線より 1 °C 高くなり**かつ**その段階が最後に必要だった時から 30 分が経つまで終わりません。
保護は注意を経ずにそのまま解除されることがあります。室内の値が途絶えたときは、作動中の段階を最大 30 分保持して終了し、値がないまま新たに
始まることはありません。段階は再起動をまたぎます(直近 30 分の記憶)。

**他の規則との関係。** 霜と[猛暑保護](#heat-protect)は同時に作動しません — 霜が作動している間、猛暑保護は解除され、始まりません。
霜は、保温カーテンの夜間結露すき間(根拠 46)、朝のランプ(47)、日射負荷・朝の排湿の換気下限(51、54)に優先します。カーテンは閉じたまま、
窓はそれ以上開きません。雨と霜が同じ窓を制限するときは、雨の上限が残ります。低温緊急と重なるときはそちらの値が立ち、霜は循環ファンと
噴霧・CO₂・冷房の停止を加えます。存在しない装置には指令を出しません(暖房機のない施設でも閉じ込めは行い、警報メールが暖められないことを知らせます)。
施設チェックは、霜注意・霜保護にいた時間(分)を報告します。

### Post-Gate(L3の後、送信前に確認) { #post-gate-checked-after-l3-before-dispatch }

| チェック | 動作 |
|-------|--------|
| 非有限な指令値(NaN/Inf) | アクチュエーターは安全時デフォルト位置にフォールバックします。 |
| 範囲外の指令値 | [0, 100]にクランプされます。 |
| 手動ロック中 | ロックされた値で上書きされます。 |
| ミスト用の水なし([ミスト用の水供給](#water-supply)) | すべての噴霧器を0に強制します — 手動ロック中でも同様です。ポンプを空転させてはならないためです。 |
| 疑わしいアクチュエーターの保留(理由42) | まったく送りません — いる位置に置いたままにします([疑わしいアクチュエーター](#actuators-suspected))。安全ゲート・ハード上下限・猛暑保護がその位置に置いた命令は、そのまま送られます。 |
| 冷房機とヒーターが同時にON(どちらも5%超) | 許可されません。ハード上下限への対応まですべて終わった**最後**に確認し、指令の出どころが強いほうを残します — 安全ゲート > 猛暑保護 > 手動ロック > 通常の制御。出どころが同じなら、コスト指数が低いほうを残し、もう一方を0に強制します。L3も温度の要求と逆側(暑いときはヒーター、寒いときは冷房機)をあらかじめ休ませるため、このチェックまで来ることはまれです。 |

### 緊急停止と安全状態 { #emergency-stop }

| 起点 | 説明 |
|-------------|-------------|
| Functionコマンド → 緊急停止 | UI上のボタン。 |
| Conditional / Trigger → `force_safe_state` | 外部の自動化からの即時発動。 |
| RPC `output_off` | 個別のOutputだけを止めるバイパス経路。 |

緊急停止のあと、次のサイクルは60秒遅延します。直後にアクチュエーターが
動かないのはこの遅延であり、故障ではありません。

## トラブルシューティング { #troubleshooting }

| 症状 | 確認すること |
|---------|---------------|
| 画面に目標が表示されない | この施設/ベイで区画が育っているか、その区画にプログラムが付いているか、そのプログラムが確認済みか。これらのいずれかがないと、コーディネーターは自身の推奨範囲だけで動きます — これは正常であり、故障ではありません。 |
| 目標はあるのに1つの軸だけ無視される | その目標項目に測定値が選ばれていない可能性があります。その場合は*参考のみ*として扱われます。カーブに従う項目は、区画画面に入力された数値をすべて無視します。 |
| アクチュエーターが動かない | Actionが登録されていて、Outputが有効か。Actionや施設を変更したあとは**アクチュエーターを再読み込み**を使ってください。 |
| on/offリレーがごく短時間だけオンになる | 指令がおそらく5%未満で、時間比例アダプターがそこでオフになる範囲です。 |
| ポンプが常に1.0 L/minで計算される | 施設のエミッターの流量がゼロでないこと、かんがいレイヤーがそのポンプのOutputを指していることを確認してください。 |
| 強風でも開口部が閉じない | 強風しきい値と、この施設の屋外風センサーの設定を確認してください。 |
| とても暑い午後に窓が閉じている | [猛暑保護](#heat-protect)中は、外が室内より暑いと窓を閉じます — 開けるとさらに熱い空気が入るからです。施設のポップアップは*猛暑 — 外の方が暑いため窓を閉めています*と表示します。冷やすのは遮光・冷房と(空気がまだ水を受け取れるなら)噴霧の役目です。 |
| 夜間、開口部が閉じたままになる | **夜間は閉じておく**がオンのときの想定どおりの動作です — 施設のポップアップに*夜間のため閉じ*と表示されます。ハードな温度/湿度の上下限と安全ゲートは、それでも優先して解除します。 |
| 屋外の測定値が「なし」と表示される | センサーデータの最大有効時間が、そのソース自身の周期より短い可能性があります。各センサーが自身の周期で判定するよう、0のままにしてください。 |
| 冷暖房が両方動いた | 送信直前のインターロックがそれを禁止しています([Post-Gate](#post-gate-checked-after-l3-before-dispatch))。推奨範囲がハード上下限より広い設定の場合、保存画面はブロックせず警告だけを出し、コーディネーターは推奨範囲をハード上下限の内側に狭めて使います。 |
| ある設定が無視されているように見える | 条件付きの可能性があります — カスタム駆動周期は*カスタム*プロファイルのときだけ、夜間の時刻欄は夜間を固定時刻で判定しているときだけ適用されます。画面は、入力されているのに使われていない値を知らせます。 |
| すべての装置がその場で止まっている | 室内の測定値が消えた可能性があります。温度・湿度を測定できないとその軸は制御から外れ、測定できる軸が1つも残らない装置は**何もしません** — 閉じも開けもしません。施設のポップアップに*今は測定できないためそのまま*と表示され、ログにも1回記録されます。センサーの接続とセンサーデータの最大有効時間を確認してください。 |
| 図面に描いた装置が制御に現れない | 制御が扱う種類ではない可能性があります(開口部・遮光スクリーン・保温カーテン・冷暖房・噴霧・CO₂・補光・ファン)。そうした設備は登録から外れ、そのことがログに1回記録されます — 施設エディターで種類を変えれば取り込まれます。 |
| 施設を変更しても反映されない | **アクチュエーターを再読み込み**を実行するか、Functionを無効化してから再度有効化してください。 |
| ウォッチドッグが長時間の停止を報告する | 稼働時間の時間帯の外にいる、またはアクチュエーターが1つも登録されていない、といった意図的な休止は、故障ではなく休止として報告されます。本当の停止であれば、それでも警告されます。 |

## AI連携 { #ai-integration }

AoTのAIチャットと、MCPで接続したAIは、次のツールでこのコーディネーターを扱います。
書き込みツールはすべて人の承認を経ます。

| ツール | すること |
|------|--------|
| `get_control_state` | 読み取り。コーディネーターごとの目標・許容誤差・優先度・安全範囲・稼働時間帯と、直近のサイクルが実際に使った目標・制限要因・安全ゲートの状態・装置ごとの指令とその理由。制御について助言する前に最初に読む値です。コーディネーターごとの直近サイクルには、現在のVPDもラベル付きで載ります — `vpd.air_kpa`は温度・湿度から計算した空気VPD、`vpd.leaf_kpa`(と`leaf_temp_c`)は葉温を実際に測っているときだけ現れます。目標の基準(`air`か`leaf`)は`vpd_basis`で伝えるので、偏差を取り違えたVPDと比べることはありません。 |
| `get_cumulative_status` | 読み取り。DLI・GDDの日別累積と不足分(DLI / GDDトラッカーがオンの場合)。 |
| `get_function_detail` | 読み取り。Functionの設定全体。 |
| `modify_function_options` | 書き込み。このFunctionのオプションを変更し、再読み込みします。 |
| `activate_function` / `deactivate_function` | 書き込み。Functionをオン/オフします。 |

目標はこのFunctionではなく、区画のステージ計画にあります。1つの区画の目標だけを
変えるには、区画画面で編集します。AIはプログラムを編集するツール(`modify_program`)で
ステージの目標を変えることもできますが、そのプログラムを使うすべての区画に適用されます。
