# AI 도구 표면 — 해소·질의·표면의 분리

> 상태: 설계 확정 전 초안 (2026-08-15). 구현 착수 전에 이 문서의 §불변식과
> §이행 단계에 합의가 있어야 한다. 코드보다 계약이 먼저다 — 이 문서가 없으면
> 다음 개선도 즉흥이 되고, 즉흥은 이 도메인에서 늘 몇 주 뒤에 사고로 돌아왔다.

## 배경 — 증상이 넷이었고 뿌리는 하나였다

2026-08-14 하루에 AI 도구 경로에서 버그 넷을 고쳤다. 각각 다른 기능, 다른
파일이었는데 원인이 같았다.

| 증상 | 실제 원인 | 그때의 처방 |
|------|-----------|-------------|
| AI가 집계 함수(VPD·평균)의 값을 못 읽음 | 값 읽기 경로 **4곳**이 각자 "장치 = Input" 이라 가정 | `get_sensor_detail` 에 분기 하나 추가 |
| uuid 를 이름 폴백이 잡아 무관한 구역을 답함 | `loc_id` 한 파라미터가 이름·uuid 겸용, **해석을 도구가 각자** 함 | `_looks_like_uuid` 가드 2곳 |
| 도형 포함 판정이 5갈래(완전포함·대표점·중심점) | 같은 도메인 개념을 **5곳**이 각자 정의 | `containment_point` 게이트웨이 |
| 장치를 지워도 사용자 코드 파일이 남음 | 정리하는 곳이 10경로 중 5곳, 그마저 **3벌 인라인 복제** | `delete_python_file` 게이트웨이 |

넷 다 **"도메인 개념의 주인이 없다"** 의 다른 얼굴이다. 그리고 처방 넷은 전부
"사고 하나에 게이트웨이 하나" 였다 — 흉터이지 구조가 아니다.

### 현재 실태 — 해소가 도구마다 흩어져 있다

`aot/ai/services/aot_data_tool_service.py` 한 파일(**7,863줄**) 안에서:

| 패턴 | 횟수 |
|------|------|
| `GeoShape.query` 직접 조회 | 25 |
| `Input.query.filter` 직접 조회 | 12 |
| uuid 직접 비교 (`unique_id ==`) | 22 |
| 이름 부분일치 판정 | 8 |
| 도메인 모듈 경유 (`device_membership`·`planting_context` 등) | 40 |

마지막 줄이 핵심이다. 도메인 모듈을 **쓰기도 하고 안 쓰기도 한다.** 어느 쪽이
규칙인지 코드가 말해주지 않으므로, 새 도구를 만드는 사람은 옆 도구를 보고
따라 쓴다 — 그 옆 도구가 직접 쿼리하는 쪽이면 결함이 복제된다. 위 표의 네
버그가 전부 이 경로로 생겼다.

### 고정비 — 도구가 두꺼워서 나눌 수가 없다

| | 도구 수 | 대략 토큰 |
|---|---|---|
| 에이전트 루프 매니페스트 | 87 | 약 12,000 |
| MCP 카탈로그 (`tools/list`) | 97 | 약 18,600 |

이 비용은 **모든 질문에** 붙는다. "1구역 온도 몇 도야?" 에도 12,000 토큰을
먼저 읽는다. 흔한 처방은 "매니페스트를 줄이자" 인데, 그것만으로는 안 된다 —
지금 도구가 두꺼운 이유가 **각자 해소 로직을 품고 있어서**이기 때문이다.
해소를 밖으로 빼지 않으면 도구를 쪼갤 수도, 조합할 수도 없다.

그래서 이 문서는 매니페스트 크기를 **목표가 아니라 결과**로 다룬다.

### 실사용 분포 — 87개를 싣고 6개를 쓴다

로컬 `ai_history` 689행(실제 대화)의 `actions_json` 에서 도구 호출을 세면:

| 도구 | 호출 |
|------|------|
| `operate_device` | 84 |
| `get_sensor_detail` | 43 |
| `get_device_measurements` | 11 |
| `create_note` | 9 |
| `get_function_list` | 7 |
| `mcp_influxdb` | 6 |

**사실상 6개가 전부다.** 매 호출에 87개를 실어 12,000 토큰을 쓰는데, 실제로
불리는 것은 그중 한 줌이다. 이것이 원칙 4(예산)의 근거이자 Phase 2 의 출발점이다.

⚠ **이 표본은 신뢰할 수 있는 근거가 아니다.** 로컬·배포 양쪽 다 MCP 를 제대로
쓴 기간이 짧고, AI 도 이제 시작이라 표본이 1,000건도 안 된다. 게다가 그 대화
상당수가 **개발 과정에서 만든 요청**이라 범위가 좁고 한쪽으로 쏠려 있다.
현장에서 실제로 할 법한 요청을 넣어 보긴 했지만 그것도 우리가 상상한 범위다.

그래서 이 표는 **"매니페스트에 안 쓰이는 것이 많다" 는 방향성**까지만 지지한다.
빈도로 도구를 자르는 결정의 근거로 쓰면, 얇고 편향된 표본을 **구조에 굳히게**
된다. 이 위험이 §단계별 설계를 이 문서의 1급 제약으로 만든 이유다.

한 가지 더 — `goal` 문자열에는 `[MODE: FAST] …` 같은 프레임워크 접두사가 섞여
있다. 시나리오를 뽑을 때 그대로 쓰면 사용자의 말이 아니라 우리 프롬프트를
평가하게 된다. 정제가 필요하다.

### 응답 페이로드 — 센서 응답의 87%가 원시 값이다

고정비(매니페스트)만 문제가 아니다. 도구 **결과**도 매 턴 컨텍스트에 남아
누적된다. 실측:

| 응답 | 크기 |
|------|------|
| `get_sensor_detail` 채널 1개 | 약 1,500자 — 그중 **원시 readings 20건이 86~88%** |
| `get_zone_sensor_summary` (구역 7) | 6,026자 ≈ 1,506토큰 |
| `list_plantings(with_sensors)` (구획 22) | 15,879자 ≈ **3,969토큰** |

원시 값 한 건이 이렇게 생겼다:

```json
{"t": "2026-08-10T10:14:44.237637+09:00", "v": 528.0, "u": "none"}
```

- 마이크로초까지 찍힌 타임스탬프가 한 건당 32자다.
- 단위(`u`)는 채널마다 상수인데 20번 반복된다.
- 그리고 이 장치는 묻지도 않은 `rssi`·`snr`·`electrical_potential`·`unitless`
  까지 함께 돌려준다.

**LLM 에게 20개의 부동소수점을 주고 평균을 내게 하는 것이 맞는가** — 아니다.
사람이 "지금 마른가" 를 물으면 필요한 것은 최신값·통계·추세 방향이지 원시
시계열이 아니다. 원시 값은 그래프가 읽을 것이고, 그래프는 이 도구를 쓰지 않는다.

## 설계 원칙

**원칙 1 — 도구는 문자열을 해석하지 않는다.**
사용자가 말한 것("1포장", "콩밭", uuid, "토양수분 센서")을 도메인 참조로
바꾸는 일은 **리졸버 한 곳**이 한다. 도구는 이미 해소된 참조를 받는다.
`loc_id` 처럼 이름과 uuid 를 겸하는 파라미터를 새로 만들지 않는다 — 겸하는
순간 그 도구가 해석 규칙을 갖게 되고, 규칙은 도구 수만큼 갈린다.

**원칙 2 — 도메인 질문은 도메인 모듈만 답한다.**
"이 구역의 장치는 무엇인가", "이 구획의 센서는 무엇인가", "이 도형의 부모는
무엇인가" 에 도구가 직접 답하지 않는다. `device_membership` 이 스스로
*"이 모듈이 소속 판정의 유일한 정본"* 이라고 선언한 것을 표면 전체로 확장한다.

**원칙 3 — 잘못된 상태를 표현 불가능하게.**
`docs/design/geo-data-integrity.md` 원칙 1과 같다. 검사해서 거부하는 방어는
다음 코드 경로가 우회하면 끝이다. uuid/이름 혼동은 가드로 막을 것이 아니라
**타입으로 불가능하게** 만든다.

**원칙 4 — 매니페스트도 응답도 예산이다.**
도구를 늘리는 것은 공짜가 아니다. 새 도구는 예산 안에서만 추가하고, 넘으면
무엇을 뺄지 함께 정한다. (이 문서를 쓰게 된 작업에서 `get_zone_sensor_summary`
를 추가하며 1,784자를 썼다 — 왕복을 줄이려다 고정비를 늘린 것이고, 이 긴장을
명시하지 않으면 "질문 모양마다 도구 하나" 로 흘러 매니페스트가 30k 가 된다.)

응답에도 같은 예산이 걸린다. **기본은 요약이고 원시 값은 요청해야 준다**
(summary-first). 판단에 쓸 수 없는 숫자를 던져 놓고 LLM 에게 연산을 시키는 것은
토큰과 지연을 둘 다 쓰면서 정확도는 서버 계산보다 낮다.

**원칙 5 — 정책은 데이터가 없을 때의 행동을 먼저 정한다.**
사용 빈도처럼 시간이 지나야 쌓이는 신호에 기대는 정책은, **신호가 없거나 얇을
때 무엇을 하는지**를 함께 정의하지 않으면 초기에 잘못된 상태를 굳힌다.
§단계별 설계가 이 원칙의 구현이다.

## 아키텍처 — 3층 분리

```
L3  도구 표면      얇은 어댑터 + 매니페스트 + 승인 게이트
                   (aot/ai/services/tool_registry.py, 도구 함수)
        ↑ 해소된 참조만 받는다
L1  리졸버         사용자 말 → 타입 있는 도메인 참조
                   aot/utils/ 에 둔다 (확정) — AI 전용이 아니라 화면·API 도
                   같은 해소를 써야 하므로 aot/ai/ 밑은 대표성이 없다.
                   씨앗은 resolve_target_tool 의 _resolve_target_shape.
        ↓ 참조로 묻는다
L2  도메인 질의    "무엇이 참인가" — 화면과 AI가 같은 것을 쓴다
                   (device_membership · planting_context · device_binding ·
                    geo_hierarchy · facility_sensors …)
```

L1 과 L2 는 **AI 전용이 아니다.** 웹 화면도 같은 것을 쓴다. AI 전용 복사본을
만드는 순간 두 벌이 되고, 두 벌은 반드시 갈린다 — 이 저장소가 이미 여러 번
겪은 실패다.

### L1 — 리졸버가 답해야 하는 것

지금 `resolve_target_tool` 이 부분적으로 하고 있다(완전일치 → 토큰 →
구체적 타입 우선 → 부분일치 → 작물명 폴백). 그것을 **표면 전체의 입구**로
승격한다.

리졸버의 반환은 문자열이 아니라 **타입 있는 참조**다:

```
Ref = (kind, id)
  kind ∈ { 'site', 'zone', 'facility', 'facility_bay', 'planting',
           'device', 'measurement' }
```

- `device` 의 하위 종류는 `DEVICE_LINK_TABLES` 어휘(**7종**: input · output ·
  pid · trigger · conditional · custom_controller · function)를 그대로 쓴다.
  도구가 "장치란 Input 이다" 를 가정할 수 없게 하는 것이 목적이다.
- **`measurement` 는 1급 참조가 맞다**(확정). 사람은 장치가 아니라 측정을
  가리켜 말한다("토양수분", "3포장 온도"). 다만 참조로 인정하는 것과 그 값을
  통째로 실어 보내는 것은 별개다 — 아래 응답 규약을 함께 지킨다.
- **모호하면 고르지 않는다.** 후보를 돌려주고 사람에게 묻는다. 이미
  `resolve_target` 이 `available_targets` 로 그렇게 한다 — 그 계약을 표준으로
  삼는다. 하나로 찍어 주는 편의가 조용한 오답을 만든다.
- uuid 로 들어온 것은 **해석하지 않고 조회만** 한다. 못 찾으면 "없다" 가 정답이다.

### L2 — 도메인 질의가 지켜야 하는 것

이미 있는 모듈들이 이 층이다. 새로 만들 것보다 **경계를 명확히 하는 일**이 크다.

- 판정 기준은 모듈이 소유한다(`containment_point` 가 그 예다).
- 반환은 도메인 값이다. 표현(문구·단위 표기·요약)은 L3 의 몫이다.
- **저장하지 않고 파생한다** — 소속·센서 참조는 매번 계산한다
  (`planting_context.sensors_for_planting` 의 경고 참조).

### 측정값 응답 규약 — summary-first

측정값이 토큰의 최대 발생원이므로(§응답 페이로드) 규약을 따로 못 박는다.

**기본 응답은 판단에 필요한 것만 낸다.**

```
{ measurement, unit,
  last: {v, t},                      # 최신값
  stats: {min, max, avg, n},         # 기간 통계 — 서버가 계산
  trend: "rising"|"falling"|"flat",  # 구간 비교로 서버가 판정
  stale: bool }                      # 주기 대비 신선도
```

- **원시 시계열은 기본으로 주지 않는다.** 필요하면 명시적으로 요청한다
  (`include_readings=true`, 상한 있음). 그래프는 이 도구를 쓰지 않는다 —
  원시 값의 소비자는 위젯이고, 위젯은 자기 경로로 받는다.
- **추세는 서버가 판정한다.** LLM 에게 20개 값을 주고 "오르는 중인가" 를
  묻는 것보다, 구간 평균을 비교해 한 단어로 주는 편이 싸고 정확하다.
  (`query_flux` 가 `group_sec` 로 버킷 집계를 이미 지원한다.)
- **요청한 측정만 낸다.** 지금은 묻지도 않은 `rssi`·`snr`·`unitless` 까지
  함께 나간다. 링크 진단은 그것을 묻는 도구가 따로 답한다.
- **타임스탬프는 초 단위로 충분하다.** 마이크로초·오프셋까지 32자를 쓸 이유가
  없다. 단위는 채널 헤더에 한 번만 둔다(행마다 반복 금지).

이 규약만으로 채널 하나가 약 1,500자 → 200자 수준이 된다. 다만 **정확한
절감치는 Phase 0 계측으로 확인한다** — 이 문서의 다른 수치와 달리 이것은
아직 추정이다.

### L3 — 도구 표면

- 도구는 리졸버가 준 참조를 받아 L2 를 부르고, 응답을 LLM 이 읽기 좋은
  모양으로 줄이는 일만 한다.
- 새 도메인 지식을 여기에 넣지 않는다. 여기에 `Input.query` 가 나타나면
  L2 에 있어야 할 것이 샌 것이다.

## 단계별 설계 — 개발 · 도입 · 안정화

이 시스템은 아직 **개발 단계**다. MCP 를 제대로 쓴 기간이 짧고 AI 도 막
시작했으며, 쌓인 대화 대부분이 우리가 만든 것이다. 그런데 위에서 제안한
"빈도로 노출 등급을 조정한다" 는 정책은 **데이터가 쌓여야 작동한다.**

여기서 흔한 실패가 나온다 — 얇은 데이터로 정책을 돌려 놓고, 그 결과를 다시
데이터로 삼는 것이다. 안 불린 도구를 숨기면 LLM 이 못 찾고, 못 찾으니 계속
안 불리고, 그래서 영영 숨겨진다. **자기실현적 강등**이다.

그래서 정책을 단계로 나눈다.

| 단계 | 사용 데이터 | 등급 결정 | 강등 |
|------|-------------|-----------|------|
| **개발** | 없음 / 우리가 만든 것 | **도메인 분류만**. 빈도 미사용 | 없음 |
| **도입** | 얇음 · 편향 | 빈도는 **승격에만** 쓴다 | **금지** |
| **안정화** | 충분 · 실사용 | 승격·강등 모두 | 보호 명부 제외 |

**핵심 규칙 — 얇은 데이터는 도울 수만 있고 해칠 수는 없다.**
도입 단계에서 빈도는 도구를 **올리는** 근거로만 쓴다. 내리는 근거로는 쓰지
않는다. "아직 안 불렸다" 와 "안 쓰인다" 를 구별할 수 없기 때문이다. 이 규칙
하나로 자기실현적 강등이 성립하지 않는다.

**단계 전환은 자동이 아니다.** "표본 N건" 같은 숫자만으로 넘기지 않는다 —
개발 중 만든 대화가 N 을 채울 수 있다. 전환 조건은 최소한 다음을 함께 본다:
실사용 기간, 서로 다른 사용자 수, 질문 주제의 분산(우리가 만든 범위를 벗어난
질문이 실제로 들어오는가). 전환은 사람이 판단하고 기록한다.

**보호 명부는 안정화 단계에도 남는다.** 호출 수가 낮아도 내리면 안 되는
도구가 있다 — 계절성(방제·수확), 저빈도 고중요(진단·안전·복구). 이런 도구는
정확히 **필요한 순간에 처음** 불린다. 빈도로 자르면 그 순간에 없다.

## 노출 등급과 서랍 — 두 축으로 가른다

빈도로 **등급**을 정하고, 도메인으로 **서랍**을 정한다. 두 축을 섞지 않는다.

```
등급(tier)   상시 노출  →  서랍 안  →  비활성
서랍(drawer) 관수 · 환경제어 · 일정 · 기록/노트 · 지도/공간 · 진단 · 시스템
```

**왜 서랍을 도메인으로 묶는가.** (⚠ 아래 근거는 여전히 타당하지만, 실측에서
검증되지 **않았다** — 서랍을 실제로 연 관측이 1건뿐이라 "한 번에 맞힌다" 는
반증되지도 확인되지도 않았다. 관측된 실패는 "여러 서랍을 연다" 가 아니라
**"서랍을 안 열고 대체·환각한다"** 였다.)
"자주 쓰지 않는 도구 모음" 같은 빈도 기준
서랍은 LLM 이 **안을 예측할 수 없다** — 열어 보기 전에는 원하는 것이 거기
있는지 모르므로, 결국 여러 서랍을 열게 되고 왕복이 늘어난다. 고정비를 줄이려다
변동비를 늘리는 것이다. 도메인 이름은 예측 가능하다: "관수 밸브를 찾는다"
→ 관수 서랍. 한 번에 맞힌다.

**서랍 목록(이름 + 한 줄 설명)은 상시 노출에 남긴다.** 서랍이 있다는 사실과
그 안에 무엇이 있는지의 힌트까지 숨기면 LLM 은 서랍을 열 생각을 못 한다.
목록 자체는 싸다(서랍 7개 × 한 줄 ≈ 수백 자).

**꺼내는 수단은 이미 있다.** `get_tool_detail` 이 도구 하나의 상세를 준다.
서랍은 그 앞 단계(그룹 목록)일 뿐이므로, 새로 만들 것은 "서랍 열기" 하나다.

**비활성(숨김)과 삭제는 다르다.** 기본은 숨김이어야 한다 — 되돌릴 수 있기
때문이다. 다만 숨긴 채로 두면 죽은 코드가 쌓이므로, 숨김에는 **만료와 재검토
시점**을 붙인다. 만료 때 "이 도구는 N개월간 한 번도 서랍에서 꺼내지지 않았다"
가 확인되면 그때 삭제를 논의한다.

## 로컬 적응 — 전송 없이 각 배포가 스스로 맞춘다

노출 등급을 **그 배포의 자기 사용 기록으로** 조정한다. 서버로 아무것도 보내지
않는다.

**왜 로컬인가.** 셋 다 성립한다.

- **데이터가 이미 거기 있다.** `ai_history` 는 각 농장의 DB 안에 있다. 개선에
  필요한 신호를 얻으려고 밖으로 내보낼 이유가 없다.
- **농장마다 수요가 다르다.** 버섯 농장과 노지 밭은 쓰는 도구가 다르다. 중앙에서
  모은 평균은 오히려 각 농장에 **덜** 맞는다. 로컬 적응은 평균이 아니라 그 농장에
  맞춘다.
- **프라이버시 비용이 0이다.** 질문 원문도, 인자 값도, 장치 이름도 나가지 않는다.
  나갈 곳이 없기 때문이다.

출하 기본값을 우리가 개선하는 일(= 배포들에서 배우는 일)은 **별개 목표**다.
그것만 전송이 필요하고, 그 논의는 이 절의 범위가 아니다.

### 선언 — `Tool(...)` 에 세 필드를 더한다

등급 정책도 SSOT 를 지킨다. 도구 하나의 성격은 선언 한 줄에서 나온다.

```python
domain:      'irrigation'|'environment'|'schedule'|'record'|
             'space'|'diagnostic'|'system'      # 어느 서랍인가
base_tier:   'core'|'drawer'                    # 데이터 없을 때의 자리
never_demote: bool = False                      # 강등 보호 명부
```

`never_demote` 는 **호출 수가 낮아도 내리면 안 되는 도구**다 — 계절성(방제·수확),
저빈도 고중요(진단·안전·복구). 이런 도구는 정확히 필요한 순간에 처음 불린다.

### 유효 등급 — 단계가 규칙을 고른다

```
effective_tier(tool):
    if 적응 꺼짐:            return 'core'          # 오늘과 동일한 동작
    t = tool.base_tier
    if 단계 >= 도입   and calls(tool, 창) >= 승격_임계:  t = 'core'
    if 단계 == 안정화 and calls(tool, 창) == 0
                      and not tool.never_demote:        t = 'drawer'
    return t
```

- **개발 단계에서는 빈도를 아예 보지 않는다.** `base_tier` 가 그대로 유효 등급이다.
- **도입 단계에서 빈도는 올리기만 한다.** 얇은 데이터가 해를 끼칠 수 없다(§단계별 설계).
- **강등은 `drawer` 까지다.** 자동으로 숨기지(비활성) 않는다 — 숨김은 사람의 결정으로만.
  이 규칙 하나로 적응이 **기능을 잃게 만들 수 없다.** 최악이 "한 번 더 열어야 함" 이다.

**단계는 자동으로 오르지 않는다.** 설정값(기본 `development`)이고 사람이 바꾼다.
호출 수만으로 올리면 개발 중 만든 대화가 전환을 일으킨다.

### 신호 — 스키마를 바꾸지 않고 시작한다

`ai_history.actions_json` 을 창(예: 최근 90일) 안에서 세어 캐시한다. 매니페스트는
호출마다 만들어지므로 **매번 세면 안 된다** — 프로세스 캐시 + TTL, 그리고 창 밖
행은 읽지 않는다.

전용 카운터 테이블이 더 싸지만 마이그레이션이 필요하다. 처음에는 만들지 않는다 —
집계 비용이 실측으로 문제가 될 때 옮기고, **그 판단 근거를 그때 남긴다.**
(대화가 수만 건이 되면 옮겨야 할 것이다.)

### 안전장치

| | |
|---|---|
| **킬 스위치** | 적응을 끄면 전부 `core` — 오늘과 똑같이 동작한다. 의심되면 되돌릴 수 있어야 한다 |
| **서랍 목록은 항상 노출** | 서랍의 존재까지 숨기면 LLM 이 열 생각을 못 한다 |
| **강등 하한** | 자동 강등은 `drawer` 까지. 비활성은 사람만 |
| **관측 가능** | 지금 어떤 등급이고 **왜** 그런지 볼 수 있어야 한다. 근거 없는 자동 조정은 디버깅 불가능한 마법이 된다 |

마지막 항목이 중요하다. "이 도구가 왜 서랍에 있지?" 에 답할 수 없으면, 문제가
생겼을 때 적응을 끄는 것 말고 할 수 있는 일이 없다.

### 이 절이 답하지 않는 것

**초기 `base_tier`·`domain` 배정**은 여기서 정하지 않는다(§열린 질문 2).
메커니즘과 데이터를 일부러 분리했다 — 메커니즘이 특정 목록을 품으면, 목록을
고칠 때마다 메커니즘을 건드리게 된다.

## 초기 배정안 — 상시 노출 후보 (검토 대상)

§열린 질문 2 에 대한 **제안**이다. 확정이 아니며, 여기 무엇을 넣고 빼는지는
사람이 정한다. 다만 근거 없이 고르면 또 즉흥이 되므로 기준을 먼저 적는다.

### 기준 — 농장 관리자의 일상 동선

**보기 · 켜고 끄기 · 기록 · 일정.** 여기에 두 가지를 더한다 — 말한 것을
대상으로 바꾸는 **해소**, 모호할 때 되묻고 서랍을 여는 **대화 수단**.

얇은 실사용 표본도 같은 방향을 가리킨다(`operate_device`·`get_sensor_detail`·
`get_device_measurements`·`create_note`·`get_function_list`). **근거가 아니라
방향 확인으로만** 쓴다(§단계별 설계).

### 후보 14개

| 도구 | 왜 상시인가 |
|---|---|
| `resolve_target` | 말 → 대상. 거의 모든 질문의 입구다 |
| `ask_user` | 모호하면 되묻는다. 없으면 AI 가 찍는다 |
| `get_tool_detail` | **서랍을 여는 수단.** 이것이 빠지면 나머지가 영영 안 열린다 |
| `get_local_time` | 시간 관련 질문의 전제 |
| `search_devices` | 장치 찾기 |
| `get_device_measurements` | 이 장치가 무엇을 재는가 |
| `get_zone_sensor_summary` | 구역 값 요약 |
| `get_weather` | 날씨 |
| `get_function_list` | 무엇이 돌고 있나 |
| `create_note` | 기록 |
| `search_notes` | 기록 조회 |
| `search_schedule` | 일정 조회 |

`operate_device`·`set_output_state`·`get_sensor_detail`·`get_output_state` 는
에이전트 매니페스트에 **원래 없다**(네이티브 브리지·MCP 표면에서 처리). 즉
상시 노출 논의의 대상이 아니고 매니페스트 비용도 0이다.

반드시 함께 읽을 것 — §이 숫자를 오해하지 말 것.

### 이 숫자를 오해하지 말 것 — ⚠ 실측으로 반증됨 (2026-08-15)

여기 원래 "절감액이지 순이익이 아니다. 그 빈도를 아직 재지 않았다" 고 적어
두었다. **재 봤고, 순손실이었다.**

A/B 실측(요청 10개 × 등급 끔/켬, gemini-2.5-flash, DB 사본).
전문: `.local/reports/ai-tool-drawer-ab-20260815.md`

| 요청당 평균 | 끔 | 켬 | |
|---|---:|---:|---|
| 선언된 도구 수 | 105 | 24 | **−77%** (예고대로) |
| 왕복당 입력 토큰 | 161,780 | 118,645 | −27% |
| LLM 왕복 | 2.9 | 3.8 | **+31%** |
| **요청당 총 입력 토큰** | 469,161 | 450,852 | **−4%** |

**서랍이 필요한 요청만 보면 +77% 손해다**(318,833 → 562,861).

원인은 단순하다. **왕복 하나가 11.9만 토큰인데 등급으로 아끼는 것은 왕복당
4.3만 토큰뿐이다.** 손익분기는 원래 왕복 2.75회 이상인데 관측 중앙값은 2회다.
서랍을 한 번이라도 열면 그 요청은 진다.

**그리고 설계가 예측한 실패 모드가 틀렸다.** "LLM 이 못 찾아 포기한다" 를
걱정했는데 포기는 **0건**이었다. 대신 셋이 나왔다:

1. **대체** — 보이는 도구로 비슷하게 답한다(`search_archives` 대신
   `search_notes`). 그럴듯해서 **틀린 줄 모르고 지나간다. 가장 위험하다.**
2. **직접 호출** — 숨긴 도구 이름을 기억해 서랍 없이 부른다. 성공한다.
3. **환각** — 기억이 틀리면 없는 이름을 만든다(`controller_deactivate`).

2번이 나오는 이유가 이 설계의 급소다. `virtual_tool_registry()` 는 등급으로
거르지 않으므로 **선언에서 뺀 도구도 그대로 디스패치된다.** 숨김이 비활성이
아니게 하려던 안전장치가, 동시에 **모델이 서랍을 열 유인을 없앴다.** 서랍은
강제가 아니라 힌트로 동작한다.

**살아남은 것**: "틀렸을 때의 대가가 작다" 는 맞았다. 하드 실패가 없었고,
기본이 꺼짐이라 배포 영향이 0이며, 킬 스위치를 쓸 일조차 없었다.
`_TIER_ASSIGNMENT` 를 표로 뺀 것도 옳았다 — 다만 **이번 문제는 배정 가감으로
풀리지 않는다**(필요한 도구를 core 로 올리면 −4% 절감이 0 이하가 된다).

**추가 확인(2026-08-15, 채널 A/B): "서랍은 강제가 아니라 힌트"는 채널을
바꿔도 그대로다.** `AOT_AI_TOOL_CHANNEL=native`(프롬프트 쪽 도구 사본을 빼고
네이티브 함수호출만 남기는 조건)에서도 서랍 열기 2/6·정확 1/6로 위 표와
동일했고, 2번(직접 호출)·3번(환각, 같은 이름 `controller_deactivate`)이
그대로 재현됐다. 전문: [ai-tool-channel-ab-20260815.md](../../.local/reports/ai-tool-channel-ab-20260815.md).

## `never_demote` 후보 — 기준부터 다시 잡는다

처음에 이 명부를 "계절성 · 저빈도 고중요" 로 규정했는데, 설계를 마치고 보니
그 기준이 느슨하다. **강등돼도 서랍에 있으므로 "사라진다" 가 아니다.** 그러면
무엇을 보호하는 것인가.

### 진짜 기준 — 사용자가 말해주는가, AI 가 떠올려야 하는가

서랍은 **단서가 있을 때** 작동한다. 사용자가 "구획 나눠줘" 라고 하면 AI 는 공간
서랍을 연다. 그런데 사용자가 **그 도구의 존재를 모르는 채** 증상만 말하는
경우가 있다:

> "왜 안 켜졌지?" → 원인이 승인 대기열일 수 있는데, 사용자는 `list_pending_confirmations`
> 라는 것이 있는 줄 모른다. **AI 가 스스로 떠올려야 한다.**

이때 그 도구가 서랍에 있으면 AI 는 열 생각을 못 하고, 결국 "원인을 모르겠다"
고 답한다. **보호해야 하는 것은 이 경우다.**

| | 서랍에 있어도 되는가 |
|---|---|
| 사용자가 이름·의도를 말해준다 ("구획 만들어줘", "센서 추가") | **된다** — 단서가 서랍을 고른다 |
| 사용자는 증상만 말하고 AI 가 도구를 떠올려야 한다 ("왜 안 돼?") | **안 된다** — 보호 대상 |

이 기준이 원래 것보다 좁고 날카롭다. 계절성만으로는 보호 사유가 안 된다 —
정식·수확은 사용자가 **명시적으로 요청**하기 때문이다.

### 후보 5개 (강한 순)

| 도구 | 근거 |
|---|---|
| `list_pending_confirmations` | **"왜 안 켜졌지?" 의 흔한 원인.** 실제로 예약 10건이 전부 승인 대기에 걸려 장치가 한 번도 안 켜진 사건이 있었다(2026-08-13). 그때 아무도 큐를 안 봤다 |
| `analyze_system_failure` | "왜 안 돼?" 에 AI 가 떠올려야 하는 전용 진단 도구 |
| `respond_to_confirmation` | 위 큐를 발견해도 답할 수단이 없으면 반쪽이다. 쌍으로 움직인다 |
| `read_manual` | 모르는 것을 만났을 때 AI 가 스스로 찾아봐야 한다. 사용자는 "매뉴얼 봐" 라고 말하지 않는다 |
| `knowledge_search` | 위와 같다 — 축적된 지식은 떠올려야 쓰인다 |

### 보호하지 않기로 한 것 (근거를 남긴다)

- **작기 도구**(`create_planting`·`end_planting`·`get_planting_history`·분할) —
  계절성이지만 사용자가 명시적으로 요청한다. 서랍으로 충분하다.
- **장치 CRUD**(`create_input`·`modify_output`·`rebind_device` …) — 센서 교체는
  드물지만 "센서 바꿨어" 라는 말과 함께 온다.
- **`get_system_update_status`·`get_storage_tier_status`** — 드물고, 못 떠올려도
  대가가 작다(사용자가 다시 물으면 된다).

### ⚠ 배정 모순 — `read_manual` (2026-08-15 실측에서 드러남)

`read_manual` 은 `never_demote` 인데 서랍(`system`)에 있다. 실측에서 모델이
막히면 **가장 먼저 집는 도구가 `read_manual`** 이었고(5회 호출), 이는 "AI 가
스스로 떠올려야 하는 도구" 라는 이 명부의 기준에 정확히 부합한다. 서랍에 두면
그 목적이 반쯤 무력화된다.

`base_tier='core'` 로 올리는 것이 기준에 맞다. **다만 지금 고치지 않는다** —
서랍 방식 자체가 재검토 대상이라(§이 숫자를 오해하지 말 것) 그 결론이 난 뒤에
함께 정한다.

### 이 명부는 매니페스트 비용이 아니다

다섯 개 전부 매니페스트에 있지만, `never_demote` 는 **자동 강등만 막을 뿐
상시 노출을 뜻하지 않는다.** `base_tier='drawer'` 인 채 보호할 수 있다 — 그러면
평소에는 비용이 0이고, 안정화 단계에서 "안 불린다" 는 이유로 더 내려가지만
않는다.

**다만 `list_pending_confirmations`·`analyze_system_failure` 는 `base_tier='core'`
로 두는 것을 함께 제안한다.** 위 사고가 정확히 "그 순간에 아무도 안 봤다" 였고,
서랍에 있으면 AI 도 안 본다.

### 남은 배정

나머지 약 83개의 `domain` 배정은 기계적이라 구현 커밋에서 함께 한다.
판단이 필요한 것은 core 목록(14 + 위 2)과 이 명부뿐이다.

## ⚠ 더 큰 덩어리 — 도구 정의가 한 요청에 두 번 실린다 (2026-08-15 발견)

A/B 실측 중에 나왔고, **등급보다 크고 부작용이 없다.**

`base_ai.py:313` 이 context 전체를 프롬프트 텍스트로 JSON 덤프하는데 그 안에
`capabilities.system_tools`·`capabilities.mcp_tools` 가 들어 있다. 그리고
`_build_tools_schema()` 가 **같은 것을** `tools[]`(function_declarations)로 또
보낸다. 왕복 하나에 실리는 문자수(실측):

| 구성 | 끔 | 켬 |
|---|---:|---:|
| `tools[]` 선언 | 61,202 | 15,651 |
| 프롬프트 안 `capabilities.*` | 137,855 | 34,399 |
| **도구 정의 소계** | **199,057 (37.6%)** | 50,050 (14.3%) |
| `system_state`(마스터 컨텍스트) | 120,306 | 120,297 |
| 나머지 프롬프트 | 210,416 | 180,596 |

한쪽만 남기면 **왕복당 최대 13.7만자(≈3.8만 토큰, −26%)** 가 사라진다.
등급을 켜서 얻는 것과 맞먹는데 **왕복을 늘리지 않는다.**

**⚠ 여기 원래 "프롬프트 쪽을 지우면 네이티브 함수호출로 강제되고, 그러면
서랍이 비로소 실제로 강제된다" 고 적었다. 실측으로 반증됐다**(2026-08-15,
`.local/reports/ai-tool-channel-ab-20260815.md`).

채널 4가지를 같은 요청 10개로 돌린 결과:

| 요청당 | both(기준선) | native | native+등급ON | prompt |
|---|---:|---:|---:|---:|
| 총 입력 토큰 | 259,171 | 103,289 | 212,739 | 171,166 |
| LLM 왕복 | 1.9 | 1.2 | 2.8 | 1.4 |
| **도구를 아예 안 부름** | **0/10** | **7/10** | 2/10 | **6/10** |

**서랍은 여전히 강제되지 않았다.** `native`+등급ON 의 서랍 지표가
`both`+등급ON(전작)과 거의 정확히 같다 — 필요 6건 중 연 것 2건, 정확한 서랍
1건, 안 열고 넘어감 4건. 실패 모드(대체·직접호출·환각)도 5건 중 3건이 **완전히
동일하게** 재현됐고, 존재하지 않는 이름 `controller_deactivate` 환각은 두 실험·
두 채널에서 똑같이 나왔다(모델 쪽 패턴이지 채널 문제가 아니다).

### 왜 강제되지 않았나 — `native` 구현이 반쪽이었다

이건 가설이 틀린 것과 **구현이 미완인 것이 겹쳐 있다.**

`native` 모드는 프롬프트에서 `capabilities`(도구 목록)를 빼는데, **프롬프트는
여전히 텍스트 JSON 으로 action 을 내라고 요구한다**(`_build_prompt` 는 "explicitly
requests JSON output", RULE 1 은 "Current Context 로 답하라"). 그래서 모델이
텍스트 JSON 경로를 고르면(`native`+등급ON 에서도 6/10) **도구 목록이 아예 없는
채로** 답을 만든다. 무행동 7/10 은 그 결과다 — 절감의 정체가 효율이 아니라
**일을 안 한 것**이다.

즉 `native` 를 제대로 시험하려면 **출력 계약도 함께 바꿔야 한다**: 텍스트 JSON
action 을 더 이상 요구하지 않고 네이티브 함수호출만 받는다. 그것 없이 도구
목록만 뺀 것은 공정한 시험이 아니었다.

**다만 서랍 결론은 그와 무관하게 선다.** 모델이 실제로 행동한 경우(텍스트 JSON
6/10)에도 서랍을 열지 않았고 같은 실패 모드를 반복했다. 서랍이 강제되지 않는
원인은 `virtual_tool_registry()` 가 등급으로 거르지 않는 것이고, **그것은 채널과
독립이다.**

### 설명되지 않은 것

`prompt` 모드(= `tools[]` 만 제거, 프롬프트 사본은 그대로)에서도 무행동이
6/10 이다. 이 조건에서는 텍스트 JSON 경로가 도구 목록을 **그대로 갖고 있으므로**
위 설명이 통하지 않는다. API 에 `tools` 키가 없는 것 자체가 모델을 도구 사용에서
멀어지게 하는지, 표본 10개의 잡음인지 갈리지 않는다. **후속 확인이 필요하다.**

### 그래서 순서

1. 서랍을 정말 강제하려면 **텍스트 JSON action 경로에서 디스패치 전에 선언된
   집합과 대조**해야 한다. 채널을 바꿔도 이건 안 생긴다. 있으면
   `controller_deactivate` 같은 환각이 12회 왕복까지 가지 않고 "그런 도구 없음"
   으로 즉시 끝난다.
2. `native` 로 가려면 도구 목록만 빼는 것이 아니라 **출력 계약을 함께 바꾼다.**
3. 그 전까지 기본값은 `both` 다.

## ⚠ 그 위의 덩어리 — 왕복 단가

등급을 켠 뒤에도 왕복당 35만자 중 도구 정의는 14%뿐이다. 나머지(마스터
컨텍스트 12만자 + 시스템 프롬프트·지시문 18만자)를 줄이지 않으면 **어떤 도구
노출 전략도 소수점 싸움**이다.

실측에서 이 크기 때문에 요청 한두 개로 분당 입력 토큰 100만 쿼터에 걸렸다
(20턴 중 429 응답 4회).

**§열린 질문 1(예산 목표치)에 답이 생겼다: 지배 변수는 도구 예산이 아니라
왕복 단가다.**

## 선례 학습 — 숨기는 대신 고르는 것을 돕는다 (방향 전환)

서랍은 **보류한다.** 두 실험이 같은 결론을 냈고(순손실 · 강제되지 않음), 무엇보다
실패 방식이 위험하다 — 한 번 안 열린 서랍은 계속 안 열리고, 그러면 그 도구는
사실상 사장된다. LLM 은 단계를 건너뛰려는 성향이 강하고, 그것이 이 설계의
전제를 정면으로 친다.

**방향을 바꾼다.** 두 실험이 공통으로 보여준 것은 이것이다:

```
포기("그런 기능 없다")        0건
대체(비슷한 도구로 답)         있음 — 그럴듯해서 틀린 줄 모른다
환각(없는 이름을 지어냄)       두 실험·두 채널에서 동일 재현
```

**모델은 도구를 못 찾는 게 아니라 잘못 고른다.** 그러면 처방은 "덜 보여주기"
(서랍)가 아니라 **"고르는 것을 돕기"** 다. 과거에 성공한 요청→도구 경로를
기록해 두고, 비슷한 요청에서 힌트로 보여준다.

서랍과 결정적으로 다른 점:

| | 서랍 | 선례 힌트 |
|---|---|---|
| 성격 | 빼기 — 안 보이게 한다 | **더하기** — 정보를 얹는다 |
| 최악의 경우 | 도구가 사장된다 | **힌트 없음 = 오늘과 동일** |
| 실패의 누적 | 자기실현적(안 열림→계속 안 열림) | 없음 |
| 비용 축 | 고정비(작다) | **왕복(지배 변수)** |

마지막 줄이 중요하다. 두 실험이 확정한 것은 **왕복 단가가 지배 변수**라는
것이다(왕복 하나 11.9만 토큰). 힌트 수백 자로 첫 시도에 맞히게 하면 왕복
하나가 통째로 사라진다 — `function` 요청 하나가 12왕복 91만 토큰을 태웠는데,
"이런 요청엔 `get_function_list` → `deactivate_function`" 한 줄이면 끝날 일이었다.

### ⚠ 그런데 지금 데이터로는 시작할 수 없다 (실측)

착수 전에 "학습할 사례가 몇 건인가" 를 쟀다. 전문:
`.local/reports/precedent-learning-feasibility-20260815.md`

1. **왕복이 기록되지 않는다.** 요청당 AI 턴이 311건 중 대부분 **1행**이다 —
   에이전트 루프의 내부 왕복이 `ai_history` 에 안 남는다. A/B 에서 본 12~16
   왕복 폭주가 여기서는 "1턴짜리 성공" 으로 보인다. 그래서 "헤맸는가" 를
   판정할 근거가 **아예 없다.**
2. **모양만으로는 오답을 못 거른다.** 필터를 통과한 61건 중 "오늘 1포장에 어떤
   작업이 진행 되었지?" → `get_function_list` 처럼 **구조적으로 깨끗한 오답**이
   섞여 있다. 그것이 바로 대체 실패모드인데, 그걸 정답으로 배우면 이 방향의
   존재 이유가 사라진다.
3. **88%가 도구 하나짜리다.** "요령" 이라 부를 다단계 경로가 거의 없다. 단일
   도구 선택도 대체·환각을 고치므로 값어치가 있지만, 기대를 **"이런 요청엔 이
   도구"** 수준으로 맞춰야 한다.
4. 요청문에 `[Page Context: …]`·`[MODE: FAST]` 접두사가 섞여 있다. 걷지 않으면
   사용자의 말이 아니라 **우리 프롬프트를 학습한다.**

### 선행 조건과 단계

**기록부터 바꿔야 한다.** 왕복과 도구 호출 순서를 상시 기록해야 한다. 계측
코드는 이미 있다 — `aot/tests/ai_eval/tool_call_probe.py` 가 A/B 를 위해 만든
것이고, 그것을 실험용에서 상시 기록으로 승격하는 것이 1단계다.
`experience_memory.py` 의 `usage` 타입이 *"scaffolded here, populated later"*
로 비어 있는데 그 자리가 여기다.

성공 판정은 **두 축**이어야 한다. 모양(왕복·반복·failed)만으로는 위 2번을 못
거르고, 결과(되묻지 않음·불만 마커 없음)는 사용자가 반응해야 신호가 생긴다 —
**침묵은 만족인지 포기인지 구분되지 않는다.** 이 한계는 없앨 수 없고, 그래서
선례는 **강제가 아니라 힌트**여야 한다.

```
1. 기록 승격(왕복·순서·접두사 제거)
2. 관찰 — 실사용에서 다단계 경로가 쌓이는가
3. 판정(모양 + 결과 두 축)
4. 주입(상위 1~3건, 예산은 원칙 4)
5. A/B
```

**2단계에서 멈출 가능성이 크고 그것이 정상이다.** 지금 데이터는 대부분 개발 중
우리가 만든 것이라(§단계별 설계), 실사용이 쌓이기 전에는 학습할 것이 없다.

## 불변식과 강제 수단

검사만으로는 부족하다는 것이 이 저장소의 반복된 교훈이므로, 각 불변식마다
**무엇으로 강제하는지**를 함께 정한다.

| # | 불변식 | 강제 수단 |
|---|--------|-----------|
| T1 | L3 도구 함수는 `*.query` 를 직접 부르지 않는다 | AST 가드(신규) — 예외는 명부에 근거와 함께 |
| T2 | 이름과 uuid 를 겸하는 파라미터를 새로 만들지 않는다 | AST 가드 + 리뷰. 기존 겸용 파라미터는 명부에 등재하고 단계적으로 이전 |
| T3 | 장치 종류 어휘는 `DEVICE_LINK_TABLES` 하나 | 이미 있는 상수를 L1 이 import — 재정의 금지 |
| T4 | 포함/소속 판정은 `containment_point`·`device_membership` 경유 | 기존 가드 확장 |
| T5 | 매니페스트 총량 예산 | 테스트가 토큰 근사치 상한을 고정. 넘으면 실패 |
| T6 | 모호한 해소는 후보를 돌려준다 (임의 선택 금지) | 리졸버 단위 테스트 |
| T7 | 자동 강등은 `drawer` 까지 — 비활성(숨김)은 사람만 | 적응 로직 단위 테스트 |
| T8 | 적응이 꺼지면 전부 `core`(오늘과 동일) | 킬 스위치 테스트 |
| T9 | 사용 신호는 배포 밖으로 나가지 않는다 | 적응 모듈이 네트워크를 쓰지 않음(AST 가드) |

T9 는 로컬 적응이 조용히 텔레메트리로 자라는 것을 막는다. 전송이 필요하다는
결론이 나면 그때 **별도 설계와 별도 동의**로 한다 — 적응 코드에 슬쩍 얹지 않는다.

T5 의 상한은 **현재값보다 낮게** 잡는다. 지금(87개/12k)을 기준선으로 두면
줄일 이유가 사라진다. 목표치는 §이행 단계 Phase 2 에서 측정 후 확정한다.

#### T5 재기준선 (2026-08-20) — 그리고 등급 상한을 따로 둔 이유

08-15 상한(에이전트 12,000 · MCP 18,700)이 다섯 커밋 동안 넘긴 채로 있었다.
어디서 늘었는지 재 보니 전부 **도구를 더한 기능 작업**이었다(구획 분할 인자 확장,
관리 프로그램 레이어 +4, 구획 단계·자원 도구 +3 → 87개 → 94개). 문구가 부푼 것이
아니어서, 87개용 예산을 94개에 그대로 씌우면 과거의 실패에서 나온 규칙을 지워야
맞출 수 있었다. 그래서 상한을 13,020 · 19,800 으로 올리고 **증가분의 출처를
테스트 상수 옆에 표로 남겼다**(`test_tool_cost_budget.py`).

그 과정에서 드러난 함정 하나: 실패 메시지는 "무엇을 서랍으로 내릴지 정하라" 고
말하는데 **그 조치로는 이 숫자가 내려가지 않는다.** 여기서 재는 것은 등급을 끈
(기본값) 매니페스트라 도구가 전부 실리기 때문이다. 그래서 상한을 하나 더 뒀다 —
`TIERED_MANIFEST_TOKEN_CEILING`(등급 ON: 15개 · 약 2,787토큰, 끈 상태의 21%).
도구 수가 늘면 반드시 오르는 앞의 두 숫자와 달리, 이쪽은 **core 를 늘릴 때만**
오르므로 "무엇을 상시 노출할까" 를 실제로 판단하게 만든다.

## 이행 단계

`geo_binding` Phase A~C 의 방식을 그대로 쓴다 — **옛 경로를 남긴 채** 새 경로를
붙이고, 측정으로 전환하고, 폴백이 0 인 것을 확인한 뒤에 지운다. 한 번에
갈아엎지 않는다. 큰 리팩터가 새 장애를 만드는 것이 이 방향의 가장 흔한 실패다.

각 단계에는 **중단 조건**(무엇을 측정해서 다음으로 넘어가는가)이 있다.

### Phase 0 — 계측 (비파괴)

지금 하네스(`aot/tests/ai_eval/`)는 골든셋 24개와 `latency_ms`/`approx_tokens`
를 갖고 있지만, `approx_tokens` 는 **최종 답변 글자수 ÷ 4** 다. 도구 호출
횟수도, 도구 결과 크기도, 매니페스트도 세지 않는다. 검증 기준 24개는 전부
`min_insight_len`("글자가 나왔는가")이다. **즉 지금 하네스로는 이 문서가
다루는 문제를 감지할 수 없다.**

- 하네스에 추가: 도구 호출 횟수 · 도구별 결과 바이트 · 매니페스트 토큰 ·
  왕복당 누적 컨텍스트.
- 시나리오는 상상이 아니라 **실제 기록에서** 뽑는다. 로컬에 `ai_history`
  689행, `audit_log` 1,564행이 있다. 읽기 전용·복사본에서만(라이브 DB 금지).
- **중단 조건**: 골든셋이 실제 사용 분포를 반영하고, 시나리오마다 위 네 지표가
  기록된다. 이 데이터 없이 Phase 2 의 목표치를 정하지 않는다.

### Phase 1 — 리졸버 승격 (폴백 유지)

- `_resolve_target_shape` 를 독립 모듈로 올리고 반환을 타입 있는 참조로 바꾼다.
- 도구를 **하나씩** 이전한다. 이전한 도구는 문자열 해석 코드를 잃는다.
- 옛 경로(도구 내부 해소)는 남기되 **폴백 로그**를 남긴다 — `geo_binding` 이
  레거시 컬럼에 한 것과 같다.
- **중단 조건**: 주요 조회 도구가 리졸버를 지나가고, 폴백 로그가 정상 운용
  기간 동안 0 에 수렴한다.

### Phase 2 — 표면 재구성

- L2 로 내려갈 것을 내리고 나면 도구가 작아진다. 그 시점에 **비로소** 티어링
  (핵심 상시 노출 + 나머지는 `get_tool_detail` 로 꺼내기)이 가능해진다.
  `get_tool_detail` 은 이미 있다 — 2단 공개가 원래 의도였는데 매니페스트가
  87개를 통째로 싣고 있다.
- **중단 조건**: Phase 0 지표로 잰 단순 질의의 고정비가 목표치 이하이고,
  복합 질의의 왕복 수가 회귀하지 않는다.

### Phase 3 — 겸용 파라미터 제거

- T2 명부가 비면 `_looks_like_uuid` 같은 가드도 함께 사라진다. 가드가 필요
  없어지는 것이 이 작업이 성공했다는 신호다.
- **중단 조건**: 명부가 비고, 관련 가드 테스트가 "표현 불가능" 을 근거로
  삭제된다.

## 기각한 대안

**A. 매니페스트만 줄인다.**
가장 싸고 즉효지만, 도구가 두꺼운 근본 원인을 두므로 다음 도구가 다시 늘린다.
Phase 2 에 포함하되 **단독으로는 하지 않는다.** (급할 때는 이것만 먼저 해도
되지만, 그때는 "응급 처방" 임을 문서에 남길 것.)

**B. 질문 모양마다 서버측 합성 도구를 만든다.**
효과는 확실하다(이번에 `get_zone_sensor_summary` 로 20회 → 3회를 봤다). 그러나
원칙 4와 정면으로 충돌한다 — 무한히 늘릴 수 없다. 합성은 **자주 반복되는
모양에만**, 예산 안에서.

**B'. AI 조회를 위해 집계 Function 을 만들어 둔다.**
기각. 대상도 기간도 질문마다 달라 고정 계산기로는 답할 수 없다. Function 은
제어 입력이 되거나 이력을 남겨야 할 때만 만든다(2026-08-14 검토 결론).

**C. 도구를 자동 생성한다(스키마에서 파생).**
도구 설명의 가치는 대부분 "언제 쓰지 말아야 하는가" 같은 판단인데, 그것은
스키마에 없다. 자동 생성은 그 판단을 잃는다.

## 결정된 것 (2026-08-15)

1. **리졸버 위치 — `aot/utils/`.** AI 전용이 아니라 화면·API 가 같은 해소를
   써야 하므로 `aot/ai/` 밑은 대표성이 없다.
2. **`measurement` 는 1급 참조.** 단 값은 summary-first 규약으로 줄인다 —
   판단에 못 쓰는 숫자를 던지고 LLM 에게 연산시키지 않는다.
3. **노출은 빈도로 등급, 도메인으로 서랍.** 두 축을 섞지 않는다.
4. **숨김이 기본, 삭제는 만료 뒤 논의.**
5. **정책은 단계(개발·도입·안정화)를 갖는다.** 얇은 데이터는 승격에만 쓴다.

1. **매니페스트·응답 예산의 목표치.** Phase 0 측정 전에는 숫자를 못 정한다.
2. ~~초기 `base_tier` 배정~~ → **§초기 배정안(14개) · §never_demote 후보(5개)에
   제안 있음.** 남은 판단은 두 목록의 가감뿐이다.
9. **`get_sensor_detail` 이 에이전트 매니페스트에 없는 것이 의도인가.**
   실사용 2위(43회)인데 매니페스트에는 없고 MCP 카탈로그·네이티브 경로에만
   있다. 의도라면 근거를 적어 두어야 하고, 아니라면 상시 노출 후보다.
3. **서랍 경계.** 위의 7개(관수·환경제어·일정·기록/노트·지도/공간·진단·시스템)
   가 맞는지. 서랍이 너무 잘면 어느 것을 열지 헷갈리고, 너무 굵으면 열어도
   여전히 크다.
4. **단계 전환의 판단 주체와 기록.** 사람이 판단한다고 정했으나, 어디에
   기록하고 무엇을 근거로 남길지.
5. **원시 시계열이 정말 필요한 AI 경로가 있는가.** 없다면
   `include_readings` 자체를 두지 않는 편이 낫다 — 있으면 결국 쓰인다.
6. **적응의 창과 임계.** 최근 며칠을 보고 몇 회부터 승격하는가. Phase 0 의
   동적 계측이 없으면 근거 없이 고르게 된다.
7. **집계 비용의 전환점.** `ai_history` 세기가 언제부터 느려지는가 —
   전용 카운터 테이블로 옮길 시점의 판단 근거.
8. **배포들에서 배우는 일(출하 기본값 개선)을 할 것인가.** 로컬 적응과 별개
   목표다. 하기로 하면 별도 설계·별도 동의·별도 opt-in 이 필요하다.
   기존 `stats_opt_out` 은 **기본값이 "전송함"** 이므로(Mycodo 유산) 거기
   얹으면 동의를 구한 것이 아니게 된다.
