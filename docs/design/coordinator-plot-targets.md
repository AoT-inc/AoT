# 코디네이터가 구획에서 목표를 가져온다

`env_coordinator` 와 관리 프로그램(`GeoProgram`)의 접점. 정본 둘을 잇는 문서이고
양쪽 정본은 각각 `program-layer.md`(프로그램) · `env_coordinator_user_guide.md`
(코디네이터)다.

---

## 왜 — 작물 목표가 지금 세 곳에 있다

| 어디 | 무엇 | 누가 고치나 |
|------|------|-------------|
| `CROP_PRESETS` (`env_control/photosynthesis.py`) | 작물 5종의 권장 목표·모델 상수 | **코드** — 사용자가 못 고친다 |
| `GeoProgram.targets` · `.photosynthesis` | 단계별 목표 + `T_base`·`dli_target`·`gdd_daily` | 사람 (프로그램 화면) |
| 코디네이터 옵션 (`target_vpd`·`target_co2`·`dli_target`…) | 실제로 제어가 읽는 값 | 사람 (함수 설정) |

세 번째가 **실제로 도는 값**이고, 앞의 둘은 그것을 채우는 재료다. 그런데 재료가
둘이라 "지금 이 온실은 무엇을 목표로 도는가" 의 답이 화면마다 다르다.

**정본은 프로그램으로 옮긴다.** 코디네이터는 "어떻게 달성하는가" 만 갖는다.

| | 정본 | 담는 것 |
|---|---|---|
| 구획 · 프로그램 | 무엇을 기르는가 | 대상 · 단계 · 단계별 목표 · 기간 |
| env coordinator | 어떻게 달성하는가 | 장비 구성 · 안전 한계 · 우선순위 · 튜닝 · 응급 |

**이 분담은 지켜야 한다.** 온실의 안전 한계를 프로그램에 넣으면 그 프로그램을 다른
시설에 재사용할 수 없다 — 같은 상추라도 이 동은 천창이 있고 저 동은 없다.

## 새 구조가 아니다 — 이미 있는 것의 소스를 바꾸는 일이다

`crop_preset` 이 지금 하는 일이 정확히 그 모양이다(`env_coordinator._sync_crop_targets`):

- 프리셋에서 목표를 **자기 옵션 필드로 끌어온다**
- Method 곡선을 쓰는 항목은 건너뛴다 (사용자 설정 우선)
- 사람이 손댄 값은 보존하고 자동으로 채워졌던 값만 갱신한다
- `crop_preset_applied` 마커로 같은 것이면 아무 일도 하지 않는다
- `cmd_apply_crop_targets` 버튼으로 명시적 재적용도 된다

이 규율을 그대로 쓰고 **소스만** `CROP_PRESETS` → 이 시설의 구획으로 바꾼다.
데몬에서 geo 테이블을 읽는 길도 이미 있다(`_profile_loader_mixin` 이 app context 를
열어 `get_facility_integration` 을 부른다).

## 규칙 1 — 기준 구획을 고르는 법 (확정)

**구현은 한 곳뿐이다: `plot_context.plot_for_coordinator(function_row)`.**
코디네이터(데몬)와 화면(Flask)이 같은 함수를 부른다. 이 저장소가 반복해서 겪은
실패가 "읽는 경로마다 기준이 다름" 이므로, 화면에 규칙을 다시 쓰지 않는다.

- **R0 스코프** — 코디네이터의 `geo_facility_id` + `bay_scope`.
- **R1 후보** — `plots_in_facility(facility_uuid, bay_id)`. 활성 판정은 그 함수가
  이미 `is_active` 와 같은 부등호(`ended_on IS NULL OR ended_on > 오늘`)를 쓴다.
- **R2 후보 0개** — 아무것도 하지 않는다. 코디네이터는 자기 값으로 돈다.
  **폴백을 없애지 말 것** — 온실을 비워도 난방은 돌아야 한다.
- **R3 후보 1개** — 그것이 기준 구획이다. **저장하지 않는다.** 파생값을 컬럼에
  써 넣으면 구획이 끝나도 옛 값이 남고, 그것이 사람이 고른 것인지 계산된 것인지
  구분할 수 없게 된다(`expected_end` 와 같은 규율).
- **R4 후보 2개 이상** — **자동으로 고르지 않는다.** 겹침(간작·혼작)이 정상인
  도메인이라 자동 선택은 조용히 틀린다. 사람이 지정한다
  (`source_plot_id` 옵션). 지정 전까지 [가져오기]는 비활성이고 화면이
  "구획 2개 — 기준을 정하세요" 라고 말한다.
- **R5 놓아주기** — 지정된 구획이 끝났거나 스코프 밖으로 갔거나 사라지면
  **판정에서 제외**하고 R2~R4 를 다시 적용한다. 옵션 값은 지우지 않는다 —
  조용히 지우면 사람이 무엇을 골랐었는지 알 수 없다. 대신 화면이 "지정한 구획이
  끝났습니다" 라고 말한다(P6 의 "죽은 참조는 지우지 않고 보인다" 와 같다).

### 방향이 다르면 기준도 다르다 — 비대칭은 의도된 것이다

같은 두 행을 두고 묻는 질문이 반대다.

| 질문 | 함수 | 시설 전체 구획 × 구역 코디네이터 |
|------|------|-----------------------------------|
| 이 **구획**을 맡는 제어가 누구인가 | `facility_control_for_plot` | **제외** — 구획 전체를 대표해 맡는다고 말할 수 없다 |
| 내 **구역**에서 무엇이 자라나 | `plots_in_facility` | **포함** — 그 작물은 이 구역에서도 자란다 |

기준 구획 선택은 **후자**다("내 설정값이 무엇을 위한 것인가"). 둘을 같게 만들려
하지 말 것 — 답이 달라야 하는 서로 다른 질문이다. 회귀로 이 비대칭을 고정한다.

## 규칙 2 — 무엇을 가져오는가

**코디네이터가 실제로 목표로 쓰는 축만 가져온다.**

| 프로그램 | 코디네이터 옵션 | 조건 |
|----------|------------------|------|
| `targets.vpd` | `target_vpd` | `vpd_sp_type != 'method'` |
| `targets.co2` | `target_co2` | `co2_sp_type != 'method'` |
| `targets.dli` | `dli_target` | — |
| `photosynthesis.gdd_daily` | `gdd_target_daily` | 값이 있을 때 |
| `targets.temp_day` · `temp_night` · `rh` | **없음** | 아래 참조 |

### 온도·습도에 대응하는 목표 필드가 **없다**

코디네이터의 1차 목표는 VPD 이고, `temp_max`/`temp_min`·`humid_max`/`humid_min` 은
설정 화면이 스스로 "Constraints — not a primary target" 이라고 적어 둔 **한계**다
(초과하면 VPD 목표를 무시하고 강제 냉·난방). 온도 목표는 VPD 를 분해해서 나온다
(`situation._decompose_vpd`).

**그래서 `temp_day: 24` 를 `temp_max` 에 쓰면 안 된다.** 24도가 목표가 아니라
"24도를 넘으면 냉방" 이 되어, 목표가 한계로 둔갑한 채 아무 에러 없이 돈다.
`guide_T_min/max` 도 아니다 — 그쪽은 밴드이고 주/야 설정점은 두 값이다.

**선택지 하나는 준다.** 단계에 온도와 습도가 **둘 다** 있고 `vpd_sp_type` 이
`static` 이면, 그 둘을 VPD 로 환산해 `target_vpd` 에 넣는 것을 사람이 고를 수 있다
(`situation.compute_vpd(T, RH)` — 코디네이터가 분해에 쓰는 것과 같은 식이라
왕복이 어긋나지 않는다). 환산했다는 사실과 원래 값(24°C / 70%)을 화면에 남긴다.
주간·야간이 다르면 주간 값을 쓰고 그렇게 적는다 — 시간대별 목표는 Method 곡선의
일이다.

### 절대 하지 않을 것

- 목표를 한계 필드(`temp_max`·`temp_min`·`humid_max`·`humid_min`)에 쓰기
- 값이 0 이거나 없는 항목을 0 으로 밀어 넣기 (0 은 "프리셋 기본값 사용" 을 뜻하는
  자리가 있다 — `dli_target`·`gdd_target_daily`)
- Method 를 쓰는 항목 덮어쓰기

## 규칙 3 — 언제 가져오는가: 사람이 누를 때만

프로그램은 스스로 코디네이터를 고치지 않는다. P6 에서 자원 함수를 사람이 켜기로
한 것과 같은 결이고, 근거도 같다 — 설정 변경은 물리 동작으로 이어진다.

- 명령 버튼 `cmd_apply_plot_targets` ("구획에서 목표 가져오기").
- 적용 마커 `plot_targets_applied = "<plot_id>:<stage_index>:<signature>"`.
  같은 값이면 no-op(`crop_preset_applied` 와 같은 규율).
- **단계가 바뀌면 마커가 어긋난다** → 화면이 "단계가 3단계로 넘어갔습니다 —
  목표를 다시 가져오시겠습니까" 배지를 띄운다. 자동으로 적용하지 않는다.
- 저장 시 자동 동기화(`_sync_crop_targets` 같은 암묵 실행)는 **붙이지 않는다.**
  프리셋은 코드에 박힌 상수라 저장 때 따라와도 놀랄 일이 없지만, 구획 목표는
  사람이 어제 바꿨을 수 있다.

## 옵션 추가

| id | 형 | 기본 | 뜻 |
|----|----|------|-----|
| `target_source` | select | `crop_preset` | `manual` \| `crop_preset` \| `plot` |
| `source_plot_id` | text | `''` | 후보 2개 이상일 때의 기준 구획 |
| `plot_targets_applied` | (숨김) | `''` | 적용 마커 |

**기본값을 `plot` 으로 두지 말 것** — 업그레이드만으로 돌던 온실의 목표가 조용히
바뀐다. 기존 설치는 `crop_preset` 그대로이고, 사람이 바꿀 때만 옮겨간다.

## 단계

### Phase 1 — 표시 (제어를 바꾸지 않는다)

코디네이터 설정 페이지와 시설 모달에 나란히 보인다:

```
이 구역의 구획   상추 · 3단계(개화기) · 42일째
단계 목표        VPD 0.9 kPa · CO₂ 800 ppm · 주간 24°C
지금 설정        VPD 1.1 kPa · CO₂ 700 ppm · (온도는 VPD 에서 분해)
```

읽기만 하므로 위험이 없고, 지금의 혼란("어느 쪽이 실제로 도는 값인가")은
대부분 여기서 사라진다. 값이 다르면 다르다고 말할 뿐 고치지 않는다.

### Phase 2 — 가져오기

위 규칙 1~3. `_sync_crop_targets` 의 채우기 규칙을 재사용하고 소스만 갈아끼운다.

#### 구현 결과 (2026-08-19) — 설계가 정하지 않아 여기서 정한 것

- **명령 버튼이 아니라 Flask 엔드포인트다.** 설계는 `cmd_apply_plot_targets`
  (데몬 custom action)를 적었지만, 이 포크의 함수 옵션 템플릿은 `custom_actions`
  를 **아예 렌더하지 않는다**(`utils_export.py` 외에는 참조가 없다). 선례로 삼은
  `cmd_apply_crop_targets` 도 그래서 화면에서 누를 수 없는 상태였다. 버튼을 거기
  두면 만들자마자 도달 불가가 되므로, 비교 카드 안의 버튼 → `POST
  /api/geo/coordinator/<uuid>/plot-targets` 로 갔다. 비활성 코디네이터에서도
  눌린다는 이점도 있다(설정 중에 쓰는 기능이다).
- **돌고 있으면 재시작한다.** 컨트롤러는 옵션을 기동 때 읽으므로 DB 만 고치면
  화면에는 새 값이 보이는데 제어는 옛 값으로 돈다. `controller_restart` 를 부르고,
  실패는 삼키지 않고 `restarted: false` + `restart_error` 로 말한다.
- **기준 구획 지정은 별도 엔드포인트다**(`POST …/reference-plot`). 고르는 일과
  설정을 바꾸는 일을 한 클릭에 묶으면 어느 쪽을 의도했는지 되짚을 수 없다.
- **`can_apply` 는 서버가 판정한다.** 화면이 권한을 스스로 판단하면 곧 갈라지고,
  그 갈라짐은 "눌러도 403" 으로만 드러난다.
- **`applied_before` 로 첫 사용과 낡음을 가른다.** 마커가 없는데 "단계가
  바뀌었습니다" 가 뜨면 무슨 단계에서 무엇으로 바뀌었다는 것인지 알 길이 없다.
  (실제로 그렇게 만들었다가 브라우저에서 보고 고쳤다.)
- **버튼은 현재 값을 덮는다.** 자동 동기화가 아니라 명시적 재적용이라
  ("사람이 손댄 값 보존" 을 여기서 하면 누른 사람이 아무 일도 안 일어난 것으로
  본다), Method 를 쓰는 항목만 건너뛴다.
- `_sync_crop_targets` 는 `target_source != 'crop_preset'` 이면 **맨 앞에서
  반환**한다. 안 막으면 다음에 작물 프리셋을 바꾸는 순간, 가져온 단계 목표가
  저장만으로 조용히 되돌아간다.

### Phase 3 — 제어가 구획을 **정본으로 읽는다** (2026-08-19 완료, Phase 2 를 대체)

**값 복사를 폐기했다.** Phase 2 는 목표를 함수 옵션으로 옮겨 담았는데, 그러면
같은 사실이 두 곳에 남고 사람은 어느 쪽을 고쳐야 하는지 매번 판단해야 한다.
지금은 제어가 매 사이클 프로그램을 읽는다 — 설정하는 곳이 한 군데다.

배포된 서버 중 이 기능을 쓰는 곳이 하나도 없어(2026-08-19 확인) 단계적 이행
(폴백 → 관찰 → 제거) 없이 한 번에 정리했다. 쓰는 서버가 있었다면 그 절차가
필요했다.

#### 걷어낸 옵션과 대신 읽는 곳

| 걷어낸 것 | 정본 |
|---|---|
| `target_vpd`·`vpd_sp_type`·`vpd_method_id` | 단계 `targets.vpd` / `targets_methods.vpd` |
| `target_co2`·`co2_sp_type`·`co2_method_id` | 단계 `targets.co2` / `targets_methods.co2` |
| `dli_target` | 단계 `targets.dli` |
| `gdd_target_daily` · GDD 기준온도 | 프로그램 `photosynthesis.gdd_daily` · `T_base` |
| `schedule_start_time` | 구획 `started_on` |
| `target_source` · `plot_targets_applied` · `cmd_apply_plot_targets` | 복사가 없어져 불필요 |
| `_sync_crop_targets` · `cmd_apply_crop_targets` · `_CROP_PRESET_OPTION_MAP` | 프리셋이 목표를 채우던 경로 |

#### 코디네이터에 남는 것 — 전부 "이 시설이 어떻게"

한계(`temp_max/min`·`humid_max/min`) · guide 범위 · 액추에이터·시설 연결 ·
우선순위·허용오차 · 응급 · 풍속 게이트 · HVAC 인터록 · 육묘 모드 · 보정·예보 ·
`schedule_week_offset` · `crop_preset`(광합성 모델 상수 전용).

`schedule_end_time` 은 남되 이름이 **"제어 종료일"** 이다 — 수확일이 아니라
"이 날 이후 제어 정지" 라는 안전 결정이고, **구획이 끝나는 것과 별개다**(빈
온실도 안전 한계는 지켜야 한다).

#### 목표가 없는 것은 고장이 아니다

구획이 없거나 프로그램이 없거나 검토 안 된 AI 프로그램이면 목표가 없다. 그때
코디네이터는 **예전부터 guide 범위 중앙**으로 돌았다(`_cycle_mixin` 의 VPD
미설정 분기) — "안전 범위만 지킨다" 가 이미 정의된 동작이라 새로 만들 것이
없었다. 화면은 이유를 말한다(`reason`: `none`·`no-program`·`program-unreviewed`·
`no-stage`).

#### 세 번째 중복도 함께 걷었다

목표를 설정할 수 있는 곳은 셋이었다 — 프로그램 · 함수 옵션 · **시설 위젯의
setpoint 팝업**(`GeoFacilitySetpoint` + `/api/aot/facility/<id>/setpoints`).
팝업에서 VPD·CO₂ 목표 행을 없앴고, API 는 그 두 값을 받으면 **거부한다**(조용히
무시하면 저장된 것처럼 보이는데 제어는 쓰지 않는다 — 이 저장소가 반복해 겪은
"성공이라 답하는데 안 돈 것"). 팝업에 남는 것은 안전 한계와 guide 범위다.

화면이 색칠에 쓰는 목표는 `_effective_targets()` 로 **제어와 같은 계산**을
거친다. 저장된 열과 견주면 "화면은 목표대로인데 제어는 다른 값을 좇는" 상태가
보이지 않는다.

#### 한 사이클에서는 한 번만 읽는다

`_run_cycle` 이 캐시를 비우고 `_plot_targets()` 가 그 사이클 동안 재사용한다.
항목마다 읽으면 DB 를 여러 번 치는 것도 문제지만, 그 사이 값이 바뀌면 **한
사이클 안에서 서로 다른 목표**를 보게 된다.

#### 광합성 모델 상수도 프로그램으로 (2026-08-19)

`A_max`·`K_L`·`K_C`·`T_opt`·`T_sigma`·`VPD_half` 는 `crop_preset`(코드에 박힌
작물 5종)에 있었다. 같은 작물을 프로그램과 함수 **두 곳**에서 정하는 셈이었고,
함수에서 고른 것이 실제로 심긴 것과 다를 수 있었다.

- 프로그램 편집기에 접힌 **[광합성 모델]** 블록을 열었다. 대부분은 손대지 않고
  템플릿에서 만들면 이미 채워져 있어서 펼쳐 두지 않는다 — 펼쳐 두면 "채워야 할
  칸" 으로 읽힌다.
- 키 이름은 `CropParams` 와 **같다**(그 계약이 이미 있었다). 갈리면 값이 조용히
  무시되고 모델은 기본값으로 돈다 — `test_keys_match_the_control_side_dataclass`
  가 그것을 막는다.
- 코디네이터는 `_crop_params()` 로 프로그램 값을 `CropParams` 에 얹어 쓴다.
  **`crop_preset` 옵션은 제거했다** — 구획이 없으면 generic 기본값이다.
  기를 것이 없으면 최적화할 대상도 없다.
- 서버가 범위를 본다(`_check_photosynthesis`). 틀린 값이 들어가도 **에러가 나지
  않고** 모델이 엉뚱한 제한 요인을 고를 뿐이라, 저장할 때 한 번 본다. 모르는
  키는 거부하지 않는다 — 어휘가 늘 때 저장이 막히면 안 된다.
- 저장할 때 **숫자로 되돌려 담는다.** 화면은 입력칸의 문자열을 보내므로 그대로
  두면 `"19.5"` 가 저장되고, 다음 저장에서 `"19.5" != 19.5` 라 바뀌지 않았는데도
  바뀐 것으로 잡혀 버전이 헛돈다.

내장 템플릿(`seed_programs`)은 이미 `_CROP_PRESETS` 에서 이 값을 싣고 있었다 —
사람이 만들 때의 출발점이 그쪽이다.

## 하지 않는 것

- **코디네이터 안에 단계·GDD·일정을 다시 만들기.** 프로그램 기능의 재구현이다.
- **목표를 코디네이터 옵션으로 되돌리기.** 값을 복사해 두면 같은 사실이 두 곳에
  남고, 사람은 어느 쪽을 고쳐야 하는지 매번 판단해야 한다. 방향은 언제나
  코디네이터가 매 사이클 **읽어 가는** 쪽이다.
- **구획이 없을 때 제어를 멈추기.** R2 참조 — 빈 온실도 안전 한계는 지킨다.
- **목표를 한계 필드로 보내기.** 24℃ 목표가 "24℃ 넘으면 냉방" 으로 둔갑한다.

## 회귀로 고정한 것 (`test_geo_plot.py`)

1. 후보 0/1/2개 각각의 판정 (R2·R3·R4)
2. 지정 구획이 끝나면 놓아준다 (R5)
3. 방향 비대칭 — 구역 코디네이터 × 시설 전체 구획이 두 함수에서 반대로 나온다
4. 목표가 단계에서 온다 (값·곡선·시작일)
5. 검토 안 된 AI 프로그램은 제어에 쓰이지 않는다
6. 구획·프로그램·단계가 없는 것은 에러가 아니다 (이유를 말한다)
7. 걷어낸 옵션이 되살아나지 않는다 / 안전 옵션은 그대로 있다
8. 프리셋이 목표를 채우던 경로가 없다
9. 설정점 해석기가 `_plot_targets()` 를 읽는다 (`self.target_*` 아님)
10. 사이클이 캐시를 비운다
