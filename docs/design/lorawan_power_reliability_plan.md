# LoRaWAN 밸브 제어 — 배터리 절감 + 명령 신뢰성 통합 설계

작성 2026-06-29 · 대상: 차기 스케줄러 + 펌웨어 업데이트 · 검증 환경: aot-004(옥정호, 네이티브 ChirpStack 4.14.1, 단일 게이트웨이 붕어섬, 활성 Class C 밸브 14대)

---

## 1. 결론 먼저 (측정 기반)

- **HB·confirmed 다운링크는 배터리에 사실상 영향 없음(<1%)**. 배터리 소모의 ~99%는 **Class C 연속 수신(RX)**.
- 현재 현장은 **클래스 컨트롤러가 전부 비활성**(class_scheduler 1 + mode_manager 9, 모두 `is_activated=0`)이라 디바이스가 부팅 기본값 Class C에서 **24/7 상주** → 배터리 최대 소모.
- 따라서 배터리 전략 = **Class C 점유 시간 최소화**. HB 주기 단축/confirmed 제거로는 의미 있는 절감 불가.

---

## 2. 전력 모델 (RAK3172 / STM32WLE5, KR920, typical)

| 상태 | 전류 |
|---|---|
| Class C 연속 RX (radio+MCU) | ~5.5 mA (상시) |
| Class A idle (Stop2+RTC) | ~0.003 mA |
| TX @14dBm | ~45 mA (airtime 동안) |
| 업링크 1회 airtime (SF7, ~18B) | ~56 ms → **0.7 µAh/회** |

### 일일 소모량 (디바이스 1대)

| 시나리오 | RX/idle | HB | 합계 | 절감 |
|---|--:|--:|--:|--:|
| **Class C 24/7 (현재)** | 132.0 | 0.03 | **132 mAh/day** | 0% |
| 스케줄러 ON: C 13h(05–18)+A 11h | 71.5 | 0.07 | **72 mAh/day** | 46% |
| AUTO: C 5h(관수시만)+A 19h | 27.6 | 0.03 | **28 mAh/day** | 79% |
| **Class A 기본 + 온디맨드 C 1.5h** | 8.3 | 0.03 | **8 mAh/day** | **94%** |

### HB·confirmed 정량 (사용자 질문에 대한 답)
- **HB**: Class C에선 RX가 지배해 HB는 무관(2분 주기여도 0.5 mAh/day). Class A에서도 30분 주기 ~0.1 mAh/day. **HB를 절반으로 줄여도 ~0.05 mAh/day 절감 — 132 mAh 앞에서 무의미.** HB는 배터리 레버가 아니라 *명령 지연(Class A)·업링크 충돌(신뢰성)* 레버다.
- **confirmed**: confirmed 다운링크 1건당 디바이스 ACK 업링크 +1회(~0.7 µAh). 50건/day여도 **0.035 mAh/day — 무시 가능**.
- **"HB+confirmed 중복"의 배터리 증가 = 합쳐도 1% 미만.** 배터리 관점에서 둘 다 최적화 대상이 아니다.

> 주: aot-004 전 디바이스 vbat=0xFFFF(INA219 미작동 센티넬)이라 **실측 배터리는 확인 불가**. 위 수치는 데이터시트 기반 엔지니어링 추정. 용량(예: 2000 mAh 가정) 대비 현재 132 mAh/day ≈ 15일, 온디맨드 시 8 mAh/day ≈ 250일.

## 3. 목표

1. 배터리: Class C 24/7 → **온디맨드/윈도우 기반으로 80–94% 절감**.
2. 신뢰성: 절전(Class A) 상태에서도 **명령 누락 0에 수렴**(앱레벨 재전송으로 보장).
3. 안전성: 스케줄러 장애·디바이스 리부팅 시에도 **자동으로 절전(Class A)로 폴백**(배터리 트랩 방지).

## 4. 펌웨어 변경안 (차기 FW)

현행(v26.07): 부팅 Class C(`DEFAULT_CLASS_A=0`), `SETUP_DEFAULT_PERIOD_MIN=2`, 스케줄러가 한 평가주기 내 Class A로 강등 가정. **그러나 스케줄러가 꺼지면 영구 Class C.** (현장 펌웨어는 5/6/8B HB 혼재 — 버전 불일치도 정리 필요.)

1. **[핵심] 자가 폴백(self-fallback) 추가** — 조인/부팅 후 일정 시간(T_fallback, 예: 10–15분) 내 서버 CFG·다운링크를 못 받으면 **자동으로 Class A로 강등**. 스케줄러 장애가 곧 배터리 방전이 되는 현 구조의 안전망. 부팅은 빠른 초기 제어를 위해 잠깐 C 유지 가능하되, 미수신 시 반드시 A로.
2. **[핵심] 타임드 온디맨드 C** — CFG에 "C로 N분 유지 후 자동 A 복귀" 명령 추가(예: `[0xD0, mode=3, hb, ttl_min]` 확장 또는 신규 SIG). 서버가 복귀를 잊어도 디바이스가 **하드 배터리 상한**을 보장. 온디맨드 제어 세션의 핵심.
3. **부팅 기본값 재검토** — `DEFAULT_CLASS_A=1`(A로 부팅) + 제어 세션 때만 C 승격. 1·2와 결합 시 가장 안전.
4. **앱레벨 ACK 유지·강화** — 현행 FP11 ctrl_ack + FP12 status(open/close_done) 유지. 이게 서버 재전송의 정지 신호(물리 작동 증거). Class A에선 명령 수신 즉시 FP11/FP12를 다음 업링크로 송신해 서버가 빨리 확인하도록.
5. **HB 정리** — 펌웨어 버전 통일(5/6/8B 혼재 제거), ext 프레임 주기(HB_EXT_EVERY_N) 유지. HB 자체는 배터리 무관하므로 *충돌·지연* 기준으로만 설정.
6. **INA219 복구** — vbat=0xFFFF 원인(미장착/캘리브레이션) 해결. 배터리 인지형 스케줄링과 모니터링의 전제.

## 5. 스케줄러 변경안 (차기 class_scheduler)

현행 `lorawan_class_scheduler`는 이미 ACTIVE(C)↔REST(A)↔겨울(A) 전환 로직 보유. 문제는 **비활성 + 구형 mode_manager 9개와 혼재**.

1. **단일 권위로 통합·활성화** — 구형 per-device `lorawan_mode_manager` 9개 제거, per-site `lorawan_class_scheduler` 1개만 활성화. (현재 둘 다 off라 24/7 C의 직접 원인.)
2. **기본 REST(Class A)** — 야간·비관수 시간은 무조건 A. ACTIVE(C)는 *실제 제어가 필요한 구간*에서만.
3. **온디맨드 C 세션** — 사용자가 UI에서 제어를 시작하면 해당 사이트(또는 디바이스)를 **C로 짧게 승격(force-active N분) 후 자동 A 복귀**. 펌웨어 타임드-C(4-2)와 이중 안전. 가장 큰 절감(94%).
4. **AUTO 창 최소화** — 환경 스코어(일사/토양/강우)로 C 구간을 관수 실제 필요 시간으로 압축. 고정 MANUAL이면 창을 실제 운영시간으로 좁힘.
5. **전이 순서 보존** — C 진입: profile.supports_class_c ON → 디바이스 CFG C. C 해제: 디바이스 CFG A → profile OFF. (현행 로직 유지 — 전이 중 다운링크 유실 방지.)
6. **배터리 인지(INA219 복구 후)** — 저전압 디바이스는 C 창 단축/HB 연장.

## 6. 명령 신뢰성 (배터리 절전과 동시 충족)

별도 분석 결론: **ChirpStack v4.14.1은 미응답 confirmed 다운링크를 자동 재전송하지 않음**(13건 전송, 재전송 0 실측). 따라서:

1. **LoRaWAN confirmed 폐기** — 자동 재전송 없고 ACK 업링크 트래픽만 추가(반이중 게이트웨이에 불리). aot-004 출력 `confirmed`는 다음 정의된 재시작 때 되돌림.
2. **앱레벨 재전송 도입** — AoT 출력이 **FP12 status(실제 작동 증거)**를 타임아웃 내 못 받으면 명령 재발송(최대 N회, 백오프). 가장 강한 신호 기반이라 confirmed보다 우수. 이미 로컬에 구현된 출력 모듈 작업 활용:
   - 자기 DevEUI 업링크 MQTT 구독 → `ingest_uplink`
   - **vid 필터**(한 컨트롤러=여러 밸브, 형제 밸브 오염 방지)
   - `is_on` 신뢰성(in-flight 의도표시→confirmed, 실패 시 거짓전환 없음)
   - **per-DevEUI 직렬화·페이싱**(동시 다운링크 충돌 방지)
   - → 여기에 *재전송 루프* 추가.
3. **Class A에서의 명령 전달** — 명령은 디바이스의 다음 업링크(HB) RX 창에서 전달. 즉시성이 필요하면 온디맨드 C 세션으로 승격. 둘 다 앱레벨 재전송으로 누락 0 수렴.

## 7. 적용 순서 (마이그레이션)

1. (즉시·무코드) aot-004 `state_startup`을 `Do Nothing`으로 — 재시작마다 밸브에 close 나가는 부작용 제거. confirmed=true 원복(다음 의도된 재시작에 묶음).
2. 펌웨어: 자가폴백 + 타임드-C + 부팅 A + INA219 복구 + 버전 통일.
3. 스케줄러: mode_manager 제거 → class_scheduler 단일 활성, 기본 REST, 온디맨드 C, AUTO 창 압축.
4. AoT 출력: confirmed 폐기 + 앱레벨 재전송(로컬 모듈 작업 배포).
5. 검증: event_up(FP12)/event_tx_ack로 명령 작동률, node_class 추이로 C 점유시간, (INA219 복구 후) vbat 추이로 실측 절감 확인.

## 9. 코드 검증 결과 (2026-07-28) — 계획 수정

이 문서(06-29) 이후 실제 코드를 재검증한 결과, **계획의 전제 일부가 틀렸고 우선순위를 바꿔야 한다**는 결론이 나왔다. 핵심은 "기능을 새로 만드는 일"보다 **"이미 만든 안전장치가 데이터 배선 누락으로 조용히 죽어 있던 일"**이 더 컸다는 점이다.

### 9.1 SC-2 밸브 인터록이 완전히 무력화되어 있었음 (수정 완료)

`lorawan_class_scheduler._any_valve_open()` 은 `st.get('valves')` 를 읽는데, 배포본 `_lorawan_common.fetch_device_state()` 는 `valves` 키를 **반환하지 않았다**(aot/ 트리 전체 0회 등장). 따라서 `(None or 0) != 0` → 항상 False → **인터록이 어떤 경우에도 발동하지 않았다.**

- 영향: 밸브가 열린 채 사이트가 REST(Class A, 기본 HB 30분)로 강등될 수 있고, `sec=0` 으로 연 밸브는 펌웨어상 자동 타임아웃이 없어 STOP 이 도착할 때까지 열린 채 유지된다 → 관수 과잉 위험. 이는 인터록 주석이 방지하겠다고 명시한 바로 그 시나리오다.
- 원인: SC-3 변경이 git 미추적 개발본(`rak/`)에만 반영되고 배포 트리에 병합되지 않음. **역방향으로 배포본에만 페이싱(`claim_send_slot`)이 있어 단순 복사는 금물**이며 양방향 병합이 필요했다.
- 조치: 병합 완료. `node_class_actual` 도 함께 공급되어 SC-1 reconcile 이 폴백이 아닌 본래 신호(실제 적용 클래스)로 동작한다.
- 잔여 전제: `fetch_device_state()` 는 ChirpStack **metrics API** 를 읽으므로 코덱이 필드를 내보내는 것만으로 부족하고, 디바이스 프로파일에 `valves`/`node_class_actual` 이 **측정값으로 선언**돼 있어야 한다. 미선언 시 재발하므로, 전 디바이스가 `valves` 를 하나도 보고하지 않으면 경고 로그를 남기도록 했다.

### 9.2 valves 판정식 버그 — GPS 비트를 밸브 열림으로 오판 (수정 완료)

펌웨어는 밸브 3개 상태를 bit0\~5 에 담고 **bit6/bit7 을 GPS 존재·전원으로 재사용**하며, 코덱은 이 바이트를 raw 로 전달한다. 기존 판정식 `valves != 0` 은 GPS 장착 유닛에서 bit6 가 상시 1이므로 **인터록 영구 발동 → 사이트가 Class C 에 고정**된다. 이 문서가 없애려는 배터리 트랩과 동일한 결과다.

`VALVE_STATE_MASK = 0x3F` 로 마스킹해 수정했다. 9.1 병합 전에는 `valves` 가 항상 None 이라 드러날 수 없던 잠복 버그로, 병합이 데이터를 흘리는 순간 활성화될 지뢰였다. 현 편성은 `GPS_PRESENT 0`/`GPS_POWER_PIN -1` 기본값이라 해당 블록이 컴파일에서 빠져 실기 영향은 없었을 가능성이 크다.

### 9.3 §2 절감 모델이 현행 C노드 펌웨어에 성립하지 않음

§2 표는 **Class A idle = 0.003 mA(Stop2+RTC)** 를 전제로 94% 절감을 계산한다. 그러나 `rak3172-C-S` / `rak3172-C-E` 어디에도 `api.system.sleep.*` / `lpm` 호출이 **한 건도 없다**(대조: 센서노드 `rak3172-S` 에는 있음).

→ Class A 로 강등해도 MCU 는 계속 loop 를 돌며 깨어 있다. 꺼지는 것은 라디오 연속 RX 뿐이다. **§4-1 자가폴백만으로는 §3-1 의 목표(80\~94%)를 달성할 수 없으며, C노드에 절전 슬립 루프를 함께 이식해야 한다.** 이 항목이 원래 계획에 없었다.

### 9.3.1 센서노드 딥슬립 현장 실증 (2026-07-28) — 이 문서 최초의 실측 근거

`rak3172-S` 의 딥슬립 설계가 테스트 및 현장 설치로 검증되었다(사용자 보고).

- 배터리가 **상당히 절약**됨.
- **게이트웨이 미조인 상태에서 24시간을 정상 수행**.
- 사용자 표현: "오히려 **과거 방식(깨어 있기)이 깨어나지 못하게 만드는 독**이었다."

§2 절감표는 전 디바이스 `vbat=0xFFFF` 탓에 데이터시트 추정에 머물러 있었는데, 이것이 첫 실증이다. "절전을 위해 재우면 안 깨어날 위험"이라는 통념과 반대 결과라는 점이 핵심이며, C 계열에 같은 방식을 넣는 근거가 된다(새로운 위험 감수가 아니다).

참고: RAK 포럼에 "`sleep.all(duration)` 을 `loop()` 에서 부르면 LoRaWAN 세션 상실·자동 de-join" 보고가 있으나, `rak3172-S` 가 정확히 그 구성(조인 상태 Class A 수면)으로 정상 동작하므로 이 구성에서는 재현되지 않는 것으로 본다 — **현장 증거를 포럼 보고보다 우선**한다.

### 9.3.2 C-S 딥슬립 적용 (완료) — "자가폴백이 선행조건"은 틀렸다

위 실증을 근거로 `rak3172-C-S` 에 두 구간의 수면을 넣었다. 둘 다 "지금 깨어 있어도 받을 수 있는 다운링크가 없다"는 공통점이 있어 통신을 전혀 훼손하지 않는다.

- **(A) 미조인 구간** — 백오프가 길어진 뒤(`tries≥5`) 다음 조인 시도까지. 조인이 안 된 노드는 애초에 다운링크를 받을 수 없다.
- **(B) 조인 + Class A 구간** — 다음 하트비트까지. Class A 라디오는 업링크 직후 RX1/RX2 에서만 수신하므로, 그 창이 닫힌 뒤 자는 것은 아무것도 잃지 않는다. 지연은 Class A 를 택한 시점에 이미 정해진 것이고 수면은 순수 이득이다. **Class C 에서는 절대 자지 않는다** — 상시 수신이 존재 이유다.

즉 이 절의 초안에 있던 "딥슬립은 자가폴백보다 먼저 넣을 수 없다"는 **틀렸다**. 스케줄러가 이미 REST(Class A)로 내리고 있으므로 자가폴백 없이도 (B) 만으로 REST 구간의 절감을 즉시 얻고, (A) 는 조인 상태와 무관하다. 자가폴백은 "스케줄러가 죽었을 때의 안전망"으로서 여전히 필요하지만 슬립의 선행조건은 아니다.

밸브 컨트롤러 고유의 안전 게이트를 두었다(센서노드에는 불필요한 부분): 자는 동안 `valve_maintain()` 이 멈춰 펄스 타이머의 자동 OFF 가 지연되므로, **밸브가 하나라도 동작 중이거나 타이머가 걸려 있으면 자지 않는다.** 부팅 시퀀스 진행 중, 송신 큐 잔여, 미처리 다운링크 명령, 보류 중 ACK, GNSS 취득 중에도 마찬가지다.

### 9.3.3 부팅 밸브 CLOSE 기본 비활성 (완료)

현장 판단에 따라 `BOOT_CLOSE_DEFAULT 0` 으로 전환했다(`AT+BOOTCLOSE=1` 런타임 토글은 유지). 매 부팅마다 밸브를 닫을 필요가 없고, 이 시퀀스가 켜져 있으면 "리부팅 = 관수 강제 중단"이 되어 **복구 수단을 쓰기 어렵게 만든다** — 리부팅 비용이 너무 커서 워치독 주기를 짧게 잡을 수 없었다. 끄면 리부팅이 싸진다.

**서버측 후속 필요**: 부팅 CLOSE 를 끄면 리부팅 후 펌웨어의 밸브 상태 섀도(`v1_state` 등)는 idle 로 초기화되지만 **물리 밸브는 열린 채 남을 수 있다.** 이 섀도가 ext-HB 의 `valves` 비트필드로 올라가고 스케줄러 SC-2 인터록(9.1)이 그것을 읽으므로, 실제로는 열려 있는데 "전부 idle"로 보일 수 있다. 서버가 디바이스 리부팅(HB `uptime` 리셋)을 감지하면 의도한 상태를 재하달하는 것이 정석이다.

### 9.3.4 I2C 버스 stuck 복구 (C-E·C-S 완료)

슬레이브가 트랜잭션 도중 멈추면 SDA 를 low 로 물고 있어 이후 모든 `endTransmission()` 이 실패한다. **재시도로는 절대 안 풀린다** — 버스를 물고 있는 쪽이 슬레이브이기 때문이다. SCL 을 최대 9클럭 수동 토글해 슬레이브가 남은 비트를 밀어내게 한 뒤 STOP 을 만들고 페리페럴을 재초기화하는 루틴을 `rak3172-S` 에서 두 C 보드로 이식했다.

두 보드 모두 릴레이/밸브가 I2C 익스팬더에 물려 있어 **버스가 물리면 제어가 통째로 죽는다.** 특히 C-E 에서 중요한 지점: 슬레이브는 MCU 리셋으로 초기화되지 않으므로 **리부팅해도 안 풀린다.** 그러면 부팅 스캔이 보드 0개를 반환하고 장치가 "살아 있지만 릴레이가 죽은" 상태로 기동하며, 워치독이 재부팅시켜도 같은 상태가 반복된다. 그래서 C-E 는 부팅 스캔이 0개일 때도 복구를 시도한다.

적용 지점 — C-E: `xl_write()` 재시도 소진 / 부팅 스캔 0개 / `sht31_read()` 실패. C-S: `i2cWrite()` · `i2cRead()` 재시도 소진.

### 9.4 미조인 워치독 — 판정식 결함과 수정 (3개 펌웨어 전부 완료)

`rak3172-S` 의 `WATCHDOG_UNJOINED_ENABLE` 은 주석이 말하는 것과 코드가 하는 일이 다르다. 조건이 `!joined && (long)(millis() - 24h) >= 0` 이라 **"24시간 연속 미조인"이 아니라 "가동시간 24시간 경과 && 지금 미조인"** 이며, 미조인 시작 시각을 추적하지 않는다.

부작용으로 `millis()` 가 약 2,233,883,648 ms(**25.85일**)를 넘으면 부호 있는 32비트 비교가 다시 음수가 되어 **워치독이 조용히 무력화**된다. 결과적으로 이 워치독은 "부팅 후 한 번도 조인 못 함"은 커버하지만, 주석이 명시한 목적인 **"장기 가동 중 커버리지 이탈 후 미재조인"은 커버하지 못한다**(장기 가동 노드는 이미 사각지대에 있다).

→ **미조인 시작 시각 기반으로 재작성**했다. `g_unjoined_since` 를 두고 조인↔미조인 전이에서 갱신하며, 경과시간으로 판정하므로 절대 시각과 무관하다(경과시간 24.8일 미만이면 오버플로 안전).

**적용 상태: `rak3172-C-S` / `rak3172-C-E` / `rak3172-S` 3개 모두 수정 완료.** 센서노드도 현장 운용 중이지만 같은 결함을 갖고 있어 함께 고쳤다(다른 동작은 건드리지 않은 외과적 수정 — 특히 `g_join_tries` 리셋 같은 부수 변경은 하지 않았다).

검증: 판정 로직을 C 로 떼어내 ARM 환경(`millis()`=uint32, `long`=int32)을 모사해 9개 시나리오를 실행. 신 방식은 9건 전부 미조인 후 정확히 24시간에 발동(위반 0건)하며, `millis()` 롤오버가 미조인 도중 발생하는 최악 케이스를 포함한다. 구 방식은 9건 전부 다르게 동작했다 — 10일 가동 후 순간 이탈에 **즉시 리부팅**, 26일 후 이탈에는 **593시간(약 24.7일) 지연**.

### 9.4.1 워치독으로는 못 잡는 고장 — 하드웨어 IWDG 와 딥슬립의 배타 관계

소프트 워치독은 `loop()` 안에서 돌기 때문에 **`loop()` 자체가 멈추는 진짜 행업은 잡지 못한다**(워치독도 같이 멈춘다). 그것을 복구할 수 있는 것은 하드웨어 IWDG 뿐인데, RUI3 에서 다음 제약이 확인되었다.

- `api.system.wdt` 는 `enable(ms)` / `reset()` 만 있고 **`disable()` 이 없다** — 한번 켜면 전원 재인가 전까지 끌 수 없다.
- 최대 **8초**(초과 지정해도 8초로 잘림).
- **`api.system.sleep.all()` 이 IWDG 를 먹이지 않는다** → 자면 8초 뒤 리셋.

따라서 **딥슬립과 하드웨어 워치독은 한 보드에서 공존할 수 없고**, 보드별로 하나만 고른다.

| 보드 | 전원 | 선택 | 근거 |
|---|---|---|---|
| `rak3172-S` (센서) | 배터리+태양광 | 딥슬립 + 소프트 워치독 | 절전 우선 |
| `rak3172-C-S` (밸브) | 태양광+배터리 | 딥슬립 + 소프트 워치독 | 절전 우선. IWDG 를 넣으면 수면 8초 뒤 리셋 → 리부팅 루프 |
| `rak3172-C-E` (릴레이) | 상시전원 | **IWDG 8초** + 소프트 워치독 | 절감 불필요. 현장에서 "조인 실패 몇 회 뒤 얼어붙는" 증상이 보고됨 |

**알려진 공백**: 딥슬립을 쓰는 두 보드는 완전 행업에 대한 대응 수단이 원리적으로 없다. RAK 포럼의 우회책(무기한 `sleep.all()` + 타이머에서 `wdt.reset()`)이 있으나 루프 구조 전면 개편이 필요하다.

두 파일 주석에 "여기에 IWDG 를 넣지 말 것"과 그 이유를 박아두었다 — C-E 에는 있고 C-S 에는 없는 것이 실수로 보이기 쉽기 때문이다.

### 9.5 `DEFAULT_CLASS_A` 는 죽은 매크로

§4-3 "부팅 기본값 재검토"를 `DEFAULT_CLASS_A=1` 로 플래그만 뒤집어 수행하면 **아무 일도 일어나지 않는다.** 이 매크로는 정의만 있고 참조가 0건이다(바로 옆 `DEFAULT_BAND` 는 실제로 사용되어 더 헷갈린다). 실제 배선이 필요하다.

### 9.6 §5(스케줄러) 전제 정정 — 문서가 자기 코드를 과소평가함

문서 작성 다음 날 커밋 `9cf8964`(06-30)로 SC-1\~SC-6 이 들어가, §5 가 "필요하다"고 한 항목 상당수가 이미 구현돼 있었다. §5-3 온디맨드 C 도 수동 버튼(`force_active_now`)은 06-27부터 존재했다. 실제 미실행 항목은 다음으로 좁혀진다.

- §5-1 **`lorawan_mode_manager` 제거 — 미실행.** 파일이 살아있고 `FUNCTION_INFORMATION` 도 그대로라 UI 함수 목록에 노출되어 **새 인스턴스를 계속 만들 수 있다.** 권위 이원화 유지 중.
- 제어 시작 시 **자동** C 승격 — 미구현(`on_off_chirpstack.set_mode_period()` 는 정의만 있고 호출자 없음).
- §4-2 펌웨어 하드 TTL(`[0xD0, mode, hb, ttl_min]`) — 미구현.

"모두 `is_activated=0`" 은 런타임 DB 상태라 코드로 판정 불가하며 별도 확인이 필요하다.

### 9.7 수정된 적용 순서 (§7 대체)

1. **`_lorawan_common.py` 양방향 병합** — SC-2 복구. (9.1, 9.2 — **완료**)
2. **INA219 검출 재작업** — 후보 주소 스캔(0x40/41/44/45) + 하트비트마다 재탐지(자가복구) + `AT+INA?` 버스 스캔 진단. (**완료**) 종전에는 부팅 시 1회 검출이 실패하면 영구히 "미장착"으로 굳었고, 미장착인지 주소 상이인지 버스 고장인지 구분할 수단이 없어 원인 미상으로 방치되었다. `AT+BAT=?` 도 하드코딩 스텁에서 실측값 반환으로 교체. **단, 물리적 미장착이면 코드로는 해결 불가 — 실기에서 `AT+INA?` 를 실행해 확정해야 한다.**
3. **미조인 워치독 재작성** — 3개 펌웨어 전부 (9.4 — **완료**). C-E 는 하드웨어 IWDG 8초 추가(9.4.1).
4. **C노드 절전 슬립** — 미조인 + 조인된 Class A 두 구간 (9.3.2 — **완료**).
5. **I2C 버스 stuck 복구** — C-E·C-S 이식 (9.3.4 — **완료**).
6. **부팅 밸브 CLOSE 기본 비활성** (9.3.3 — **완료**). 서버측 후속(리부팅 감지 시 상태 재하달) 필요.
7. **자가폴백 + 타임드-C**, `mode_manager` 정리 — 미착수.

부팅 클래스 변경(§4-3)은 §8 미결 정책 사안이며 9.5 의 함정을 먼저 해소해야 한다.

### 9.8 펌웨어별 게이트웨이 / join 시나리오 대조

| 시나리오 | `rak3172-S` (센서) | `rak3172-C-S` (밸브) | `rak3172-C-E` (릴레이) |

| 정상 부팅→조인 | HB 시작, 주기 수면 | Class C 유지, 제어 대기 | Class C 유지, IWDG 급전 |

### 9.9 빌드 검증

RUI3 코어와 툴체인은 로컬에 설치되어 있다(Arduino IDE 번들 `arduino-cli` + `rak_rui:stm32` 4.2.4). 3개 펌웨어 모두 컴파일 확인.

```bash
"/Applications/Arduino IDE.app/Contents/Resources/app/lib/backend/resources/arduino-cli" \
  compile --fqbn rak_rui:stm32:WisDuoRAK3172EvaluationBoard --warnings all \
  rak/rak3172-C/rak3172-C-S-v26.07
```

| 펌웨어 | 플래시 | 사용률 | RAM |
|---|---|---|---|
| `rak3172-S` | 166,608 B | 83% | 70% |
| `rak3172-C-S` | 173,656 B | 86% | 72% |
| `rak3172-C-E` | 165,816 B | 82% | 71% |

이 수치는 §9.6 의 FUOTA 판단에도 직결된다 — 플래시의 82\~86% 를 이미 쓰고 있어 **두 번째 이미지 슬롯을 둘 자리가 없다.** 안전한 롤백이 불가능하다는 것이 추정이 아니라 측정된 사실이며, 외장 플래시를 가진 RAK3172-F 가 사실상 전제조건이다.

경고는 3개 파일 모두 기존 코드에서만 발생하며(미사용 함수/변수, AT 등록 문자열 리터럴, `snprintf` 절단 가능성), 이번 변경분에서는 0건이다.
