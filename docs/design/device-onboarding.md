# 장치 온보딩 — 목록에서 고르기를 폴백으로 내리기

**상태**: 설계 초안 (2026-08-17). 구현 착수 전.
**관련**: `device-tier.md`(장치 계층) · `plc-modbus-integration.md`(Modbus 경로) ·
`ai-tool-architecture.md`(AI 도구 계약) · `geo-device-binding.md`(장치-공간 바인딩)

---

## 요약

설치는 스크립트 하나로 끝나는데, 그 다음 "센서 하나 붙이기"에서 사용자가 멈춘다.
현재 진입점은 **드롭다운에서 모듈을 고르는 것 하나뿐**이고(`input.html:59`,
`form_add_input.input_type`), 목록에는 입력 154개가 들어 있다. 이 UI는 사용자가
자기 하드웨어에 대응하는 모듈명을 **이미 알고 있을 때만** 성립한다. 매뉴얼이
높은 허들인 이유가 여기다 — 매뉴얼이 불친절해서가 아니라, 매뉴얼을 읽어야만
첫 화면을 넘어갈 수 있는 구조이기 때문이다.

이 문서는 진입점을 뒤집는 설계를 정한다. 핵심 판단은 넷이다.

1. **발견이 정본, 목록은 폴백.** 장치가 자기를 신고하게 하고, 사용자는 확인만 한다.
2. **새 메타데이터를 만들지 않는다.** 판정에 필요한 정보는 이미 모듈 선언에 있다
   (`i2c_location` 66개 · `interfaces` 117개). 새 필드를 추가하면 154개 모듈에
   그 필드를 채우는 일이 선행 조건이 되어 착수 자체가 막힌다.
3. **완료의 정의는 "저장됨"이 아니라 "값이 들어옴"이다.** 지금은 저장이 성공해도
   값이 안 들어오는 이유를 사용자가 알 방법이 없다.
4. **발견은 읽기 전용이고 등록만 쓴다.** 스캔이 DB를 건드리면 실패한 스캔이
   찌꺼기를 남긴다.

## 1. 현재 상태 (실측)

### 1-1. 이미 있는 자산

착수 전에 확인한 결과, **필요한 부품의 상당수가 이미 있다.** 없는 것은 부품이
아니라 부품 사이의 연결이다.

| 자산 | 위치 | 상태 |
|------|------|------|
| I2C 주소 선언 | `aot/inputs/*.py` 의 `'i2c_location'` | 66개 모듈, 고유 주소 47개 |
| 인터페이스 분류 | `'interfaces'` | 117개 모듈 |
| I2C 스캔 실행 | `routes_page.py:719-733` (`i2cdetect -y N`) | 동작함. info 페이지 전용 |
| ChirpStack 장치 조회 | `utils_chirpstack.list_chirpstack_devices()` | 동작함 |
| ChirpStack → 입출력 등록 | `utils_chirpstack.register_device_as_input()` / `..._as_output()` | 동작함 |
| ChirpStack 온보딩 UI | `settings/chirpstack.html`(297줄) + `routes_settings.py:162-245` | 동작함. **설정 페이지에만 있음** |
| 단발 측정 | `aot_client.input_force_measurements()` → `utils_input.force_acquire_measurements()` | 동작함 |
| AI 장치 생성 | `create_input` / `modify_input` / `list_device_types` / `get_device_type_options` | 동작함 (create-then-configure) |

`interfaces` 분포는 다음과 같다. 발견 경로의 우선순위 근거가 된다.

```
I2C 67 · UART 26 · FTDI 11 · GPIO 10 · AoT 8 · 1WIRE 7 · BT 4 · SPI 3 · IP 2 · 기타 3
```

### 1-2. 결손

- **I2C 폼의 스캔 버튼은 아무 일도 하지 않는다.** `form_options/I2C.html:20` 이
  `processRequest(this, 'i2c_scan')` 을 부르지만, `input.html:283` 의 액션
  화이트리스트에 `i2c_scan` 이 없고 서버측 핸들러도 없다. 클릭해도 조용히 끝난다.
  스캔 능력은 info 페이지에 이미 있는데 정작 필요한 자리에서 죽어 있다.
- **ChirpStack 발견은 설정 페이지에만 있다.** 장치를 추가하려는 사용자가 가는 곳은
  `/input` 인데, 거기서 설정 > ChirpStack 으로 갈 이유를 알 방법이 없다.
- **주소 → 후보 모듈 매핑이 없다.** 스캔 결과가 `0x76` 이어도 그것이 어느 모듈인지
  잇는 코드가 없다. 정보는 선언에 다 있는데 뒤집어 놓은 적이 없을 뿐이다.
- **추가 직후 검증 루프가 없다.** `input_acquire_measurements` 액션은 존재하지만
  기존 입력의 상세 화면에 있고, 추가 흐름에는 엮여 있지 않다.

## 2. 역인덱스 — 새 데이터 없이 154개를 3개로

`i2c_location` 을 뒤집으면 `{주소: [모듈…]}` 이 나온다. 실측 결과는 다음과 같다.

```
고유 주소 47개 / 선언 모듈 66개
주소당 후보 수 분포: 1개→19, 2개→15, 3개→1, 4개→3, 5개→4, 7개→2, 8개→1, 9개→2
후보가 1개뿐인 주소: 19/47 (40%)
```

의미는 이렇다.

- **주소의 40%는 스캔 결과만으로 모듈이 확정된다.** 사용자에게 물을 것이 없다.
- 나머지도 **154개 목록이 평균 3.3개 후보로 줄어든다.** 충돌이 큰 쪽은
  `0x40`(9개) · `0x49`(9개) · `0x77`(8개) · `0x76`(7개) · `0x48`(7개) 정도이고,
  이들은 애초에 하드웨어적으로 구분이 안 되는 주소라 **사람도 육안으로 골라야
  한다.** 이 경우 후보 목록에 `input_library` 와 모듈명을 함께 보여 주고 고르게 한다.

인덱스는 **런타임에 파생한다.** 입력 모듈 정보는 이미 기동 시 파싱되므로
(`parse_input_information`), 거기서 한 번 뒤집어 캐시하면 추가 비용이 사실상 없다.
DB 테이블도, 마이그레이션도, 모듈 선언 변경도 필요 없다.

> **주의**: 역인덱스를 정적 파일(JSON 등)로 굳혀 커밋하지 말 것. 모듈이 추가되면
> 그 파일이 조용히 스테일해지고, 새 센서만 발견에서 빠지는 형태로 나타난다 —
> 번들 드리프트와 같은 계열의 조용한 실패다. **선언이 정본이고 인덱스는 파생물이다.**

## 3. 단계

### Phase 1 — 발견 트레이 (`/input` 상단)

목록 드롭다운 **위에** "발견된 장치" 영역을 둔다. 페이지 진입 시 자동 스캔하지
않고 버튼으로 시작한다(스캔은 수 초가 걸리고, 장치를 추가할 생각이 없는 방문에도
매번 도는 것은 낭비다).

발견 경로는 셋이며, 각각 독립적으로 붙일 수 있다.

1. **LoRaWAN (ChirpStack)** — `list_chirpstack_devices()` 를 그대로 쓴다. 이미 등록된
   DevEUI 를 걸러내는 로직도 `routes_settings.py` 에 있으므로 서비스 함수로 뽑아
   공유한다. 등록은 `register_device_as_input()` / `..._as_output()`.
2. **I2C** — `routes_page.py` 의 `i2cdetect` 호출을 서비스 함수로 뽑고
   (`caps.get('i2c')` 게이트 포함), 결과 주소를 §2 역인덱스에 통과시킨다.
3. **1-Wire** — `/sys/bus/w1/devices/` 나열. 주소 체계가 고유해 후보가 거의 항상 1개다.
   구현 비용 대비 확정률이 가장 높다.

각 항목은 `(발견된 식별자, 후보 모듈 목록, 이미 등록됨 여부)` 를 갖는다. 후보가
1개면 "추가" 버튼 하나, 여러 개면 후보 중 선택 후 추가.

**Phase 1 에서 함께 처리할 것**: 죽어 있는 `i2c_scan` 버튼. 서비스 함수가 생기면
그 버튼도 같은 함수를 부르게 해서 살린다. 살리지 않을 거면 버튼을 지운다 —
**눌러도 아무 일도 안 하는 버튼을 남겨 두는 것이 가장 나쁘다.**

### Phase 2 — 검증 루프 ("값이 들어와야 완료")

추가 직후 실측 1회를 시도하고 결과를 보여 준다. 여기서 배선·주소·권한 문제의
대부분이 그 자리에서 드러난다.

흐름: `추가 → 활성화 → input_force_measurements() → 결과 폴링 → 값·단위 표시`

- 성공: 값과 단위를 보여 주고 "완료" 상태로 넘긴다.
- 실패: 원인 후보를 제시한다(주소 응답 없음 / 의존성 미설치 / 권한 / 타임아웃).
  의존성 미설치는 이미 추가 흐름이 감지하고 있다(`dep_unmet` 분기,
  `input.html:311`) — 그 정보를 검증 결과에 합류시킨다.

> **함정 — `input_force_measurements()` 는 컨트롤러가 떠 있어야 한다.** 비활성
> 입력에 부르면 실패한다. 따라서 검증은 활성화 후에 하고, 검증 실패 시 입력을
> 지울지 비활성으로 남길지 결정해야 한다. **비활성으로 남기는 쪽을 권한다** —
> 배선을 고치고 다시 시도하는 것이 정상 경로이고, 지워 버리면 사용자가 방금 채운
> 설정을 처음부터 다시 입력해야 한다.

> **함정 — 값이 없는 것을 장애로 표시하지 말 것.** 주기가 긴 입력은 첫 값까지
> 시간이 걸린다. 검증은 `force` 로 즉시 1회를 받아 보는 것이지 주기를 기다리는
> 것이 아니며, 타임아웃은 "실패"가 아니라 "아직 확인 못 함"으로 표시한다.
> (측정값 신선도 판정 원칙은 CLAUDE.md "측정값 신선도는 장치 주기 대비로만" 참조.)

### Phase 3 — 옵션 계층화

`options_enabled` / `options_disabled` 구조가 이미 있으므로, 여기에 **필수 / 고급**
축을 하나 더 얹는다. 기본 화면에는 필수만 노출하고 나머지는 접는다.

기준은 기존 원칙을 그대로 쓴다 — 결정 가능한 값은 내장하고 UI 를 만들지 않는다
(CLAUDE.md "불필요한 설정 금지"). AoT_map 위젯을 44개 → 6개 + 고급 접힘으로 줄인
선례가 있고, 같은 판단을 장치 폼에 적용하는 것이다.

필드 도움말은 새로 쓰지 않고 **기존 `help_page` 링크 시스템을 필드 단위 앵커까지
내린다**(`project_help_link_system` 참조). 매뉴얼을 찾아 읽게 하는 대신 그 자리에서
읽게 하는 것이 목적이다.

### Phase 4 — 레시피 / AI 진입점 (뒤로 미룸)

- **레시피**: "온실 환기 자동화" 같은 목적에서 진입해 Input + Output + Function +
  위젯을 한 묶음으로 적용한다. 실행부는 AI 도구가 이미 4종을 다 만들 수 있으므로
  새로 만들 것은 번들 포맷과 롤백뿐이다.
- **AI 진입점 승격**: `create_input` 경로는 이미 동작하지만 AI 페이지 안에 있어,
  설정을 헤매는 사용자가 도달하지 못한다. 장치 추가 화면에 진입점을 두는 것이
  실질적 변경이다.

**Phase 1~3 이 자리 잡은 뒤에 착수한다.** 발견과 검증이 없는 상태에서 레시피를
얹으면, 실패했을 때 무엇이 잘못됐는지 알 수 없는 덩어리가 하나 더 생긴다.

## 4. 비목표

- **자동 등록.** 발견은 목록을 보여 줄 뿐이고, 등록은 항상 사람이 누른다. 스캔
  결과를 자동으로 입력으로 만들면 남의 I2C 장치나 남의 애플리케이션 DevEUI 까지
  끌어온다.
- **모듈 목록 UI 제거.** 발견이 못 잡는 인터페이스가 여전히 많다(HTTP·MQTT·가상
  입력 등). 목록은 남기되 순서를 뒤로 민다.
- **모듈 선언 스키마 변경.** §2 의 전제다.
- **출력(Output) 발견.** ChirpStack 경로는 이미 출력 등록을 지원하므로 그대로
  따라오지만, I2C·1-Wire 발견을 출력으로 확장하는 것은 이 문서의 범위 밖이다.

## 5. 미해결

- **I2C 후보가 9개인 주소를 어떻게 보여 줄 것인가.** 모듈명만으로는 사용자가 못
  고른다. `input_library` 와 측정 항목(`measurements_dict` 의 측정 종류)을 함께
  보여 주면 "온습도인가 전류인가" 수준의 구분은 가능하지만, `0x40` 처럼 htu21d ·
  si7021 · ina219x 가 섞이는 자리는 여전히 애매하다. 검증 루프(Phase 2)가 있으면
  **틀린 후보를 골라도 그 자리에서 드러나므로** "일단 골라 보고 값으로 확인"이
  현실적인 답일 수 있다. 결정 필요.
- **도커 환경의 I2C·1-Wire 접근.** `caps.get('i2c')` 게이트가 이미 있어 없으면
  건너뛰지만, 디바이스 매핑이 없는 컨테이너에서 발견이 통째로 비는 것이 정상인지
  아니면 안내가 필요한지 정해야 한다.
- **UART/Modbus 발견.** `interfaces` 기준 UART 26개로 두 번째로 큰 축인데, 주소
  스캔이 파괴적일 수 있어(잘못된 보레이트로 쓰기) 읽기 전용 발견이 가능한지
  확인이 필요하다. Phase 1 범위에서 뺀 이유다.
