# 식생 구획(작기) — 짧게 살고 겹치는 공간 단위

**상태**: 설계 초안 (2026-08-13). 구현 착수 전.
**관련**: `geo-device-binding.md`(공간-장치 바인딩) · `geo-data-integrity.md`(불변식 I1~I9) ·
`color-system.md`(테마색 정본) · `map-site-summary.md`(계층 요약)

---

## 요약

지도에 `site > zone > facility > equipment > aot_device` 가 있지만 **어디에 무엇이
심겨 있는지**를 담는 자리가 없다. 구역 하나에 작물이 여러 종류면 지금은 구분할
방법이 아예 없다.

이 문서는 그 자리를 **`GeoShape` 가 아닌 별도 테이블 `geo_planting`** 으로 만드는
설계를 정한다. 핵심 판단은 셋이다.

1. **작기는 짧게 살고 기하까지 함께 죽는다.** 노지 두둑은 갈아엎으면 위치가
   바뀐다. 그래서 "반영구 구획 + 시간축 속성" 이 성립하지 않는다.
2. **수명은 구조가 아니라 데이터로 표현한다.** 엽채류 30일부터 과수 30년까지를
   같은 구조가 담아야 한다 — 종료일 하나로 갈린다.
3. **센서를 매달지 않는다.** 공간 포함으로 파생한다. 3개월 뒤 사라지는 대상에
   바인딩을 매다는 것은 `map_overlay_id` 가 겪은 오염 계열로 되돌아가는 것이다.

용어: 코드·테이블은 `planting`(작기), UI 문구는 "식생 구획". 이 문서에서 "구획"은
`geo_planting` 행 하나를 뜻한다.

## 배경 — 지금 무엇이 없는가

작물 정보는 **시설 안에만 절반쯤 있다.**

| 자리 | 무엇을 아는가 |
|------|---------------|
| `facility.bays[].crop` ([facility_bays.py](../../aot/aot_flask/geo/facility_bays.py)) | 온실 동(棟)별 작물 이름 하나 |
| `env_coordinator` 의 `crop_preset` | 시설 단위 제어 프리셋 |
| `facility_registry.yaml` | `crop_type` + `planting_date` → 생육단계 (없는 설치가 정상) |
| **노지 zone** | **아무것도 없다** |

즉 온실은 동별 작물을 알고 노지는 모른다. 그리고 `bays[].crop` 은 **문자열 하나**라
작기 이력이 없다 — 다음 작물을 적으면 이전 작물은 사라진다.

이 빈틈이 실제로 막는 것:

- `get_crop_status` 가 노지에 대해 답할 수 없다 → 작물을 모르면 재배 조언이 성립하지 않는다.
- **연작 장해·윤작 계획**을 세울 근거가 없다. "이 자리에 최근 3년간 뭐가 있었나"는
  토양 병해(3~5년 주기)에서 가장 자주 필요한 질문인데 시스템이 답을 못 한다.
- 같은 zone 의 센서값 하나를 여러 작물이 공유하는데, **작물별로 판정 기준이 다르다는
  사실**을 표현할 데가 없다.

## 폐기된 대안 — 왜 안 되는지 기록으로 남긴다

### ✗ facility 도형 재활용

"facility 는 `geo/facility` 로 분리돼 `geo/design` 에서 죽은 도형" 이라는 관찰은
**화면에 대한 것이지 데이터에 대한 것이 아니다.** design 패널의 facility 티어에
색 피커·"Facility Design" 진입·라벨 토글만 있어 편집 기능이 없어 보일 뿐, 도형은
살아서 참조된다.

| 참조처 | 하는 일 |
|---|---|
| [geo_overlays.py:100,190](../../aot/aot_flask/geo/geo_overlays.py) | `type=='facility'` 도형에 `GeoFacility` 메타 병합 |
| [site_summary.py:379](../../aot/aot_flask/geo/site_summary.py) | 계층 트리의 `kind='facility'` 판정 |
| [routes_notes_api.py:93](../../aot/aot_flask/routes_notes_api.py) | 노트 타깃 `'facility'` — 좌표 자동 채움 |
| `aot_data_tool_service.py` / `ai_summary_service.py` | AI 스코프 어휘 `scope_type='facility'` |
| [geo_integrity_ddl.py:34](../../aot/databases/geo_integrity_ddl.py) | I1 타입 화이트리스트 |

게다가 `GeoShape.type` 은 **I7 로 불변**이다. 기존 facility 도형을 식생으로 전환할
수단이 없어 "재활용"이 아니라 같은 이름의 두 의미가 섞인 상태가 된다 — 2026-08-03
사고(도형 종류가 5개 필드에 중복돼 읽는 경로마다 기준이 달랐던 것)의 재생산이다.

### ✗ `GeoShape` 에 `type='vegetation'` + 유효기간 컬럼

`GeoShape` 는 지금 **전부 반영구**다(site·zone·facility·facility_bay·equipment·마커).
만료라는 개념 자체가 없다. 한 종류만 시간축을 가지면 `GeoShape` 를 읽는 **모든 경로**가
"만료된 건 빼라"를 각자 기억해야 한다 — `get_overlays` · `site_summary` ·
`check_geo_integrity` · 지도 위젯 · 시설 위젯 · AI 도구. 한 곳이 빠지면 지도가 3년치
옛 두둑으로 뒤덮이고, 무결성 검사는 만료 도형을 고아로 신고한다.

이것이 이 저장소가 이미 크게 데인 **"읽는 경로마다 기준이 다름"** 의 성립 조건이다.

### ✗ 반영구 구획(GeoShape) + 작기(별도 테이블) 하이브리드

"구획은 오래 가고 작물만 바뀐다"를 가정한다. 온실 베드·과수원에서는 맞지만
**노지에서 깨진다** — 두둑·이랑은 작기마다 새로 만들어지고 갈아엎으면 위치가 바뀐다.
가정이 절반에서만 참이면 나머지 절반은 우회로를 쓰게 되고, 우회로가 곧 두 번째 정본이 된다.

---

## 설계 원칙

- **P1 — 작기 하나 = 행 하나 = 기하 + 작물 + 기간.** 도형과 작기가 같은 것이므로
  정본이 하나다. 기하를 `GeoShape` 에 두고 작물을 딴 데 두면 정본이 둘이 된다.
- **P2 — 수명은 데이터다.** 종료일이 빈 행 하나가 과수 30년을 담고, 45일짜리 행이
  한 해에 여러 개 생긴다. 구조는 같다.
- **P3 — 소속은 저장하지 않고 파생한다.** [device_membership.py](../../aot/aot_flask/geo/device_membership.py)
  가 확립한 원칙. 저장하면 복제가 남의 링크를 복사하고 zone 재생성이 참조를 끊는다.
- **P4 — 센서는 참조하되 매달지 않는다.** 소속(장치가 누구 것인가)과 참조(작기가
  어느 센서를 보는가)는 다른 축이다. 아래 §"센서 참조 계약" 참조.
- **P5 — 겹침은 정상이다.** 간작·혼작이 실제로 흔하다. 겹침을 막는 제약을 걸지 않는다.
- **P6 — 종료된 작기는 이력이다.** 지도에서 사라지되 DB 에는 남고, 기하는 수정되지 않는다.

## 스키마

```python
class GeoPlanting(CRUDMixin, db.Model):
    """식생 구획(작기) — 짧게 살고 기하까지 함께 죽는 공간 단위.

    GeoShape 가 아닌 이유는 docs/design/geo-vegetation-planting.md 참조.
    한 줄로: GeoShape 는 전부 반영구이고 만료 개념이 없다.
    """
    __tablename__ = 'geo_planting'

    id          = Integer, PK
    unique_id   = String(36), unique, default=set_uuid

    # --- 공간 ---
    geo_id      = String(64), NOT NULL, index     # GeoMap.unique_id (GeoShape 와 같은 규약)
    feature     = JSON, NOT NULL                  # GeoJSON Feature, Polygon | MultiPolygon
        # zone 소속 컬럼은 **없다** — 공간 포함으로 파생한다(P3).
        # properties 에 device_id/channel_id/색 사본을 넣지 않는다(VP-4).

    # --- 작물 ---
    crop        = String(64), NOT NULL            # 작물명
    variety     = String(64), nullable            # 품종

    # --- 시간 (Date, DateTime 아님) ---
    planted_on      = Date, NOT NULL              # 파종/정식일
    ended_on        = Date, nullable              # NULL = 재배 중
    expected_end_on = Date, nullable              # 예상 종료 (계획·알림용)
    ended_reason    = String(16), nullable        # 'harvested'|'failed'|'replaced'|'removed'

    # --- 출처 ---
    source_kind = String(16), NOT NULL, default 'drawn'
        # 'drawn'        — zone 안에서 직접 그림
        # 'bay_snapshot' — 시설 bay 기하를 복사 (아래 §시설 bay 흡수)
        # 'copied'       — 지난 작기 복사
    source_ref  = String(80), nullable
        # bay_snapshot → GeoFacility.unique_id + ':' + bay_id
        # copied       → 원본 GeoPlanting.unique_id

    # --- 표시 ---
    name        = String(120), nullable           # 구획 이름 ("하우스 앞 두둑")
    color       = String(16), nullable            # 사용자가 고른 구분색

    created_at  = DateTime, default=utcnow
    updated_at  = DateTime, onupdate=utcnow
```

### 왜 `Date` 이고 `DateTime` 이 아닌가

농사의 단위는 날이다. 파종 시각의 시분초는 의미가 없고 tz 변환 문제만 부른다
(`timezone-management.md` §4 의 tz 상속 체인을 탈 이유가 없다). "오늘 심었다"는
지도의 tz 가 무엇이든 같은 날짜여야 한다.

### `color` 는 "색 각인 금지" 규칙과 충돌하지 않는다

`color-system.md` 가 금지하는 것은 **계산된 테마색을 도형에 되써 넣는 것**
(sync-back)이다. 여기 `color` 는 사람이 작물 구분용으로 **의도적으로 고른 데이터**이고,
`GeoShape.feature` 에는 절대 들어가지 않는다.

미설정이면 테마의 식생 기본색으로 수렴한다 — `aot-geo-theme-colors.js` 의 `DEFAULTS`
에 `vegetation` 키를 **한 벌만** 추가하고, 새 폴백을 다른 곳에 만들지 않는다.

## 공간 계약 — zone 안에서 나눈다

### 진입은 zone 을 고르는 것에서 시작한다

구획을 지도 아무 데나 그리지 않고 **zone 을 고른 뒤 그 안에서** 만든다. 그래야
부모가 자동 결정되고, "어느 자원을 나누는 중인가"가 화면에서 분명해진다.

### 분할은 느슨하다 — 합집합이 zone 일 필요는 없다

엄격한 분할(조각의 합 = zone, 빈틈·겹침 없음)은 통로·둑·휴경지를 전부 조각으로
만들어야 해서 실제 밭에서 성립하지 않는다. 대신:

- **zone 경계로 클리핑한다.** 구획이 zone 밖으로 나가면 잘린다.
- **미배정 면적을 자동으로 보여준다.** `zone 면적 − 유효 구획들의 합집합 면적`.

자원 배분에 필요한 것은 "합이 100%"가 아니라 "각자 몇 %이고 얼마가 남았나"이다.

### zone 을 못 찾으면 자르지 않는다 (구현 확정)

클리핑 기준 zone 은 ① 클라이언트가 보낸 `zone_uuid` ② 없으면 공간 포함으로 파생
순서로 정한다. **둘 다 실패하면 자르지 않고 그대로 저장한다.**

거부하지 않는 이유: zone 을 그리지 않은 밭이 실제로 많고, site 안이지만 어느 zone
에도 안 속하는 자리(통로·진입로 옆)도 정상이다. 여기서 막으면 그런 설치는 식생
기능을 아예 쓸 수 없다.

반대로 **zone 이 특정된 경우 그 밖은 400 으로 거부한다** — 사용자가 "이 구역에
넣겠다"고 말했는데 딴 데 저장되면 그것은 침묵 실패다.

> `zone_uuid` 로는 반드시 `feature.properties.shape_uuid`(= `GeoShape.unique_id`)를
> 보낼 것. `node_id` 는 클라이언트가 만든 값이라 저장된 도형에서는 둘이 다르고,
> node_id 를 보내면 서버가 그 도형을 찾지 못해 **클리핑 기준이 조용히 사라진다**
> (구현 중 실제로 밟았다 — `_selectedAreaShapeId` 가 같은 함정을 주석으로 남겨 뒀다).

### 종료일은 "마지막 재배일"이 아니라 "종료된 날"

`ended_on` 인 날부터 이미 활성이 아니다(`ended_on > 기준일`). `>=` 로 두면 "재배
종료"를 누른 사람이 화면에서 사라진 구획을 새로고침하면 다시 보게 된다 — 하루만
어긋나는 종류라 버그로 신고되기도 어렵다(구현 중 브라우저 검증에서 발견).

`GeoPlanting.is_active` 와 `active_plantings` 의 쿼리가 **같은 부등호**를 써야 한다.
이력 조회는 이 판정과 무관하게 전 기간을 보므로 종료 당일 기록이 사라지지 않는다.

### 겹침은 허용한다 (확정)

간작·혼작 — 고랑 사이에 다른 작물, 과수 아래 하부 작물 — 이 실제로 흔하다.
**동시 유효한 구획끼리 기하가 겹쳐도 막지 않는다.**

이 결정에는 따라오는 것이 셋 있다.

1. **면적 비율의 합이 100%를 넘을 수 있다.** UI 는 "합계"를 보여주지 않는다.
   각 구획의 면적/비율과 미배정 면적만 보여주고, 합산은 사람이 판단한다.
2. **미배정 면적은 반드시 합집합으로 계산한다.** 단순 합으로 빼면 겹친 만큼
   이중으로 빠져 미배정이 음수가 된다.
3. **클릭이 모호해진다.** 겹친 도형 클릭은 이 저장소가 이미 사고를 낸 자리다
   (겹친 도형 전량삭제 버그 → 단일 리졸버로 최상단 1개만). 식생 구획은 겹침이
   **정상**이라 그 상황이 상시화되므로, 클릭 시 **후보 목록을 띄워 고르게 한다.**
   삭제는 반드시 선택된 하나에만 적용한다.

## 센서 참조 계약 — 매달지 않는다

```python
# aot/aot_flask/geo/planting_context.py (신설)
def sensors_for_planting(planting_uuid):
    """구획이 참조할 센서. 저장하지 않고 매 호출 파생한다.

    반환: {'in_plot': [device_id…], 'from_zone': [device_id…], 'zone_uuid': str|None}
    """
```

- **1순위**: 구획 폴리곤 안의 장치 — `device_membership.device_ids_in_shape` 재사용
  (인자를 shape 행이 아니라 기하로 받도록 일반화만 하면 된다).
- **2순위**: 소속 zone 의 장치 — 구획 안에 센서가 없을 때. 노지 zone 의 센서는
  현실적으로 한두 개라 **이쪽이 기본 경로가 된다.**
- **저장하지 않는다.** 바인딩 행도 컬럼도 만들지 않는다.

### 폴백에서 하나를 고르는 기준 — 거리보다 **값을 주는가**가 먼저 (2026-09-04)

소비처는 zone 후보를 전부 싣지 않는다. 전부 실으면 한 구역에 든 구획들의 화면과
일지가 서로 같은 문서가 되기 때문에, **하나만** 골라 "구획 밖에서 왔다"는 표시
(`scope='nearest'` 배지·`sensor-from-zone:<m>` 단서)와 함께 낸다.

그 하나를 **거리만으로 고르면 안 된다.** 무응답 센서를 골라 놓으면 폴백은
성립했는데 화면은 그대로 비어, 사용자는 "옆에 센서가 있는데 왜 값이 없나"를
묻게 된다. 실측(김제 3-2 청자5호): 최근접 온습도계(35.8m)가 2026-08-31 이후
무응답인데 14m 더 먼 토양센서는 값을 내고 있었다. 같은 구역의 다른 구획은
최근접이 그 살아 있는 센서라 멀쩡했다 — 한 구획만 비는 이유가 정렬 하나였다.

기준은 화면과 일지가 **다르다**. 묻는 질문이 다르기 때문이다.

| | 판정 | 근거 |
|---|---|---|
| 구획 모달(지금) | 값을 주는 것 먼저, 그 안에서 최근접 | `routes_geo_plot._live_first` → `site_summary.live_device_ids` |
| 일지(기간) | 기간 끝자락 → 기간 전체 → 최근접 | `plot_journal._pick_with_data` |

일지에 "지금 살아 있는가"를 쓰면 **지나간 기간의 문서가 만들 때마다 달라진다.**
그래서 일지는 *그 기간에 값이 있었는가*로 판정하고, 끝자락(마지막 하루)을 먼저
본다 — 기간 중간에 끊긴 센서가 앞부분 자료만으로 통과하면 뒤쪽이 통째로 빈다.

양쪽 모두 **후보가 전부 비어도 최근접을 낸다.** 빈손으로 돌아서면 고장이 화면에서
사라지고, "이 센서로 봤는데 없었다"가 "아무것도 안 봤다"보다 낫다. 구획 안 센서가
값을 못 줄 때 목록에서 빼는 대신 `no_data` 를 남기는 것과 같은 태도다.

⚠ 일지의 기간은 **집계와 승인 게이트가 같은 값을 넘겨야 한다**
(`resolve_devices(..., period=)`). 게이트가 빼먹으면 다른 센서의 채널을 세고
통과한다.

### 여러 구획이 같은 센서값을 봐도 되는 이유

같은 25도라도 상추에는 높고 토마토에는 적정이다. 식생 구획은 **센서의 단위가 아니라
해석의 단위**다 — 값을 나누는 것이 아니라 값에 대한 판정 기준을 나눈다. 그래서
센서를 매달지 않아도 목적을 달성한다.

### ⚠ 절대 하지 말 것 — `_CONTAINER_TYPES` 에 넣기

[device_membership.py](../../aot/aot_flask/geo/device_membership.py) 의
`_CONTAINER_TYPES = ('site', 'zone')` 은 장치의 **소속** 판정 정본이고, 규칙은
"겹치면 zone 이 site 를 이긴다"이다. 여기에 식생 구획을 넣으면 식생이 zone 을
이기게 되어 **장치의 소속이 3개월마다 바뀌고, 작기가 끝나는 순간 그 밸브가
무소속이 된다.**

소속과 참조는 다른 축이다. 식생은 참조만 하고 소속 판정에 참여하지 않는다.

## 자원 배분 — v1 은 계산하지 않고 재료만 낸다

관수 밸브와의 관계는 **계층이 아니라 교차**다. `type='device'` 폴리곤(밸브 담당
범위)과 식생 구획은 일치하지 않는다 — 밸브 하나가 상추와 배추를 같이 적시고,
한 작물이 두 밸브에 걸치기도 한다. **두 레이어를 합치지 않는다.**

v1 이 내는 것은 여기까지다:

- 이 구획을 적시는 밸브 목록 (폴리곤 교차)
- 각 구획의 면적과 zone 대비 비율
- zone 의 미배정 면적 (합집합 기준)

**자동 자원 계산은 v1 범위 밖이다.** 겹친 영역에서 물은 물리적으로 공유되므로
작물별 요구량을 합산하면 틀린 숫자가 나온다. 규칙을 성급히 박는 대신 재료를 보여주고
사람이 판단하게 한다.

### 치수와 식재량 — 면적은 방향이 없다 (구현 확정, 2026-08-13)

실제로 나온 질문들이다: *"콩을 40cm 간격으로 8줄 심으려는데 공간이 충분할까"*,
*"두둑을 몇 줄이나 만들 수 있을까"*, *"모종을 얼마나 준비해야 할까"*.

전부 **방향이 있는 질문**인데 AI 에게 주던 공간 정보는 `area_m2` 스칼라 하나뿐이었다.
1837m² 가 40×46 인지 5×367 인지에 따라 답이 갈리는데, 그 구분이 없었다. 원인은
`_planting_brief` 가 `feature`(원본 좌표 수백 개)를 떼는 것이고 — **그 판단은 옳다.**
그래서 좌표를 되살리는 대신 계산된 요약을 얹는다.

- **`dimensions`** — 최소회전 외접사각형(`minimum_rotated_rectangle`)의 두 변.
  `width_m` 이 항상 짧은 변이다(줄은 긴 변을 따라 놓고 짧은 변을 가로질러 센다).
- **`capacity_estimate`** — `row_spacing_cm` + `plant_spacing_cm` 을 주면
  줄 수·그루 수·총 그루. **서버에서 센다.** `get_facility_capacity` 가 냉난방
  용량을 서버에서 계산하는 것과 같은 이유다 — LLM 에 암산을 맡기면 조용히 틀린다.
  `edge_margin_cm` 으로 가장자리 여백을 추가로 뺄 수 있다.

정한 것 셋:

1. **축 정렬 bounding box 가 아니라 최소회전 사각형.** 비스듬히 놓인 두둑을 축으로
   재면 10×50 이 30×45 로 부풀어, 폭에서 세는 줄 수가 세 배가 된다.
2. **미터 평면에서 사각형을 구한다.** 도(degree) 공간에서 구하면 위도 35°에서
   경도 1도가 위도 1도의 0.81배인 만큼 찌그러진 채로 최소화되어, 실제 최소 사각형이
   아닌 것이 나온다. 투영은 새 라이브러리를 들이지 않고 `facility_calc._ring_area_m2`
   와 **같은 근사**를 쓴다 — 같은 지도에서 면적과 치수가 다른 평면에서 재어지면
   `width × length` 와 `area_m2` 가 설명 없이 어긋난다.
3. **비사각형 경고를 반드시 실어 보낸다.** 외접사각형 면적이 실제 면적의 1.3배를
   넘으면 `shape_note` 가 붙고, 같은 문구가 `capacity_estimate.basis` 에도 들어간다
   (capacity 만 읽는 호출자에게도 닿아야 한다). 이것이 없으면 삼각형 밭에서 AI 가
   정확히 두 배로 세고, 그 숫자가 그대로 모종 주문량이 된다. 얼마나 깎을지는
   `rect_fill_pct`(구획이 사각형을 채우는 비율)로 판단하게 한다 — 삼각형(50%)과
   살짝 기운 사각형(95%)에 같은 말을 할 수는 없다.

**세는 방식: 한 그루가 간격 하나만큼의 칸을 차지한다** (`floor(폭 / 간격)`).

처음에는 울타리 기둥 세기(`구간 수 + 1`)로 셌다. 그것은 양 끝 줄이 경계선 **위에**
서 있다고 보는 계산이라 밭에서 성립하지 않는다 — 폭 4m 를 40cm 간격으로 나누면
기둥 세기는 11줄을 내지만 맨 바깥 두 줄이 경계에 걸려 있다. 칸으로 세면 10줄이고
양쪽에 20cm(간격의 절반)씩 자동으로 남는다. **가장자리 여백은 파라미터가 아니라
계산 방식 자체에서 나오는 것이 기본값**이어야 한다.

그 위에 `edge_margin_cm` 으로 **추가** 여백을 뺀다. 농기계 선회 공간이나 두둑 어깨는
미터 단위라 간격의 절반으로 감당되지 않는다. 기본값은 0 이고, 0 일 때 `basis` 는
"헤드랜드를 빼지 않았다" 고 명시한다 — 빼지 않은 것을 뺐다고 말하지 않는다.
`usable_width_m` / `usable_length_m` 을 같이 내어 어떤 폭에서 나눈 숫자인지 검산할 수
있게 한다. 여백이 밭을 다 먹으면 음수가 아니라 0 과 함께 "Nothing fits" 를 답한다.

간격을 한쪽만 주거나 여백만 주면 조용히 건너뛰지 않고 오류로 답한다 — 사용자가 말한
조건이 답에 반영되지 않은 것을 아무도 모르는 상태가 최악이다.

#### 두둑을 모르면 숫자를 내밀지 않는다

여기까지도 여전히 **밭 전체에 줄을 균일하게 깐다**고 보는 계산이다. 실제 노지 채소는
두둑 위에 심고 고랑에는 아무것도 안 심는다. 실측(상추 구획 폭 28.4m, 줄 간격 40cm):

| 배치 | 계산 | 줄 수 | 총 그루 |
|---|---|---|---|
| 균일 | 2840 ÷ 40 | 71 | 31,808 |
| 두둑 120 + 고랑 40 | 18두둑 × 3줄 | 54 | 24,192 |

**24% 과다추정**이다. 비사각형(삼각형 50%)을 그렇게 경고해놓고 정작 이쪽에서 더 자주,
더 크게 새고 있었다. 게다가 애초에 받은 질문 중 *"두둑을 몇 줄이나 만들 수 있을까"* 는
두둑 **개수**를 묻는 것인데 그 숫자를 낼 수단 자체가 없었다.

- `bed_pitch_cm` + `rows_per_bed` 를 주면 두둑 배치로 센다. `beds_possible` 을
  따로 내어 두둑 개수 질문에 바로 답한다.
- **간격은 고랑을 포함한 중심간 거리 하나로 받는다.** `row_spacing_cm` 은 평평한
  배치에서만 쓴다 — 두둑 배치에서는 두둑당 줄 수가 그 자리를 대신하므로,
  요구하면 쓰지도 않을 값을 묻는 셈이 된다.
- **규격을 모르면 응답에 `ask_user` 가 실린다.** 평평하게 깐 값을 계산해 주기는
  하되, "묻거나 제안해서 확정한 뒤 다시 부르라" 고 시킨다. 규격을 서버가 정해
  내려보내지 않는 이유는 작물·지역·농기계 폭에 따라 달라 아는 척할 수 있는 값이
  아니기 때문이다 — 정하는 것은 사람이고, 도구는 그 자리를 비워둔 채 넘어가지
  않도록 막는 역할만 한다.

`layout` 필드가 `'flat'` / `'beds'` 로 어느 쪽으로 센 값인지 말한다.

#### ✗ 폐기: 두둑 폭 + 고랑 폭을 따로 받기

처음에는 `bed_width_cm` + `path_width_cm` 두 개를 받았다. **사용자에게 이상하게
들리는 질문이었다** — 농부는 두둑과 고랑을 따로 세지 않는다. 두둑을 만들면 고랑은
딸려 온다. 그래서 "두둑 폭" 을 물으면 고랑을 뺀 윗면으로 답하는 사람과 고랑까지
포함한 한 세트로 답하는 사람이 갈리고, **같은 밭이 120+40 으로도 160+0 으로도
기록된다.** 에러는 나지 않고 두둑 수만 달라진다.

일본어 `畝幅` 에서 같은 모호함이 먼저 눈에 띄었지만 한국어에도 똑같이 있었다 —
번역 문제로 좁혀 본 것이 오진이었다.

#### ✗ 폐기: 두둑 배치를 컬럼으로 저장하기 (P6-35 → P6-36 에서 제거)

`geo_planting.bed_width_cm` / `path_width_cm` 컬럼과 지도 폼 입력·ko/ja 라벨을
만들었고 **26.08.5 로 출시까지 됐다가** `p6_36` 에서 걷어냈다. 이유는 둘이다.

1. **모호한 사람의 말이 정수 칸에 들어가지 않는다.** 컬럼은 "어느 쪽 의미로
   적었는지" 를 담지 못한다(위 절).
2. **대화에서 나오는 결론마다 컬럼을 늘릴 수는 없다.** 두둑 배치는 시작일 뿐이고
   멀칭 여부·지주 방식·관수 관행·품종별 습관이 뒤따른다. 그것을 전부 정량화해
   스키마에 담는 것이 어렵기 때문에 **노트가 존재한다.**

대신 확정된 배치는 **구획 노트**로 남긴다(`create_note(target_type='planting')`).
엔티티별 노트 다이제스트가 이미 AI 컨텍스트에 미리 실리므로, 다음 대화는 그 문장을
읽고 숫자만 조회 파라미터로 넘긴다. 계산은 여전히 서버가 한다.

`p6_36` 은 **값이 있는 행을 노트로 옮긴 뒤** 컬럼을 지운다. 출시 후 하루라 실제
입력본은 거의 없겠지만, 사람이 확인해 적은 사실을 스키마 결정 때문에 없애는 것은
다른 문제다. 옮긴 노트는 두 값을 그대로 적고 "두둑 간격으로 세려면 더하라" 는
말을 붙인다 — 서버가 어느 쪽 의미였는지 모르므로 변환하지 않는다.

> ⚠ 그 통로가 실제로 열려 있어야 한다. `get_note_digests` 의 이름 해석기가
> `GeoShape`/`Input`/`Output`/`Function` 만 훑고 있어 **구획에 노트를 붙여도 이름이
> 풀리지 않았다**(같은 커밋에서 `GeoPlanting` 을 등록해 고쳤다). 여기가 비면
> "적어 두라" 는 지시 자체가 헛돈다 — 회귀로 고정해 둔 이유다.

#### AI 문구에 나라를 박지 않는다

`ask_user` 첫 판은 *"Most **Korean** open-field vegetables…"* 로 시작했다. 이 제품은
ko/ja 를 함께 쓰고 설치처의 나라도 고정이 아니라, 다른 지역 사용자에게는 틀린 근거가
된다. 두둑 농사 자체는 어디서나 흔하므로 나라 이름 없이도 같은 말이 된다. 화면 문구
(`Bed layout` / `Bed width (cm)` / `Furrow width (cm)` / `Not known`)는 번역 함수를
거치고 ko·ja 카탈로그에 함께 넣는다 — 셋 다 회귀로 고정한다(문구에 나라 이름이 없을
것, 두 카탈로그에 번역이 있을 것, `.mo` 가 `.po` 보다 오래되지 않았을 것).

## 만료 표시 — 슬라이더는 뒤로 미룬다 (확정)

- **지도 기본 렌더**: `ended_on IS NULL OR ended_on >= 오늘` 인 구획만.
- **이력 조회**: 구획(또는 zone) 을 클릭하면 **"이 자리 이력"** 목록 — 공간 교차로
  과거 작기를 뽑는다. 지도 레이어가 아니라 모달 목록이다.
- **시점 슬라이더는 별개 작업으로 미룬다.** 지도 전체를 과거 시점으로 되돌리는 것은
  식생만의 문제가 아니라 지도 전 레이어의 문제라 범위가 다르다.

이력 목록만으로 연작 장해·윤작이라는 핵심 가치는 나온다. 슬라이더는 그 위의 편의다.

## 시설 구획 — 위치의 정본은 기하가 아니라 **부모**다 (구현 확정, 2026-08-18)

온실에서는 기하를 새로 그리지 않고 **구역을 골라 작기를 만든다.** 처음에는 bay
기하를 스냅샷으로 복사하는 방식을 전제했지만(아래 백필이 그 방식이다), 새로 만드는
구획은 **기하 없이 부모 참조만으로** 성립한다(`p6_39`).

노지와 시설은 무엇이 고정인지가 반대이기 때문이다.

| | 노지 두둑 | 시설 구획 |
|---|---|---|
| 물리적으로 고정된 것 | 없다 — 갈아엎으면 위치가 바뀐다 | 동·구역이 구조물로 존재한다 |
| 사람이 부르는 방식 | "저 아래 밭" (그려야 안다) | **"3동"** |
| 정본 | **기하** (소속은 공간 포함으로 파생) | **부모 참조** (기하는 시설에서 파생) |

**VP-5("소속을 컬럼으로 저장하지 않는다")와 충돌하지 않는다.** VP-5 의 근거는
"**파생 가능하니까** 물질화하지 않는다" 였다. 기하를 그리지 않는 시설 구획은 소속을
파생할 근거 자체가 없으므로 그 전제가 성립하지 않는다 — 예외가 아니라 조건이 다른
경우다. 그래서 `facility_uuid` + `bay_id` 를 컬럼으로 둔다.

**`source_ref` 파싱으로 대신하지 않는다.** `'<facility>:<bay_id>'` 를 소속의 정본으로
승격시키면 `unique_id = 'uuid::채널'` 과 같은 문자열 파싱 계약이 하나 더 생긴다.
`source_*` 는 원래 뜻인 **출처 기록**으로 둔다.

**단동(`bay_count=1`)은 저장 시 `bay_id='bay_1'` 로 자동으로 채운다.** 구역이 하나라
사람이 고를 것이 없고, NULL 로 두면 "시설 전체"와 "구역 1"이 같은 대상을 두 가지로
표현하게 된다. 다동에서 NULL 은 "시설 전체" 라는 뜻으로 살아 있다.
**구역 id 는 클라이언트 말을 믿지 않는다** — `compute_bay_slices()` 의 실제 목록과
대조한다(geo_binding 에서 프런트의 `aot_type` 을 믿었다가 구역 배정이 마커 배정으로
저장된 것과 같은 계열).

### 구역 기하는 편집기와 **같은 규칙**으로 파생한다 (구현 확정, 2026-08-18)

지도에 그리고 클릭하려면 좌표가 있어야 하므로 `facility_bays.slice_geometry()` 가
구역의 자리를 만든다. 재료는 전부 `geometry_3d` 에 있다 —
`center_lng`/`center_lat`/`orientation_deg`/`span_width_m`/`length_m`/`spacing_m`.

- **`aot-facility-design.js` 의 `rotatedRectRing` 과 같은 계산이어야 한다**
  (상수 111320 까지 같은 값을 쓴다). 여기서 더 정확한 측지 공식을 쓰면 편집기가
  그린 외피와 구역이 미세하게 어긋나 "구역이 시설 밖으로 삐져나온" 것처럼 보인다.
- **분리동은 MultiPolygon 이다.** 동 사이가 실제로 비어 있는데 하나의 사각형으로
  덮으면 건물이 아닌 땅까지 그 구역인 것처럼 보인다.
- **재료가 없으면 `None` 을 돌려준다**(지도에 아직 배치되지 않은 시설). 호출부가
  시설 외피로 폴백한다 — 좌표를 지어내지 않는다. 엉뚱한 자리에 그리면 사람은
  그것을 측량 결과로 읽는다.
- 구역 기하·이름은 시설 하나당 한 번만 계산해 `facility_brief` 캐시에 담는다
  (`bay_geometries` · `bay_names`). 구획마다 다시 만들면 같은 삼각함수를 행 수만큼 돈다.

### 읽기는 `geometry_of` 한 곳에서 봉합한다

기하 정본(노지)과 부모 정본(시설)이 한 테이블에 살면 "읽는 경로마다 기준이 다름"이
재발할 수 있다. 막는 것은 규율이 아니라 **단일 진입점**이다 —
`planting_context.geometry_of()` 가 이미 `area_m2` · `dimensions` ·
`sensors_for_planting` · `zone_for_planting` · `valves_for_planting` 의 목이므로,
거기에 시설 기하 폴백을 한 번 넣으면 나머지가 따라온다.
**새 읽기 경로에서 `row.feature` 를 직접 파지 말 것** — 그 자리에서 시설 구획만
조용히 빠진다.

파생 기하는 **응답에만** 싣는다(`derived_feature`). `feature` 에 넣으면 클라이언트가
그대로 되돌려 저장했을 때 파생이 정본으로 승격해, 시설을 옮겨도 구획은 옛 자리에
남는다(색 각인 sync-back 이 만든 것과 같은 고정).

### 면적·치수·식재량을 내지 않는다

두 가지가 겹친다.

1. **같은 구역에 여러 작물이 섞이는 것이 정상이다.** 그것을 면적으로 가르려면 사람이
   두둑 경계를 그려야 하는데, 온실에서 그 노동은 값에 비해 비싸다. "3동에 토마토와
   바질" 까지만 알면 센서도 제어도 그 구역 단위로 공유되므로 판단에 부족하지 않다.
2. **시설은 형태에 따라 면적이 생산 단위가 아니다.** 같은 100㎡ 라도 노지형(땅에 심고
   온실만 씌운 것)·베드형·수직형의 재배 규모가 전혀 다르고, 세는 단위 자체가 갈린다
   (두둑 수 / 베드 줄 수·길이 / 층수·트레이 수). 면적에 재식거리를 곱하는 노지식
   추정을 시설에 쓰면 **형태에 따라 몇 배씩 틀린 숫자가 나오는데, 틀렸다는 표시가
   어디에도 없다.**

그래서 `area_m2` 는 `None`(0 이 아니다 — 0 은 "면적이 없다"는 거짓말이다), `dims` ·
`valves` · `capacity_estimate` 는 싣지 않고, `zone_allocation` 배분에서도 제외한다.
**`_planting_brief`(AI 경로)는 `dimensions`/`capacity_estimate` 를 직접 부르므로
`to_dict` 의 방어를 우회한다** — 거기에도 같은 분기가 있어야 한다.

규모를 적는 자리는 스키마가 아니라 **구획 노트**다(`p6_36` 이 배치 컬럼을 걷어낸 것과
같은 이유 — 모호한 사람의 말이 정수 칸에 들어가지 않고, 대화에서 나오는 결론마다
컬럼을 늘릴 수는 없다). "베드 12줄 × 30m, 3단" 은 노트 한 줄이면 되고, 노트
다이제스트가 AI 컨텍스트에 실린다. **여기서 컬럼을 늘리기 시작하면 시설 형태 수만큼
늘어난다.**

### 센서는 마커가 아니라 fitting 에서 찾는다

시설 센서는 `facility.fittings[]` 에 로컬 미터 좌표로 붙어 있고 **지도 마커가 아니다.**
그래서 `device_ids_in_geometry`(마커만 본다)로는 하나도 잡히지 않는다 — 이것이 온실 안
구획이 시설 **밖** zone 센서로 폴백하던 원인이다. 폴백 순서를 확장한다:

```
in_plot(기하 있는 구획만) → in_bay(부모 구역의 fitting 센서)
                          → from_facility(시설 전체) → from_zone
```

`source` 어휘는 `'plot' | 'bay' | 'facility' | 'zone' | 'none'`. 부모 참조가 구역 id 를
이미 들고 있으므로 **기하 겹침 계산이 필요 없다**(`build_fitting_bay_map` 이 로컬 x
좌표로 귀속한다). 시설 구획은 마커 판정을 아예 건너뛴다 — 파생 기하가 시설 외피라,
그것으로 폴리곤 안 마커를 세면 시설 어딘가의 장치가 전부 이 구획의 것이 된다.

### 위젯 표시 (구현 확정, 2026-08-18)

- 지도 위젯은 `p.feature.geometry` 가 없으면 **`derived_feature`** 로 폴백한다
  (`aot-map-plot.js` 의 `_geomOf`). 폴리곤과 라벨이 **같은 접근자**를 쓴다 —
  한쪽만 고치면 "폴리곤은 뜨는데 이름이 없는" 상태가 된다.
- **파생을 저장 쪽으로 되돌리지 않는다.** 라벨 위치 저장(`label_lnglat`)은 자기
  기하가 있는 구획에만 해당한다.
- 시설 구획의 작물 칩은 구역 중심에서 **아래로 비켜 놓는다**. 구역 칩
  (`aot-map-bay`)이 이미 중심에 있어 그대로 두면 둘이 포개져 둘 다 못 읽는다.
- 구획 모달은 면적 대신 **"어디"** 를 말한다(`시설 · 구역`) + 면적을 내지 않는
  이유 한 줄. 값이 그냥 비어 있으면 사람은 "아직 계산 안 됐나" 로 읽는다.
- **geo/design 은 시설 구획을 그리지 않는다.** 기하가 없어서가 아니라 그 페이지가
  *도형을 만들고 고치는 곳*이기 때문이다 — 편집할 수 없는 것을 편집기에 그려 놓으면
  사람은 그것을 옮기거나 지우려 한다.

### 제어 축과 만나는 지점 (구현 확정, 2026-08-19)

**식생 → 제어**: `planting_context.facility_control_for_planting()` 이 구획을 맡는
코디네이터·액추에이터를 낸다. 노지의 `valves_for_planting()`(지도 도형과의 면적
교차)이 시설 안에서는 통하지 않기 때문이다 — 창호·팬은 지도 도형이 아니라
`fittings[]` 에 로컬 좌표로 붙어 있고, 환경 제어는 밸브 하나가 아니라 코디네이터가 한다.

- **`bay_scope` 가 같은 것과 시설 전체를 둘 다 낸다.** 구역 전담이 있어도 시설
  전체 코디네이터가 함께 도는 구성이 정상이고, 한쪽만 보이면 사람은 "왜 내 설정이
  안 먹지" 를 설명할 근거를 잃는다. 어느 쪽인지는 `scope` 가 말한다.
- **시설 전체 구획을 구역 전담 코디네이터가 대표할 수는 없다** — 그 경우는 뺀다.
- **읽기 전용이다.** 제어를 걸지 않는다(관수량을 계산하지 않는 것과 같은 결).
  회귀 테스트가 이 함수에 `DaemonControl`·`set_output`·`db.session.commit` 이
  들어오는 것을 막는다.
- 구획 모달의 [환경·제어]는 시설 구획일 때 **기하 경로를 타지 않는다**
  (`_build_facility_planting_contents`). 파생 기하로 마커를 세면 시설 어딘가의
  장치가 전부 이 구획의 것으로 잡힌다.

**제어 → 식생**: `plantings_in_facility()` 가 시설 런타임(`/runtime`)과 AI 의
`list_env_coordinators` 에 "지금 무엇이 며칠째" 를 싣고, **시설(구역) 모달의
[현황]이 그것을 그린다**(`buildFacilityPlantingsHtml` + `_appendFacilityPlantings`).
줄을 누르면 그 구획 모달로 내려가 거기서 고친다. 구역 뷰는 그 구역 것과 **구역이
지정되지 않은 것**(시설 전체)을 함께 내고, 후자에는 "시설 전체" 라고 밝힌다 —
안 밝히면 이 구역 전용으로 읽힌다.

**위젯에서 새로 심을 수 있어야 한다.** 시설 구획은 기하를 그리지 않으므로 구역을
고르고 작물을 적는 것이 전부이고, 그 일은 시설 모달에서 된다(`여기에 심기`). 이것이
없으면 구획이 하나도 없는 시설은 위젯에서 손댈 것이 **아무것도 없고**, 시설
편집기(geo/facility)까지 갈 수 있는 계정만 온실 식생을 관리하게 된다 — 지도만 쓰는
사람에게는 기능이 없는 것과 같다. 그래서 **비어 있어도 쓰기 권한이 있으면 블록을
낸다**(권한이 없으면 종전대로 생략 — 창고·기계고에 빈 칸이 매번 뜨지 않게).
권한 축은 시설 [현황]과 같은 `edit_settings` 다. 버튼이 보이는데 저장이 403 이면
그게 더 나쁘다.

⚠ **[현황]은 폴링 주기마다(위젯 설정, 기본 5초) 다시 그려진다.** 그때 값이 하나도
안 바뀌었는데 DOM 을 갈아끼우면 모달이 **계속 깜빡인다.** 네 자리(본문·환경·식생·기록)
모두 "같으면 손대지 않는다" 로 두어야 한다. 실측(2026-08-19): 44초에 DOM 변경 15건 이상
→ 0건(변화가 있을 때만 2건).

여기에 함정이 둘 있다.

- **문자열 HTML 과 DOM 의 `outerHTML` 을 직접 비교하면 안 된다.** 브라우저가 파싱하며
  속성 순서·따옴표·`style` 표기를 정규화하므로(`display:none` → `display: none;`)
  내용이 같아도 항상 다르다 — 비교를 넣어도 깜빡임이 그대로다. 양쪽 다 파싱한 뒤
  비교한다(`_parseNode`).
- **비동기로 채워지는 부분은 비교에서 빼야 한다.** 노트 목록은 `buildRecordBlock` 이
  '…' 로 두고 나중에 채우므로, 그대로 비교하면 폴링마다 교체 → 노트 재로딩 → 다시
  교체가 무한히 돈다. 지금 화면의 노트를 새 노드에 옮겨 심고 비교한다.

⚠ **[현황]이 그대로면 배선도 다시 붙이지 않는다.** 노트 배선을 다시 붙이면 목록을
되쓰면서 또 깜빡이고 클릭 리스너가 겹친다. 공용 노트 블록도 캐시를 되쓸 때 같은 내용이면
건너뛴다(`sensor-label.js`).

⚠ **작성 중인 폼은 갱신에서 제외한다.** 작성 중인 폼이 열려 있으면 갱신을
건너뛴다(`_plantEditing`). 이 잠금이 없으면 폼을 열자마자 사라져 **"버튼이 안
먹는다"** 로 보인다(실제로 그렇게 한 번 만들었다). 설명 편집의 `_ovEditing` 과 따로
두는 이유는 둘이 동시에 열릴 수 있고, 한쪽을 닫을 때 다른 쪽 보호까지 풀리면 안 되기
때문이다. 팝업을 닫을 때 잠금도 함께 푼다 — 아니면 다음에 열었을 때 갱신이 멈춰 있다.

⚠ **응답에 싣는 것과 화면에 그리는 것은 다른 일이다.** 런타임에 `plantings` 를
넣고도 위젯을 건드리지 않아 화면에는 아무것도 없던 적이 있다(2026-08-19). 서버만
보고 "구현했다" 고 판단하지 말 것 — 회귀 테스트가 위젯 쪽 배선까지 함께 본다. 설정값을 보는 화면이
그것을 말할 수 있어야 값의 근거가 생긴다 — 같은 25도가 상추에는 높고 토마토에는
적정이다. **구역이 지정되지 않은 구획(시설 전체)은 어느 구역 뷰에서도 함께 보인다.**
런타임은 폴링 응답이라 이 조회가 실패해도 조용히 비운다(3D 위젯이 멈추면 안 된다).

### 구역 구성이 바뀔 때 (구현 확정, 2026-08-19)

`bay_count` 를 줄이거나 구역을 병합하면 그 구역을 가리키던 활성 구획이 갈 곳을
잃는다. **막지 않는다** — 온실 구조를 바꾸는 것은 정당한 작업이고, 막으면 구획을
먼저 지우는 길밖에 없다. 대신 세 겹으로 드러낸다.

| 층 | 무엇 | 시점 |
|----|------|------|
| 1 | 저장 전 확인(`plannedBayIds` + `FacilityPlantingUI.orphansFor`) | 사람이 결정 |
| 2 | 저장 응답의 `orphaned_plantings` + 서버 경고 로그 | 사실의 정본 |
| 3 | `check_geo_integrity` 의 `planting-unknown-bay` | 나중에라도 |

**층 1 은 서버 규칙을 그대로 따라야 한다.** 구역 편집기 상태(`bays`)와 동 수
입력(`bay_count`)은 서로 다른 위젯이라 **어긋난 순간이 실재한다.** 동 수를 2→1 로
줄인 직후 편집기가 아직 `bay_1_2` 를 들고 있으면, 그 목록을 그대로 믿는 판정은
"사라지는 구역 없음" 으로 결론짓고 경고 없이 저장한다 — 서버는 `bay_count` 로 다시
자르므로 실제로는 그 구역이 사라진다. **2026-08-19 검증 중 실제로 그렇게 저장돼
구획 하나가 갈 곳을 잃었고, 남은 것은 서버 경고 로그 한 줄뿐이었다.** 그래서
미리보기도 서버와 같은 두 단계를 밟는다: `bay_end <= bay_count` 로 거르고, 남는
것이 없으면 bay 당 1구역으로 합성한다.

**층 2 의 판정은 저장된 시설을 기준으로 한다** — 페이로드가 아니다. 부분 저장에서
"페이로드에 없는 것 = 없앤 것" 으로 읽으면 멀쩡한 구역이 사라진 것으로 잡힌다
(`sync_facility_bindings` 가 같은 이유로 저장된 facility 를 본다). 구역 목록을 만들
수 없는 시설(치수 미입력)에서는 **판정하지 않는다** — 근거 없이 경고하면 멀쩡한
구획이 매 저장마다 경고로 뜬다.

### 모달에서 고치는 것 — 노지와 같은 자리 (구현 확정, 2026-08-19)

지도 위젯의 구획 모달은 작물·품종·이름·기간·색을 그 자리에서 고친다. 그 배선은
종류를 가리지 않으므로(기하를 보내지 않는다) 시설 구획도 그대로 동작한다.
**다만 위치를 고치는 수단이 달라야 한다** — 노지는 도형을 옮겨 자리를 바꾸지만
(그 편집은 geo/design 이다), 시설 구획의 위치는 `bay_id` 라 옮기는 일이 곧 **고르는
일**이다. 그래서 편집 폼에 구역 선택을 둔다(`facility_bays` 가 선택지를 싣는다).
없으면 온실 구획만 위치를 못 고쳐 시설 편집기까지 다녀와야 한다.

- 빈 선택은 **"시설 전체"** 다(다동에서만 의미가 있다).
- 종료된 작기의 이동은 서버가 거부한다(VP-6) — 위치가 바뀌면 "작년에 여기 뭐가
  있었나" 의 답이 달라지는 것은 부모 참조에서도 같다.
- 위치 블록은 **시설과 구역을 두 행으로** 낸다. "온실1 · 3동" 처럼 이어붙이면 한
  열에 두 정보가 들어가고, 블록 제목과 행 라벨이 같은 말이 되면("위치/위치")
  사용자는 그것을 오류로 읽는다.

### 대가 (알고 받아들인 것)

1. **구역 구성을 바꾸면 과거 구획의 참조가 흔들린다.** `bay_count` 나 구역 병합을
   바꾸면 `bay_id` 가 같은 물리 공간을 안 가리킬 수 있다(위 3층으로 드러낸다).
2. **한 구역 안 여러 구획은 위치로 구분되지 않는다.** 이름·작물명으로만 갈린다 —
   의도한 것이다. 세부가 필요하면 그때만 기하를 그린다(그린 구획은 노지와 똑같이 동작).
3. **정본이 두 종류다.** `geometry_of` 단일 접근자가 유일한 방어다.

### 옛 방식 — bay 기하 스냅샷 (백필 전용)

`bays[].crop` 백필분은 여전히 기하를 복사해 온다(`source_kind='bay_snapshot'`).
**참조로 붙이지 않는 이유는 그대로다** — 나중에 `bay_count` 를 바꾸면 bay 기하가
재계산되는데, 과거 작기가 그것을 따라가면 이력이 거짓말이 된다. 그 방식으로 들어온
행은 `facility_uuid` 가 없으므로, **"시설 구획인가" 를 판별할 때 두 축을 모두 봐야
한다**(`facility_uuid` 있음 **또는** `source_kind='bay_snapshot'`). 한쪽만 보면
나머지 절반이 조용히 노지로 분류된다 — `get_crop_status` 가 실제로 그랬다.

전환 순서 (`geo_binding` Phase C-4 와 같은 패턴):

1. `GeoPlanting` 도입, `get_crop_status` 를 **GeoPlanting 우선 → `bays[].crop` 폴백** 으로.
2. 운영 서버 배포 + 기존 `bays[].crop` 백필.
3. 폴백 사용 로그가 0 인 것을 확인한 뒤 `bays[].crop` 제거.

**2 를 건너뛰고 3 을 하면** 백필이 돌지 않은 서버의 작물 정보가 즉시 사라진다.

## 이름 해석 — 관리인은 '3-1' 이 아니라 '콩밭' 이라 부른다 (구현 확정, 2026-08-13)

현장 사람은 구역을 **지도 이름이 아니라 거기 자라는 것**으로 부른다. 그런데
`AoTDataToolService._resolve_note_target()` 은 GeoShape 이름만 훑었고, 그래서
`resolve_target('콩밭')` 이 `needs_disambiguation` 과 함께 `['1포장','3-1',…]` 를
내놓았다 — 지도 이름을 모르는 사람에게는 답할 수 없는 되물음이다.

그 리졸버의 **마지막 단계**로 작물명 폴백을 둔다(`_resolve_target_by_crop`).
앞선 4단계(정확일치 → 계층 토큰 → 부분문자열 → 장치명)를 전부 지나온 뒤에만
돌므로, 정식 이름이 있는 구역은 이 폴백에 도달하지 않는다.

세 가지가 이 폴백의 성격을 정한다:

- **활성 구획만 본다.** 작년 배추가 올해 노트를 끌고 가면 안 된다.
- **구획이 아니라 zone 을 돌려준다.** 이 리졸버의 소비처(`add_schedule`·
  `create_note`·`schedule_device_control`)는 전부 GeoShape 에 쓴다. `GeoPlanting`
  은 쓰기 대상이 아니고(3개월 뒤 사라진다), zone 은 `zone_for_planting` 으로
  파생한다 — 여기서도 소속은 저장하지 않는다. zone 밖 구획은 매치 없음이다.
- **애매하면 매치하지 않는다.** 같은 작물이 두 구역에 있으면 `None` 이다.
  5-튜플 계약에 "모호함"을 담을 자리가 없는데다, 이것은 **쓰기 도구가 함께 쓰는
  리졸버**다 — 둘 중 하나를 골라버리면 엉뚱한 밭에 조용히 기록이 남는다. 대신
  `resolve_target` 의 실패 응답에 `crop_targets`(작물 → zone)를 실어 되물을 수
  있게 한다.

접미사 제거('콩밭'→'콩', '상추 재배지'→'상추')는 작물명 정확일치가 실패한 뒤의
보조 수단이다. `포장`·`구역` 도 목록에 있지만 여기서는 무해하다 — 실재하는
'3포장' 은 1단계에서 이미 잡혀 이 코드에 오지 않는다.

부분일치는 양쪽 모두 두 글자 이상일 때만 허용한다. 한 글자 작물명('마')은
어지간한 낱말 안에 다 들어 있어('고구마') 그대로 두면 오매치가 기본값이 된다.

## 불변식 (VP-n)

| | 내용 | 강제 위치 |
|---|---|---|
| VP-1 | 기하는 `Polygon` \| `MultiPolygon` 만. Point/LineString 금지 | 저장 검증 + 검사 |
| VP-2 | `ended_on >= planted_on` | 저장 검증 + 검사 |
| VP-3 | **겹침에 제약을 걸지 않는다** (유니크 인덱스 금지) | 문서 — 아래 주 참조 |
| VP-4 | `feature.properties` 에 device_id/channel_id/색 사본 금지 | 저장 시 제거 + 검사 |
| VP-5 | zone 소속을 컬럼으로 저장하지 않는다 | 스키마 |
| VP-6 | 종료된 작기(`ended_on` 있음)의 **기하·소속은 수정 불가** | 저장 검증 |
| VP-7 | `feature`(기하)와 `facility_uuid` 중 **적어도 하나**는 있어야 한다 | 저장 검증 + 검사 |

VP-3 을 불변식으로 적는 이유: "겹치면 안 될 것 같다"는 직관이 나중에 유니크 인덱스나
검증 규칙으로 들어오기 쉽다. **겹침은 버그가 아니라 요구사항**이라는 것을 명시적으로
남긴다.

VP-6 은 이력 보호다. 날짜 정정·이름 변경·삭제(오기입)는 허용하되, 기하가 바뀌면
"작년에 여기 뭐가 있었나"의 답이 조용히 달라진다. **시설 구획에서는 `bay_id` 가 곧
위치**이므로 소속 변경도 같은 이유로 막는다.

VP-7 은 "어디에도 없는 구획"을 막는다. 기하도 부모도 없으면 지도에 그려지지 않고 어떤
소속 판정에도 걸리지 않는데, 목록에는 계속 보인다.

### 무결성 검사

`check_geo_integrity` 에 6종을 추가한다 — `planting-bad-geometry`(VP-1) ·
`planting-bad-dates`(VP-2) · `planting-embedded-ref`(VP-4) · `planting-phantom-map`
(존재하지 않는 `geo_id`) · `planting-no-location`(VP-7) ·
`planting-dangling-facility`(실존하지 않는 시설 참조).

**기하가 없는 것 자체는 위반이 아니다** — 시설 구획에서는 정상이다. VP-1 은 기하가
**있을 때만** 본다. 여기서 거르지 않으면 정상 시설 구획이 전부 위반으로 올라와 진짜
위반이 그 안에 묻힌다.

**`HEADINGS` 에 넣으면 출력 루프가 따라온다.** 예전에는 출력 키 목록이 따로 하드코딩돼
있어 검사를 추가해도 집계에만 잡히고 화면에 안 나왔다.

요구량을 합산하면 틀린 숫자가 나온다. 재료(밸브·겹친 면적·비율)만 내고 판단은
사람이 한다. 테스트가 `water_l`·`liters` 같은 키가 생기지 않는 것을 고정한다.

**남은 것**: zone 면적 배분 표시(`zone_allocation` 은 서버에 있으나 화면에 붙일
자리를 아직 정하지 않았다 — geo/design 은 도형만 다루고, 위젯 구획 모달은 구획
하나가 단위라 zone 전체 배분과 결이 다르다).

### 구역 분할 — `orientation` 은 `parts` 등분에서만 뒤집는다 (구현 확정, 2026-08-14)

`planting_split.split_shape()`(`aot_flask/geo/planting_split.py`)는 zone/site 도형을
`propose_planting_split`/`apply_planting_split` 로 조각내는 순수 기하 계산이다. 처음엔
방향이 항상 **최소회전 외접사각형의 긴 변**이었다 — 노지 두둑은 실제로 밭의 긴 방향을
따라 놓이므로(고랑 = 배수·농기계 작업 방향) 그 자체는 맞는 기본값이다.

문제는 이 정책이 `strip_width_cm`(두둑 폭 지정)과 `parts`(단순 N등분) 두 경로에
**똑같이** 걸려 있었다는 것이다. 실사용에서 걸렸다: 2,618.6㎡ 구역을 `parts=5` 로
나눴더니 6.43m × 81.7m 짜리 띠 5개(비율 12.7:1)가 나왔다. `parts` 는 "이 구역에 작물
5개를 나눠 심겠다"는 뜻일 뿐 두둑·고랑 개념이 없다 — 그런데 긴 변을 강제로 따르니
관리하기 불편한 가늘고 긴 모양만 나올 수 있었다("누가 이렇게 가늘고 긴 밭을
선호하냐").

**두 경로가 서로 다른 이유로 서로 다른 결론에 도달한다:**

- **`strip_width_cm`(두둑)** — 고랑 방향이 실제 작업 방향과 일치해야 하므로 긴 변
  기준이 맞다. **건드리지 않는다.**
- **`parts`(등분)** — 두둑 개념이 없다. 오히려 정방형에 가까울수록 관리(밸브 배치,
  접근성, 시각적 구분)가 편하다.

**채택한 안**: `orientation='long'|'short'` 파라미터를 `split_shape()` 에 추가한다.
당시 기본값은 `'long'`(기존 동작과 동일) 이었고, `'short'` 를 주면 짧은 변을 눕혀 그
반대쪽을 등분한다 — 위 사례라면 16.4m × 32m(비율 2:1)가 된다. 최소회전 사각형의 두
변은 서로 수직이므로 구현은 긴 변 각도에 90도를 더하는 것 하나다(`_longest_edge_angle()`
재사용, 새 기하 계산 불필요) — `strips`/`length_m`/`area_m2` 응답 계약은 그대로다.

> **갱신(2026-08-16)**: "파라미터를 주지 않으면 `'long'`" 이던 기본값을 모드별로
> 갈랐다 — 아래 "`orientation` 기본값을 모드별로 분기" 절 참조. 이 절의 나머지
> 내용(두 경로가 왜 다른 결론에 도달하는지, 종횡비 경고, 격자 분할을 기각한 이유)은
> 그대로 유효하다.

**기각한 안**: 격자 분할(rows × cols)로 항상 정방형에 가깝게 만드는 안. `parts=5`,
`7` 처럼 소수인 경우 격자 조합이 `1×N` 밖에 없어 예외 처리가 필요하고, 기존 "조각
하나 = strips 리스트 한 행" 계약을 깨거나 별도 분기를 요구한다. `orientation` 두
값이면 실사용 사례를 충분히 덮으면서 계약을 그대로 유지할 수 있어 이쪽을 택했다.

**종횡비 경고**: `orientation` 을 굳이 켜지 않아도 사람이 알아챌 수 있도록,
`parts` 등분에서 조각 종횡비가 4:1 을 넘으면 `info['aspect_ratio']` 와 `note` 에
`orientation='short'` 를 써 보라는 문구가 붙는다. `strip_width_cm` 는 원래 가늘고
긴 것이 정상 설계라 이 경고 대상이 아니다(`aspect_ratio` 는 `null`).

지도 UI(`geo/design` 식생 모드, `aot-geo-plot.js`)의 분할 폼에는 "방향" 선택이
`parts`(등분) 모드에서만 보이고 `strip_width_cm`(띠 폭) 모드로 바꾸면 숨겨지며 값도
`'long'` 으로 되돌아간다 — 의미 없는 조합을 화면에서부터 없앤다.

### 구역 분할 — `angle_deg` 로 임의 각도 지정, 지도 위 기준선 회전 (구현 확정, 2026-08-14)

`orientation='long'|'short'` 두 프리셋만으로는 부족한 경우가 실사용에서 나왔다 —
농부가 원하는 두둑 방향이 밭의 긴 변도 짧은 변도 아닌 경우다(예: 인접 필지의 기존
두둑과 줄을 맞추고 싶을 때). 각도를 자유롭게 줄 방법이 없어 이번에 추가했다.

**서버**: `split_shape()` 에 `angle_deg`(0≤값<180) 파라미터를 추가했다. 주어지면
`_longest_edge_angle()`/`orientation` 계산을 건너뛰고 그 각도를 그대로 조각
elongation 축으로 쓴다 — 회전 원점(`rect.centroid`)과 이후 자르기 로직은 손대지
않았다. **`orientation` 과 동시에 주어지면 `angle_deg` 가 이긴다** — `orientation`
값은 조용히 무시되고, 응답의 `info['orientation']` 은 `'custom'` 이 된다.
`REST`(`_split_args`/`_compute_split`)는 두 파라미터를 그대로 통과시킬 뿐이라 별도
분기가 없다.

**AI/MCP 도구는 처음엔 건드리지 않았다** — 당시 `propose_planting_split`/
`apply_planting_split` 에는 `angle_deg` 를 노출하지 않았다. LLM 은 지도를 볼 수
없어 임의 각도를 스스로 고를 근거가 없고, 쓰지 않을 설정을 노출하는 것 자체가
비용이라(불필요한 설정 추가 금지 원칙) UI 전용 파라미터로 시작했다.

> **갱신(2026-08-16)**: 실사용에서 "사람이 지도에서 각도를 정하고 그 값을 AI에게
> 불러 주는" 흐름(예: 사람이 드로어에서 슬라이더로 각도를 확인한 뒤 "이 각도로
> 만들어 줘"라고 말하는 경우)이 나오면서 스키마에 추가했다 — 아래 "MCP 도구에
> `angle_deg`/`widths_cm` 노출, 여백 단위를 m 로" 절 참조. LLM 이 스스로 각도를
> 지어내면 안 된다는 원칙은 그대로라, 도구 설명에 "사람이 지도를 보고 정한 값만
> 전달하고 직접 고르지 말 것"을 명시했다.

**지도 UI**(`aot-geo-plot.js`): "방향" select 에 세 번째 선택지
"자유 각도"(`custom`)를 추가했다 — 고르면 각도 슬라이더(0~179°)가 나타난다.
슬라이더를 움직이면:

1. **기준선** — 선택된 구역의 중심(turf.centroid)을 지나는 점선을 그 각도로 즉시
   그린다. **서버를 부르지 않는다** — feature 는 이미 클라이언트에 있고
   (`_findAreaFeature()`), turf 만으로 충분하다. 각도 → 나침반 방위각 변환은
   `bearing = 90 - angleDeg` 다(`planting_context.local_frame()` 이 위경도=동/북 축
   등장방형 근사를 쓰므로 지역 규모에서 이 변환이 맞는다).
2. **분할 조각** — 250ms 디바운스로 `split-preview` 를 다시 불러 점선 폴리곤을
   갱신한다. 이 "초안" 레이어(`_splitLiveSrc` 등)는 **커밋된 미리보기와 다른 GL
   소스**를 쓴다 — 폼을 다시 열어 각도만 만져보다 취소하면, 이미 커밋된
   `this._split.info` 와 화면에 남는 점선이 달라지는 사고를 막기 위해서다. 모달이
   어떻게 닫히든(`hidden.bs.modal`) 초안 레이어는 무조건 지운다.

"미리보기" 버튼(폼 제출)을 누르면 기존 흐름 그대로 `_previewSplit()` 이 **같은
파라미터로 다시 계산**해 커밋된 레이어에 그리고 모달을 닫는다 — 슬라이더로 보던
것과 같은 각도이므로 결과가 달라지지 않는다. "구획 만들기" 도 기존과 동일하게
`split-apply` 가 같은 파라미터로 재계산한다(좌표를 클라이언트가 되돌려보내지
않는다는 원칙은 유지).

### 구역 분할 — `parts` 와 `strip_width_cm` 를 같이 주면 균등분할이 아니다 (구현 확정, 2026-08-14)

지금까지 `parts`(등분)와 `strip_width_cm`(띠 폭)는 상호배타였다 — 하나만 주면
서버가 나머지를 계산했다(등분은 폭이 나오고, 폭이면 개수가 `floor` 로 나온다).
"N개를, 정확히 이만큼 간격으로" 직접 정하고 싶은 경우(예: 이미 정해진 재식
간격으로 5줄만 자르고 나머지 공간은 통로로 남기기)는 이 둘 중 어느 쪽으로도
표현할 수 없었다 — 등분은 남는 폭을 허용하지 않고, 띠 폭은 개수를 직접 고를
수 없었다.

**채택한 안**: `split_shape()` 이 이제 `parts` 와 `strip_width_cm` 를 **동시에**
받는다. 둘 다 주면 정확히 `parts`개를, 정확히 `strip_width_cm` 폭으로 자르고,
`parts × strip_width_cm` 을 채우고 남는 치수는 (등분·자동폭 모드와 같은 규칙으로)
짧은 축 양쪽에 절반씩 여백으로 돌린다. 남는 치수가 음수면(그 개수·폭이 도형보다
크면) 거부한다. 세 가지 입력 조합이 이제 모두 다른 결과를 낸다:

| 입력 | 개수 | 폭 | 여백 |
|---|---|---|---|
| `parts=3` | 3 (고정) | 자동(짧은 축/3) | 없음 |
| `strip_width_cm=400` | 자동(`floor`) | 4m (고정) | 있음(자동 계산된 만큼) |
| `parts=3, strip_width_cm=400` | 3 (고정) | 4m (고정) | 있음(사용자가 사실상 결정) |

**방향도 다시 의미를 가진다.** `strip_width_cm` 단독 모드는 고랑 방향이 실제
작업 방향과 같아야 해서 방향을 고정했지만(위 "orientation" 절), 개수까지 같이
주면 그때부터는 `parts` 처럼 "N개를 어느 방향으로 늘어놓을지"의 문제가 되므로
`orientation`/`angle_deg` 를 그대로 받는다.

**지도 UI**(`aot-geo-plot.js`): "띠 폭" 모드에 "정확한 조각 수(선택)" 칸을
추가했다 — 비우면 지금까지처럼 자동(`floor`)이고, 채우면 그 개수로 정확히
자른다. 이 칸이 채워지면 "방향" 행이 다시 나타난다(자유 각도 포함). REST
계층(`_split_args`/`_compute_split`)은 `parts`/`strip_width_cm` 를 원래도 무조건
같이 통과시키고 있었으므로 **변경이 필요 없었다** — 상호배타 검증은
`split_shape()` 안에만 있었다.

**AI/MCP 도구는 당시 건드리지 않았다** — `propose_planting_split` 의 스키마 설명이
그때는 "Give this OR parts, never both" 라고만 돼 있었다.

> **갱신(2026-08-16)**: 다른 파라미터(`angle_deg`/`widths_cm`/`edge_margin_m`)를
> 정리하는 김에 이 문구도 실제 동작(둘을 같이 주면 정확한 개수·정확한 폭 조합이
> 된다)에 맞게 고쳤다 — "Give this OR parts (or both together for an exact count
> at an exact width), never with widths_cm." 기능 자체는 이미 2026-08-14 부터
> `split_shape()` 에 있었고, 이번엔 스키마 설명 문구만 실제와 맞췄다.

### 구역 분할 — `widths_cm` 로 조각마다 다른 폭 (구현 확정, 2026-08-14)

지금까지 세 가지 입력(`parts`/`strip_width_cm`/둘 다)은 모두 **조각들의 폭이
서로 같다**는 전제를 공유했다. 실제 밭은 그렇지 않을 때가 있다 — 가장자리
한 줄만 통로로 넓게 두거나, 작물별로 필요한 이랑 폭이 달라서 구획마다 폭을
다르게 잘라야 하는 경우다. 등분·자동폭·조합 모드 중 무엇으로도 표현할 수
없었다.

**채택한 안**: `split_shape()` 에 `widths_cm`(cm 단위 리스트, 2개 이상)를
추가했다. 있으면 `parts`/`strip_width_cm` 는 완전히 무시된다(대체이지 조합이
아니다 — 목록 자체가 이미 개수와 각 폭을 다 말하고 있어서 둘을 섞을 이유가
없다). 리스트 합이 도형의 짧은 축보다 작으면 그 차이를 여백으로 양쪽에 절반씩
돌린다(자동폭 모드와 같은 규칙). 크면 아래 "마지막 조각 자동 축소" 절대로
처리한다 — 무조건 거부하지 않는다. 다른 모드와 마찬가지로
`orientation`/`angle_deg`/`edge_margin_cm` 은 그대로 받는다 — 목록은 축을 따라
놓일 조각들의 두께만 정하고, 축 자체는 여전히 방향 파라미터가 정한다.

합 비교에는 **조각당 0.5cm 허용오차**(`0.005 * 조각수`, 미터)를 둔다. UI 가
이 함수 자신의 균등분할 결과(`strip_widths_m`, cm 로 반올림)를 그대로
되돌려보내는 왕복 경로가 있는데, cm 반올림 자체가 조각마다 최대 0.5cm 오차를
낼 수 있어 "도형과 정확히 같은 폭인데 부동소수 오차로 거부됨" 이 나올 수
있었다(실사용에서 68.2/68.2 경계에 걸린 회귀, `test_widths_cm_round_trip_from_
equal_split_is_accepted`).

`info` 딕셔너리에 `strip_widths_m`(각 조각의 실제 폭, m) 를 추가했다 — 이제
모든 모드(등분·자동폭·조합·목록)에서 항상 채워진다. UI 가 "기본은 균등분할,
그 결과를 시작점으로 조각별 폭을 편집" 이라는 흐름을 만들 수 있는 것은 이
값이 모드에 상관없이 항상 나오기 때문이다.

**마지막 조각 자동 축소.** widths_cm 합이 도형을 넘으면 무조건 거부하던 첫
구현을 되돌렸다 — 조각을 하나씩 입력하다 마지막 값이 남는 자리보다 커서
거부당하는 것이 실사용에서 흔했다("마지막 입력값이 커서 전체 가로폭을
초과해도 가능한 최대 크기로 분할하게 할 것"). 이제는 **마지막 조각만** 남는
자리(`across - 앞선 조각들의 합`)에 맞춰 줄인다. 앞선 조각들만으로도 이미
넘치면(마지막을 0으로 줄여도 안 들어가면) 그건 "마지막이 커서" 가 아니라
애초에 안 맞는 요청이므로 그대로 거부한다. 잘렸으면
`info['widths_clamped_from_cm']` 에 원래 요청값(cm)을 남기고 `note` 에도
문구를 붙인다 — `strip_widths_m` 의 마지막 값은 이미 잘린 값이므로, 저장 시
서버가 같은 파라미터로 다시 계산해도 미리보기와 똑같은 결과가 나온다("본
것과 저장된 것이 같다" 원칙은 그대로 유지된다).

**지도 UI**(`aot-geo-plot.js`): 분할 폼에 "구획별 폭 직접 조정" 토글을
추가했다. 끄면 지금까지의 등분/띠 폭 모드 그대로다. 켜면:
- 이미 나온 미리보기의 `strip_widths_m` 로 조각별 입력칸을 채운다(없으면
  2개짜리 기본값으로 시작). 조각 수/폭 칸은 숨긴다 — 더 이상 의미가 없다.
- 입력 단위는 **m** 이다(예: `22.73`) — 서버 `widths_cm` 는 cm 이므로 전송
  직전에만 ×100 한다. 밭 폭은 보통 수십 cm~수십 m 라 cm 입력은 자릿수가
  크고 소수점 두 자리로 딱 떨어지는 값(예: 22.73m)을 표현할 수 없었다.
- 각 칸을 고치거나, 조각을 더하고 뺄 수 있다(최소 2개 — 서버 검증과 같은
  하한). 값이 바뀔 때마다 위 모드들과 같은 250ms 디바운스 실시간 미리보기가
  돈다.
- 마지막 조각이 서버에서 잘렸으면 입력칸은 **원래 값 그대로 둔다**(사용자가
  타이핑 중인 값을 되돌려쓰지 않는다) — 대신 요약 줄에 "마지막 구획을 줄여
  맞춤 N m" 을 띄워 실제로 무엇이 만들어질지 알린다.
- "방향" 행은 목록 모드에서도 항상 보인다 — `parts+strip_width_cm` 조합 모드와
  같은 이유로, 이미 N개를 명시적으로 늘어놓는 것이라 방향이 늘 의미를 갖는다
  (`hasExactCount()` 가 이 토글도 같은 취급을 한다).
- `.aot-modal-option-row` 는 공용 CSS 가 `display: flex !important` 로 못
  박아 둔다(드로어에서 버튼 묶음 줄을 세로로 쌓기 위한 규칙,
  `aot-base-ui.css`). 이 토글을 만들며 발견한 **기존 버그** — "정확한 조각
  수"/"방향"/"각도" 행을 여닫던 기존 코드가 `row.style.display='none'`(플레인,
  !important 없음)이라 실제로는 전혀 숨겨지지 않고 있었다. `showRow()` 헬퍼
  (`el.style.setProperty('display','none','important')`)로 여기서 함께
  고쳤다.

지도 미리보기 폴리곤에 **조각 번호 라벨**을 붙였다(`_aot_split_preview_label`,
symbol 레이어) — 입력칸의 "구획 1", "구획 2" 와 지도 위 어느 조각인지 맞춰
볼 수 있게. **미리보기에만** 있다 — 저장된 실제 구획은 이름으로 구분하지
번호 라벨을 달지 않는다.

REST 계층(`routes_geo_planting.py`): `_split_args` 에 `widths_cm` 파서
(`_num_list`)를 추가했다 — POST(JSON)는 배열 그대로, GET(라이브 미리보기의
쿼리스트링)은 값이 문자열뿐이라 콤마로 구분해 받는다(`widths_cm=500,1000,300`).
`_compute_split` 은 이를 그대로 `split_shape()` 에 전달한다.

**AI/MCP 도구는 당시 건드리지 않았다** — `propose_planting_split` 스키마에
`widths_cm` 을 노출하지 않았다.

> 단위를 m 로" 절에서 노출했다.

### `orientation` 기본값을 모드별로 분기, MCP 도구 노출, 여백 단위를 m 로 (구현 확정, 2026-08-16)

세 가지를 한 번에 정리했다 — 셋 다 위 세 절(orientation/angle_deg/widths_cm)이
"당시엔 이렇게 남겨 뒀다"고 적어 둔 미완의 꼬리였다.

**1. `orientation` 생략 시 기본값이 모드로 갈린다.** 위 "orientation" 절이 이미
`parts`(등분)와 `strip_width_cm`(두둑)이 서로 다른 결론에 도달해야 한다고
결론 내렸는데도, 실제 기본값은 두 모드 모두 `'long'` 으로 남아 있었다 — 이유
자체는 있는데 정작 적용은 안 된 상태였다. 이제 `orientation=None`(생략)이면
`split_shape()` 이 직접 고른다:

- `strip_width_cm` 이 주어졌으면(단독이든 `parts` 와 조합이든) `'long'`.
- 주어지지 않았으면(순수 `parts` 등분, 또는 `widths_cm` 단독) `'short'`.

**`strip_width_cm` 모드의 기본값은 절대 건드리지 않는다** — 이번 작업에서 가장
쉽게 저지를 수 있는 실수가 이것이었다(두둑 방향이 실제 작업 방향과 어긋나는
회귀). 직접 `orientation='long'|'short'` 을 주면 모드와 상관없이 그 값이
언제나 이긴다 — 이 분기는 **생략했을 때만** 적용된다.

분기는 `split_shape()` 하나에만 있다. 예전에는 `aot_data_tool_service.py` 의
MCP 핸들러 두 개와 `routes_geo_planting.py` 의 `split_args_from` 이 각자
`orientation='long'` 을 파라미터 기본값으로 하드코딩해 두고 있었다 — 둘 다 정본
분기를 우회해서 항상 `'long'` 만 서버에 전달했다는 뜻이다. 이제 둘 다
`orientation=None` 을 그대로 통과시킨다. 이 드리프트(같은 개념이 여러 곳에
따로 박제된 것)를 방치했다면 REST 라우트와 MCP 도구가 서로 다른 기본값을 내는
사고가 조만간 났을 것이다 — 회귀 `test_mcp_and_route_layer_agree_on_the_
default_orientation` 이 그 둘의 일치를 고정한다.

지도 UI(`aot-geo-plot.js`)는 이 서버 쪽 기본값 변경에 맞춰 고치지
**않았다** — 드롭다운은 여전히 "긴 변(기본)"을 시각적으로 기본 선택해 두고,
값을 만지지 않으면 `orientation` 을 아예 보내지 않는다(생략). `parts`(등분)
모드에서 사용자가 방향을 건드리지 않으면, 화면은 "긴 변"을 보여주면서 실제로는
서버 기본값(`'short'`)으로 계산된다 — **알려진 화면 표시 불일치**다. 기능적으로
틀린 것은 아니다(오히려 새 기본값이 사용자가 원하는 정방형에 가까운 결과를
낸다), 다만 드롭다운이 실제로 적용된 방향을 정확히 보여주지 못한다. 드롭다운의
기본 선택을 모드별로 맞추려면 `_splitArgsFrom` 이 `'long'` 을 명시적으로 보내지
않고 생략하는 부분도 함께 고쳐야 왕복(재렌더 시 이전 선택 복원)이 깨지지
않는데, UI 문구·상태 동기화까지는 이번 범위에 넣지 않았다 — 필요해지면 그때
고친다.

**2. `angle_deg`/`widths_cm` 를 MCP 도구까지 관통시켰다.** `propose_planting_split`/
`apply_planting_split` 시그니처와 `tool_registry.py` 의 두 스키마에 추가했다.
설명 문구는 `planting_split.py` 모듈 docstring 수준으로 옮겨 적었고, "`angle_deg`
는 사람이 지도를 보고 고른 값만 전달할 것 — LLM 이 스스로 지어내지 말 것"을
명시했다(LLM 은 지도를 볼 수 없다). `orientation` 과 동시에 주면 `angle_deg` 가
이긴다는 계약도 두 스키마 설명에 동일하게 적었다 — `apply_planting_split` 는
"propose 와 같은 값을 쓰라"는 기존 패턴을 그대로 따른다.

**3. `edge_margin_cm`(cm) → `edge_margin_m`(m).** 이름과 단위를 함께 바꿨다 —
단위만 조용히 바꾸면 옛 이름으로 부르는 호출자가 100배 잘못된 값을 에러 없이
받는다(이 저장소가 여러 번 데인 "조용한 실패" 모양과 같다). 이름까지 바꾸면
옛 키워드로는 `TypeError` 로 확실히 실패한다. `split_shape()`/MCP 두 도구/REST
`_split_args`(`_split_args_from`)/지도 UI 두 개(`aot-geo-plot.js`,
`aot-geo-device-split.js`)를 모두 맞췄다. **`get_planting`/`create_planting` 의
동명 `edge_margin_cm`(식재량 계산용, `planting_context.capacity_estimate`)은
완전히 다른 기능이라 건드리지 않았다** — 그쪽은 여전히 cm 다.

지도 UI 입력칸 자체는 여전히 cm 로 받는다(`widths_cm` 입력이 이미 m 로 받고
서버 전송 직전에만 ×100 하는 것과 반대 방향의 같은 규칙) — 사용자가 여백을
입력하는 감각은 두둑 폭과 비슷한 자릿수(수십~수백 cm)라 바꿀 이유가 없었다.
`_splitArgsFrom`/`_argsFrom` 이 전송 직전에만 ÷100 해서 `edge_margin_m` 으로
보낸다.

### 분할 폼을 모달에서 설정 드로어로 (구현 확정, 2026-08-14)

분할 폼은 지도를 덮는 Bootstrap 모달이었다. 그래서 "미리보기" 를 누르면 **모달을
닫아야** 점선을 볼 수 있었고, 조건을 고치려면 다시 열어야 했다 — 설정과 그 결과를
동시에 볼 수 없다는 것이 이 화면의 근본 문제였다. 자유 각도 슬라이더를 넣으면서
임시로 "초안 레이어(모달 안에서 라이브) + 커밋 레이어(모달 닫고 확정)" 2층 구조를
뒀는데, 이는 모달이라는 제약을 우회하려던 것이지 원하는 구조가 아니었다.

**geo/design 의 모드 패널 전체를 드로어로 옮기면서 함께 해결했다.** 하단 가로바에는
모드 탭만 남기고(`nav-v-panel` 90px→50px), 각 모드의 설정 tier 는
`#geo-settings-drawer` 로 간다. 드로어는 대시보드 위젯·Input/Output 설정이 이미
쓰는 `.aot-widget-drawer` 공용 컴포넌트라 **새 CSS 도 새 열림 로직도 쓰지 않았다** —
`aot-modal-modern.css` 가 지도를 덮는 대신 페이지를 드로어 폭만큼 밀어내고,
`common/aot-widget-drawer.js` 가 `body.aot-widget-drawer-open` 토글과 push 후
resize(맵 reflow)를 맡는다. 드로어 안에서 tier 가 세로로 감싸도록 하는 규칙만
`#geo-settings-drawer` 로 범위를 좁혀 더했다(가로바용 기본값은 한 줄 고정 +
가로 스크롤이라 520px 세로 패널에서 잘린다).

그 결과 분할은 **자체 모달을 버리고** 식생 모드의 하위 tier(`split`)가 됐다. 내용과
배선은 여전히 vegetation 모듈이 쥔다(`splitPanelHtml()` / `bindSplitPanel()`) —
폼이 지도(미리보기 점선·기준선)와 한 몸이라 패널이 흉내 낼 수 있는 것이 아니다.
패널은 tier 자리만 내주고 `_buildTier` 에서 배선을 위임한다.

**2층 미리보기와 "확정" 단계를 없앴다.** 드로어가 지도를 가리지 않으므로 화면에
보이는 것이 곧 제안이다. 값이 바뀌면 기준선은 즉시(turf, 서버 없이), 조각은 250ms
디바운스로 갱신되고, "구획 만들기" 를 누르면 서버가 **같은 파라미터로 다시 계산**해
저장한다 — "본 것과 저장된 것이 같다" 는 보장은 그 재계산이 하지 확정 단계가 하는
것이 아니었다. 함께 사라진 것: 초안 레이어(`_splitLive*`), `_previewSplit`/
`_liveSplitPreview` 2벌, 패널 막대의 적용·취소 버튼과 `_refreshPanel()`(요약은 이제
tier 를 다시 그리지 않고 드로어 안에서 제자리 갱신한다 — 다시 그리면 편집 중인
폼이 날아간다).

편집 중 서버가 거절하면 토스트 대신 요약 줄에만 남긴다 — 슬라이더를 끄는 동안
매번 알림이 뜨면 그것이 방해다. 저장을 막아야 할 오류는 만들기 때 분명히 알린다.

### 식생 구획이 생성 직후 안 보이거나 테두리가 없던 버그 (구현 확정, 2026-08-14)

"구획을 만들었는데 즉시 화면에 안 나온다", "구획에 테두리가 없다" 는 두 신고는
증상만 다른 **같은 버그**였다. 지도를 열자마자 그 밭의 구획 18개를 한 번에
붙이는 실험으로 재현했다: 1개만 화면에 남고 17개는 GL 소스도 레이어도 아예
없었다(그러니 도형도, 도형에 붙는 line 레이어인 테두리도 없다).

**원인**: MapLibre 는 같은 동기 틱(같은 함수 호출 안) 에서 서로 다른 구획에
대해 `addSource`+`addLayer` 를 여러 번 연달아 부르면 **첫 번째만 실제로 붙고
나머지는 예외 없이 조용히 사라진다.** `_addLayer()` 가 구획마다
`layer.addTo(map)`(직접, 재시도 없음) 를 부른 **다음** `store.addLayer(layer)`
(레이어 그룹의 `doAdd()`, `idle` 재시도·스타일 캐시 재적용까지 하는 더 성숙한
경로) 도 불러 같은 레이어를 두 개의 부착 경로로 동시에 밀어 넣고 있었다 —
이것도 원인에 한몫했다(다른 도형 종류는 `group.addLayer()` 하나만 쓴다).

**확인**: 콘솔에서 `layer.addTo()` 를 프레임 하나씩 띄워 순서대로 부르면
전부 붙고, 동기 루프로 한 번에 부르면 처음 하나만 붙는 것을 직접 실측으로
재현·반증했다.

**고친 방식**: `_addLayer()` 에서 직접 `layer.addTo()` 를 부르지 않고,
`store.addLayer(layer)` 하나로 통일하면서 **부착을 requestAnimationFrame
큐로 직렬화**했다(`_queueAttach`/`_drainAttachQueue`) — 여러 구획이 한꺼번에
등록돼도 프레임당 하나씩만 실제 GL 부착을 시도한다. `load()`(지도 로드),
`_addLayer()`(신규/수정), `_verifyAttached()`(재확인 안전망) 가 모두 이
큐를 거친다. `setEmphasis()`(모드 전환 시 강조/배경 전환)는 대상을 바꾸지
않았다 — 이미 붙은 레이어의 `setPaintProperty` 재적용일 뿐이라 같은 종류의
버그가 아니고, 여기까지 큐로 미루면 모드 전환마다 구획들이 한 프레임씩
어긋나며 켜지는 새로운 깜빡임이 생긴다.

### 거리 조회 — 읽기전용 리졸버를 따로 둔다 (구현 확정, 2026-08-14)

`nearest` / `distance_between` (`aot/utils/geo_distance.py`). 실제로 나온 요청은
*"관리사무소에서 가까운 순으로 품종을 배정해 달라"* 였고, 그때는 임시 스크립트로
중심점과 거리를 계산해 **숫자 목록을 만들어 준 뒤** AI 가 그것을 읽게 했다. 그
계산을 도구로 고정한 것이다 — LLM 은 좌표 산술을 조용히 틀리고, 틀린 거리는
그대로 배치 결정이 된다.

#### 쓰기 리졸버를 빌려 쓰지 않는다 (설계의 핵심)

`_resolve_note_target` 이 이름을 해석하지만, 작물명은 `_resolve_target_by_crop`
→ `_one_zone()` 을 거쳐 **구획이 아니라 소속 zone 으로 치환된다.** 그래서 한
zone 을 5등분해 서로 다른 품종을 심은 상태(바로 이 문서가 다루는 정상 상태)에서
품종명 다섯 개를 넘기면 **다섯 개가 전부 같은 zone 중심으로 해석되어 거리가
전부 같게** 나온다. 형식은 멀쩡하고 숫자만 틀리는 종류라 알아채기 어렵다.

그 리졸버를 고쳐서 구획을 돌려주게 만들 수도 **없다.** 호출처 17곳 중
`add_schedule` · `create_note` · `schedule_device_control` 이 **쓰기** 도구이고,
"target 은 무언가를 쓸 수 있는 GeoShape 여야 한다" 가 이 문서의 정본이다
(위 §"이름 해석" 절, `_active_crop_plots` docstring). 거기를 건드리면 예약이
GeoPlanting uuid 에 걸린다.

그래서 **읽기전용 리졸버를 따로 둔다**(`geo_distance.resolve_query`). 읽기전용
이라는 것이 곧 능력이다 — 쓰기 리졸버가 못 하는 두 가지를 할 수 있다.

1. **구획 자신을 가리킨다.** 쓸 대상이 아니므로 GeoShape 로 올라갈 이유가 없다.
2. **모호하면 고르지 않고 후보를 uuid 와 함께 돌려준다.** 5-튜플 계약에는
   "모호함" 을 담을 자리가 없어 쓰기 리졸버는 그냥 실패해야 했지만, 여기서는
   되물을 수 있다.

검정콩을 다섯 조각에 심었으면 *"검정콩까지 거리"* 는 **답이 없는 질문**이다
(1-4 구역이 실제로 그 상태다). 하나를 골라 답하면 그 숫자가 조용히 틀린다.

#### 해석 층위 — 위에서 하나라도 걸리면 아래로 안 내려간다

| | 층위 | 비고 |
|---|---|---|
| 0 | `unique_id` | 도구 체이닝이 이름 검색을 거치면 안 된다 |
| 1 | GeoShape 이름 정확일치 | **지도의 정식 어휘가 항상 이긴다** — 구획 이름이 우연히 '3-1' 이어도 구역 '3-1' 이 먼저다 |
| 2 | 활성 구획의 `name`/`crop`/`variety` 정확일치 | 활성만 — 작년 배추가 올해 질문을 끌고 가면 안 된다 |
| 3 | 장치 이름 정확일치 | |
| 4 | 부분일치(위 셋을 한꺼번에) | **양쪽 다 두 글자 이상**일 때만 — 한 글자 작물명 '마' 가 '고구마' 에 걸리는 것을 막는다(`_resolve_note_target` 과 같은 가드) |

정확일치 층에서 여러 개가 나오면 그것은 **진짜 모호**다. 층을 섞어 점수를
매기지 않는 이유가 그것이다 — 섞으면 "왜 이게 골라졌는지" 를 설명할 수 없다.

`nearest` 는 후보마다 이 검색을 돌리므로 **카탈로그(도형·구획·장치 목록)를
호출당 한 번만 만든다**(`build_catalog`). 안 그러면 후보 200개에 전체 스캔이
200번 돈다.

#### 대표점은 개체마다 하나씩, 기존 정본을 깨지 않는다

| 개체 | 대표점 | 근거 |
|---|---|---|
| `GeoShape` | `get_centroid()` (꼭짓점 평균) | **이미 `get_address`·`get_local_time` 이 쓰는 정본.** 여기서만 면적 중심으로 바꾸면 "3-1 이 어디냐" 의 답이 도구마다 달라진다 |
| `GeoPlanting` | 면적 중심, 오목이면 `representative_point()` | 기존 정본이 없었으므로 옳은 쪽을 고른다 |
| 장치 | 자기 `latitude`/`longitude` | `resolve_location_coords` 그대로 |

`GeoShape` 쪽이 면적 중심이 아닌 것은 알고 남긴 타협이다 — 정확도보다 **한
시스템 안에서 한 개체의 좌표가 하나** 인 것이 우선한다(이 저장소가 반복해서
데인 형태).

`resolve_location_coords`(`aot/utils/device_tz.py`)에 GeoPlanting 분기를 넣지
않고 `geo_distance` 에 따로 둔 이유도 같다 — 그쪽을 고치면 `get_address` ·
`get_local_time` 의 동작까지 함께 바뀐다.

#### 거리 정의를 매번 응답에 싣는다

**중심점 사이의 직선거리**다. 맞닿은 두 구획도 중심이 40m 떨어져 있으면 40m 로
답한다 — 경계 사이 최단거리가 아니다. `basis` 가 이것을 매번 말하지 않으면
읽는 쪽이 경계 거리로 오해한다. 투영은 `planting_context`·`facility_calc` 와
**같은 평면 근사**를 쓴다(같은 지도에서 면적과 거리가 다른 평면에서 재어지면
설명 없이 어긋난다).

#### 조용히 줄이지 않는다

- 해석 못 한 후보는 목록에서 빠지지 않고 `unresolved`(그런 이름이 없다) 또는
  `ambiguous`(여럿에 걸렸다) 로 나온다 — **없는 것과 먼 것과 못 고른 것은
  전부 다르다.** 목록이 짧아진 것을 "멀어서 빠졌나" 로 읽으면 안 되고, 특히
  `ambiguous` 는 **답이 있는데 못 고른 것**이라 되물으면 해결된다.
- 후보 200개를 넘으면 잘라내지 않고 **거부한다**(`planting_split` 과 같은 규칙).
- 응답에 **좌표를 싣지 않는다** — 호출자가 좌표로 다시 계산하기 시작하면 이
  도구를 만든 이유가 사라진다.
- 구획의 `name` 은 분할로 만들면 비어 있는 것이 정상이라, 표시명은
  `name → crop (variety) → uuid 앞자리` 로 떨어진다. 폴백이 없으면 결과가
  `null` 다섯 줄이 된다(실제 데이터가 그랬다).

회귀: `aot/tests/test_geo_distance.py` (35건). 쓰기 리졸버
(`_resolve_note_target` / `_resolve_target_by_crop`)를 끌어다 쓰기 시작하는
회귀를 소스 검사로 막고, 같은 작물이 여러 구획에 있을 때 하나를 골라버리는
회귀를 해석 테스트로 막는다.

## 확정된 결정

1. **별도 테이블** — `GeoShape` 에 타입을 늘리지 않는다.
2. **zone 안에서 분할** — 느슨한 분할 + 경계 클리핑 + 미배정 면적 표시.
3. **겹침 허용** — 제약을 걸지 않는다. 면적 합계를 UI 에 내지 않는다.
4. **센서는 파생 참조** — 구획 안 → zone 폴백. 바인딩을 만들지 않고
   `_CONTAINER_TYPES` 에도 넣지 않는다.
5. **시점 슬라이더는 Phase 4** — 이력은 목록으로 먼저 낸다.
6. **bay 는 스냅샷 복사** — 참조가 아니다.

## 미결

- **작물 이름의 어휘**: 자유 텍스트로 시작할지, 사전(작물 코드)을 둘지.
  자유 텍스트면 "토마토"/"방울토마토"/"대추방울"이 서로 다른 작물이 되어 이력 조회가
  샌다. 사전을 두면 등록 안 된 작물을 못 심는다. → Phase 1 은 자유 텍스트 + 자동완성,
  사전화는 실사용 데이터를 보고 정한다.
- **구획 안에 구획**(과수 아래 하부 작물의 계층 표현)이 필요한지. 지금은 겹침으로
  표현되며, 계층이 정말 필요한지는 실사용에서 확인한다.
- **생육단계 연동**: `GrowthStageResolver` 가 `facility_registry.yaml` 의
  `planting_date` 를 쓴다. `GeoPlanting.planted_on` 이 그 입력이 되어야 하는데,
  레지스트리가 없는 설치가 정상이므로 결합 방식을 Phase 2 에서 정한다.
