# MCP 이름 사전·호출 기록 활용 계획 (1단계 수집만 착수 — 2~4단계는 관찰 뒤)

- 작성: 2026-10-14
- 상태: **4-0(호출 기록 집계, 읽기 전용)만 착수.** 4-1~4-4(별칭 사전·되물음 후보·operation 후보·
  유의어)는 §0 착수 조건이 끝난 뒤다. 처음(2026-10-14 이른 시각)에는 전부 보류였으나, 같은 날 사용자가
  "1-2주를 보내기 위해서 수집하는 걸 시작해도 된다" 로 바꿨다 — 수집·집계는 해석에 영향을 주지 않는다.
- 관련: `mcp-domain-surface.md`(§2-2 대상 해석).

## 0. 착수 조건 — "안정화" 의 뜻

4-1 이후 단계는 아래가 모두 끝난 뒤 시작한다(4-0 집계는 예외 — 위 상태 참고).

1. 웹 커넥터가 붙는 로컬 서버에서 `AOT_MCP_SURFACE=domain` 으로 claude.ai 웹 테스트를 마쳤고,
   거기서 나온 실패를 틀(해석기·명부·어휘) 안에서 고쳤다.
2. 도메인 표면을 기본값으로 켰다(스위치 기본 전환은 사용자 결정).
3. 켠 뒤 한동안(예: 1~2주) 실제 사용에서 새 결함 보고가 잦아들었다.

이유: 사전은 해석기 위에 얹는 층이다. 해석기 규칙이 아직 움직이는 동안 사전을 쌓으면,
규칙이 바뀔 때마다 사전 항목이 "필요 없음" 또는 "이제 틀림" 으로 변해 정리 비용만 생긴다.

## 1. 왜 — 사용자 제안(2026-10-14)

자주 나는 오탐, 같은 뜻 다른 말(유의어)로 인한 오해, 사용자가 자주 쓰는 기능 조합·해석을
인덱스나 캐시처럼 쓰면 어떨까.

## 3. 원칙

1. **사전은 하나.** 기존 `AIDomainGlossary` 를 넓혀 쓴다. 두 번째 사전 테이블을 만들지 않는다
   (갈라지면 느슨한 쪽이 실질 판정이 된다).
2. **읽는 곳도 하나.** 대상 해석기(`targets.resolve`)의 한 단계로만 읽는다. `search_devices` 의
   별칭 읽기는 해석기 경유로 옮기거나 걷어낸다.
3. **정확일치가 사전을 이긴다.** 순서: id → 이름 정확일치 → **사전** → 낱말 대조 → 느슨한 해석.
   사전이 실제 이름을 가리면 '김제' 문제(이름에 김제가 든 장치를 집음)가 사전 손에서 다시 난다.
4. **사전은 이름이 아니라 대상 id 를 가리킨다.** 지금 `definition` 은 "영어 정식 이름" 텍스트라,
   이름이 바뀌면 조용히 틀리고 같은 이름이 둘이면 다시 모호해진다. 대상이 지워지면 항목은
   '무효' 로 드러나야 한다(조용히 빠지지 않는다).
5. **효력은 사람이 승인한 항목만.** 자동으로 모은 것은 후보(`pending`)까지다.
6. **해석 결과 자체는 캐시하지 않는다.** 해석은 이미 빠르고, 장치·도형 이름이 바뀌면 낡은 답을
   낸다. 쓰기는 승인 뒤 실행 직전 대상 재확인(`targets.changed`)이 이미 있다.
7. **쓰기의 되묻기 규칙은 그대로.** 사전이 후보를 하나로 좁혀도 승인 화면에 "사전 'X' 로 해석" 을
   보인다(`matched='alias'`). 사람이 무엇을 승인하는지 알아야 한다.
8. **범위를 가른다.** 장소·장치 별칭 = 농장 데이터(모두 공용). 말버릇·조합 선호 = 사용자별.

## 4. 단계

### 4-0. 호출 기록 집계(읽기 전용, 먼저)

사전이 실제로 얼마나 필요한지, 무엇을 operation 으로 만들지의 근거를 만든다. 만들지 말지는
이 숫자를 본 뒤 정한다.

- 기간: 도메인 표면을 켠 뒤의 기록(옛 표면 기록은 도구 이름이 달라 섞지 않는다 — 비교용으로만).
- 셀 것:
  1. `target` 해석 결과별 건수 — exact / tokens / path / loose / prefix / ambiguous / none.
  2. **none·ambiguous 의 물음 원문 상위 N** — 같은 물음이 반복되는가.
  3. ambiguous 뒤 같은 세션에서 다시 부른 대상(= 사용자가 고른 답)의 쌍: (물음 → 고른 id).
  4. 같은 세션 안 연속 호출 조합(도구.op 2~3개 연쇄) 상위 N과 그 왕복 수.
- 결과는 `.local/reports/` 에 보고서로. 운영 서버에는 읽기 전용 스크립트로만 돌린다.
- 전제 확인: 도메인 해석 결과(`matched`)가 감사 기록에 남는지 먼저 본다 — 안 남으면 그것부터
  싣는다(값 하나).

### 4-1. 사전을 해석기에 붙인다

- 스키마: `AIDomainGlossary` 에 대상 칸(`target_kind`·`target_id`) 추가, 또는 별칭 범주의
  `definition` 을 id 로 바꾸는 안 — **결정 필요**(§6-1). `term` 이 전역 unique 라 같은 낱말이
  별칭과 제어 의도에 동시에 못 들어가는 제약도 함께 본다.
- 해석기: §3-3 순서로 한 단계. 결과에 `matched='alias'`.
- 별칭 낱말도 낱말 대조와 같은 정규화(띄어쓰기·조사·순서 무관)로 맞춘다.
- 무효 항목: 대상이 없거나 종류가 바뀐 항목은 해석에 쓰지 않고 관리 화면·검사에 드러낸다.
- 기존 시드 정리: '기온'·'기상' → OpenWeather 는 해석기 경유로 옮길 때 다시 판단한다
  (측정 낱말을 장치로 묶는 것은 도메인 틀의 `measurement` 어휘와 충돌한다).
- 테스트: 정확일치가 사전을 이긴다 · 무효 항목은 쓰이지 않는다 · 쓰기 승인 화면에 별칭 해석이
  보인다 · 이름을 바꿔도 별칭이 따라간다.

### 4-2. 되묻기에서 후보를 모은다(자동은 후보까지)

- ambiguous 응답 뒤 같은 세션에서 후보 중 하나를 골라 다시 부르면 (물음 → id) 를 한 번 센다.
- 같은 물음에 같은 선택이 일정 횟수(예: 3회, 2명 이상 또는 7일 이상에 걸쳐) 반복되면
  `pending` 후보로 올린다. 다른 선택이 섞이면 올리지 않는다(물음이 정말 모호하다는 뜻).
- 승인은 사람이 관리 화면에서 한다. 화면은 "이 물음에 사람들이 고른 답" 과 횟수를 보인다.
- 사용자별 선호(말버릇)는 이 단계에서 다루지 않는다 — 공용 사전이 먼저.

### 4-3. 자주 쓰는 조합 → operation 후보

- 4-0 의 연속 호출 조합 상위를 보고, 서버가 한 번에 처리하면 왕복이 줄어드는 것을 operation
  명부(`registry_data.py`) 후보로 올린다. 만들지는 사람이 정한다("새 기능은 새 도구가 아니라
  operation" 규칙과 같은 길).
- 목록 크기 상한(운영 8,000·설정 13,000)과 래칫 안에서.

### 4-4. 유의어(언어 낱말)

- `vocab.py` 표는 코드 상수라 설치별로 못 늘린다. 설치별 낱말(농장마다 쓰는 말)을 사전의 다른
  범주로 둘지는 4-0 결과를 보고 정한다 — 오해의 대부분이 이름이면 4-1 로 충분하다.

## 5. 재는 것(효과 판정)

- 4-0 의 none·ambiguous 비율이 사전 적용 전후로 줄었는가(같은 물음 집합으로).
- 잘못 집음(사전 때문에 엉뚱한 대상) 0건 — 벤치 시나리오에 사전 항목이 있는 물음을 추가해 고정.
- 대화당 입력 토큰·왕복 — 4-3 operation 도입 전후.

## 6. 결정할 것

1. 별칭의 대상 표현: 새 칸(`target_kind`·`target_id`) vs `definition` 재해석.
2. 4-2 후보 승격 기준(횟수·사람 수·기간).
3. 사용자별 선호를 언젠가 다룰지(개인정보·공용성).
4. 사전 관리 화면을 어디에 둘지(AI 메뉴 재설계 진행 상황과 맞춘다).

## 7. 하지 않을 것

- 해석 결과 캐시.
- 자동 학습한 별칭의 즉시 효력.
- 정확일치보다 앞서는 사전.
- 사건별 별칭을 코드에 하드코딩(시드 포함) — 별칭은 데이터다.
