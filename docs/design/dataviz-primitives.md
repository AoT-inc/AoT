# 데이터 시각화 프리미티브 — 밴드 바 · 불릿 · 기간 바

지도 위젯 모달(site · zone · facility · plot)과 앱 화면이 공유하는 표준
그래픽 3종. 구현은 두 파일뿐이다.

| | 파일 |
|---|---|
| 모양·색 | `aot/aot_flask/static/css/components/aot-dataviz.css` |
| 값 → 위치(%) 계산 | `aot/aot_flask/static/js/common/aot-dataviz.js` (`window.AoTViz`) |

## 왜 만들었나

모달의 [현황]·[개요]는 전부 라벨-값 텍스트 행(`_pRow`)이다. 그래서 "지금
정상인가" · "목표 대비 얼마나 왔나" · "다음 단계까지 며칠인가" 를 사람이
숫자를 읽고 매번 계산해야 한다. 값을 **위치**로 바꾸면 그 계산이 사라진다.

세 가지를 각자 만들지 않은 이유는 톤 때문만이 아니다. 값을 %로 바꾸는 계산이
버그가 사는 자리이고(범위가 뒤집힌 경우 · 폭이 0 인 경우 · 범위를 벗어난 경우 ·
값이 아예 없는 경우), 화면마다 각자 나누기를 하면 그 네 가지를 각자 틀린다.

## 하나의 골격

셋은 같은 마크업이다. 켜는 부품만 다르다.

```
.aot-viz-head     라벨 + 값
.aot-viz-track    전체 범위 — 중립 회색
  .aot-viz-ok       적정 구간 / 현재 단계 구간
  .aot-viz-fill     실측 막대            (불릿)
  .aot-viz-tick     구간 경계            (기간 바)
  .aot-viz-now      현재 위치            (밴드 · 기간 바)
  .aot-viz-event    사건 표식            (기간 바)
  .aot-viz-target   목표 눈금            (불릿)
.aot-viz-scale    양 끝 눈금
```

## 색은 셋뿐이고, 세 컴포넌트에서 뜻이 같다

| 역할 | 뜻 | 토큰 | custom_ui 필드 |
|---|---|---|---|
| 트랙 | "전체 범위" | `--aot-color-text-primary` 10% 혼합 | `text_color_primary` |
| 구간 | "여기다" | `--aot-band-3` (#32c85a) | `band_3` |
| 마커 | "이 지점" | `--aot-color-brand-secondary` | `brand_secondary` |

**초록은 전역 토글의 켜짐 색과 같은 값이다.** `components/aot-toggle.css` 의
`.btn-toggle-input:checked + .btn-toggle-slider` 가 `#32c85a` 이고, 그것이
밴드 팔레트의 '적정'(`--aot-band-3`)과 같은 값이다. 처음에는 `color_success`
를 45% 로 옅혀 썼는데, 옅힌 초록은 4px 선 위에서 연약해 보여 "여기다" 라고
말하지 못했다. (`aot-toggle.css` 는 아직 토큰이 아니라 리터럴을 갖고 있다 —
그쪽을 `--aot-band-3` 으로 바꾸면 두 곳이 한 출처가 된다.)

**마커 색은 브랜드 보조색이다** — 액추에이터 슬라이더의 현재값 표시
(`.aot-3way-current-dot`)가 쓰는 `--aot-color-brand-secondary` 와 같다.
글자색(`text_color_primary`)을 쓰면 라이트에서는 값이 같아 구분이 안 되지만,
마커가 글자와 같은 무게로 서서 트랙 위에 있어야 할 것이 글자처럼 읽힌다.

**셋 다 settings/custom_ui 가 제어하는 필드다**(`forms_settings.THEME_COLOR_FIELDS`).
custom_ui 가 제어하지 않는 색을 여기에 새로 넣지 말 것 — 운영자가 테마를 바꿔도
이 컴포넌트만 옛 색으로 남는다.

역할이 같으면 **색도 모양도 같아야 한다.** 불릿의 채운 막대는 밴드 바의 적정
구간과 같은 초록이고(둘 다 "여기다" 를 말하는 면이다), 불릿의 목표 눈금은
밴드 바의 현재 마커와 같은 마커다(둘 다 "이 지점" 이다). 트랙 높이와 라운드도
셋이 같다. 여기서 하나라도 갈라지면 세 블록이 나란히 놓였을 때 서로 다른
그림처럼 읽힌다 — 실제로 한 번 그렇게 만들었다가 되돌렸다(불릿만 진한 회색
막대 + 달성 시 밝은 초록, 트랙 높이 10/14/12px).

**줄마다 색을 바꾸는 손잡이를 두지 않는다.** 한 화면에 여러 줄이 서로 다른
색으로 서면 그것이 곧 "제각각" 이다. 지표를 구분하는 것은 색이 아니라 왼쪽의
이름이고, 계열별 색이 필요한 자리는 그래프 위젯이다. 같은 지표를 단계별로
여러 색으로 칠하지도 않는다 — 단계는 위치가 말한다.

**목표 달성도 색으로 말하지 않는다.** 막대가 목표 눈금을 넘었는지로 읽는다.
달성색을 하나 더 두면 같은 화면의 밴드 바·기간 바와 톤이 갈린다.

**트랙을 회색 토큰(`--aot-bg-off` 등)으로 칠하지 말 것.** 그 토큰들은 다크
재정의가 `custom-dark.css` 에 없어 값이 갈리지 않는다 — 어두운 카드 위에서
밝은 회색 덩어리가 된다. 글자색을 섞으면 두 테마 모두에서 "배경보다 한 단계
진한 면" 이 된다.

## 굵기 규칙 — 굵기는 내용이 쓰고, 제목은 크기로 앞선다

문자의 색·크기·굵기가 여러 갈래로 갈리면 시선이 갈 곳이 분산된다. 층은
**둘**이다: 내용(이름 + 값)은 굵고, 그것을 거드는 것(단위·눈금)은 눕는다.
카드 제목은 굵기 경쟁에 끼지 않고 **크기로** 앞선다.

| 요소 | 색 | 크기 | 굵기 |
|---|---|---|---|
| 카드 제목 (`.aot-ov-sec-title`) | primary | base × **1.2** | **400** |
| 내용 이름 (`.aot-viz-label`) | primary | base | **700** |
| 값 (`.aot-viz-value`) | primary | base | **700** |
| 값의 부속(단위·목표) | secondary | xs | 400 |
| 눈금 — 축의 끝 · 기준 | secondary | xs | 400 |

색 2개 · 크기 3개 · 굵기 2개. 한 번 다섯 갈래까지 갔다가 되돌렸다
(값 700 / 부속 600 / 기준 라벨 primary 600 / 라벨 secondary 400 / 축 끝 400).

**카드 제목이 굵지 않은 이유**: 굵은 글자가 화면에 여럿이면 어느 것이 층인지
모양이 말해 주지 못한다. 제목은 블록당 하나뿐이므로 크기 한 단계면 충분하고,
굵기는 블록 안에서 여러 줄이 경쟁하는 자리에 남겨 둔다.
⚠ `.aot-ov-sec-title` 은 지도·시설 모달의 **모든 블록**이 쓰는 공용 클래스다.

**무엇이 기준인지는 색이나 굵기가 아니라 위치가 말한다** — 눈금의 기준 라벨은
마커 바로 아래에 서 있다. 거기에 강조를 하나 더 얹으면 한 줄에서 시선이 갈
곳이 둘이 되고, 줄이 여섯이면 열둘이 된다.

예외는 **범위를 벗어난 값**뿐이다. 값 글자만 색이 바뀌고 막대는 그대로다 —
이건 장식이 아니라 사람이 알아야 하는 한 가지다.

**그 색은 위험(danger)이 아니라 경고(warning)다.** 적정 범위를 벗어난 것은
주의할 일이지 고장이 아니다 — 센서는 멀쩡하고 값도 정상적으로 들어온다.
위험색은 실제 장애(통신 두절·제어 실패)에 남겨 둔다. 벗어난 값마다 빨간
글자가 뜨면 진짜 장애가 났을 때 빨강이 아무 말도 하지 못한다.

**`--aot-color-warning`(#FEA60B) 을 그대로 쓴다.** 한때 대비를 이유로 같은
축의 어두운 짝(`--aot-tint-warning-fg`, #94650a)을 썼는데, 그건 배지 **배경 위**
글자용이라 단독으로 쓰면 경고색이 아니라 **갈색**으로 보인다. 앱의 다른 경고
표시와 색이 갈리는 쪽이 대비보다 나쁘다. 라이트에서 흰 배경 위 1.97:1 인 것은
알고 쓴다 — 이 자리는 색만으로 뜻을 전하지 않는다(벗어났다는 사실은 마커
위치가 이미 말하고 숫자 자체도 그대로 보인다).

**마커에 카드 바탕색 링을 두르지 않는다.** 예전에는 링 + 트랙 밖 돌출인
세로 막대였는데, 링은 트랙에 흰 홈을 파고 돌출은 막대에서 삐져나온 것처럼
보여 눈에 걸렸다.

## 모양은 액추에이터 슬라이더에서 가져왔다

환경/제어 탭의 액추에이터 슬라이더(`.aot-act-slider` in `aot-facility-widget.css`,
`.aot-3way-*` in `components/aot-3way.css`)가 이 저장소에서 가장 단순하고 잘
읽히는 값 표시다. 그것을 새로 만들지 않고 **어휘를 그대로 가져왔다.**

| | 액추에이터 슬라이더 | 이 컴포넌트 |
|---|---|---|
| 트랙 | 4px 헤어라인 | 4px 헤어라인 |
| 마커 색 | `--aot-color-brand-secondary` | 같음 |
| 마커 모양 | 원 (핸들) | **세로 선** 3 × 12px |

**트랙이 얇을수록 그 위의 원이 주인공이 된다.** 처음에는 12px 알약 막대였는데,
여섯 줄이 쌓이면 그 굵기 자체가 화면의 무게가 돼 산만해졌다. 선을 4px 로
줄이자 같은 데이터가 훨씬 가볍게 읽힌다.

**가져온 것은 트랙과 색이고, 모양은 가져오지 않았다.** 원은 슬라이더 핸들의
모양이라 읽기만 하는 값에 쓰면 만질 수 있는 것처럼 보인다. 현재값을 채운
원으로, 목표를 속 빈 원으로 그렸다가 둘 다 세로 선으로 되돌렸다.

**마커는 전부 같은 세로 선이다**(3 × 12px, `--aot-viz-mark-w/h`). 테두리도
그림자도 없다. 현재와 목표가 같은 모양이어도 헷갈리지 않는다 — **한 줄에 둘이
함께 서는 경우가 없기 때문이다.** 밴드 바·기간 바의 마커는 현재 하나뿐이고,
불릿의 마커는 목표 하나뿐이다(불릿의 현재는 채운 막대의 끝이 말한다).

## 눈금 줄도 규칙이 하나다

양 끝은 축의 끝을 적고, **가운데는 그 줄의 기준**을 적는다. 기준은 가운데
고정이 아니라 **가리키는 것의 실제 위치**에 붙는다.

| | 가운데 라벨 | 붙는 위치 |
|---|---|---|
| 밴드 바 | 적정 범위 | 적정 구간의 중앙 |
| 불릿 | 목표 | 목표 눈금 |
| 기간 바 | 오늘 | 오늘 마커 |

가운데 고정으로 두면 기준이 왼쪽 끝에 있는데 라벨은 가운데 있어, 둘이 서로
다른 것을 가리키는 것처럼 읽힌다. 양 끝 12% 안쪽이면 끝에 붙여 세우고 같은
쪽 축 라벨을 가린다 — 축의 끝은 트랙이 이미 보여 주지만 기준은 이 라벨 말고
적을 자리가 없다.

### 겹침은 위치가 아니라 **글자 폭**이 정한다 — `AoTViz.settle(root)`

위 12%/88% 는 그릴 때 위치만 보고 내리는 짐작이다. 기준이 한가운데에서 조금
비켜난 정도(예: 18%)면 감추지 않는데, 축 라벨이 길면 그래도 부딪힌다 —
기준 라벨의 불투명 바탕이 축 라벨을 **반만** 덮어 `2026/0[오늘]` 처럼 잘린 채
읽혔다. 그래서 붙인 뒤에 실제로 재서 겹치는 축 라벨만 감춘다.

레이아웃이 잡힌 뒤에 불러야 한다. 지도 위젯 모달은 호출부마다 부르는 대신
`_showFacilityCenterOverlay` 가 본문에 `MutationObserver` 를 걸어 한 번씩 다시
잰다 — 본문 상당수가 슬롯에 나중에 채워지므로, 슬롯이 늘어도 따라온다.
**다시 재는 예약에 `requestAnimationFrame` 을 쓰지 말 것** — 숨은 탭에서는
아예 발화하지 않아, 탭을 다시 열면 라벨이 겹친 채로 남는다. 타이머는 느려질
뿐 멈추지 않는다.

### 가릴 것이 없으면 바탕도 깔지 않는다

기준 라벨의 불투명 바탕은 **축 끝 라벨을 가리려고** 있는 것이다. 눈금에 기준
라벨 하나뿐인 줄(환경 목록이 그렇다 — 축의 끝을 적지 않는다)은 부딪힐 상대가
없는데, 그런 줄에까지 카드 바탕색을 깔면 **그 줄의 배경이 다른 상태일 때 흰
상자가 떠 보인다.** 대표 측정으로 지정된 줄과 마우스를 올린 줄이 정확히 그
경우다. `:only-child` 면 바탕과 좌우 여백을 모두 없앤다.

## 어느 것을 쓰나

| 질문 | 쓰는 것 |
|---|---|
| 지금 값이 적정 범위 안인가 | `AoTViz.band` |
| 쌓아서 도달하는 목표에 얼마나 왔나 | `AoTViz.bullet` |
| 전체 일정에서 지금 어디인가 | `AoTViz.timeline` |
| **여러 지표가 지금 목표에서 얼마나 벗어났나** | `AoTViz.deviation` |
| 축 없는 값이 오르는 중인가 내리는 중인가 | `AoTViz.spark` |
| 기간 동안 대충 오르내렸나(훑기) | `AoTViz.trend` |
| **기간마다 얼마나 컸나(서로 독립인 값)** | `AoTViz.range` + `bars` |
| **기간마다 얼마였고 목표에서 얼마나 벗어났나(보고서)** | `AoTViz.range` |

**불릿을 상·하한 목표에 쓰지 말 것.** "주간 최고온도 28°C 이하" 를 불릿으로
그리면 막대가 채워질수록 잘하고 있는 것처럼 읽히는데 실제로는 정반대다.
그런 목표는 밴드 바가 맞다. 그래서 `bullet` 에는 적정 구간 인자가 아예 없다 —
구간이 필요하다는 것 자체가 밴드 바여야 한다는 뜻이다.

## 쓰는 법

```js
AoTViz.band({
  label: _t('Air temperature'), value: 26.4, valueText: '26.4', valueSub: '°C',
  min: 10, max: 40, okMin: 22, okMax: 28,
  scale: ['10', { text: okRangeText, anchor: true }, '40']
});

AoTViz.bullet({
  label: _t('Daily irrigation'), value: 1.8, target: 2.4,
  valueText: '1.8', valueSub: '/ 2.4 L',
  scale: ['0', { text: targetText, anchor: true }, '3.0']
});

AoTViz.timeline({
  label: stageName, valueText: 'D22', valueSub: '/ 98',
  segments: [{span: 14}, {span: 7}, {span: 20, current: true}, {span: 22}, {span: 35}],
  positionPct: 22.4,
  events: [{ pct: 0, label: '2026-07-25 육묘' },
           { pct: 18, label: '2026-08-14 생육' }],
  scale: [startText, { text: todayText, anchor: true }, endText]
});

AoTViz.group([ rowA, rowB, rowC ]);   // 줄 사이 여백만 담당 (세로 목록)
```

### 사건 표식 — `events` (기간 바)

"그날 실제로 무엇을 했다" 를 축 위에 점으로 찍는다. 구간 경계(`tick`)와 다른
것을 말한다: 경계는 *계획이 여기서 갈린다* 이고 사건은 *그날 실제로 했다* 다.
승인을 미루면 경계는 그대로인데 사건만 뒤로 간다.

**색을 늘리지 않는다.** 사건은 '이 지점' 이므로 오늘 마커와 **같은 마커 색**
이고, 구분은 모양이 한다 — 오늘은 세로 선(트랙 밖으로 나간다), 사건은 트랙
안에 들어가는 점. 색으로 가르면 이 문서의 세 색 규칙이 넷이 되고, 나란히 선
밴드·불릿과 톤이 갈린다.

같은 날 전환을 확인했으면 둘이 겹치는데, 그때 가려지는 쪽은 **사건**이다
(빌더가 사건을 먼저 얹는다). 오늘이 어디인지는 축 전체를 읽는 기준이라 무엇
에도 가려지면 안 된다.

`pct` 를 부르는 쪽이 준다 — 날짜에서 비율을 내는 계산을 여기서 하지 않는다.
구획 위젯은 **단계의 시작 경계**(`timeline.stages[].from_pct`)를 그대로 쓴다:
축의 경계는 서버가 계획·승인을 반영해 이미 잡아 둔 것이라, 화면이 날짜 산술을
따로 하면 두 값이 갈리고 끝이 열린 작기에서는 아예 낼 수도 없다.

### 편차 축 — `AoTViz.deviation` (2026-08-28)

**여러 지표를 하나의 축에 모은다.** 위 셋이 "지표 하나에 그림 하나" 인 것과
근본이 다르다.

지표마다 게이지를 하나씩 세우면, 여섯 개를 본 사람이 머릿속에서 여섯 번
판단하고 그것을 다시 합쳐야 한다. **게이지를 작게 만들어도 그 합치는 일은
그대로다** — 크기를 줄이는 것은 배치의 문제이지 읽는 부담의 문제가 아니다.
구획 하나를 계속 지켜보는 화면이 물어야 하는 것은 "온도가 몇 도인가" 가 아니라
**"지금 무엇이 어긋나 있나"** 하나다.

단위가 다른 값들을 **적정 구간 기준으로 정규화**해 한 축에 세운다:

```
d = (값 − 구간중앙) / (구간폭 / 2)
```

`d = 0` 이 구간 한가운데, `|d| = 1` 이 구간 경계, 그 너머가 벗어난 정도다.
°C 든 % 든 kPa 든 **같은 자로 잰 값**이 되어 나란히 설 수 있다. 축은 ±2.2 에서
자른다 — 더 멀리 간 값을 그대로 그리면 축이 그 하나 때문에 늘어나 나머지가
전부 가운데로 뭉친다.

```js
AoTViz.deviation({
  label: _t('Against target'), valueText: '2개 벗어남',
  items: [{ key: 'T', name: '온도', valueText: '25.2 °C',
            value: 25.2, okMin: 17, okMax: 27 }, …],
  scale: [_t('Low'), { text: _t('In range'), anchor: true }, _t('High')]
});
```

가운데 초록은 적정 구간(±1)이고, **값이 아니라 기준이라 지표가 무엇이든
움직이지 않는다.** 그 밖에 있는 점이 곧 답이다 — 색으로 경고하지 않고,
얼마나 밖인지는 거리가 말한다. 벗어난 지표는 라벨 **글자 굵기**로 앞선다.

**지표가 늘어도 그림이 커지지 않는다.** 점이 하나 늘 뿐이다.

이름은 점 바로 아래에 선다. 가까운 점끼리 라벨이 겹치므로 줄을 나눠 계단으로
쌓고(최대 3줄), 축 끝에 붙은 라벨은 안쪽으로 붙인다 — 가운데 정렬이면 폭의
절반이 트랙 밖으로 나가 잘리는데, **벗어난 지표가 바로 그 끝에 서므로 제일
중요한 것부터 못 읽게 된다**(실제로 그렇게 만들었다가 고쳤다).

적정 구간을 만들 수 없는 지표는 이 축에 세우지 않는다 — 벗어날 기준이 있어야
"얼마나 벗어났나" 가 성립한다. 그런 값은 따로 적는다.

### 격자 — `.aot-viz-grid`### 격자 — `.aot-viz-grid`

여러 줄을 **가로로도** 늘어놓는다. `.aot-viz-group` 이 세로 목록이라면 이쪽은
한 화면에서 여러 지표를 동시에 보는 자리다(구획 위젯의 종합 뷰).

목록으로만 두면 지표가 여덟일 때 여덟 줄 스크롤이라 "한 눈에" 가 성립하지
않는다. 그렇다고 화면마다 자기 그리드를 인라인으로 짜면 열 간격이 줄 사이
간격(32px)과 어긋나, 같은 프리미티브가 화면마다 다른 리듬으로 선다.

**가로 구분선은 긋지 않는다.** 그 선은 세로로 이어진 줄들을 가르는 것이라,
격자에서는 열마다 다른 높이에서 끊겨 오히려 어지럽다 — 격자에서는 거리가 이미
묶음을 말한다.

열 수는 폭이 정한다(`auto-fit`, 최소 220px). 좁으면 한 열이다 — 폰에서 두 열로
우겨 넣으면 같은 데이터가 덜 읽힌다(여백 절의 같은 이유).

반환은 **HTML 문자열**이다 — 지도 팝업 빌더(`aot-map-popup.js`)가 문자열을
이어 붙이는 방식이라 거기에 그대로 섞인다.

### 상태 플래그

| 인자 | 뜻 | 화면 |
|---|---|---|
| `stale: true` | 값이 오래됐다 | 값과 마커를 흐리게. **숨기지 않는다** |
| (자동) 범위 밖 | `okMin`/`okMax` 를 벗어남 | 값 글자만 위험색. 막대 색은 늘리지 않는다 |
| (자동) 값 없음 | `value` 가 없거나 범위가 성립 안 함 | 마커를 그리지 않는다. 0 으로 그리면 "없음" 이 "가장 낮은 값" 으로 읽힌다 |

## 문구는 만들지 않는다

라벨·값·눈금은 **이미 번역·서식된 문자열**을 받는다. 서식(소수점 자릿수·단위·
날짜)은 부르는 쪽이 이미 알고 있고, 번역 문구를 빌더에서 만들면 msgid 가 그
파일에 갇힌다. 특히 리터럴 `%` 는 babel 이 python-format 으로 읽어
`pybabel compile` 이 **그 언어 전체를 거부한다**(CLAUDE.md 의 리터럴 % 금지).

## 여백 — 전역 척도만 쓴다

기준은 `aot-theme-variables.css` 의 `--aot-space-1..6` = **4 / 8 / 12 / 16 / 24 / 32px**
이다. 이 컴포넌트는 여기 있는 값만 쓴다. 임의의 숫자를 넣지 말 것 — 지적받을
때마다 한 값씩 올리면 값들이 서로 어긋나고, 그 어긋남이 "정돈이 안 됐다" 로
보인다(이 파일이 실제로 그 길을 한 번 갔다: tail 10→16, gap 20→34).

| 자리 | 값 | 어떻게 | 주인 |
|---|---|---|---|
| 값의 부속 정보 | 4px | `space-1` | `.aot-viz-value small` |
| 줄 안 (제목↔트랙, 트랙↔눈금) | 12px | `space-3` | `--aot-viz-inner` |
| **줄 사이** | **32px** | `space-6` | `.aot-viz + .aot-viz` |
| 줄 사이 — **환경 목록** | **16px** | `space-4` | `.aot-env-now.aot-viz-group` |
| 제목 아래 — 환경 목록 | **16px** | 제목 8 + 묶음 8 | `.aot-ov-envnow .aot-ov-sec-title` |
| 마지막 아래 — 환경 목록 | **16px** | 묶음 0 + 카드 16 | `.aot-env-now.aot-viz-group` |
| **카드 제목 ↔ 첫 줄** | **28px** | 제목 12 + 카드 안여백 16 | `.aot-ov-sec-title` + `.aot-ov-block` |
| **마지막 줄 ↔ 카드 아래** | **16px** | 카드 안여백 16 | `.aot-ov-block` |
| 카드 안쪽 | 16px | `space-4` | `.aot-ov-block` |
| 카드 ↔ 다음 카드 | 16px | `space-4` | `.aot-ov-block` |

⚠ **묶음(`.aot-viz-group`)은 세로 여백을 스스로 더하지 않는다.** 예전에는 위
24px·아래 16px 을 보태 ②③ 을 혼자 만족시켰는데, 카드가 이미 균일한 안여백을
주는 자리에서 두 겹으로 쌓여 구획 [현재] 카드가 위 40px·아래 32px 로 유독
헐거워 보였다(2026-08-20 에 걷어냈다). **위아래는 전부 담는 카드가 정한다** —
그래서 ④(카드 안여백 ≥ 라운드)가 이 컴포넌트의 유일한 세로 여백 규칙이 됐다.

### 규칙 넷

**⓪ 환경 목록은 셋 다 절반이다**(줄 사이·제목 아래·마지막 아래 모두 16px).
한 줄이 사실 하나(이름·값·축)뿐이고, 여러 줄을 위아래로 훑어 "지금 어디가
벗어났나" 를 찾는 자리다 — 블록처럼 떨어뜨리면 한 화면에 서너 줄밖에 안 들어와
훑는 일이 스크롤이 된다.

**줄 사이만 좁히지 않는다.** 위아래를 그대로 두면 목록이 블록 가운데에 떠 있는
것처럼 보인다. 셋이 모두 같은 값이라 목록 전체가 한 덩어리로 읽힌다.

구획 [현황]의 기간 축처럼 **한 줄이 그 자체로 한 덩어리**인 곳은 기본값(40 /
36 / 32)을 그대로 쓴다.

**① 줄 사이는 줄 안의 두 배 이상** (12 → 32, 2.7배). 가까운 것끼리 묶여 보이는
것은 선이 아니라 거리가 정하므로, 두 간격이 비슷해지는 순간 세 줄짜리 한
덩어리가 아홉 줄짜리 목록으로 읽힌다 — 그 되짚음이 곧 "복잡해 보인다" 이다.

**② 카드 제목과 첫 줄 사이는 줄 사이보다 좁으면 안 된다.** 좁으면 제목이 첫
줄에 붙어 그 줄의 일부처럼 읽히고, 아래로 갈수록 간격이 벌어져 목록이 기울어
보인다.

**③ 마지막 줄 아래는 카드 안여백이 낸다.** 줄 사이(32px)보다 좁지만, 카드
테두리는 이웃한 줄이 아니라 **경계**라 같은 값일 필요가 없다.

**④ 카드 안쪽 여백은 모서리 라운드 이상.** `.aot-ov-block` 은
`border-radius: 16px` 인데 세로 padding 이 10px 뿐이었다 — 그래서 제목 위가 늘
답답했다. 16px 로 맞췄다.

**이 규칙이 ②③ 을 대신 만족시킨다.** `.aot-viz` 와 `.aot-viz-group` 은 자기
바깥 여백을 갖지 않으므로(위 "바깥 여백은 갖지 않는다"), **담는 카드를 고를 때
④ 를 확인하는 것이 곧 세로 여백을 맞추는 일**이다. 저장소의 호출부는 전부
`.aot-ov-block`(사방 16px)에 담는다 — 지도 팝업·구획 위젯이 그렇다.

⚠ **`.aot-modal-container` 는 그대로 쓰면 안 된다.** 그 상자는
`padding: 0 16px !important` 로 **세로가 0** 이라(`.aot-modal-option-row` 가
자기 세로 여백을 갖는 것을 전제한다) 그림이 라운드 안쪽에 그대로 닿고, 트랙
밖으로 나오는 마커(`.aot-viz-now`)는 테두리를 뚫는다. 일지 화면이 실제로 그렇게
나왔다(2026-09). 담아야 한다면 스코프 클래스로 세로 padding 을 16px 되돌린다 —
`.aot-viz` 쪽에 마진을 주는 것이 아니다. 선례:
`aot-drawer-form.css`, `geo-program.css`, `journal_view.html`.

**한 줄에 굵은 글자를 셋 두지 않는다.** 제목·값이 이미 굵으므로 눈금의 기준
라벨은 한 단계 가볍다(600). 셋이 같은 무게면 어디를 먼저 볼지 정해지지 않는다.

## 좁은 화면

**줄 간격을 좁히지 말 것.** 줄이 좁아지는 것이 아니라 화면이 좁아지는 것이라,
폰에서는 오히려 위아래 이웃과 붙어 보이기 쉽다. 묶음의 경계는 선이 아니라
여백이 만든다 — 줄 안(제목·트랙·눈금)보다 줄 사이를 넉넉히 벌린다.
트랙 높이와 글자 크기도 줄이지 않는다(마커를 못 읽는다).

## 다크 조정 — `custom-dark.css` §1.4b

라이트 값을 그대로 쓰면 **어두운 카드 위에서 트랙도 마커도 안 보인다.**
라이트에서 같은 비율이 잘 읽히는 것과 무관하다 — 어두운 배경에서는 같은
명도차가 훨씬 덜 보인다. 야외 화면에서는 아예 구분되지 않는다.

### 혼합 비율은 트랙과 초록의 줄다리기다

트랙을 밝힐수록 카드에서는 잘 떨어지지만 그 위의 초록(`band_3` #32c85a,
고정)과는 가까워진다. 실측(카드 `#1e1e1e`):

| 혼합 | 트랙 | 트랙/카드 | 초록/트랙 | 마커/트랙 |
|---|---|---|---|---|
| 10% (라이트 값) | `#333434` | 1.33 | 5.68 | 11.48 |
| 26% | `#555656` | 2.26 | 3.35 | 6.77 |
| **35%** | **`#696A69`** | **3.07** | **2.47** | **4.99** |
| 45% | `#7E7F7F` | 4.15 | 1.83 | 3.69 |

**35% 를 택한 근거**: 트랙 대 카드는 **회색 대 회색이라 명도차 말고 단서가
없다** — 여기가 3:1(비문자 요소 기준)을 넘어야 한다. 반면 초록 대 트랙은
채도까지 다르므로 2.47 로도 갈린다. 둘 중 하나를 희생해야 한다면 단서가
하나뿐인 쪽을 살린다.

### 다크에서 바꾸는 것

| 이름 | 라이트 | 다크 |
|---|---|---|
| `--aot-viz-track-mix` | 10% | **35%** |
| `--aot-viz-mark` | `brand_secondary` | **`text_color_primary`** |

마커는 다크에서 가장 밝은 글자색을 쓴다 — 트랙 대비 4.99:1, 카드 대비
15.33:1. 이 줄에서 반드시 보여야 하는 것이 현재 위치 하나이기 때문이다.

범위 밖 글자는 따로 두지 않는다 — `--aot-color-warning` 이 `custom-dark.css`
위쪽에서 이미 다크용(`#e09509`, 카드 대비 6.73:1)으로 재정의돼 있다.

**`brand_secondary` 자체를 다크에서 밝게 재정의하지 않았다** — 그 토큰은
`aot-entry-ui.css` 에서 **흰 글자를 얹는 배경색**으로도 쓰여, 밝히면 그쪽이
흰 글자 + 밝은 배경이 된다. 그래서 이 컴포넌트의 마커만 바꾼다.

### ⚠ 이 두 이름을 `aot-dataviz.css` 에서 정의하지 말 것

`--aot-viz-track-mix` · `--aot-viz-mark` 은 **사용처에서
`var(이름, 라이트 기본값)` 으로만 읽는다.** 컴포넌트 파일에서 `.aot-viz` 에
정의하면 특이도가 `custom-dark.css` 의 `:root` 와 같고(둘 다 0,1,0) 나중에
로드되는 쪽이 이기므로, 다크 override 가 **조용히 죽는다** — 에러도 경고도
없이 다크만 라이트 값으로 렌더된다. 실제로 그렇게 만들었다가 브라우저에서
계산값을 찍어 보고 발견했다.

### ⚠ 다크는 브라우저 캐시를 걷고 볼 것

`custom-dark.css` 에는 `?v=` 가 없다. 파일을 고쳐도 브라우저가 옛 사본을
계속 쓰기 때문에 **고친 것을 안 고친 것처럼 보게 된다** — 이 작업에서 실제로
그 상태로 "다크가 아직 어둡다" 를 두 번 주고받았다. 검증할 때는 링크에
캐시버스팅 파라미터를 붙이거나 계산값(`getComputedStyle`)을 직접 찍어
확인한다. (같은 함정이 `color-system.md` 5-4 절에도 적혀 있다.)

### 구획 위젯 (AoT_plot, 2026-08-28)

구획 하나를 대시보드에 상주시키는 위젯이 네 묶음을 이 프리미티브로 세운다.

| 묶음 | 쓰는 것 |
|---|---|
| 어디까지 왔나 | `timeline({compact:true})` + `events`(전환 이력) — **한 줄** |
| 목표 대비 지금 | `deviation` — 지표 전부가 **한 축에** |
| 추세 | 편차 축 라벨의 방향 표시(`↑`/`↓`) |
| 누적(적산온도) | `bullet` — 진행 카드 안(같은 질문의 다른 자) |

껍데기는 앱의 카드 골격을 그대로 쓴다 — 제목은 박스 밖(`.aot-ov-card-title`),
내용은 박스 안(`.aot-ov-block`). 위젯이 자기 여백·배경을 적으면 같은 성격의
화면이 앱 안에서 저마다 다른 카드가 된다.

**두 번 틀린 뒤에 나온 모양이다.**

처음에는 지도 팝업의 [환경] 블록(`buildEnvNowHtml`)을 통째로 불러 썼다. 판정을
다시 짜지 않으려던 것인데, 그 블록은 큰 모달용이라 카드에 얹으니 지표 셋이
400px 을 먹고 스크롤이 생겼다 — 위젯의 목적(한 눈에)이 그 자리에서 깨졌다.
*"이게 요약된 정보야? 사실상 지도 위젯에 있던 거 그냥 가져온 거잖아."*

그다음엔 같은 밴드 줄을 **작은 칸(타일)으로 줄였다.** 그것도 틀렸다 — 지표마다
게이지가 하나씩 서는 구조가 그대로라, 여섯 번 판단하고 합치는 일이 줄지 않았다.
*"그냥 작게 만들면 다냐? 스케일 조절 정도면 되는 거야?"* 크기가 아니라 **읽는
방식**을 바꿔야 했고, 그래서 나온 것이 편차 축이다(타일은 걷어냈다).

그래서 **판정과 그림을 갈랐다.** `_envNowRowHtml` 안에 있던 축·기준 판정을
`envRowSpec` 으로 꺼내 내보내고(같은 파일), 그림은 화면마다 다르게 그린다 —
모달은 밴드 줄, 카드는 타일. 판정을 복사하지 않은 이유는 그대로다: **온도·습도는
목표가 아니라 한계**이고(프로그램이 목표로 정하는 것은 vpd·co2·dli 뿐이다), 그
구분이 `_NOW_TO_TARGET`/`_NOW_TO_LIMIT` 두 표에 있다. 화면이 다시 조립하면
*아무도 정한 적 없는 숫자가 목표로 둔갑*하는 실패로 곧장 되돌아간다.

실측(구획 하나, 지표 셋): 밴드 줄 400px 이상 → 편차 축 포함 카드 둘 364px,
스크롤 없음. 그리고 **지표가 열이어도 이 높이는 그대로다** — 점만 는다.

⚠ `bullet` 에는 `value` 와 `valueText` 를 **둘 다** 넘겨야 한다. 앞은 막대
길이를 정하는 수이고 뒤는 머리줄에 적을 글자다. 글자만 넘기면 막대가 통째로
비는데 값은 제대로 적혀 있어서 "아직 0" 으로 읽힌다(구현 중 실제로 그랬다).

### 서버가 기간 축을 함께 실어야 한다

단계 이름·경계·오늘 위치는 `plot_context.timeline()` 이 이미 만들고 있었는데,
그 값이 **`plot_brief_for_control`(시설 목록용)에만** 실려 있었다. 모달이 쓰는
`plot_detail` 응답에는 없어서, 구획 모달은 단계 이름 없이 "경과/남음" 두 칸으로만
그릴 수 있었다. 같은 함수를 그쪽에도 실어(`out['timeline']`) 두 화면이 같은
계산을 본다 — 화면이 단계 길이를 다시 조립하면 두 곳이 곧 갈린다.

### AoTViz 가 없으면 옛 텍스트 행으로 되돌아간다

`_plotProgressRows()` 가 그 몫이다. 조용히 빈 칸을 내면 진행 정보가 통째로
사라진 것을 아무도 모른다.

### 배선 세 가지

1. `tools/bundles.json` 의 `aot-map-widget` 입력에 `common/aot-dataviz.js`
   (팝업 빌더보다 **앞**에) → 재빌드 후 `dist` 까지 같은 커밋에.
2. `AoT_map.py` head 에 CSS 링크. **`url_for` 를 쓴다** — 수동 `?v=` 는 파일을
   고칠 때마다 올려야 하고, 한 번 빠뜨리면 1년 캐시가 옛 파일을 계속 낸다.
   이 작업에서 **세 번** 밟았다(`aot-dataviz.css` · `aot-sensor-label.css` ·
   `aot-map-sensor-labels.js`) — 고친 것이 화면에 없어서 코드를 의심하다가
   계산값을 찍어 보고서야 캐시인 줄 알았다. 셋 다 `url_for` 로 바꿨다.

   ⚠ **CSS 로드 순서에 주의.** `components/aot-dataviz.css` 는
   `widget/aot-sensor-label.css` 보다 **뒤에** 온다. 클래스 하나짜리 선택자끼리는
   나중이 이기므로, 앞 파일에서 `.aot-viz-group` 의 `display:block` 을 덮으려면
   선택자에 두 클래스를 다 적어야 한다(`.aot-env-now.aot-viz-group`). 안 그러면
   목록이 조용히 block 으로 돌아가 줄 사이 여백이 통째로 사라진다.
3. 위젯 `.py` 를 고쳤으면 `generate_widget_html()` + 재시작.

### 환경 — 축은 밴드 색과 같은 표에서 온다

`AoTMapSensorLabels.bandScale(key, ranges)` 가 5단계 밴드를 축으로 바꾼다.
stages 는 각 단계의 **상한**이므로(`[s0..s4]`) 축은 `s0~s4`, 적정 구간은
밴드 3 = `s1~s2` 다. 범위 출처는 시설의 `view_options.sensor_ranges`, 없으면
`DEFAULT_RANGES`.

**색 판정(`bandColor`)과 같은 표를 쓴다.** 화면이 범위를 따로 들면 라벨 색과
축이 곧 갈린다. 단위 환산(`bandValue`)도 같이 쓴다 — VPD 를 Pa 로 저장하는
입력이 실제로 있어서, 축과 값이 같은 공간에 있어야 마커가 제자리에 선다.

**축을 모르는 지표는 축을 지어내지 않는다.** 기본 범위가 없는 키(CO2·토양수분
등)는 `AoTViz.value`(머리줄만)로 낸다. 같은 머리줄을 쓰므로 한 목록에 섞여도
줄이 어긋나지 않는다. 억지로 축을 그리면 그 끝이 무슨 근거인지 아무도 답할 수
없다.

**축의 끝을 눈금에 적지 않는다.** 밴드 축의 양 끝(10~45°C 등)은 5단계 색을
나누려고 정한 값이라 사람이 읽을 뜻이 없고, 기준 라벨이 그 자리로 움직이다
보면 끝 숫자와 겹쳐 "0.40 0.80–1.20" 처럼 한 덩어리로 읽힌다. 이 줄에서 알아야
하는 것은 **기준과 지금 위치**뿐이다.

### 초록 구간은 **출처가 달라도 같은 모양**이다

프로그램이 정했든 앱 기본값이든, 뜻이 같으면(= "여기면 된다") 모양도 같아야
한다. 한때 프로그램 값만 선(상·하한)으로 따로 그렸는데, 한 줄에 선이 셋
(하한·지금·상한) 서면 **어느 것이 지금인지 모양이 말해 주지 못했다.**
지금은 어느 출처든 초록 면 하나로 그린다.

| 출처 | 구간 | 눈금 라벨 |
|---|---|---|
| 프로그램 목표 (vpd·co2) | 값 ± 10% | `목표 0.90` |
| 프로그램 한계 **둘** (주/야간 온도) | 그 사이 | `범위 15–25` |
| 프로그램 한계 **하나** (습도) | 값 ± 10% | `범위 75` |
| 목표가 **곡선** — 코디네이터 있음 | 풀린 값 ± 10% | `목표 0.62` |
| 목표가 **곡선** — 코디네이터 없음 | 없음 | `곡선을 따름: 이름` |
| 아무것도 없음 | 앱 기본 밴드 | `18–26` |

### 값이 하나뿐이면 ±10% 를 구간으로 잡는다

프로그램이 주는 것은 대부분 **값 하나**다(습도·VPD·CO2). 폭이 없으면 그릴
구간도 없고, 그러면 그 줄은 "지금 어떤가" 에 답하지 못한다 — 숫자만 남는다.
그래서 그 값을 가운데로 보고 ±10% 를 구간으로 잡는다.

**10% 는 이 화면의 약속이지 프로그램이 말한 값이 아니다**(`_ENV_SINGLE_TOL`).
프로그램에 허용 오차 칸이 생기면 그 값이 이것을 대신해야 한다. 값이 0 이면
폭도 0 이라 구간을 만들지 않는다.

곡선은 가운데를 **빌려 온다**(아래 절). 빌릴 데가 없을 때만 예외다.

### 무엇을 "목표" 로 볼지는 `coordinator_plot` 이 정한다

`program_targets()` · `program_limits()` · `program_target_methods()` 세 함수가
`coordinator_plot.py` 에 있다 — 무엇을 목표로 보고 무엇을 한계로 볼지는 그 파일이
이미 `TARGET_MAP` · `UNMAPPED_UNITS` 로 정하고 있기 때문이다. 라우트마다 다시
고르면 **시설 모달과 구획 모달이 같은 단계를 두고 다른 말을 한다**(실제로 그렇게
갈렸다). 구획은 `/api/geo/plot/<uuid>/contents`, 시설은
`/api/aot/facility/<uuid>/overview` 가 같은 함수를 부른다.

목표는 `TARGET_MAP` 과 **같은 목록**(vpd · co2 · dli)만 내보낸다. 주간·야간 온도와 습도는 넣지 않는다 —
단계가 정한 그 값들은 **한계**이지 목표가 아니고, 목표 칸에 넣으면 한계가 목표로
둔갑한다(`coordinator_plot.display_state` 가 같은 이유로 `unmapped` 로 따로 뺀다).
화면이 이 판정을 다시 하면 어휘가 두 곳에 생긴다.

곡선이 걸린 항목(`value=None`)은 내보내지 않는다 — 숫자 없이 "목표" 라고만
적으면 축 위 어디를 가리키는지 알 수 없다.

### 한계는 **선**으로 긋는다 (온도 주/야간 · 습도)

면(초록)은 "여기면 된다", 선은 "여기까지" 다. 단계의 `temp_night`·`temp_day` 가
두 경계가 되고, 습도는 값이 하나뿐이라 **선 하나**만 긋는다.

| | 초록 구간 | 선 | 범위 밖 판정 |
|---|---|---|---|
| 목표(vpd·co2) | 없음 | 없음(눈금 라벨만) | 하지 않음 |
| **한계 둘**(온도) | **그 사이를 채운다** | 둘 | **함** |
| 한계 하나(습도) | 없음 | 하나 | 하지 않음 |
| 곡선 | 없음 | 없음 | 하지 않음 |
| 아무것도 없음 | 앱 기본 밴드 | 없음 | 함 |

**한계가 둘이면 그 사이는 곧 "여기면 된다" 다** — 프로그램이 두 경계를 직접
정했으므로 채워도 지어내는 것이 없다. 선은 그대로 둔다: 채움은 "이 안", 선은
"정확히 여기까지" 를 말하고 둘 다 필요하다. 하나뿐이면 채우지 않는다 — 어느
쪽이 안인지 모른다.

**한계가 하나뿐이면 범위 밖을 말하지 않는다.** 그것이 상한인지 하한인지 아무도
선언한 적이 없다 — 한쪽으로 단정하면 "습도가 낮아서 문제" 를 "정상" 으로 읽게
만들 수 있다. 어느 쪽이 큰지도 값이 정하게 둔다("야간이 하한" 이라고 못 박지
않는다).

한계선은 현재 마커보다 **가늘고 낮고 옅다**(2 × 8px, 55%). 한 줄에 선이 셋
(하한·지금·상한) 설 수 있는데 셋이 같은 모양이면 어느 것이 지금인지 알 수 없다.
색은 늘리지 않는다.

### 온도·습도는 "목표" 가 아니다

시설 코디네이터의 `summary.targets` 에는 `temperature`·`humidity` 도 들어 있지만
그것은 목표가 아니다. `build_env_target` 의 주석이 못 박고 있다:

> R3: T/RH 는 호출자가 constraint 로 별도 관리 (이 함수는 추적 목표용 변수만 반환)

VPD 를 1차 목표로 쓰는 코디네이터에서 T/RH 는 guide 대역의 **중앙값**으로
계산된 보조값이다. 그것을 "목표" 라고 적으면 아무도 정한 적 없는 숫자가 목표로
둔갑한다 — **실측으로 그렇게 나왔다**: 상추 육묘장이 "목표 32.0°C / 85%" 를
띄우고 있었는데, 그 구획 프로그램의 해당 단계는 주간 25 · 야간 15 · 습도 75
였다. `_NOW_TO_TARGET` 에서 T·RH 를 빼고 `_NOW_TO_LIMIT` 로 옮겼다.

### 밴드 3 이 '적정' 인 키만 축으로 쓴다

5단계 팔레트는 두 가지로 쓰인다 — 온도·습도·VPD 처럼 **가운데가 좋은 것**과,
바람·기압·조도처럼 그냥 **세기**인 것. 후자에 "적정 4–6 m/s" 를 그리면 바람 한
점 없는 날이 경고로 뜬다(실측으로 그렇게 나왔다). `AoTMapSensorLabels.bandScale`
이 `OK_BAND_KEYS`(T·RH·VPD) 밖의 키에 `null` 을 돌려주고, 화면은 값만 낸다.
색(`bandColor`)은 세기 표시로 계속 쓴다 — 축과 적정 구간만 끊는다.

### 목표가 **곡선**이면 — 코디네이터가 있으면 풀린다

단계가 목표를 곡선(메서드)으로 정하면 `stage.targets` 의 값은 `None` 이다.
곡선의 "지금 값" 은 메서드 종류마다 계산 인자가 달라 `_stage_targets` 에서
일반적으로 구할 수 없다(그 함수 주석이 그렇게 적고 있다). 처리는 **두 갈래**다:

**곡선을 푸는 것은 데몬의 사이클뿐이다.** `control_targets` 는 풀지 않는다 —
`method_id` 만 넘긴다(메서드 종류마다 계산 인자가 달라 조회 시점에 일반적으로
풀 수 없다는 것이 `_stage_targets` 의 판단이다). 실제로 푼 값은
`FunctionRuntimeState.summary_json` 의 `targets` 에 남는다.

`program_targets()` 가 그 스냅샷을 **빌려 온다**(`_coordinator_live_targets`).
구획이 시설에 있고 그 시설에 코디네이터가 있으면, 구획 모달과 시설 모달이
**같은 숫자**를 말한다.

| | 곡선의 현재 값 | 화면 |
|---|---|---|
| 시설·구획(코디네이터 있음) | **있다** — 마지막 사이클이 푼 값 | `목표 0.62` + ±10% 구간 |
| 구획(코디네이터 없음 — 노지 등) | 없다 | `곡선을 따름: 고추육묘 VPD` |

⚠ **스냅샷이다.** 코디네이터가 멈춰 있으면 마지막 값이 남아 있고, 한 번도 돈
적이 없으면 아무것도 없다 — 그때는 곡선 이름으로 되돌아간다. 지어낸 숫자를
목표라고 적는 것보다 낫다.

풀린 키는 `program_target_methods()` 목록에서 **뺀다** — 두 목록에 같은 키가
남으면 화면이 "무엇을 먼저 볼지" 를 또 정해야 한다.

어느 쪽이든 **앱 기본 구간은 그리지 않는다** — 곡선이 다스리는 값에 다른 기준을
겹쳐 말하는 것은 목표·한계일 때와 같은 문제다.

**남은 것**
- CO2 는 목표가 있어도 그릴 축이 없다(기본 밴드가 없다). 축을 지어내지 않으므로
  값만 나온다 — 시설이 `sensor_ranges` 에 CO2 범위를 설정하면 그때 축이 생긴다.
- 시설의 한계는 `plots_in_facility` 의 **첫 구획**에서 온다. 한 시설에 여러
  구획이 있으면 어느 것을 따를지는 아직 정하지 않았다(관수 근거가 이미 같은
  방식을 쓰고 있어 그 관례를 따랐다).

**구획 [현황]의 자리는 위젯이 채운다.** 값은 별도 조회(`/contents`)라 빌더가
`data-slot="envnow"` 자리만 잡아 두고 도착하면 채운다 — 블록이 위아래로 튀면
사용자가 읽던 줄이 움직인다. 구획 창에는 대표 측정 지정을 넘기지 않는다:
`rep_key` 는 시설의 설정이라, 구획 창에서 쓰면 그 시설을 보는 **다른 사람의**
화면이 바뀐다.


## 적용 2차 (2026-08-20)

| 자리 | 이전 | 지금 |
|---|---|---|
| 시설 [현황] **제어 상태** | `커튼 40%` 텍스트 | 0–100% **막대** (환기 면적은 0–전체 면적) |
| 구획 [현황] **목표** | `주간 온도 25 °C` 텍스트 | — 카드를 없앴다(아래) |
| [현재] 목록 순서 | 서버 순서 그대로 | **VPD · 광량 · CO2 를 위로** |

### 개도에는 목표 눈금이 없다

"얼마나 열려 있나" 에는 "얼마여야 한다" 가 없다. 제어가 지금 그만큼 열어 둔
것이고, 그것이 옳은지는 위의 편차·한계 줄이 말한다. 그래서 채운 막대만 그린다.

**0 이면 막대를 아예 그리지 않는다.** `min-width` 로 남긴 점이 "조금 열려 있다"
로 읽혀, 꺼진 장치가 켜진 것처럼 보였다. 0 과 "값 없음" 은 값 글자로 갈린다.

### [목표] 카드를 없앴다 (2026-08-20)

한 번은 막대로 만들어 봤다 — `data-slot="targets"` 를 글자로 채워 두고 측정값이
도착하면 위젯이 목표 ±10% 구간 + 지금 값 마커로 다시 그렸다. 축도 [현재] 와
같은 표(`bandScale`)에서 가져와 두 블록의 마커 위치를 맞췄다.

**그러고 나니 [현재] 와 거의 같은 말을 하고 있었다.** 같은 시기에 [현재] 가
값 옆에 기준(목표/범위)을 세우게 됐기 때문이다 — 같은 지표가 두 카드에 나오면
사용자는 어느 쪽이 정본인지 매번 확인한다.

남는 차이는 **재는 센서가 없는 항목**(관수량·EC 등 `t.observable === false`)
뿐인데, 그것들은 지금 값과 나란히 놓을 수 없어 결국 "목표 숫자 목록" 으로
남았다. 그 목록은 프로그램 설정 화면이 이미 보여 준다.

그래서 카드를 지웠다. 목표가 사라진 것은 아니다 — 지금 값이 있는 항목은
[현재] 의 눈금이 "그래서 지금 맞나" 까지 함께 답한다.

> 되살리려면 먼저 답할 것: **센서가 없는 목표를 어디에 어떻게 보일 것인가.**
> 문구로 적는 것은 이미 걷어냈다("(여기 센서 없음)" 은 목표를 권하는 자리에서
> 시설의 결함을 지적하는 말이 된다). 서버는 `t.observable` 을 계속 실어 준다.

### 광합성에 직접 얽힌 값을 위로

VPD · 광량 · CO2 · DLI 순. 나머지가 덜 중요한 것이 아니라, 이 넷이 **지금
광합성이 되고 있는가** 를 직접 말하는 값이라 먼저 보인다(온도·습도는 그것을
만드는 조건에 가깝다). **데이터가 있는 것만 올라간다** — 빈 줄을 위에 두면
"있어야 하는데 없다" 로 읽히는데 실제로는 그 센서가 없을 뿐이다. 나머지는 서버
순서를 그대로 지킨다(대표값 우선 같은 판단이 거기 들어 있다).

## 스파크라인 — 축이 없는 지표의 추세 (2026-08-20)

적정 범위를 만들 수 없는 지표(CO2·토양수분·이슬점·풍속·기압…)는 값 하나로는
좋은지 나쁜지 말할 수 없다. **그런데 추세는 범위를 몰라도 그릴 수 있다** —
"612ppm" 은 판단할 수 없어도 "오르는 중" 은 값 몇 개면 보인다.

```js
AoTViz.spark({ label: 'CO2', valueText: '612', valueSub: 'ppm',
               points: [590, 600, 596, 608, 612] })   // 오래된 것 → 최신
```

**세로축에 숫자를 붙이지 않는다.** 붙이면 그 축이 판단 기준처럼 읽히는데,
여기서는 최소~최대에 맞춰 늘린 **상대 모양**일 뿐이다(값 두 개짜리도 화면을
가득 채운다). 판단은 하지 않고 방향만 말한다.

### 그리지 않는 경우 셋

| 경우 | 이유 |
|---|---|
| 점이 **2개 미만** | 점 하나로는 방향이 없다. 빈 칸이 "아직 모른다" 를 정직하게 말한다 |
| 그 key 의 센서가 **여럿**(`n > 1`) | 값은 평균인데 선은 센서 하나다 — 평균은 오르는데 선은 내려가는 화면이 나온다 |
| **순환값**(`wind_deg`) | 359° 와 0° 는 1도 차이인데 세로축에서는 정반대 끝이다. 바람이 안 바뀌어도 요동친다 |

두 번째를 이력 평균으로 맞출 수도 있지만, 그러면 화면이 서버의 집계 규칙(신선도
판정 포함)을 다시 구현하는 것이 된다.

### 조회는 덤이다

`/data_batch` 의 `kind:'past'` 로 **한 번에 묶어** 받는다(센서 팝업 차트와 같은
경로). 값은 이미 그려져 있고 이력이 도착하면 그 자리만 바뀐다 — 실패하면 조용히
지나간다. 스파크라인이 없다고 값이 사라지면 안 된다.

응답 길이가 요청과 다르면 **아무것도 그리지 않는다** — 잘못 짝지으면 CO2 자리에
이슬점 모양이 들어간다.

## 추세 띠 — 목표 대비 위치가 있는 시계열 (2026-09-03)

스파크라인은 **판단하지 않는다**(위 절) — 그런데 판단이 필요한 시계열도 있다.
구획 일지(§geo/journal)의 "일자별 기록"이 매일 같은 표(측정값 10행 × 목표·
Δ)를 반복해 문서 대부분이 같은 표의 사본이 됐다 — 사람의 기록(노트)보다
반복되는 수치가 지면을 훨씬 많이 차지했다. 필요한 것은 "이 기간 동안 값이
목표 대비 어떻게 움직였나" 를 **한 줄**로 보여주는 것이었다.

```js
AoTViz.trend({
  label: _t('Air temperature'), valueText: '28.7 °C', valueSub: _t('latest'),
  points: [
    { k: '08-15', min: 22.1, max: 34.8, avg: 27.6 },
    { k: '08-16', min: 23.0, max: 33.0, avg: 28.0 },
    // …
  ],
  band: { lo: 20, hi: 25 }     // 적정 구간. 없으면 target(단일 값)을 본다
});
```

**밴드 바(`band`)를 시간축으로 늘인 것**이라고 보면 된다 — 밴드 바가 "지금
값이 적정 범위 안인가" 하나를 답하듯, 추세 띠는 그것을 여러 날에 걸쳐 잇는다.
그래서 색도 밴드 바를 그대로 옮긴다(새 색을 만들지 않는다):

| 요소 | 뜻 | 색 |
|---|---|---|
| 범위 띠(`min`~`max`) | 그날의 변동폭 — 트랙과 같다 | 중립(트랙 10% 혼합) |
| 평균 선 | 여러 "이 지점" 이 이어진 것 | 마커(`brand_secondary`) |
| 목표 구간(`band`) | 밴드 바의 적정 구간과 같은 뜻 | 구간(`band_3`), 18% 로 옅혀서 뒤가 비친다 |
| 단일 목표선(`target`) | 목표 구간과 같은 뜻, 범위가 없을 때 | 구간과 같은 색, **대시**로만 구분 |

`points` 는 오래된 것 → 최신 순이고, 자리마다 하루(또는 접힌 한 구간)를
가리킨다. **`avg` 가 없는 자리는 결측**이다 — 그 자리는 이어 그리지 않는다
(스파크의 "점이 2개 미만이면 안 그린다" 와 같은 이유: 없는 값을 지어내지
않는다). 결측 앞뒤로 값이 있어도 서로 잇지 않고 끊어진 조각마다 따로 그리되,
x 위치는 **전체 점 수 기준**이라 결측이 있어도 날짜 간격이 어긋나지 않는다.

**세로축에 숫자를 붙이지 않는 것도 스파크와 같다** — 실제 값·목표는
머리줄(`valueText`)이 말하고, 그림은 "목표 대비 어디 있었나" 라는 모양만
말한다. `band`(범위 목표)와 `target`(단일 목표) 중 있는 쪽만 그리고, 관측
범위 밖의 목표도 세로 범위 계산에 넣으므로(그렇지 않으면 목표를 계속 못
채운 기간에서 목표선 자체가 그림 밖으로 사라진다) 목표를 벗어난 기간도
그림이 잘리지 않는다.

**스파크(`spark`)와 헷갈리지 말 것** — 둘은 답하는 질문이 다르다. 스파크는
"오르는 중인가 내리는 중인가"(축을 모르는 값), 추세 띠는 "목표 대비 어디
있(었)나"(축이 있는 값을 여러 날에 걸쳐). 축이 없는 지표(CO2·이슬점 등)에는
여전히 스파크를 쓴다.

## 범위 도표 — 보고서용 시계열 (2026-09-04)

`AoTViz.range`. **밴드 바를 세로로 돌려 기간마다 하나씩** 세운 것이다.
그것뿐이다 — 마크업도 색도 라운드도 밴드 바 그대로고, 바뀌는 것은 축이다.

| 가로(밴드 바) | → | 세로(범위 도표) |
|---|---|---|
| 트랙 `height` | → | `width`, 세로 100% |
| 구간 `left`/`width` | → | `bottom`/`height` |
| 마커 `top:50%` · 세로 선 | → | `left:50%` · 가로 선 (캡 보정은 그대로) |

값이 '크기' 인 계열(DLI 하루 적산·장치 가동시간)은 밴드 바가 아니라 **불릿**을
돌린다 — 트랙 + 채운 양(`.aot-viz-fill`, 바닥에서 올라온다). 서로 독립인 값을
선으로 이으면 하나의 오르내림으로 읽히기 때문이다.

**막대 굵기는 밀도가 정한다**: 칸 `≤24 → 8px`, `≤60 → 4px`, 그 이상 `2px`
(`--aot-viz-range-bar`). 8px 로 못박으면 기간이 51 개인 문서에서 트랙이 칸보다
굵어(칸 폭 10.3px) 서로 붙어 한 덩어리로 뭉갠다.

**기간이 하나면 이 그림을 쓰지 않는다.** 막대 하나가 가로폭을 통째로 먹고
날짜 눈금이 같은 값 둘("07-15 / 07-15")이 된다 — 그 자리는 밴드 바 자체가
맞다(실측 높이 1400px → 414px). **모든 자리가 같은 그림일 필요는 없다.**

### 이 자리에서 네 번 어겼다 — 무엇을 어겼고 무엇이 막는가

전부 실사용 지적으로 되돌아왔다.

1. 축 눈금·목표를 그림 전체를 가로지르는 **선**으로 → "너무 산만하다".
2. 시키지 않은 **배경 면**을 깔았다 → "가독성이 떨어진다".
3. **투명도를 세 번 만들었다** — `text_primary 45%`(시스템에 없는 회색) →
   `mark 55%` → `zone 18%`. 마지막 것은 "기존 선례" 라고 적어 두기까지 했는데,
   그 선례(`.aot-viz-trend-band`)는 SVG 추세 띠 이야기이고 **밴드의 구간은
   언제나 원색**이다. 이 파일 머리말이 이미 적어 두었다 — "예전에는
   color_success 를 45% 로 섞어 썼는데, 옅힌 초록은 연약해 보여 '여기다' 라고
   말하지 못했다."
4. **구간(초록)을 마커 색으로** 칠하고 **라운드를 없앴다** → "저건 now 색이고
   band 는 녹색이다", "돌렸을 뿐인데 라운드는 왜 안 돌아갔냐".

막는 방법은 규칙 하나다. **범위 도표 CSS 블록은 색·배경·라운드를 선언하지
않는다.** 축을 바꾸는 규칙만 둔다 — 나머지는 클래스가 이미 갖고 있다.
회귀 테스트가 그 블록에 `background`·`color-mix`·`opacity`·`transparent` 가
없는지 검사한다.

큰 면을 칠하기 부담스러워 색을 옅히고 싶어지면, **색이 아니라 모양을 줄인다.**

## 어휘를 하나로 — 초록은 실측, 직각선은 목표 (2026-09-04)

밴드 바와 불릿이 한 카드에 나란히 서면 초록과 선의 뜻이 줄마다 뒤집혔다.
표현을 다섯 번 바꿔 봐도 안 풀렸고(색·원·깃발·기준 라벨 글자·트랙 세 칸),
그제서야 원인이 표현이 아니라 **두 어휘를 공존시키려 한 것**임이 드러났다.

    초록  = 실측   — 지금 값 · 그 기간의 최저~최고 · 지금까지 쌓은 양
    직각선 = 기준   — 목표 · 상·하한
    회색  = 축

**불릿은 처음부터 이 어휘였다**(초록 채움 = 누적 실측, 선 = 목표). 어긋나 있던
것은 밴드 바 하나였고, 그것을 불릿 쪽에 맞춘 것이 이번 변경의 전부다.

### 목표선은 트랙 크기이고 맨 위에 선다

`.aot-viz-target` 은 가로 바에서 트랙 **높이**만큼의 세로선, 세로 열에서 트랙
**폭**만큼의 가로선이다. 방향만 다르고 규칙은 하나다.

- **트랙 밖으로 나가지 않는다.** 예전 마커는 트랙(8px)보다 훨씬 긴 24px 라
  줄에서 가장 눈에 띄는 것이 목표였다. 목표는 기준이지 값이 아니다. 도표를
  가로지르는 긴 선으로도 그려 봤지만 *"시선이 너무 끌린다"* 는 지적을 받았다.
- **`z-index` 로 맨 위에 둔다.** 실측(초록)이 트랙 두께를 꽉 채우므로, 겹치는
  자리에서 목표가 그 아래로 들어가면 "넘었는지" 를 볼 수 없다. 이 한 줄이
  "굵은 실측이 목표를 덮는다" 는 앞선 시안들의 실패를 통째로 없앤다.

### 실측은 트랙 두께를 꽉 채운다

`.aot-viz-span`(최저~최고)은 트랙 굵기 전체다. 예전 2px 가는 선은 목표를 초록
**면**으로 그리던 때의 제약이었다 — 굵으면 그것을 덮었다. 목표가 선이 되면서
그 제약이 사라졌다.

⚠ **폭을 트랙 전체로 바꿀 때 가운데 맞춤 이동을 함께 끈다.** `left:50% +
translateX(-50%)` 를 남겨 두면 반 폭(4px)만큼 밀린다 — 실사용 지적으로 발견했다.

### 예외는 하나뿐이다 — on/off 장치의 가동시간 줄

`band({okZone: true})`. 그 줄에서 초록은 목표가 아니라 **평소 가동시간**이고
왼쪽 끝에서 자라며 길이 자체가 뜻이라, 선 둘로 옮길 수 없다. **이 손잡이를
다른 자리에 쓰지 말 것** — 번지는 순간 한 화면에 두 어휘가 다시 선다.
`test_the_only_green_zone_left_is_the_on_off_duty_row` 가 사용처를 하나로 고정한다.

### 되돌린 것들 — 다시 걷지 말 것

| 시도 | 왜 되돌렸나 |
|---|---|
| 색으로 가르기 | 실외에서 색 구분이 어렵다("색은 많을수록 혼란") · 이 파일이 이미 두 번 실패 |
| 원 마커 | 원은 조작 손잡이의 모양이다(`.aot-viz-step` ⌀12px) |
| 목표 마커에 삼각 깃발 캡 | *"그저 now 위에 붙인 것뿐인 것 같아 보여"* — 모양은 배워야 아는 기호다 |
| 기준 라벨을 마커 아래 글자로 | *"글자도 이상해"* · 세로 도표에서는 날짜와 겹친다 |
| 트랙을 [미달][목표][초과] 세 칸으로 | 가로에서는 좋았으나 세로 열은 축이 64px 뿐이라 칸이 알약에 가린다 |
| 채움 모양으로 가르기 | on/off 밴드가 `okMin: 0` 으로 왼쪽 끝부터 채워 이미 겹친다 |

## [현황] 밴드 줄은 **오늘의 최저~최고**를 그린다 (2026-09-05)

구획·시설 모달의 [현황] > 환경은 트랙 위에 녹색 점 하나(지금 값)였다. 그런데
*"지금 26.4 ℃"* 는 그것만으로 오늘이 어떤 날인지 말하지 못한다 — 새벽에 12 ℃
였는지 밤새 25 ℃ 였는지에 따라 같은 26.4 가 전혀 다른 뜻이다. 초록을 **폭**
으로 그리면 그 하루가 한 눈에 들어온다.

⚠ **프리미티브가 있다는 것과 쓰인다는 것은 다르다.** `band` 는 위 어휘 통일
(2026-09-04)부터 `spanMin`/`spanMax` 를 받았지만 **부르는 곳이 한 곳도 없어**
그 경로는 한 번도 실행된 적이 없었다. 이번에 배선한 것이 그것이다.

### 재료는 [7일] 도표와 **같은 버킷**이다

오늘의 폭과 [7일] 범위 도표는 같은 계열(`/env_week` → `recent_env_trends`)의
같은 버킷에서 나온다. 따로 계산하면 같은 하루를 두 보기가 다르게 말한다 —
토글 한 번에 숫자가 바뀌는 화면은 어느 쪽도 못 믿게 만든다.

그래서 조회 시점도 바뀌었다. 계열은 **누를 때만** 받다가(2026-09-05 오전,
근거는 "안 눌러도 매번 0.9~1.5초짜리 조회가 돈다") 이제 **첫 그림 뒤 배경에서**
한 번 받는다 — 기본 보기의 재료가 되었으므로 헛일이 아니다. 값은 `/contents`·
`/runtime` 에 이미 있어 즉시 뜨고 폭만 한 박자 늦게 채워진다.

⚠ **`?days=1` 로 좁혀도 아끼는 것이 없다.** `env_channel_series` 는 채널당
질의 수가 기간과 무관하다(min·max·mean 3회). 7일을 받아 [7일] 버튼까지
즉답하게 하는 편이 낫다.

### 어느 버킷이 오늘인가 — `k` 로 찾는다

**마지막 점을 오늘로 삼으면 안 된다.** 창의 끝은 늘 오늘이 아니고(단계 창·
`?end=`), 단위가 주면 마지막 버킷은 하루가 아니라 그 주다 — 그것을 오늘의
폭이라고 그리면 **일주일치 진폭이 하루로 보인다.** 서버가 `window.end` 로
말해 주고 화면은 그 키를 가진 점을 찾는다. 키가 없으면 폭을 그리지 않는다.

같은 이유로 날짜를 화면에서 만들지 않는다 — 브라우저 시간대로 자르면 시차가
있는 설치에서 하루 어긋난다.

### 그리지 않는 것 · 보정하는 것

- **누적형(`bars`)에는 폭이 없다.** 강우·DLI 처럼 0 에서 쌓이는 값의 "그날
  최저~최고" 는 읽은 값의 진폭이지 쌓인 양이 아니다 — 폭으로 그리면 누적을
  진폭으로 오독하게 된다.
- **판정 단위로 환산한다.** VPD 는 Pa 로 저장하는 입력과 kPa 로 저장하는 입력이
  공존한다. 지금 값이 `bandValue` 로 환산돼 축에 놓이므로 폭도 같은 함수를
  지나야 한다 — 안 그러면 630 Pa 짜리 최고가 kPa 축의 오른쪽 끝에 박힌다.
- **지금 값으로 폭을 넓힌다.** 계열은 10분 캐시라 방금 찍힌 최고를 아직 모를 수
  있는데, 그때 지금 값이 초록 밖에 서면 같은 줄이 스스로를 반박한다. 얼버무림이
  아니다 — 지금 값도 오늘의 관측이므로 정의상 그 폭 안이다.
- **숫자는 적지 않는다.** 폭을 글자로도 쓰면("오늘 22.8–33.7") 같은 줄의 기준
  라벨과 대시 표기가 같아 한 덩어리로 읽히고, 줄이 여섯이면 그 혼동도 여섯이다.

### 지금 위치는 트랙 **바로 위**의 역삼각형이다

폭이 초록을 차지하면서 "지금 이 안 어디쯤" 을 가리키는 표식이 사라졌다 —
숫자는 머리줄에 남지만 목표선과의 거리를 눈으로 못 잰다. 그것을 트랙 위의
▼ 가 되돌린다(`.aot-viz-cursor`).

**축을 하나 새로 쓴다 — 트랙 안이냐 밖이냐.** 트랙 안에는 이미 셋이 서 있고
(초록 실측 · 목표 직각선 · 회색 축), 그 안에서 넷째를 가르려던 시도는 위
"되돌린 것들" 표대로 여섯 번 전부 되돌아왔다. 안과 밖은 색을 늘리지 않고도
뜻을 가르는, 남아 있던 유일한 축이다.

- **색은 목표선과 같다**(`--aot-viz-mark`). 색을 늘리지 않는다는 규칙 그대로다
  — 초록(실측)과 갈리는 것이 색이고, 지금과 목표는 자리로 갈린다.
- **마커와 같은 캡 보정을 쓴다.** 빠뜨리면 트랙 라운드 밖을 가리켜 끝값에서
  최대 4px 어긋난다.
- **자리는 클래스로 마련한다**(`.aot-viz--cursor`, 빌더가 뿌리에 새긴다).
  `:has()` 를 쓰지 않는 이유는 지원 범위이고, 어느 줄이 삼각형을 갖는지
  소스에서 바로 보이는 편이 낫다.
- **on/off 가동시간 줄에는 없다.** 그 줄의 `.aot-viz-now` 가 이미 '오늘'
  이라, 삼각형을 더하면 같은 것을 두 번 가리킨다.

### 같은 밴드를 쓰는 화면은 셋이다

지도 위젯의 **구획 모달** · **시설 모달** · 대시보드의 **구획 위젯**. 셋 다
`AoTMapPopup.buildEnvNowHtml` 하나를 부르지만, **폭을 그리려면 부르는 쪽이
계열과 `weekToday` 를 넘겨야 한다** — 배선을 빠뜨린 화면은 같은 함수를 쓰면서도
예전 그림으로 남는다. 에러가 없으니 그 사실은 눈으로 견줄 때만 드러난다.

구획 위젯은 창을 고를 수 있어([오늘][일][주], 축에서 고른 단계가 창이 된다) 한
가지가 더 있다: **오늘의 폭은 고른 단계와 무관하게 늘 최근 7일·일 단위 창에서
온다.** [오늘] 줄의 숫자는 지금 값이라, 지난 단계의 창에서 오늘을 찾으면 아무
것도 안 나온다 — 그러면 단계를 골라 둔 사람만 폭을 잃는다. 그 창의 캐시 키는
[일] 모드와 **같게 맞춰 두었다**(같은 창을 두 번 묻지 않는다).

⚠ **단위 손잡이는 자료가 없다고 접지 않는다.** 그것은 자료가 아니라 보는
방법이고, 그중 [오늘] 은 언제나 내용이 있다. 접으면 지금 서 있는 칸까지 사라져
되돌아올 길이 없어진다 — [일] 을 눌러 빈 창을 만난 사람이 [오늘] 로 못 돌아오던
자리다. 계열을 미리 받게 되면서 **누르지 않아도** 그 상태에 닿을 수 있게 되어
드러났다. 빈 창은 손잡이를 없애는 대신 `rangeEmptyText` 가 말한다.

### 일지의 **한 기간짜리** 밴드도 같은 규칙이다

일지가 담는 기간이 하나뿐이면 범위 도표 대신 밴드 바를 쓴다(위 "기간이 하나면
이 그림을 쓰지 않는다"). 그 밴드도 그 버킷의 최저~최고를 초록 폭으로, 값
(그 기간 평균)을 ▼ 로 그린다 — 한 화면만 고치면 같은 값이 화면마다 다르게
읽히고, 그것이 2026-09-04 에 이 파일이 겪은 실패다.

`bars`(0 에서 쌓이는 값)는 폭을 더해도 여전히 **불릿**이다. 누적을 진폭으로
오독하게 하는 것은 폭이 아니라 그림의 종류다.

스냅샷에 min/max 가 없는 옛 일지는 폭 없이 값 점과 ▼ 만 남는다(예전 그림).
`pct()` 가 숫자가 아닌 값에 `null` 을 돌려주는 것이 그 안전장치다.

## 값 풍선 — 마우스는 따라다니고, 터치는 머문다 (2026-09-04)

사용자 지적: *"스마트폰에서 터치하면 툴팁으로 값을 보여주는데, 터치를 떼면
바로 사라져서 불편함."*

손가락은 값 위에 머무를 수 없다 — 짚은 순간 그 자리를 가리고, 떼면 볼 것이
사라진다. 그래서 터치에서는 **다음에 짚을 때까지 그대로 둔다.**

⚠ **`pointerleave` 로 닫는 것은 마우스뿐이다.** 터치도 손을 떼면 그 이벤트가
온다(포인터가 사라지므로) — 구분하지 않으면 떼는 순간 닫힌다. 이것이 그
증상의 원인이었다. 코드에는 "터치는 손을 떼도 `pointerleave` 가 오지 않는다"
는 주석이 달려 있었는데, 사실이 아니었다.

닫는 길은 남겨 둔다 — **다른 곳을 짚으면** 닫힌다. 그 배선은 문서 단위이고
**한 번만** 건다: 예전에는 도표마다 `document` 에 걸어서, 일지 한 장(범위
도표 19개)을 열면 같은 일을 하는 리스너가 19개 쌓였다.

## 축은 하루가 혼자 정하지 못한다 (2026-09-04)

진폭을 그리기 시작하니 **튄 값 하나가 한 주를 납작하게 만들었다.** 실측:
쿠마모토 온실에서 09-01 에 온도 54.9 °C 가 한 번 찍혔고(다른 날은 32~33), 그
값에서 계산된 VPD 가 10.97 kPa 였다. 축이 그것까지 담느라 0~15 로 늘어나
나머지 엿새의 막대가 전부 바닥에 깔렸다 — **읽을 수 있는 날이 사고가 난 그
하루뿐**이었다.

밴드 바에는 없던 문제다. 그쪽 축은 앱의 밴드 표에서 오는 **고정값**이고,
범위 도표만 축을 데이터에서 만든다(`plot_journal.value_scale`).

### 판정은 하루 단위로 — 분위수로 하지 말 것

`value_scale(values, keep=, groups=)` 가 **한 버킷을 빼고 다시 재 본다.**
그것만 빼도 축이 30% 이상 줄면 그 축은 그 하루가 혼자 정한 것이므로, 나머지에
맞춰 잡는다. 데이터를 고치는 것이 아니라 축만 그렇게 잡고, 밖으로 나간 값도
그대로 그려진다 — `pct()` 가 0~100 으로 눌러 축 끝에 붙인다.

⚠ **먼저 분위수(IQR) 울타리로 만들었다가 실측에서 버렸다.** 한쪽으로 쏠린
계열에서 **멀쩡한 값을 자른다** — 청자5호는 VPD 가 대부분 0 근처라 3·IQR
울타리로도 2.9 kPa 가 잘렸고(정상값이다), 습도 56% 도 잘렸다. 이 화면의
실패는 "분포가 넓다" 가 아니라 **"하루가 튀었다"** 이므로 판정도 하루
단위여야 한다.

⚠ **목표(`keep`)는 분위수든 무엇이든 계산에 섞지 않고, 축 안에 반드시
담는다.** 목표만 그림 밖으로 나가면 "한참 못 미쳤다" 가 "목표가 없다" 로
보인다.

### 눈금 간격은 올림이 아니라 가까운 쪽

`_nice_step` 이 항상 올림이라 간격이 최대 두 배가 되고, 간격이 두 배면 축의
양 끝도 그만큼 밖으로 밀렸다 — 실측: 온도 12~42 구간에서 대충 간격 10.07 이
20 으로 올라가 축이 **0~60** 이 됐고 데이터가 화면의 3분의 1만 차지했다.
가까운 쪽(10)으로 맞추면 10~50 이다. 눈금이 몇 개 더 생기는 것은 문제가
아니다 — 범위 도표는 양 끝과 가운데 **셋만** 글자로 낸다.

| 쿠마모토 습도 | 0~100 | **20~100** |
| 데이터가 축에서 차지하는 비율(26계열 평균) | — | **79%** |
| 축 밖으로 나간 값 | — | 75계열 중 **10개**(09-01·09-04 두 날) |

## 범위 도표는 그 기간의 **진폭**을 그린다 (2026-09-04)

`range()` 는 오래 `p.avg` 하나만 읽었다(`p.min`/`p.max` 는 서버가 실어 보내는데
아무도 안 봤다 — 최저~최고는 마우스 풍선 문구에만 있었다). 그런데 **하루 평균은
낮과 밤을 섞은 값**이라, 34도까지 오른 날과 종일 25도인 날이 같은 자리에 선다.
"이번 주 중 오늘은 어느 정도인가" 를 묻는 화면에서 그것이 답의 절반을 지운다.

이제 최저~최고가 오면 그 구간을 **2px 세로선**(`.aot-viz-span`)으로 긋는다.

- **색은 마커와 같다.** 진폭도 마커도 실측이다 — 목표(초록)와 갈리는 것은
  색이지 이 둘 사이가 아니다.
- **가늘어야 한다.** 트랙 폭(8px)까지 굵혀 본 시안에서 뒤에 깔린 목표대(초록
  면)가 거의 사라져 "목표 대비 어디인가" 를 읽을 수 없었다. 2px 이면 초록이
  좌우로 남는다.
- **진폭을 그리면 평균 마커는 그리지 않는다.** 최저·평균·최고 셋을 칸 폭
  38px 짜리 화면에 세우면 무엇이 기준인지 모양이 말해 주지 못한다 — 한계선
  셋을 세웠다가 되돌린 것(`.aot-viz-limit`)과 같은 이유다. 값은 풍선이 말한다.
- **최저·최고가 없거나 폭이 0 이면**(그 기간에 값이 하나뿐) 예전처럼 평균
  마커를 찍는다. 최소 높이를 줘서 진폭이 있는 척하지 않는다.
- 누적형(`bars`)은 그대로다 — 거기서 "그날의 최저~최고" 는 뜻이 없다.

⚠ **아직 안 그리는 것: `coverage_low`.** 서버는 결측이 많은 버킷에 이 표식을
달지만 `range()` 가 읽지 않아, **자료가 반쯤 빈 날이 정상인 날과 똑같이
보인다.** 진폭을 그리기 시작한 지금은 그 오독이 더 커졌다(짧은 막대가 "안정된
날" 인지 "몇 시간치만 있는 날" 인지 갈리지 않는다). 표시 수단을 정할 때
**새 투명도를 만들지 말 것** — 범위 도표 CSS 블록은 색·배경·투명도를
선언하지 않는다는 규약이 있고 테스트가 그것을 검사한다.

## 범위형과 누적형 — 마커 모양이 가른다 (2026-09-04)

한 카드 안에서 밴드 바와 불릿이 나란히 서면 **세로선과 초록이 줄마다 반대
뜻이 된다**:

| | 마커(세로선) | 초록 |
|---|---|---|
| 밴드 바(범위형) | 지금 값 | 적정 범위 |
| 불릿(누적형) | **목표** | **지금까지 쌓인 양** |

2026-08-20 에는 "한 줄에 둘이 함께 서는 경우가 없으니 같은 모양이어도 된다"
고 판단했고, 그 말 자체는 지금도 맞다. 그러나 그것은 **한 줄 안**의 문제였고
실제 신고는 **줄과 줄 사이**에서 나왔다("GDD, DLI: 목표값 = now, 현재값 =
band 사용. 나머지 측정값: 반대로 설정 됨"). 섞여 서는 자리가 실측으로 넷이다:

1. 지도 위젯 [현황] "환경" 카드 — DLI·GDD(불릿) 위에 VPD·온도·습도(밴드)
2. 지도 위젯 [제어 상태] 환기 그룹 — 비례 개도(불릿)와 on/off 장치(밴드)가
   **장치 정의 순서대로 섞여** 한 묶음에 든다
3. 구획 위젯 [진행] 카드 — 기간 바와 적산온도 불릿
4. 일지 보고서 — 범위 도표와 누적 막대

### 시도했다 되돌린 것들 — 표현으로는 안 풀렸다

**색으로 가르지 않는다.** 실외에서 색 구분이 어렵다는 지적이 있었고("색은
많을수록 혼란이 커짐 — 특히 야외 활동이 많은 경우 모니터 식별 어려움"),
이 파일이 이미 같은 실패를 겪었다(§색은 셋뿐이고…).

**채움 모양으로도 못 가른다.** "불릿의 채움은 왼쪽 끝에서 자라고 밴드의
초록은 떠 있으니 이미 갈린다" 는 기대는 실측에서 깨졌다 — on/off 장치 밴드가
`okMin: 0` 을 줘서 그 초록도 왼쪽 끝에서 자란다(`aot-map-popup.js` `_rowOf`
— "왼쪽 끝부터 평소까지 채운다"). 하필 그 카드가 위 2번, 둘이 섞이는 자리다.

**원도 못 쓴다.** 원은 조작 손잡이의 모양이다(`.aot-viz-step`,
`.aot-3way-current-dot` 둘 다 ⌀12px) — 읽기 전용 표식이 원이면 만질 수 있는
것으로 읽힌다. 2026-08-20 에 "채운 원=현재 / 속 빈 원=목표" 를 되돌린 이유가
이것이고, 그 이유는 지금도 유효하다.

**깃발 캡도 되돌렸다(2026-09-04).** 목표 마커에만 삼각 표식을 얹어 봤다.
사용자 반응이 답이었다 — *"깃발이 있으면 의미가 다르다는 거야? 잘 모르겠는데"*,
*"그저 now 위에 붙인 것뿐인 것 같아 보여"*. 모양은 **배워야 아는 기호**라,
처음 보는 사람에게 삼각형은 "다른 종류" 가 아니라 "같은 마커에 붙은 혹" 으로
읽힌다.

**기준 라벨 글자도 반려됐다** — *"글자도 이상해"*.

### 남은 물음 — 이것이 표현의 문제인가

표현을 네 가지로 바꿔 봐도 안 풀린 뒤에 나온 지적이 문제의 자리를 옮겼다:

> 처음에는 데이터를 복합적으로 압축해서 보여주겠다는 의도로 진행했음. 하지만
> 사실상 **환경/제어 탭에서 지금 상태를 거의 다 확인할 수 있는 중복 데이터를
> 다른 형식으로 보여주는 것 뿐임.** 다만 목표를 추가해서 어느 범위에 있는지는
> 알 수 있음.

즉 지도 위젯 [현황] "환경" 카드는 **[환경·제어] 탭과 같은 것을 다른 그림으로**
말하고 있고, 더한 것은 목표 하나다. 두 표현이 한 화면에서 부딪히는 것을 표현
규칙으로 봉합하기 전에, 그 카드가 **무엇을 답해야 하는가**를 먼저 정해야 한다.

방향 제안(미구현): 일지의 `range` 가 값을 갖는 이유는 **더 넓은 범위에서 지금을
보여주기** 때문이다. [현황] 카드도 "지금 몇 도인가"(이미 다른 탭에 있다) 대신
**"지난 1주일 중 오늘은 어디쯤인가"** 를 답하면, 중복이 사라지고 두 시각 언어가
한 카드에서 부딪힐 일도 없어진다.

### 같은 지표는 어느 화면에서나 같은 어휘로 (2026-09-04)

규칙을 세우고 나니 **같은 값이 화면마다 다른 타입으로 그려지고 있었다**:

- 지도 위젯의 DLI·적산온도 → 불릿(채움=쌓인 양, 깃발=목표)
- 일지 보고서의 같은 지표(기간이 하루뿐일 때) → 밴드 바(초록=목표 범위,
  세로선=값). `envChart()` 가 `pts.length === 1` 에서 `bars` 를 보지 않았다.
- 일지의 장치 가동시간(단일 기간) → 밴드 바. 가동시간은 "0 에서 쌓인 양"
  이지 축 위의 한 점이 아니다.

`bars`(=0 에서 쌓이는 계열: 적산온도·DLI·일사·강수·가동시간)이면 기간 수와
무관하게 누적형으로 그린다.

**범위 도표(`range`)의 누적형 열에서 목표를 초록 면으로 그리지 않는다.**
그렇게 하면 한 트랙 안에서 초록이 '목표대' 와 '쌓인 양' 두 뜻으로 서고, 어느
초록이 무엇인지 모양이 말해 주지 못한다. 가로 도표의 불릿과 같은 어휘로
목표 마커를 세우되, **쌓인 막대 위에 얹는다** — 먼저 깔면 막대가 목표를
넘었을 때 그 위를 덮어 "넘었는지" 를 볼 수 없다.

## 아직 글자만인 것 — 다음 후보

| 자리 | 지금 | 제안 |
|---|---|---|
| 제어 상태 — 편차/한계 줄 | 문장 | 편차를 **한 줄 막대**로(목표 0 기준, 좌우) |
| 기록 — 다가오는 일정 | 날짜 목록 | 오늘부터의 **거리 축**(기간 바 재사용) |
| 관수 — 마지막 관수 | "3시간 전" | **주기 대비** 막대(평균 간격 대비 경과) |
| 장치 목록 — 통신 상태 | 배지 | 배터리·신호를 0–100% 막대로(이미 값이 있다) |
| 단계 전환 제안 | 문장 + 버튼 | 기간 바 위에 **제안 지점**을 표시 |
| 값만 나오는 측정 (CO2·토양수분·이슬점) | 숫자 | 축이 없으므로 **스파크라인**(최근 N개) — 범위 없이도 "오르는 중/내리는 중" 을 말한다 |

마지막 줄이 특히 중요하다: 축(적정 범위)을 만들 수 없는 지표는 지금 구조에서
영원히 글자로 남는다. **추세는 범위를 몰라도 그릴 수 있다** — 값 하나로는 못
하는 말을 최근 몇 개의 값이 한다.

## 붙이는 법

```html
<link rel="stylesheet" href="/static/css/components/aot-dataviz.css?v=1">
<script src="/static/js/common/aot-dataviz.js?v=1"></script>
```

- 버전 쿼리 없이 붙이지 말 것 — 정적 자산은 `max-age` 1년으로 나간다
  (`check_static_cache_busting.py`).
- 위젯 `.py` 의 head 문자열을 고쳤으면 `generate_widget_html()` 을 다시 돌려야
  페이지에 반영된다(CLAUDE.md 의 위젯 템플릿 재생성 규칙).
- 번들에 넣는 경우 `tools/bundles.json` 에 올리고 재빌드까지 한 커밋에
  담을 것(`check_js_bundles.py`).

## 담는 곳

마커 둘레의 링은 색이 아니라 **담는 카드의 바탕**이다(`--aot-viz-surface`,
기본 `--aot-surface-card`). `.aot-ov-block` 안에서는 그대로 맞는다. 배경이
다른 곳에 넣으면 그 요소에 `--aot-viz-surface` 를 지정할 것 — 안 하면 마커
둘레에 카드색 테두리가 뜬다.
