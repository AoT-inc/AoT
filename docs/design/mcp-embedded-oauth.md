# MCP 내장 인가 서버 — 중앙 서버 없이 claude.ai 커넥터 연결

상태: **초안** (2026-10-19). 구현 전. 결정이 필요한 항목은 §9.

## 1. 왜

claude.ai 커넥터는 헤더에 API 키를 넣을 수 없어 OAuth 인가 서버가 있어야 붙는다. 지금은 인가 서버가 `auth.aotinc.co.kr`(aot-auth) 하나뿐이고 그 계정은 AoT 직원 전용이다. 고객이 자기 AoT 를 커넥터로 쓰려면 AoT 가 스스로 인가 서버가 되어야 한다. 중앙 인증은 지우지 않고 선택지로 남긴다([mcp-central-auth](../ai/overview.md#central-auth)).

## 2. 범위

- 한다: AoT 본체(`aot-app`)에 OAuth 2.1 인가 서버 경로를 내장한다. 로그인한 AoT 사용자가 곧 토큰 주인이다.
- 안 한다: 사설망·VPN 안의 설치(커넥터는 Anthropic 클라우드에서 접속하므로 **인터넷에서 닿는 HTTPS 주소가 전제**다. 그런 설치는 API 키 방식을 쓴다), 다중 사이트 통합 로그인(중앙 서버의 일), Claude 외 AI 클라이언트 확장(허용 목록에 콜백만 더하면 된다).

## 3. 배치 — 새 컨테이너 없음

| 구성 | 자리 | 이유 |
|---|---|---|
| 인가 서버 경로 | `aot-app`(Flask 블루프린트) | 로그인·세션·TOTP·동의 화면이 이미 있다 |
| 토큰 검증 | `aot_mcp`(기존) | `aot_data` 볼륨의 키 파일·DB 를 `aot-app` 과 공유한다 |
| 리버스 프록시 | 한 도메인, 경로 분기 | `/mcp`·`/.well-known/oauth-protected-resource*` → 5700, 나머지(인가 서버 경로 포함) → 8084 |

내장 모드는 **MCP 공개 주소와 웹 공개 주소가 같은 출처**여야 한다(프록시 규칙을 하나로 유지). 발급자(`iss`)는 그 출처(경로 없음)다.

## 4. 경로

| 경로 | 하는 일 |
|---|---|
| `/.well-known/oauth-authorization-server` | 인가 서버 메타데이터(RFC 8414). PKCE `S256` 만, `resource` 지원 |
| `/register` | 동적 클라이언트 등록(RFC 7591) — 되돌림 주소 허용 목록만 |
| `/authorize` | 로그인 확인 → 동의 → 인가 코드 |
| `/token` | 코드 교환·갱신 |
| `/revoke` | 갱신 토큰·연결 끊기 |
| `/.well-known/jwks.json` | 공개 키 |

보호 자원 메타데이터(`/.well-known/oauth-protected-resource`)는 지금 코드가 그대로 낸다. `authorization_servers` 가 자기 출처를 가리키게만 바꾼다.

## 5. 흐름과 규칙

중앙 서버 설계(aot-auth 저장소의 `docs/DESIGN.md` §2~§4)를 따른다. 달라지는 점만 적는다.

- **`resource` 필수**, MCP 공개 주소와 정규형까지 정확히 같아야 한다(없으면 `invalid_target`). 인가 코드·갱신 토큰은 처음 인가 때의 `resource` 에 묶인다. 정규화는 기존 `central_verify.normalize_resource` 를 쓴다.
- **로그인·동의**: 기존 로그인 세션을 쓴다. 비로그인이면 로그인 화면으로 보냈다가 `/authorize` 로 돌아온다. TOTP 를 켠 사용자는 기존 로그인 그대로 TOTP 를 거친다. 동의 화면은 **이 AoT 의 이름(농장 이름)을 가장 크게** 보이고 범위 3개(`aot.read` 필수·`aot.control`·`aot.config`)를 고르게 한다. 사용자 역할이 못 하는 범위는 꺼 둔다(토큰 범위 ∩ 역할은 `mcp_central.restrict_role` 이 어차피 적용).
- **계정 연결 단계 없음**: `sub` 가 곧 AoT 사용자 id 다. 중앙 모드의 `MCPExternalAccount` 연결·"내 계정 연결" 버튼은 내장 모드에서 쓰지 않는다.
- **토큰**: JWT(`typ: at+jwt`), ES256, 접근 1시간, 갱신 30일(쓸 때마다 교체, 옛 토큰이 다시 오면 그 연결 전체 끊기). `gid`(연결 식별자)를 싣는다.
- **다중 워커**: gunicorn 이 워커 여러 개로 돈다. 코드·갱신 토큰·등록 클라이언트·폐지 상태는 **전부 DB**(SQLite)에 둔다. 프로세스 메모리에 두지 않는다.

## 6. 저장

alembic 마이그레이션 하나로 표 3개를 더한다.

| 표 | 내용 |
|---|---|
| `oauth_client` | `client_id`, 이름, 되돌림 주소 목록, 만든 때, 마지막 사용 |
| `oauth_code` | 코드 해시, `client_id`, 사용자, `resource`, 범위, PKCE 챌린지, 만료(60초), 사용 여부 |
| `oauth_grant` | `gid`, 사용자, `client_id`, `resource`, 범위, 갱신 토큰 해시(이전 해시 1개 보관해 재사용 감지), 만료, 상태(활성·끊김) |

코드·갱신 토큰은 해시(SHA-256)만 저장한다. 사용자 삭제·비밀번호 변경 시 그 사용자의 `oauth_grant` 를 끊는다.

## 7. 서명 키

- ES256 개인 키 파일 하나: `aot_data` 볼륨 안, 권한 600. 내장 모드를 처음 켤 때 자동 생성한다. DB·로그·백업 JSON 에 넣지 않는다(백업은 키 파일을 제외하거나 암호화 — 구현 때 `docker_backup` 범위 확인).
- `aot-app` 이 서명하고 `aot_mcp` 가 같은 파일에서 공개 키를 읽어 검증한다. JWKS 를 HTTP 로 되받지 않는다.
- 키는 **설치마다 따로**다. 한 설치의 키가 새도 다른 설치 토큰은 위조되지 않는다(중앙 서버의 "키 하나가 전부" 위험이 없다). 교체 절차는 중앙과 같다(새 키를 먼저 게시, 1시간 뒤 서명 전환, 옛 키는 마지막 토큰 만료 뒤 제거).

## 8. 토큰 검증 (`aot_mcp`)

`aot/tools/central_verify` 의 확인 규칙(서명·`alg` ES256 고정·`typ`·`iss`·`aud`·`exp`/`nbf`)을 그대로 쓰되 키 출처만 바꾼다. 새 모드: 파일 키 + `oauth_grant` 상태 조회(폐지 목록을 HTTP 로 받지 않는다). `mcp_central.authenticate` 가 토큰의 `sub` 를 AoT 사용자로 바로 매긴다. 요청마다 DB 한 줄 조회이며, 부담이 보이면 30초 캐시를 둔다.

설정 모달의 "인증 서버" 칸은 **중앙 / 이 AoT(내장)** 중 고르는 방식이 된다. 내장을 고르면 인가 서버 주소·클라이언트 ID·비밀키 칸은 숨기고 "공개 주소" 하나만 받는다.

## 9. 결정할 것

1. **중앙과 내장을 동시에 켤 수 있나?** 제안: 한 번에 하나. 바꾸면 이전 모드의 토큰은 `iss` 가 달라 자연히 무효.
2. **구현 방식**: aot-auth 는 MCP SDK 인가 서버 경로를 쓰지만 AoT_ai 의 MCP 서버는 SDK 없이 Flask 로 구현돼 있다. 제안: SDK 를 새로 들이지 않고 `joserfc`(이미 의존성)로 JWT 를 다루고 흐름은 직접 구현한다(코드·PKCE·갱신 교체는 작다).
3. **되돌림 주소 허용 목록의 첫 값**: aot-auth 1단계 시험에서 고정한 값과 맞춘다. 그 값을 먼저 확인해야 한다(여기서는 아직 확인하지 않았다).
4. **남용 방어**: `/register`·`/token`·로그인 시도 횟수 제한. 기존 제한 수단이 있는지 구현 전에 확인한다. 없으면 최소한의 IP 당 제한을 더한다.
5. **인터넷 노출 안내**: 이 모드를 켜려면 AoT 를 인터넷에 열어야 한다. 설정 화면과 매뉴얼에 그 위험(로그인 화면·`/mcp` 노출, 비밀번호 강도, TOTP 권장)을 분명히 적을지.

## 10. 단계

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 1 | 표 3개·키 생성·메타데이터·`/register`·JWKS | 메타데이터를 클라이언트가 읽고 등록까지 됨 |
| 2 | `/authorize`(로그인 복귀·동의)·`/token`·갱신·`/revoke` | HTTP 로 코드→토큰→갱신→끊기 전체 시험 통과 |
| 3 | `aot_mcp` 검증 연결, 설정 모달 선택 UI | 내장 토큰으로 `/mcp` 도구 호출 |
| 4 | 적합성 시험: 다른 `aud`·끝 `/`·만료·`nbf` 미래·서명 틀림·`alg: none`/HS256·`typ` 틀림·끊긴 `gid`·재사용된 갱신 토큰 (aot-auth `tests/` 를 참고해 옮김) | 전부 401/거부. 그 뒤 claude.ai 실제 연결 |
| 5 | 매뉴얼 `docs/ai/overview*.md`(central-auth 절 옆) 갱신 | 3개 언어 |

## 11. 리소스

별도 프로세스·DB 가 없으므로 상시 메모리 증가는 거의 없을 것으로 본다(추정, 실측 전). 서명은 토큰 발급·갱신 때만 일어난다.
