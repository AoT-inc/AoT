# 지도 데이터 무결성 — 불변식 카탈로그와 강제 계층

2026-08-03 지도 데이터 오염 사고(복제 결함 → 도형 이중화 → 시설·zone 연결 단절)의
재발을 **구조적으로** 차단하기 위한 정본 문서. 전수조사(쓰기 48곳 · 읽기 90+곳 ·
링크/복제 12경로 · 프런트 저장 13경로)에서 오염원 24건이 확인됐고, 결론은
"개별 버그가 아니라 구조"였다.

## 설계 원칙

1. **잘못된 상태를 표현 불가능하게 만든다.** 검사해서 거부하는 방어(앱 계층 가드)는
   다음 코드 경로가 우회하면 끝이다. 핵심 불변식은 **DB 계층**(트리거·유니크 인덱스)
   에 둔다 — ORM·원시 SQL·alembic·AI 대량생성·복제, 어떤 경로든 통과하지 못한다.
2. **같은 사실은 한 곳에만 저장한다.** 도형의 종류가 5개 필드(`type`,
   `properties.aot_type`, `level_id`, `category`, `sub_type`)에 중복 저장된 것이
   드리프트의 뿌리다. 정본은 `GeoShape.type` 컬럼 하나. 나머지는 읽기 시 파생.
3. **파생 가능한 링크는 저장하지 않는다.** `map_overlay_id`(장치→zone 소속)는 마커
   좌표에서 완전히 유도된다. 저장하지 않으면 복제·대량생성·재생성이 오염시킬 수 없다.
4. **완성 판정은 주장이 아니라 공격 테스트로 한다.** 각 불변식마다 원시 SQL로 위반을
   시도하는 테스트가 있고, DB가 거부해야 통과한다.
   (`aot/tests/geo/test_geo_invariants_attack.py`)

## 불변식 카탈로그

| ID | 불변식 | 강제 수단 | 단계 |
|----|--------|-----------|------|
| I1 | `geo_shape.type` ∈ 화이트리스트 | 트리거 (INSERT/UPDATE ABORT) | Tier-1 |
| I2 | 장치 위치 마커는 (지도, 장치, 채널)당 정확히 1개 | 부분 유니크 인덱스, `COALESCE(channel_id,'0')` 식 인덱스로 NULL/'0' 비대칭 봉쇄 | Tier-1 |
| I3 | 도형 삭제 시 그 도형에 매달린 GeoFacility·Setpoint·bay 가 함께 삭제 | 트리거 (AFTER DELETE 연쇄) — 삭제 12경로 전부 커버 | Tier-1 |
| I4 | 도형 삭제 시 그 도형을 가리키던 7개 모델의 `map_overlay_id` 는 NULL | 트리거 (ON DELETE SET NULL 에뮬레이션) | Tier-1 |
| I5 | 지도 삭제 시 소속 도형·시설 삭제 + 7개 모델의 `map_config_id` NULL | 트리거 | Tier-1 |
| I6 | 저장된 feature JSON 에 `properties.aot_type` 키가 존재하지 않음 (읽기 시 서버가 주입) | 트리거 (`json_extract` 검사) | Tier-2 |
| I7 | `type` 은 생성 후 불변 (종류 변경 = 삭제 후 생성) | 트리거 (UPDATE OF type ABORT) | Tier-2 |
| I8 | `geo_shape.geo_id` 는 실존하는 `geo_map` 을 가리킴 (유령 지도 금지) | 트리거 | Tier-2 |
| I9 | 삭제는 명시 목록으로만 — "페이로드 누락 = 삭제" 프로토콜 폐지 | 앱 계층 (저장 프로토콜 교정) + CI | S3 |
| I10 | `clone_model` 은 교차참조 컬럼(map_overlay_id·map_config_id·geo_id)을 암묵 복사하지 않음 | 앱 계층 + 단위 테스트 | S3 |
| I11 | 소속(장치↔zone)은 저장하지 않고 마커 좌표에서 파생 | 컬럼 미사용 + `device_membership` 단일 리졸버 | S3 |
| I12 | 지도 데이터 쓰기는 geo 패키지 안에서만 — 밖은 게이트웨이 경유 | `check_geo_writes.py` (AST) + pre-commit + CI | S5 |

**Tier-1** 은 현재 데이터·현재 앱 코드와 즉시 호환된다. 단 I2 인덱스 생성 전
S2 마이그레이션에서 두 가지 사전 정리가 필수다: ① `aot_device` 마커의
`channel_id NULL → '0'` 정규화 — 장치위치 API 는 `'0'` 으로 조회하므로 NULL
레거시 행을 못 찾아 INSERT 를 시도하고, 인덱스가 이를 거부하면 위치 저장이
막힌다. ② 기존 중복 마커 정리(참조 확인 후 — 검사기 duplicate 절차 준수).
**Tier-2** 는 앱 코드 수정(저장 시 aot_type 제거, 라벨 되먹임 절단)이 선행돼야
켤 수 있다 — 그 전에 켜면 정상 기능이 막힌다.

## 트리거를 택한 이유 (FK 재구축 대신)

- SQLite 에서 기존 테이블에 FK/CHECK 를 추가하려면 테이블 재구축(batch rebuild)이
  필요하다. 운영 3서버에서 위험이 크다.
- `PRAGMA foreign_keys=ON` 은 전역 스위치라, geo 와 무관한 기존 위반
  (widget→tab 유령 48~51건/서버)까지 한꺼번에 터진다.
- 트리거는 `CREATE TRIGGER` 한 번으로 붙고, **geo 불변식만** 선별 강제하며,
  원시 SQL·bulk delete·alembic 까지 전부 잡는다. 우회 수단이 없다.

트리거 본문은 재귀를 피해 평탄화돼 있다(`recursive_triggers` OFF 기본값 하에서
동작). 도형 삭제 트리거가 bay 를 지울 때 bay 의 삭제 트리거는 재발화하지 않지만,
bay 는 시설·하위를 갖지 않으므로 안전하다.

## 지도 소유권 모델 (정본)

### 왜 이 절이 필요한가 — 초기 모델의 화석

AoT 초기에는 대지(site)·시설(facility) 개념이 없었고 지도 위에 장치만 있었다.
그래서 **장치가 지도를 소유하는** 모델로 출발했다 — 장치마다 `map_config_id`
를 부여하고 장치 쪽에서 지도를 호출·관리했다. 당시에는 옳은 설계였다.

이후 site·zone·facility 가 도입되면서 위치를 결정하는 핵심이
**장치 → 지리요소**로 옮겨갔다. 그런데 `map_config_id` 만 초기 모델 자리에
남았고, 규칙이 정비되지 않은 채 진행됐다. 그 결과 "이 장치가 어느 지도에
속하는가"에 답이 세 개가 됐다:

| 답 | 성격 |
|----|------|
| `map_config_id` 컬럼 | 초기 모델의 잔재 — 자동 생성되고 실제로는 아무도 안 쓴다 |
| `GeoShape.geo_id` (마커가 놓인 지도) | **실제 배치 = 사실** |
| 지리요소 계층(site⊃zone⊃장치) | 기하가 결정 — S3 에서 정비 완료 |

`map_config_id` 는 `map_overlay_id` 와 정확히 같은 운명이다. S3 에서
"장치↔zone 소속"은 이미 저장 컬럼에서 마커 좌표 파생으로 바꿨는데,
"장치↔지도 소속"은 저장 컬럼에 남아 **대칭이 깨진 채 절반만 정비된 상태**가
지금의 혼란이다.

2026-08-04 실측(운영 3서버): 장치 67개가 전부 `map_config_id` 를 갖는데
지도 43개 중 **도형이 있는 것은 4개(9%)**, 빈 지도 + 무참조가 koat 47% /
aot-005 60%. 41개가 `<장치명> Map (타임스탬프)` 자동 생성분이다.

### 원칙 (P1~P5 전환의 기준)

**원칙 1 — 지도는 공간이지 장치의 소유물이 아니다.**
사용자가 만드는 지리 공간만 존재한다. `category='device'` 와
`is_device_owned` 개념을 폐기한다. 지도는 그냥 지도다.
→ "사용자 지도" 판정이 4갈래로 갈려 있던 문제가 소멸한다.

**원칙 2 — 배치가 유일한 정본이다.**
"장치가 어느 지도에 있는가" = 그 장치의 마커(`GeoShape.geo_id`).
`map_config_id` 는 파생값으로 강등한 뒤 컬럼을 제거한다.
→ 고아 지도·선언과 실제의 불일치가 개념적으로 성립 불가해진다.

**원칙 3 — 배치하지 않은 장치는 어느 지도에도 없다.** *(P1 에서 구현)*
`map_config_id IS NULL` 이면 모든 지도에 표시하던 동작(`utils_geo` 의
`or_(... == None ...)`)을 폐기한다. 미배치는 미배치다. 스코프의 정본은
배치(그 지도에 마커가 있는 장치)다.
→ 배치하지 않은 Function/PID/Trigger/Conditional 이 모든 지도에 나타나던
문제가 소멸한다.

**주의 — 원칙 3 과 원칙 4 는 반드시 함께 간다.** 자동 생성만 없애고(원칙 4)
NULL 해석을 그대로 두면, NULL 이 예외에서 정상값으로 바뀌면서 **새로 만든
장치가 모든 지도에 나타난다.** P1 에서 실제로 이 회귀를 만들었다가 문서·코드
대조 점검에서 재현·수정했다(2026-08-04). 한쪽만 적용하지 말 것.

**원칙 4 — 지도는 사용자가 명시적으로 만든다.**
자동 생성 경로를 없앤다. 특히 **GET 요청은 절대 쓰지 않는다** — 페이지·
설정 모달 렌더가 지도를 만들고 커밋하던 5곳이 빈 지도 91% 의 원인이었다.

**원칙 5 — 계층은 기하가 결정한다.**
site ⊃ zone ⊃ 장치. `device_membership` 이 정본(S3 구현 완료).

### 이 기준이 없애는 것

| 기존 문제 | 새 기준에서 | 해소 단계 |
|-----------|-------------|-----------|
| 빈 지도 91% 양산 | 원칙 4 — 생성 경로 자체가 없다 | **P1 완료** |
| 미배치 장치가 모든 지도에 표시 | 원칙 3 — 미배치는 미배치 | **P1 완료** |
| 고아 지도 47~60% | 원칙 1·2 — 장치 전용 지도가 존재하지 않는다 | P1(신규 차단) / P4(기존 정리) |
| 판정 기준 4갈래 | 원칙 1 — 구분할 종류가 없다 | P3 |
| 위젯이 방금 만들어진 사설 지도로 끌려감 | 원칙 1 — 모든 지도가 동등 | P3 |
| 삭제 경로 비대칭·4종 누락 | 원칙 2 — 장치 삭제가 지도를 건드릴 이유가 없다 | P2~P5 |
| 장치 삭제가 공유 지도를 파괴(임실군 62도형) | 원칙 1·2 — 소유하지 않으므로 지울 수도 없다 | 가드로 임시 차단, P3 에서 근본 해소 |

증상마다 가드를 붙이는 대신 원칙 4개가 전부를 소멸시킨다. 이것이 이 절이
"규칙 몇 개 수정"이 아니라 **기준 정비**인 이유다.

### 전환 경로 (P1~P5)

전환 안전성은 실측으로 확인됐다 — `map_config_id` 와 실제 마커 위치를
대조했을 때 **불일치 0건**이었다(마커 보유 32개 전부 일치). 즉 파생으로
바꿔도 현재 동작이 그대로 유지된다.

```
P1 ✅ 자동 생성 중단 + 원칙 3    GET 쓰기 제거(5곳) · 장치 생성/수정/복제 시
                                생성 중단 · collect_devices 스코프를 배치
                                기반으로 (955403e, 후속 수정 포함)
P2 ✅ 읽기를 파생으로            map_config_id 독자 전부 전환(라우트 5·
                                collect_devices·AI 3·위성) + 쓰기 잔여 3곳
                                제거 → 컬럼을 쓰는 코드 0 (33329ca/bca6323)
P4 ✅ 데이터 정리               빈 지도(도형0·시설0·JSON 미참조) 삭제 —
                                koat 39 · aot-005 79 · aot-004 42.
                                **P3 보다 먼저** 해야 한다: 판정을 없애면
                                목록에 전부 노출되기 때문(2→43, 3→84)
P3 ✅ 개념 폐기                 category/is_device_owned 분기 전부 제거(16곳),
                                장치 삭제가 지도를 지우지 않게(원칙 1)
P5    컬럼 드롭                 map_config_id + (사망 처리된) map_overlay_id
```

**P1 이후 상태**: 지도 팩토리 3종(`ensure_map_config`·`create_map_config`·
`clone_map_config`)은 호출자 0 이며 독스트링에 사망 표시가 있다. 되살리면
`test_geo_map_ownership.py` 가 실패한다.

**P2 이후 상태**: `map_config_id` 를 읽거나 쓰는 코드가 없다. 소속 조회는
`device_membership` 의 `map_for_device` / `maps_for_device` /
`devices_on_map` 이 정본이다.

`map_for_device(uuid, prefer=...)` 의 `prefer` 는 **전환기 전용 안전장치**다.
같은 장치가 여러 지도에 마커를 가지면(미사용 사본 지도에 옛 마커가 남은
경우) 단순 "첫 배치"가 실사용 지도를 놓친다 — koat 실측 28건. 힌트는
**실제 배치 목록에 있을 때만** 채택되므로 정본은 여전히 배치다. P4 에서
사본 지도를 정리하면 다중 배치가 사라지고, P5 컬럼 드롭 때 인자도 제거한다.

## 잔여 위험 (구조로 소멸 불가 — 탐지 계층 담당)

| 위험 | 이유 | 대책 | 상태 |
|------|------|------|------|
| 위젯 `custom_options` 내 `map_uuid`/`device_ids` | JSON 내장 참조 — DB 가 볼 수 없음 | `check_geo_integrity.py` 에 JSON 참조 검사 | **미구현** |

| 좌표 자체가 틀린 마커 | 무결성이 아니라 입력 오류 | 사용자 확인 영역 | — |

사용자가 원인을 알기 어렵다 — JSON 참조 검사가 필요한 이유다.

## 남은 일 (구조 아님 — 운영·정리)

- **P2~P5** (위 전환 경로) — 지도 소유권 모델의 나머지 단계.
  `map_overlay_id`·`map_config_id` 컬럼 드롭은 P5 에서 함께 한다. 두 컬럼 모두
  사망 상태지만 `collect_devices` 의 컬럼 로드 목록에는 남아 있다(빼면 지연로딩
  N+1 이 되므로 컬럼 드롭과 동시에 정리).
- `check_geo_writes.py` 의 `GRANDFATHERED` 3건(장치 삭제 시 자기 마커 정리)을
  `unplace_device` 로 이관 — 예외 목록을 0 으로.
- 위젯 `custom_options` JSON 참조 검사 추가(잔여 위험 표 참조).
- 유령 지도 도형 처분(phantom-map 보고 대상) — 위젯 참조 확인 후 사람이 판단.
- 미사용 `Copy of` 지도 정리, 잔여 duplicate/orphan-label — 참조 확인 후 수동.

## 새 코드를 쓸 때

지도 데이터를 건드려야 한다면 geo 패키지의 문을 쓴다:

| 하려는 일 | 쓸 것 |
|---|---|
| 장치를 지도에 배치/이동/해제 | `geo.device_placement.place_device` / `unplace_device` |
| 도형 하나 삭제 | `geo.device_placement.delete_shape` (연쇄는 트리거가 처리) |
| 장치가 어느 zone 인지 | `geo.device_membership` (저장 컬럼 조회 금지) |
| 도형 저장 | `geo.geo_overlays.GeoOverlayManager` |

`GeoShape(...)` 를 geo 패키지 밖에서 직접 부르면 pre-commit 과 CI 가 거부한다.
