# 공간 구획(GeoPlot) — 프로그램이 적용되는 인스턴스 레이어

`GeoPlanting`(식생 전용)을 **대상 종류를 갖는 중립 인스턴스**로 일반화한 기록.
템플릿 쪽 정본은 `program-layer.md`, 식생 고유의 판단은 `geo-vegetation-planting.md`.

## 왜

`GeoProgram` 은 이미 `kind`(vegetation | livestock | facility | other)를 갖는데,
그 프로그램을 **붙일 대상이 식생밖에 없었다.** 절반만 넓힌 상태다 — 가축 프로그램을
만들 수는 있지만 어느 축사에 적용됐는지 기록할 자리가 없다.

이름도 함께 틀렸다. `GeoPlanting.crop` / `planted_on` 은 젖소에도, 가로수 점검에도,
운동장 잔디 관리에도 맞지 않는다. 어휘가 좁으면 그 용도에서 화면 전체가 어색해지고,
결국 같은 구조를 한 벌 더 만들게 된다(이 레포가 이미 두 번 겪은 경로다).

## 이름 — 왜 인스턴스는 "프로그램" 이 아닌가

**템플릿과 인스턴스는 다른 것이다.** 프로그램은 "토마토를 5단계로 이렇게 기른다"
이고, 구획은 "3동 2구역에서 3월 2일부터 그 프로그램으로 기르고 있다" 이다.
지도에 그리는 것은 프로그램이 아니라 구획이다 — 둘을 같은 말로 부르면 "프로그램을
고쳤는데 왜 지도가 안 바뀌지" 같은 질문이 생긴다.

| | 코드 | 화면(ko) | 화면(en) |
|---|---|---|---|
| 템플릿 | `GeoProgram` / `geo_program` | 프로그램 | Program |
| 인스턴스 | `GeoPlot` / `geo_plot` | 구획 | Plot |

"구획" 은 이미 쓰던 말(식생 구획)이라 사용자가 새로 배울 것이 없고, 종류를 떼면
그대로 중립어가 된다.

## 컬럼 어휘

| 옛 이름 | 새 이름 | 이유 |
|---|---|---|
| `crop` | `subject` | `GeoProgram.subject` 와 같은 축. 둘을 문자열로 맞추므로 이름도 같아야 한다 |
| `planted_on` | `started_on` | "심다" 는 식생에만 있다. 가축 입식·시설물 설치도 같은 칸을 쓴다 |
| — | `kind` | 대상 종류. `GeoProgram.kind` 와 **같은 어휘**를 쓴다 |

`ended_reason` 의 `harvested` 는 남긴다 — 식생에서 실제로 쓰는 값이고, 다른 종류는
`removed` / `replaced` 로 충분하다. 종류마다 다른 어휘가 필요해지면 그때 늘린다.

## kind 는 프로그램에서 파생하지 않는다

프로그램이 NULL 인 구획이 정상이므로(프로그램은 "있으면 자동" 이지 필수가 아니다),
`kind` 를 `program.kind` 에서 파생하면 프로그램 없는 구획의 종류를 알 수 없다.
저장하되 **프로그램을 붙일 때 종류가 다르면 거부한다** — 식생 구획에 가축 프로그램이
붙으면 단계·목표 해석이 통째로 엉뚱해지는데 에러는 나지 않는다.

## 화면·레이어 계약

지도 레이어 id 는 `aot-vegetation-*` → **`aot-plot-*`**. 레이어 컨트롤이
`getLayerIdsByType('plot')` 로 **이름을 보고** 켜고 끄므로 줄여 쓰면 체크박스가
아무 일도 하지 않는다(식생 때와 같은 계약).

위젯 custom option `show_vegetation` → `show_plots`. **옛 키를 계속 읽는다** —
이미 저장된 위젯 설정이 있고, 그 값이 사라지면 켜 두었던 레이어가 조용히 꺼진다.

## 무엇을 하지 않았나

- **종류별 전용 컬럼을 만들지 않았다.** 가축의 두수, 시설물의 규격 같은 것은
  종류마다 다르고 대화에서 계속 늘어난다 — 컬럼으로 받기 시작하면 끝이 없다.
  확정된 것은 구획 노트로 남기고, 계산이 필요하면 조회 파라미터로 넘긴다
  (배치 컬럼을 걷어낸 p6_36 과 같은 판단).
- **면적·수용량 추정을 종류에 열지 않았다.** 시설 구획에서 면적 추정을 막은 이유
  (형태에 따라 몇 배씩 틀린다)가 가축·시설물에서는 더 심하다.

### 종류 선택 UI (2026-08-19, 같은 날 이어서)

구획을 만드는 세 화면 모두 종류를 고른다. **라벨 중립화를 같은 작업에 넣었다** —
먼저 라벨만 바꾸면 식생만 만드는 화면이 괜히 모호해지고, 먼저 종류만 열면 축사를
등록한 사람이 "심은 날" 을 보게 된다.

| 옛 라벨 | 새 라벨 |
|---|---|
| 심은 것 (`Planted`) | 대상 (`What is here`) |
| 심은 날 (`Planted on`) | 시작일 (`Start date`) |
| 재배 기간 (`Growing period`) | 기간 (`Dates`) |
| 여기에 심기 (`Plant here`) | 구획 추가 (`Add a plot`) |

`Days since planting` 은 한국어가 이미 "경과 일수" 라 **msgid 만 옮겼다**
(`Days elapsed`) — 22개 언어의 기존 번역이 그대로 따라온다. 한국어가 달라져야 하는
것만 새로 넣었다.

**`Period` 를 쓰지 말 것.** 이 저장소에서 그 msgid 는 **폴링 주기**("주기")다.
기간 제목에 쓰면 영어로는 맞아 보이고 한국어에서만 틀린다 — 리뷰에서 안 보이는
종류다("Sensors"="센서류" 와 같은 계열). 그래서 `Dates` 를 쓴다.

### 종류가 바뀌면 프로그램 목록이 따라와야 한다

안 따라오면 옛 종류의 프로그램이 선택지로 남고, 그것을 고른 저장을 서버가 거절한다
— **화면에 보이는 선택지가 저장되지 않는** 상태다. 세 화면 모두 종류별로 받아
캐시하고, 종류 변경을 듣는다. 폼 전체를 다시 그리지 않고 **프로그램 select 만**
갈아 끼운다(사람이 이미 적어 넣은 값을 지키고, 5초 폴링이 도는 위젯 모달에서
통째로 갈아끼우는 것이 그대로 깜빡임이 되기 때문이다).

### 게이트웨이만으로는 부족하다 — 검사기가 같은 불변식을 본다

쓰기 게이트웨이는 **지나가는 것만** 막는다. 게이트웨이가 생기기 전에 만들어진 행,
백필, 사람이 직접 고친 DB 는 그 검사를 지나지 않는다 — 이 도메인이 반복해서 겪은
모양 그대로다. `check_geo_integrity` 에 둘을 넣었다:

- **`plot-program-kind-mismatch`** (severe) — 종류가 어긋난 채 붙어 있다.
- `plot-dangling-program` — 프로그램을 지웠는데 구획이 계속 가리킨다.

프로그램 테이블이 없는 설치(업그레이드 전)에서는 **둘 다 건너뛴다** — 없는 것을
근거로 "끊어졌다" 고 말하면 정상 서버가 매번 문제로 잡힌다.

### 종류만 바꾸는 저장도 대조한다

프로그램을 붙일 때만 대조하면 경로가 하나 뚫린다 — **프로그램은 그대로 두고 종류만**
바꾸는 저장이 그 분기를 지나간다. 그러면 식생 프로그램이 매달린 채 종류만 가축이
되고, 아무 에러 없이 단계·목표 해석이 통째로 어긋난다. `save_plot` 이 저장할 때마다
짝을 다시 본다.

### 옮기지 않은 이름

- **`bays[].crop`** — 레거시 시설 필드다. 은퇴 예정이라 새 이름을 줄 이유가 없고,
  지금 옮기면 백필(`backfill_facility_bay_crops`)의 출처 쪽 이름만 바뀐다.
- **`STAGE_DURATION_MAP` / `crop_type` / `crop_preset`** — AI·제어 쪽의 작물 전용
  레거시다. 프로그램 레이어가 이것들을 대체하는 것이 P4 이후의 일이므로, 이름만
  넓히면 넓어지지 않은 것이 넓어진 것처럼 보인다.
- **`GeoProgram.kind` 의 값 `'vegetation'`** — 종류 이름이지 레이어 이름이 아니다.
