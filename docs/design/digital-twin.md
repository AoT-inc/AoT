# 디지털트윈 출력 계약 — 상태 벡터·시간축·분위수·유효기한·저장

- 상태: **초안** (2026-10-19, P0) — 2026-10-23 시설 P1 구현(`aot/functions/utils/facility_twin`)에 맞춰 §3·§6.3·§9 를 고쳤다. 확정 전에 남은 열린 문제(§9)를 닫는다.
- 상위 계획: `AoT_dev/plans/2026-10-19_digital_twin_plan.md` (단계 P0~P6)
- 범위: 트윈 노드가 **무엇을 어떤 모양으로 내놓는가**. 계산 방법(UKF 세부, 앙상블 구성)은 P1·P2 문서에서 정한다. §3~§9 는 시설, **§10 은 노지(구획 단위) 보완**이다.
- 브랜치 정책: (2026-10-21 개정) 코드는 공개 main 에 들어가는 '준비 중' 기능이다 — 설정 > 일반 토글(기본 꺼짐), 별도 서비스 `aot_twin`, 낮은 사양 기기 잠금. 이전(10-19)의 "main 병합 금지" 는 폐기.

## 1. 한 줄 요약

트윈은 **"지금 시설 상태 추정값"과 "앞으로 48시간 실내 T·RH·VPD·CO₂ 의 10/50/90 분위수 궤적, 위험 사건 확률"** 을 InfluxDB 에 `env_twin*` 측정으로 쓴다. 모든 출력에는 발행 시각과 **유효기한**이 붙고, 지나면 소비자(화면·MCP·코디네이터)는 무시한다. 파이는 트윈이 없어도 지금처럼 돈다.

## 2. 원칙 (계획서 §4 에서 가져옴)

1. 파이는 트윈에 의존하지 않는다. 출력이 없거나 만료되면 소비자는 "없음"으로 취급한다(0 이나 마지막 값으로 채우지 않는다).
2. 처음엔 자문만. 이 계약의 어떤 값도 장치 명령 경로에 들어가지 않는다. 제어 연결(P5)은 별도 계약(권고 설정 일정)으로 다룬다.
3. 모델은 `aot.functions.utils.env_control` 한 벌. 이 계약은 그 위에서 나온 값만 담는다. 검증용 `sim/plant.py` 는 계약 밖이다.
4. 결과는 기존 저장소로: 시계열은 InfluxDB, 진단·시나리오는 SQLite/JSON(P3·P4).

## 3. 상태 벡터

트윈 내부 상태 `x` 는 그레이박스 v3(`greybox/model.py`)의 `[T, AH, CO₂]` 를 확장한다. **밖으로 나가는 것은 ①~④ 뿐이고**, 숨은 상태와 파라미터는 트윈 노드 안에 둔다(재시작 복구용 스냅샷만 노드 로컬 파일).

| # | 변수 | 기호 | 단위 | 측정 여부 | 밖으로 |
|---|---|---|---|---|---|
| ① | 실내 기온 | `T` | °C | 측정 | 예 |
| ② | 실내 상대습도 | `RH` | % | 측정 (내부는 절대습도 `AH` [g/m³] 로 적분, 출력 때 `RH` 로 환산) | 예 |
| ③ | 실내 VPD | `VPD` | kPa | 파생 (`T`, `RH`) | 예 |
| ④ | 실내 CO₂ | `CO2` | ppm | 측정 | 예 |
| ⑤ | 열질량 온도 | `Tm` | °C | **숨은 상태** | 아니오 |
| ⑥ | 외피 열손실 배율 | `θ_UA` | 무차원(1 = 기준) | 느린 파라미터 | 진단(P3)으로만 |
| ⑦ | 누기·틈새 환기 배율 | `θ_leak` | 무차원 | 느린 파라미터 | 진단(P3)으로만 |
| ⑧ | 일사 수열 배율 | `θ_sol` | 무차원 | 느린 파라미터 | 진단(P3)으로만 |
| ⑨ | 환기 능력 배율 | `θ_vent` | 무차원 | 느린 파라미터 | 진단(P3)으로만 |
| ⑩ | 증산 배율 | `θ_tr` | 무차원 | 느린 파라미터 | 진단(P3)으로만 |

- ⑧~⑩ 은 독립 참값(`sim/plant.py`) 검증에서 사전값이 가장 크게 어긋나는 자리라 추가했다(낮 편향 −4 °C, 습도 선행 13 %p). 내부 파라미터는 모두 로그 배율이며 기준의 1/10~10 배(증산은 1/300~300 배)로 자른다. 사전값은 그레이박스 파라미터(`TargetSpec.options.greybox` — 코디네이터가 배운 값 또는 시설 capacity_meta)이다. 필터는 UKF(시그마점 `2n+1 = 19`)다.
- 입력(외생): 외기 `T_ext, RH_ext, CO2_ext, solar, wind`(실측 또는 예보), 제어 입력 `cmds{heat, cool, vent, fog, co2_inj, shade, curtain}`. 이 둘은 계약의 입력이지 출력이 아니다.
- **전제(P0 감사 결과):** 상태 추정이 의미를 가지려면 (a) 실내 센서가 그 시설의 실제 장치에 반응하고 (b) 장치 개도·가동 피드백이 있고 (c) 외기 입력이 시설 근처여야 한다. 하나라도 빠진 현장은 `status = not_twinnable`(§7)로 발행하고 예측 궤적은 쓰지 않는다. 김제·영양 개발서버 현장은 현재 이 전제를 못 채운다(계획서 §P0 감사표).
- 한 시설 = 한 구역 평균(단일 구역). 다구역은 P6.

## 4. 시간축

- 모든 시각은 **UTC epoch 초**(Influx 타임스탬프). 화면 표기는 소비자가 시설 시간대로 바꾼다(`timezone-management.md`).
- **발행 시각 `t0`**: 상태 추정에 반영된 마지막 실내 측정 시각을 60 초 단위로 내린 값. 트윈이 "지금"이라고 믿는 시각이다. 발행 시계(벽시계)와 `t0` 가 어긋나면 그 차이를 `meta.stale_s` 로 남긴다.
- **선행 격자**: 간격 **600 초**(코디네이터 `update_period` 와 같다), `k = 0 … 288` → `t0 … t0 + 48 h`, 289 점.
  - `k = 0` 은 필터링된 현재 추정(nowcast). 분위수는 UKF 공분산에서 나온다.
  - `k ≥ 1` 은 예측. 분위수는 예보 앙상블 × 파라미터 사후 표본에서 나온다.
  - 내부 적분 스텝은 계약 밖이다(벤치: 600 s 격자로 줄여도 안정 서브스텝 때문에 계산량이 거의 안 준다 — M1 에서 48 h 가 60 s 격자 0.12 s, 600 s 격자 0.08 s).
- 경량 모드(파이 단독, 앙상블 없음)는 지평을 **24 h**(`k ≤ 144`)까지로 줄일 수 있다. 줄인 지평은 `meta.horizon_h` 로 알린다. 격자 간격은 바꾸지 않는다.
- 발행 주기: 트윈 노드 기본 1 시간 (노드 성능에 맞춰 시작 시 벤치로 결정 — 계획서 §4 원칙 5).

## 5. 불확실성 — 분위수 10/50/90

- 변수 ①~④ 각각 **p10, p50, p90** 세 값. 의미: 같은 발행에서 "실현값이 p10 이하일 확률 ≈ 10 %, p90 이하일 확률 ≈ 90 %".
- 항상 `p10 ≤ p50 ≤ p90`. 발행 전에 정렬해 단조를 강제한다(교차 금지).
- 앙상블이 없는 경량 모드는 **p50 만** 쓴다(p10·p90 생략). 소비자는 p10/p90 이 없을 수 있음을 처리해야 하고, `meta.ensemble_size = 1` 로 구분한다. 폭이 0 인 가짜 띠를 쓰지 않는다.
- 띠가 정직한지는 **보정(calibration)** 으로 확인한다: 리플레이·운영 기록에서 실현값이 p10~p90 안에 들어간 비율(목표 80 %±10 %p)을 `env_twin_lead` 아카이브(§6.2)로 계산해 `meta.coverage_80` 에 갱신한다. 이 값이 60 % 아래면 화면은 띠 대신 "참고용"으로 낮춘다.
- 위험 사건은 분위수가 아니라 **확률**(0~1)로 낸다(§6.1 CH50~).

## 6. 저장 — InfluxDB `env_twin*`

기존 쓰기 경로 `aot.utils.influx.write_influxdb_value(unique_id, unit, value, channel=, timestamp=, extra_tags=)` 를 그대로 쓴다. `unit` 인자가 측정 이름이 된다. 새 저장소·새 스키마를 만들지 않으므로 화면·MCP 는 기존 `measure` 조회로 읽는다.

공통 태그: `device_id` = **환경제어 함수(코디네이터)의 unique_id** (`env_control` 기록과 같다), `facility` = 시설 uuid 앞 8자. 새 측정 이름은 `env_twin` 으로 시작하는 세 개.

### 6.1 `env_twin` — 최신 예측 곡선 (덮어쓰기)

- **타임스탬프 = 예측 대상 시각**(`t0 + k·600 s`). 같은 대상 시각에 새 발행이 오면 **같은 점을 덮어쓴다**(Influx 는 같은 측정·태그·시각이면 마지막 쓰기가 이긴다). 그래서 이 측정을 시간 구간으로 읽으면 곧바로 "지금 → +48 h 최신 곡선"이다. 과거 구간은 마지막 발행이 남긴 값(= 사실상 최근 예측)이라 **평가에 쓰지 않는다**(§6.2 를 쓴다).
- 태그 추가 없음(발행 식별 태그를 안 단다 — 계열 수가 발행 수만큼 늘어나는 것을 피한다).
- 채널 배치 (`channel` 태그, 정수):

  | 채널 | 내용 | 단위 |
  |---|---|---|
  | 0 / 1 / 2 | `T` p10 / p50 / p90 | °C |
  | 10 / 11 / 12 | `RH` p10 / p50 / p90 | % |
  | 20 / 21 / 22 | `VPD` p10 / p50 / p90 | kPa |
  | 30 / 31 / 32 | `CO2` p10 / p50 / p90 | ppm |
  | 50 | 결로 위험 확률 | 0~1 |
  | 51 | 고온(설정 상한 초과) 확률 | 0~1 |
  | 52 | 동해(설정 하한 미만) 확률 | 0~1 |
  | 53 | 과습(RH 상한 초과) 확률 | 0~1 |

  위험 사건의 임계값은 코디네이터의 측정 범위 설정(`measurement_range_plan.md`)을 읽는다 — 트윈이 따로 정하지 않는다. 새 사건은 54~59 에 이어 붙인다. 채널 번호는 바꾸지 않고 추가만 한다.
- 호출 한 번의 쓰기량: 변수 4 × 3 + 사건 4 = 16 채널 × 289 점 ≈ 4.6 천 점/발행. 1 시간 주기에서 파이 Influx 가 감당할 규모다(실측은 P2).

### 6.2 `env_twin_lead` — 검증용 보관본 (덮어쓰지 않음)

- 같은 발행에서 **선행 시간이 {1, 3, 6, 12, 24, 48} 시간인 점만** 따로 보관한다.
- 타임스탬프 = 예측 대상 시각, 태그 `lead_h` ∈ {1, 3, 6, 12, 24, 48}. 같은 대상 시각·같은 `lead_h` 는 한 번만 생기므로 덮어쓰이지 않고, **실측과 같은 타임스탬프로 바로 붙여** RMSE·보정 비율을 구할 수 있다.
- 채널은 §6.1 의 0~2, 10~12, 20~22, 30~32 와 50~53 을 그대로 쓴다(의미 동일).
- 계열 수는 6 × 16 = 96 으로 **발행 수와 무관하게 고정**이다. 발행이 쌓여도 카디널리티가 늘지 않는다.
- 보존 기간은 버킷 보존 정책을 따른다. 트윈 일치도·보정 지표는 이 측정에서 계산한다(P1).

### 6.3 `env_twin_meta` — 발행 한 건의 머리말

- 타임스탬프 = `t0`(발행 시각). 값 하나당 채널 하나.

  | 채널 | 내용 | 단위 |
  |---|---|---|
  | 0 | `status` 코드 (§7) | 정수 |
  | 1 | `valid_until` — 유효기한 | UTC epoch 초 |
  | 2 | `horizon_h` — 실제 발행한 지평 | h |
  | 3 | `ensemble_size` — 1 이면 결정론 | 개 |
  | 4 | `sync_rmse_T` — 최근 24 h 1 스텝 실내온도 RMSE | °C |
  | 5 | `sync_rmse_RH` | %p |
  | 6 | `sync_rmse_T_1h` — 최근 동화 구간의 1 시간 선행 실내온도 RMSE. 선행 구간의 **실제 외기·실제 명령**을 넣어 잰다(되먹임 제어가 한 시간 안에 명령을 바꾸는 몫을 빼고 모델·상태의 실력만 본다) | °C |
  | 7 | `coverage_80` — 최근 7 일 p10~p90 적중률 | 0~1 |
  | 8 | `stale_s` — 발행 시계 − `t0` | s |
  | 9 | `model_rev` — 트윈 모델 판 번호(시설 `facility_twin.MODEL_REV`, 노지 `field_twin.MODEL_REV`; 그레이박스 물리식 판은 `params.model_version`) | 정수 |
  | 10 | `policy` — 예측에 물린 제어 정책 (0 = 현재 설정 고정, 1 = legacy 폐루프, 2 = MPC 폐루프) | 정수 |
  | 11 | `weather_src` — 예보원 (1 Open-Meteo 결정론, 2 Open-Meteo 앙상블, 3 기상청, 4 실측 외기 지속 — 시설은 24 h 전 같은 시각의 측정을 반복하는 일주기 지속, 5 대지 지정 예보 입력의 시간별 시계열 — 서버 `GET /api/twin/forecast_series`; 예보가 닿지 않는 구간·변수는 4 로 메운다) | 정수 |
  | 12 | `fc_issue_epoch` — 이 발행이 쓴 예보 발표본의 받은 시각(UTC epoch). 예보를 못 썼으면 칸을 쓰지 않는다 | s |
  | 13 | `fc_cal_rev` — 쓴 예보의 보정 판(0 = 원본. 대지에서 채택된 보정이 있으면 그 판 번호 — `forecast_series` 응답의 `cal_rev`) | 정수 |
  | 14 | `obs_origin` — 동기화에 쓴 관측의 출처(1 실측 · 2 미러 · 3 가상 · 0 미확인; 섞이면 가장 못 믿을 것). 관측이 없으면 칸을 쓰지 않는다 | 정수 |
  | 15 | `plan_src` — 예측에 물린 미래 장치 입력의 방식(0 현재 유지 · 1 등록 일정 · 2 what-if). 장치 효과(소유: 장치 효과 세션) | 정수 |
  | 16 | `effects_modeled` — 효과를 모델에 반영한 장치 수 | 개 |
  | 17 | `effects_unmodeled` — 효과를 반영하지 못한 장치 수(일부 반영·미반영·모름; 0 보다 크면 그래프가 "효과 미반영" 배지). 어느 장치가 왜인지는 머리말이 아니라 시나리오 `effects[]`·`/api/twin/plots` 가 준다 | 개 |

- `sync_rmse_*` 는 §P1 의 "트윈 일치도" 신호등의 재료다: 초록 `T_1h < 1.0 °C`·`RH < 7 %p`, 노랑 그 1.5 배 이내(`degraded`), 빨강 그 밖(`unsynced`) — P1 구현(`models/facility_greybox.py`)이 이 문턱을 쓴다. 선행 표본이 6 개 미만이면 일치도를 못 재므로 `unsynced`.

## 7. 상태 코드와 유효기한

`env_twin_meta` 채널 0:

| 코드 | 이름 | 뜻 | 소비자 행동 |
|---|---|---|---|
| 0 | `ok` | 동기화 양호, 정상 발행 | 곡선·띠·위험 표시 |
| 1 | `degraded` | 일치도 노랑, 또는 입력 일부 결측(예보 대체 등) | 표시하되 "참고용" 표기 |
| 2 | `unsynced` | 일치도 빨강·잔차 큼·센서 의심 | **예측 숨김**, 일치도만 표시 |
| 3 | `not_twinnable` | 현장이 §3 전제를 못 채움(감사 결과) | 트윈 표시 자체를 하지 않음 |
| 9 | `error` | 계산 실패 (곡선 미발행) | 없음으로 취급 |

**유효기한 `valid_until`** (UTC epoch 초): 기본 `t0 + 2 × 발행주기`(1 시간 주기면 `t0 + 2 h`). 규칙:

1. 소비자는 `now > valid_until` 이면 해당 발행의 **모든** 곡선·사건을 무시한다(만료된 값을 "마지막 값"으로 보여 주지 않는다 — 센서 신선도 설계의 "안전한 방향으로만 쓴다"와 같은 정신. 예측은 안전 판단 근거가 아니므로 쓰지 않는 쪽으로 쓴다).
2. 노드가 종료·단절돼 새 발행이 없으면 `valid_until` 이 지나는 순간 트윈이 화면에서 사라진다. 이것이 정상 동작이다(원칙 1).
3. `status ≥ 2` 이면 발행자가 `valid_until = t0`(즉시 만료)로 쓴다.
4. 소비자는 항상 **가장 최근 `env_twin_meta` 한 점**을 먼저 읽고, 유효할 때만 `env_twin` 곡선을 읽는다.

## 8. 읽는 쪽 계약 (소비자가 해야 할 것)

- 위젯·3D·지도 배지(P2)와 MCP `measure`·`weather` 의 예측 모드는 위 읽기 순서(§7-4)를 따른다. 새 저장소를 알 필요가 없다.
- 예측을 보여 줄 때는 **항상** 띠(p10~p90)와 일치도 신호등을 함께 보인다. 띠가 없는 결정론 발행은 "단일 예측"으로 표기한다.
- 코디네이터는 이 값을 **읽지 않는다**(P5 전까지).

## 9. 열린 문제

1. ~~**전송 경로**~~ **(닫힘 2026-10-20 → 바뀜 2026-10-21·10-24)** 처음엔 파이의 수신 API `POST /api/twin/ingest` 를 거쳤다(§11 통합). 배포형 전환 뒤로는 서비스 `aot_twin` 이 같은 기기에서 Influx 에 직접 쓰고, 수신 API 는 2026-10-24 에 걷어 냈다(계획서 §9.19). 원래 질문: 트윈 노드가 현장 Influx 에 직접 쓰는가(Tailscale, 쓰기 토큰 노드 보관), 파이의 수신 API 를 거치는가. 직접 쓰기가 단순하나 현장마다 토큰이 노드에 모인다.
2. **버킷**: `env_twin*` 를 기존 측정 버킷에 둘지 별도 버킷(짧은 보존)으로 둘지. `env_twin_lead` 는 길게, `env_twin` 은 짧게 두고 싶다.
3. **시설 vs 구획**: 한 시설에 여러 구획(`GeoPlot`)이 있을 때 목표는 구획별이지만 트윈은 시설 단위다. 출력은 시설 단위로 두고 구획 목표와의 비교는 소비자가 한다(지금 안).
4. **VPD 기준**: 공기 VPD 만 낸다. 잎 VPD(`leaf_vpd.py`)는 `Tm` 이 검증된 뒤 채널 추가(CH23~)로 붙인다.
5. **채널 번호 충돌 방지 표**: `log_channels.py` 의 `env_control` 채널과는 측정 이름이 달라 충돌하지 않는다. 그래도 새 채널은 한 곳(이 문서)에서만 배정한다.
6. **what-if(P4) 저장**: Influx 가 아니라 SQLite/JSON(시나리오 id)로 둔다는 안. 본 계약에 포함하지 않는다.

## 10. 노지 대상 (구획 단위)

시설 절(§3~§8)은 **공기 한 덩어리**의 계약이다. 노지는 공기를 가둘 수 없으므로 핵심 상태가 **토양 속 물·열과 작물**이고, 시간 단위가 길며(일~주), 한 구획 안에서도 위치마다 다르다. 같은 뼈대(발행 시각·분위수·유효기한·상태 코드·읽기 순서)를 쓰되 아래를 따로 정한다. 시설과 노지가 한 현장에 섞여도 같은 트윈 노드가 돌고, 출력 측정 이름만 다르다.

### 10.1 대상과 식별자

- 트윈 대상 종류 `kind`: `facility`(시설, §3~§8) · `field`(노지). 노지의 단위는 **구획**(`GeoPlot`, `kind='vegetation'`, `facility_uuid` 없음)이다. 시설 안 구획(`facility_uuid` 있음)은 시설 트윈이 맡는다.
- Influx `device_id` = **구획 `unique_id`**(uuid). 구획은 장치가 아니지만 `write_influxdb_value` 는 임의 문자열 id 를 받으므로 새 저장소가 필요 없다. 태그 `target` = `field`.
- **격자 셀 식별자**: `<구획 앞 8자>:<ix>.<iy>`. 구획 외곽을 감싸는 상자의 **남서 모서리**를 원점으로, 북 기준 정렬, 기본 간격 **10 m**, `ix`=동쪽·`iy`=북쪽 정수(0부터). 셀 중심이 구획 안에 있는 칸만 유효(마스크). 구획 모양이 바뀌면 `grid_rev` 를 올리고 셀 번호를 새로 매긴다(옛 번호는 쓰지 않는다). 센서 마커가 든 칸이 그 센서의 **관측 셀**이다.
- **격자는 Influx 에 넣지 않는다.** 구획 하나 × 셀 100개 × 채널 15 × 분위수 3 이면 계열이 수천 개로 불어난다. Influx 에는 구획 **요약값**과 **센서 셀 값**만 쓰고, 격자 지도는 트윈 노드의 JSON(`header{origin_lat,origin_lon,step_m,nx,ny,grid_rev}`, `layers{이름: 행 우선 배열}`)으로 두며 `env_twin_field_meta` 의 `grid_rev` 로 짝을 맞춘다(전송은 §9-1 과 같은 문제).

### 10.2 상태 벡터

구획(또는 셀) 하나의 상태 `x`. 층 깊이 기본값 **0~10 · 10~30 · 30~60 cm**(시범 구획에서 센서 깊이·토성으로 다시 정한다).

| # | 변수 | 기호 | 단위 | 측정 | 밖으로 |
|---|---|---|---|---|---|
| ① | 층별 체적수분 | `θ1, θ2, θ3` | m³/m³ (출력은 %) | 토양센서 1~2점(한 층) | 예 (뿌리층 평균 `θ_root` 로) |
| ② | 층별 지온 | `Ts1, Ts2` | °C | 토양센서(깊이 미상) | 예 (`Ts1`) |
| ③ | 뿌리층 고갈량 | `Dr` | mm (FAO-56) | 파생 | 예 |
| ④ | 수분 스트레스 계수 | `Ks` | 0~1 | 파생(`Dr`, 가용수분 `TAW`·`RAW`) | 예 |
| ⑤ | 적산온도 | `GDD` | °C·일 | 파생(기온, 정식·파종일 `started_on`) | 예 |
| ⑥ | 피복률 | `fc` | 0~1 | 위성 NDVI(보조) | 예 |
| ⑦ | 잎 젖음 지속 | `W` | 시간(연속) | 파생(이슬점·비) | 위험 지수로만 |
| ⑧ | 토양 수리 파라미터 | `θfc, θwp, θsat`, 배수 시정수 `τd`, 하부 배수 계수 `k_bottom` | m³/m³, 일, 0~1 | — (토성 사전분포 + 비·관수 반응으로 갱신) | 진단으로만 |
| ⑨ | 작물계수 배율 | `θ_Kcb` | 무차원(1 = 표준) | — | 진단으로만 |

- 입력(외생): 기상 `T, RH, wind, solar, rain`(실측 또는 앙상블 예보), 기준증발산 `ET0`(FAO-56, 좌표만으로). 제어 입력: 관수 깊이 `irr_mm`(셀·일 단위), 방상 장치 상태(서리 밤).
- 관측식: 센서 칸에서만 `y = a·θ_k + b`(보정 `a,b`는 센서별, 층 `k` 는 센서 깊이에서). 일 격자 관측은 대상 시각(00:00) **앞뒤 2 시간 평균**이다 — 하루 평균은 비 전·후 시간과 정전용량 센서의 온도 일주기가 섞인다(P1 구현 `field_twin`, 계획서 §9.5).
- `Ksat` 대신 선형 저수조 배수 시정수 `τd`(10 cm 층 기준, 층 두께에 비례)를 쓴다. `k_bottom` 은 맨 아래층에서 빠지는 비율이다(경반층·높은 지하수위면 0 에 가깝다). **센서 값은 관측식을 거치기 전에 유효성 검사**를 통과해야 한다(§10.5).
- 숨은 상태는 `θ1~θ3` 중 센서가 닿지 않는 층, `Dr`, 파라미터 ⑧⑨. 동기화는 **EnKF** 다(시설 UKF 와 다름). 앙상블이 곧 분위수의 재료다.

### 10.3 시간축

- 노지는 시간 규모가 둘이다.
  - **일 격자(물·생육)**: 스텝 1 일, 대상 시각 = **구획 시간대의 그날 00:00 을 UTC epoch 로 바꾼 값**. 지평 **14 일**(`k=0…14`), 단 신뢰 구간은 7 일까지로 본다(`meta.horizon_d`). `k=0` 은 오늘(필터링된 현재 추정).
  - **시 격자(서리·잎 젖음)**: 스텝 1 시간, `k=0…72`(3 일). 대상 시각 = `t0 + k·3600 s`.
- 발행 시각 `t0`: 마지막으로 동화한 센서 측정 시각을 정시로 내린 값. 발행 주기는 일 격자 하루 1 회(새벽), 시 격자는 6 시간마다(서리 철엔 1 시간마다로 올릴 수 있다).
- 관측은 시간 평균을 일 격자의 갱신에 쓴다. 비·관수 직후에는 시 격자로 한 번 더 갱신해 `θ` 의 급변을 잡는다.
- 유효기한 `valid_until`: 일 격자 `t0 + 36 h`, 시 격자 `t0 + 3 × 발행주기`. 만료 규칙은 §7 과 같다.

### 10.5 상태 코드·전제 (노지판)

`status` 코드는 §7 과 같고 노지 전제가 더해진다.

- **트윈 가능 최소 조건**: (a) 구획 안 또는 가까이(기본 30 m)에 **유효한** 토양수분 센서가 1개 이상, (b) 비 입력(관측소·예보 중 하나), (c) 좌표. 하나라도 없으면 `not_twinnable`.
- **관측 없는 구획(센서 없이 모델만)**: 구획에 토양수분 센서가 없으면 위 (a) 대신 `options.sensorless` 가 정한다 — `"predict"`(기본)는 비·ET0·기온으로 심은 날부터 물 수지만 굴리고(동화 없음, 초기값은 토성의 포장용수량) 발행한다. 상태는 늘 `degraded`, `obs_n = 0`, `sync_rmse_theta_1d`·`coverage_80`·`obs_age_s` 는 NaN(채널 생략), `theta_sensor` 곡선(채널 90~92)은 없다 — 센서가 읽을 값이 없다. 소비자는 `obs_n = 0` 을 "관측 없음 — 참고용" 으로 구분해 보이고 동기화된 구획과 같은 말로 섞지 않는다(지도: 점선 테두리 + 범례 문구). `"off"` 면 예전처럼 `not_twinnable`. 비 입력·심은 날은 이 모드에서도 필요하다. 옛 발행(`obs_n` 이 늘 1)과 호환: 1 이상은 관측 있음.
- `irrigation_known = 0` 이면 상태는 최대 `degraded` — 관수가 있는 구획의 물 수지에서 "들어옴"이 비어 있다는 뜻이므로 **예측 곡선에 "관수 제외" 표기**를 강제한다(§8). 노지에서 구획에 묶인 출력이 범용 `virtual_on_off_single` 이고 유량 정보가 없는 것이 지금의 기본 상태다.
- **센서 유효성 검사**(동화 전 필수): 채널 이름이 "토양수분"이어도 값이 물리 범위(체적수분 0~70 %)를 벗어나거나 **평탄**(24 시간 표준편차 < 0.1 %p)하면 관측으로 쓰지 않는다. 센서 장치가 토양 채널 템플릿을 공기 센서에도 달아 두는 경우가 실측되었다(김제 `온습도_N` 의 "토양수분" ≈ 3.7 %, "토양온도" ≈ −95 °C 로 고정 — 감사 문서 §9.4).
- **센서 위치 변화**: 토양온도 일교차가 앞 7 일 중앙값의 2 배를 넘고 15 °C 이상이면 센서가 얕아졌거나 드러난 것으로 보고 보정 `a,b` 의 퍼짐을 다시 연다. 비 없는 날의 큰 하락 혁신(기본 3σ)도 같게 다루고, 비 없는 큰 상승은 **입력 누락**(관측소가 놓친 비·모르는 관수)으로 보고 층 수분의 퍼짐을 연다. 김제 A 토양_3 은 09-28 11 시에 비 없이 21 → 12 % 로 떨어지고 일교차가 6~10 → 26~40 °C 가 되었다(계획서 §9.5).
- 센서 칸 밖 셀의 일치도는 말하지 않는다. `sync_rmse_*` 는 센서 셀 기준이며 소비자는 그렇게 표기한다.

### 10.6 위험 사건

| 사건 | 정의 | 채널 | 비고 |
|---|---|---|---|
| 물 부족 | `Ks < 1`(고갈량 `Dr > RAW`)이 되는 날의 확률과 첫 날 | 일 70 (그리고 71 = `Ks<0.7`) | 첫 날은 확률이 0.5 를 넘는 첫 `k` 를 화면이 계산 |
| 서리 | 구획 보정 최저기온 ≤ `T_crit` (작물·단계별, 기본 0 °C) | 일 72, 시 격자 10 | `T_crit` 는 관리 프로그램 단계 목표에서 읽는다. 격자(DEM 냉기호) 보정 후엔 셀별 확률이 격자 JSON 에 있다 |
| 병 위험 | 잎 젖음 연속 시간·기온 구간으로 만든 지수(모델 판 `disease_model`) | 일 73 | 지수 정의가 작물별로 다르다. 판 번호를 메타에 남긴다 |
| 과습 | 뿌리층이 포장용수량을 크게 넘은 상태 | 일 74 | 센서 포화(≈ 50 %)와 구별해야 한다 |

임계값은 시설과 마찬가지로 소비자·프로그램 설정을 읽는다 — 트윈이 따로 정하지 않는다.

### 10.7 시설·노지 공통 인터페이스

트윈 뼈대(동기화·예보 입력·결과 저장·화면·what-if)는 대상 모델을 아래 인터페이스로만 안다. 시설 모델(그레이박스)과 노지 모델(물·열 수지 + 작물)이 같은 모양으로 끼워진다.

```python
class TwinModel(Protocol):
    kind: str                                   # 'facility' | 'field'
    state_names: Sequence[str]                  # 상태 벡터 순서(§3, §10.2)
    param_names: Sequence[str]                  # 느린 파라미터(진단으로만 나감)
    dt_nominal_s: float                         # 권장 스텝(시설 60, 노지 일 86400 / 시 3600)

    def init_state(self, target, t0, prior) -> "State": ...
    def step(self, x, u, w, dt_s) -> "State":   # 결정론. u = 제어 입력, w = 외생(기상)
        ...
    def observe(self, x, sensor) -> float:      # 관측식 y = h(x). sensor = 칸·층·보정 a,b·노이즈 R
        ...
    def derived(self, x) -> dict:               # VPD, Ks, RH 등 파생(출력 변수)
        ...
    def risks(self, traj) -> dict:              # 위험 사건 확률 계산에 쓰는 사건 정의(§10.6)
        ...
```

- `step` 은 결정론이다. 불확실성은 뼈대가 **앙상블 멤버(기상 앙상블 × 파라미터 사후 표본 × 상태)** 로 만들고, 필터(시설 UKF · 노지 EnKF)가 `observe` 를 불러 동화한다. 모델은 확률을 모른다.
- `u` 의 뜻이 대상마다 다르다: 시설 `cmds{heat,cool,vent,fog,co2_inj,shade,curtain}`(%), 노지 `irr_mm`(셀·일 mm)와 방상 on/off. 값을 모르면 `NaN` 으로 넘기고 모델은 그 항을 빼며 `irrigation_known=0` 이 메타에 남는다.
- 출력은 대상 종류와 무관하게 **하나의 레코드**로 모은 뒤 쓰기 층이 §6·§10.4 의 측정으로 풀어 쓴다: `TwinOutput{kind, target_id, t0, grids{daily|hourly|fast}, quantiles, events, meta}`.
- 구획 종류가 모델을 고른다(`facility_uuid` 가 있으면 시설, 없으면 노지). 새 대상 종류(예: 육묘 트레이, 축사)는 이 인터페이스를 구현하고 측정 이름 접두를 하나 배정받으면 된다.

### 10.8 노지 열린 문제

1. **관수 입력**: 구획에 묶인 밸브의 유량(L/min)·노즐 정격을 어디에 쓰는가. 밸브 출력의 `custom_options` 에 `flow_lpm`·`nozzle_rating` 같은 필드를 두는 안과 `irrigation_nozzles` 시설 피팅(노지엔 시설이 없다)을 노지로 넓히는 안. 감사 결과 지금은 둘 다 비어 있다.
2. **센서 깊이·보정**: 토양센서 입력에 깊이(cm)와 보정식 `a,b` 를 둘 곳. 현재 장치 설정에 깊이 필드가 없다.
3. **구획 시간대·일 경계**: 일 격자의 하루 경계를 구획 시간대(`GeoShape.timezone`)로 둔다. 시간대가 비어 있는 구획의 폴백이 필요하다.
4. **토성 사전분포의 출처**: SoilGrids 점 조회가 서비스 장애로 막히면 격자 파일을 한 번 받아 두는 방식(다운로드)이 필요하다. 한국 정밀토양도(흙토람)는 키가 필요하다.
5. **DEM**: 무료 90 m(Copernicus)는 10 m 격자 냉기호엔 거칠다. 국토지리정보원 수치표고(5~10 m)는 키가 필요하다.
6. **우량계**: 현장 우량계가 없는 구획은 기상청 관측소·예보로 비를 넣는다. 둘이 어긋나는 날이 실측되었다(감사 문서 §9.4).
