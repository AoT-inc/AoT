# 스케줄러 프로세스 분리 — gunicorn 워커를 늘리기 위한 선행 작업

작성: 2026-08-24. 기준 문서 — 예약 실행(APScheduler)이 왜 웹 프로세스 밖으로
나가야 하는지, 어떤 방식이 있고 무엇을 고르며, 옮길 때 무엇이 깨질 수 있는지를
정한다. 성능 조사 경위와 실측 원본은 `.local/reports/` 가 아니라 이 문서의
1절에 요약해 둔다(근거와 결론이 떨어져 있으면 다음 사람이 결론만 읽는다).

**구현됨(2026-09-09).** 안 A 를 택하되 두 가지가 원안과 다르다 — 7절에 이유와
함께 적어 뒀다. 조사 중에 **웹과 데몬이 이미 동시에 스케줄러를 띄우고 있던 것**
이 드러나, 이 작업은 "워커 증설을 위한 선행 작업" 이 아니라 **이미 성립해 있던
이중 발화 조건을 없애는 수정**이 되었다(7-1절).

---

## 1. 왜 — 두 가지가 겹쳐 있다

### 1-1. 웹이 코어를 절반밖에 못 쓴다 (라즈베리파이 4B 실측, 2026-08-24)

| 동시 요청 | 처리량 | 개별 응답 |
|---|---|---|
| 1 (순차) | 3.8 req/s | 250ms |
| 6 | 2.4 req/s | 1,134~2,504ms |
| 12 | 3.5 req/s | — |

동시성을 12배로 올려도 처리량이 그대로다. 같은 순간 CPU 는:

- gunicorn 워커 **118~153%** (코어 1.2~1.5개)
- 시스템 전체 **34~52%** (4코어 중 1.4~2.1개)

워커가 100% 를 넘는 것은 일부 구간(SQLite I/O·C 확장)이 GIL 을 놓기 때문이고,
그런데도 처리량이 안 오르는 것은 **Python 바이트코드 구간이 직렬화**되기
때문이다. 코어 두 개 남짓이 논다. 메모리는 제약이 아니다(워커 441MB, 여유 6.3GB).

`threads` 를 올려도 이 천장은 그대로다 — GIL 은 스레드 사이에서 공유된다.
프로세스를 늘리는 것만이 Python 구간을 실제로 병렬화한다.

### 1-2. 그런데 지금 워커를 늘리면 예약이 중복 발화한다

`create_app()` 이 `AISchedulerService.init_app(app)` 을 부르고, 그것이
영구 잡스토어를 물린 `BackgroundScheduler` 를 띄운다.

```
aot/aot_flask/app.py        create_app() → AISchedulerService.init_app(app)
aot/ai/services/            _scheduler = BackgroundScheduler(
  ai_scheduler_service.py       jobstores={'default': SQLAlchemyJobStore(SCHEDULER_DB_PATH)},
                                job_defaults={'coalesce': True, 'max_instances': 1, ...})
```

- `_scheduler` 는 **모듈 전역** = 프로세스당 하나
- 프로세스 사이를 조율하는 장치가 **없다**(파일락·리더선출 없음)
- `max_instances: 1` 은 **한 스케줄러 안에서만** 유효하다

따라서 `workers=N` 이면 스케줄러 N 개가 같은 잡스토어에서 각자 만기 잡을 집어
실행한다. **예약이 최대 N 번 발화하고, 그 예약에는 장치 제어가 포함된다.**
밸브가 N 번 열리는 것은 캐시 불일치와 무게가 다르다.

> ⚠ 이 실패는 **재현해 보지 않았다.** 실패 모드가 물리 장치 작동이라 운영 중인
> 서버에서 돌릴 수 없다. 위 결론은 코드 근거(전역 인스턴스·가드 부재·공유
> 잡스토어)로만 확정한 것이다. 검증한다면 장치가 붙지 않은 격리 환경에서
> 더미 잡으로 할 것.

### 1-3. `preload_app` 은 답이 아니다

`preload_app = True` 로 두면 앱 팩토리가 fork 전 마스터에서 한 번 돌지만,
**스케줄러 스레드는 fork 된 자식에게 상속되지 않는다.** 결과는 예약이 **0 번**
발화하는 것이다. N 번이 0 번이 될 뿐 둘 다 조용한 고장이고, 0 번 쪽이 오히려
발견이 늦다(아무 일도 안 일어나는 것은 로그에도 안 남는다).

## 2. 무엇을 옮기는가

스케줄러가 등록하는 잡은 두 갈래다.

| 갈래 | 예 | 성격 |
|---|---|---|
| **시스템 주기 잡** | `_weather_summary_job`, `_context_broadcast_job`, `_audit_log_purge_job`, `_tier_reclassification_job`, `_realtime_alert_check_job`, `_calendar_sync_job` … | 앱 기동 시 고정 등록 |
| **사용자 예약** | `scheduler_meta_<id>` | 사람이 만든다. **장치 제어를 포함한다** |

둘 다 같은 스케줄러에 들어가므로 함께 옮긴다. 나눠서 옮기면 "무엇이 어디서
도는가" 를 두 벌 기억해야 하고, 그 기억이 갈라지는 순간이 곧 중복 발화다.

### 웹이 스케줄러에 거는 요구

웹은 APScheduler 객체를 직접 만지지 않는다 — 전부 `AISchedulerService` 의
메서드를 지난다(`routes_scheduler.py`, AI 도구):

```
propose_job / propose_job_no_commit / approve_job / reject_job
get_jobs / get_drafts / get_schedule_horizon / trigger_context_broadcast_now
```

이 중 **상태를 바꾸는 것**(approve/reject/propose)은 잡스토어에 잡을 넣거나
빼야 하고, **읽기**(get_*)는 DB(`SchedulerJobMeta`)만 보면 된다.

⚠ 여기가 분리의 핵심 난점이다. **잡스토어에 다른 프로세스가 잡을 써 넣어도
돌고 있는 스케줄러는 그것을 모른다.** APScheduler 는 다음 깨어날 시각을 자기가
아는 잡들로 계산하므로, 밖에서 추가된 잡은 그 스케줄러가 우연히 깨어날 때까지
발화하지 않는다. 즉 **"웹이 승인 → 스케줄러가 즉시 반영" 을 위한 통지 경로가
반드시 필요하다.**

## 3. 선택지

### 안 A — 데몬(`aot.service`) 안으로 옮긴다 ★ 권장

데몬은 이미 상시 돌고, 이미 장치를 제어하며, **웹→데몬 RPC(`DaemonControl`,
Pyro5)가 이미 있다.** 통지 경로를 새로 만들지 않아도 된다.

```
web(gunicorn, workers=N)  --DaemonControl RPC-->  daemon(aot.service)
                                                    └─ APScheduler (유일)
```

- 웹: `AOT_SKIP_SCHEDULER=1` 을 **기본값**으로 (지금은 MCP·prod compose 만 켠다)
- `approve_job` 등 상태 변경은 RPC 한 번으로 데몬에 통지 → 데몬이 `add_job`
- 읽기(`get_jobs` 등)는 지금처럼 DB 직접 조회 — RPC 를 태울 이유가 없다

**대가**: AI 잡(주기 요약·컨텍스트 브로드캐스트)이 제어 프로세스 안에서 돈다.
LLM 호출은 길고 무거워서 제어 루프의 타이밍에 영향을 줄 수 있다. 데몬은
`max_instances: 1` 과 별개로 자기 제어 주기를 지켜야 하는 프로세스다.
→ 완화: 잡 실행자를 별도 스레드풀로 두고 제어 스레드와 분리한다. 그래도
**같은 GIL** 이라는 사실은 남는다.

### 안 B — 전용 유닛 `aotscheduler.service`

`aotmcp.service` 와 같은 급으로 프로세스를 하나 더 둔다.

- 장점: 제어와 AI 잡이 서로 간섭하지 않는다. 책임이 이름과 일치한다.
- 대가: **통지 경로를 새로 만들어야 한다**(Pyro5 하나 더, 또는 소켓/파일 신호).
  업그레이드 경로에 유닛이 하나 더 늘고, `aotmcp` 가 그랬듯 **업그레이드
  스크립트에서 빠뜨리면 조용히 옛 프로세스가 남는다**(CLAUDE.md 의 aotmcp
  재시작 누락 이력 참조). 메모리도 한 벌 더(대략 400MB 대).

### 안 C — 워커 간 리더 선출(파일락)

워커 하나만 스케줄러를 켠다.

- 장점: 프로세스 구조를 안 바꾼다.
- 대가: **경계에서 깨진다.** 리더 워커가 죽거나 gunicorn 이 워커를 교체하면
  그 사이 예약이 멈추고, 락 해제가 늦으면 두 워커가 겹치는 창이 생긴다.
  "대부분 맞는" 안전장치는 물리 제어에서 쓰지 않는다.

### 안 D — 아무것도 안 한다 (`workers = 1` 유지)

요청당 CPU 를 줄이는 쪽으로만 간다. 지금까지 해온 방향이고 실제로 효과가
있었다(필지 요약 Influx 배치, 구획 목록 N+1, 시퀀스 상태 N+1).

- 장점: 위험 0.
- 대가: 천장은 그대로다. 사용자가 늘거나 위젯이 늘면 다시 만난다.

### 판단

**안 A 를 권한다.** 통지 경로가 이미 있다는 것이 결정적이다 — 안 B 의 장점
(격리)은 실제 문제로 확인되지 않은 반면, 안 B 의 대가(유닛 추가·업그레이드
누락 위험)는 이 저장소에서 **이미 겪은 실패**다.

안 B 는 데몬 안에서 AI 잡이 제어 타이밍을 방해하는 것이 **실측되면** 그때
옮긴다. 지금 그것을 선제적으로 하는 것은 근거 없는 복잡도다.

## 4. 옮길 때 지켜야 할 것

### 4-1. 스코프 재검사가 따라와야 한다

예약은 발화할 때 그룹 스코프를 다시 묻는다(`AISchedulerService._scope_denies`,
신원은 `SchedulerJobMeta.user_id`). 이것은 **"지금 못 켜니 1분 뒤로 예약" 이
게이트의 우회로가 되는 것**을 막는 장치다(docs/design/access-scope-groups.md).
프로세스를 옮겨도 이 검사가 같은 자리에서 돌아야 한다 — 데몬에는 요청
컨텍스트가 없으므로 `user_id` 로만 판정한다는 기존 전제가 그대로 유지된다.

### 4-2. AI 게이트를 두 번 구현하지 말 것

백그라운드 AI 잡은 `ai_autonomy_enabled()` / `ai_background_active()` 를
지나야 한다(docs 없음 — `aot/ai/services/ai_runtime_state.py`). 옮긴 프로세스가
같은 DB 를 읽으므로 판정은 그대로 동작한다. **게이트를 새로 쓰지 말 것.**

### 4-3. 잡스토어는 하나여야 한다

`SCHEDULER_DB_PATH` 는 그대로 쓴다. 옮기는 동안 **웹과 새 프로세스가 동시에
스케줄러를 켜는 창이 생기면 안 된다** — 배포 순서는

1. 웹에 `AOT_SKIP_SCHEDULER=1` 을 켜고 재시작 (이 순간부터 예약이 멈춘다)
2. 새 위치의 스케줄러를 켜고 재시작
3. 1↔2 사이가 벌어지면 그만큼 예약이 밀린다 — `misfire_grace_time`(300초)
   안에 끝낼 것. 넘기면 그 회차는 FAILED 로 남는다(정상 동작이다)

### 4-4. 검증 — "안 도는 것" 과 "두 번 도는 것" 을 둘 다 본다

옮긴 뒤 확인해야 할 것은 대칭이다:

- **0 번 발화하지 않는가**: 더미 주기 잡을 하나 넣고 `SchedulerJobMeta` 에
  COMPLETED 가 규칙적으로 쌓이는지
- **2 번 발화하지 않는가**: 같은 잡의 `executed_at` 이 한 주기에 하나뿐인지
- 웹에서 예약을 승인한 뒤 **즉시** 반영되는가(통지 경로가 실제로 도는가)

`aot/tests/test_scheduler_fake_success.py` 가 이미 "발화했는데 실행되지
않았다" 를 잡는다 — 옮긴 뒤에도 그 판정(`call_state`)이 그대로 서야 한다.

## 5. 옮긴 뒤에 할 일 (워커 증설)

스케줄러가 밖으로 나가면 `workers` 를 올릴 수 있다. 그때:

- 남은 프로세스 메모리 상태는 **경미**하다(안전 문제 아님):
  `routes_geo._openmeteo_fail_until`(상류 장애 시 60초 창에서 호출 N 배),
  `site_summary._CACHE`(30초, 적중률만 하락). flask-caching 은 이미
  `FileSystemCache` 라 공유된다.
- **늘리고 나서 다시 재라.** 1절의 실측은 "코어가 논다" 까지만 말한다.
  워커가 늘면 **SQLite 쓰기 경합**이 다음 병목 후보다 — WAL 이 켜져 있어 읽기는
  괜찮지만, SD 카드 위에서 N 개 프로세스가 쓰기를 다투는 것은 재보기 전에는
  모른다. 워커 수는 추측이 아니라 그 측정으로 정한다.

## 6. 하지 말 것

- **`preload_app = True` 로 때우지 말 것** — 1-3 절. 예약이 0 번 발화한다.
- **`workers` 만 올리지 말 것** — 이 문서가 존재하는 이유다.
- **스케줄러를 두 곳에서 켜지 말 것** — 잡스토어가 공유라 조율 장치가 없다.
  `AOT_SKIP_SCHEDULER` 는 "성능 옵션" 이 아니라 **안전 스위치**다.
- **리더 선출로 시작하지 말 것**(안 C) — 경계에서 겹치는 창이 생기고, 그 창에서
  일어나는 일이 물리 작동이다.

## 7. 구현 기록 (2026-09-09)

### 7-1. 조사 중 드러난 것 — 이중 스케줄러가 이미 돌고 있었다

`AOT_SKIP_SCHEDULER=1` 은 `aot_mcp` 에만 걸려 있었고, 데몬은
`aot_daemon.py` 에서 `create_app()` 을 직접 부른다. `create_app()` 이
`AISchedulerService.init_app()` 을 부르므로 **웹과 데몬이 각각 스케줄러를
띄우고 있었다.** 실측(로컬, 2026-09-08):

```
데몬 컨테이너 PID 1  → aot_scheduler.db 열고 있음
웹  컨테이너 PID 15 → aot_scheduler.db 열고 있음   ← 같은 파일
```

prod 도 같다(`docker-compose.prod.yml` 의 그 변수도 `aot_mcp` 에만 있다). 즉
2절이 "워커를 늘리면 생긴다" 고 적은 조건이 **워커 1개인 상태에서 이미
성립해 있었다.** 실제 이중 발화가 관측되지 않은 것은 그 시점에 무장된 장치
예약이 0건이었기 때문이고(`apscheduler_jobs` 0행, PENDING 18건은 전부
`human` 타입이라 APScheduler 트리거를 만들지 않는다), 운이 좋았던 것이다.

### 7-2. 원안과 다른 점 ① — 환경변수가 아니라 코드 기본값

3절 안 A 는 "웹에 `AOT_SKIP_SCHEDULER=1` 을 기본값으로" 라고 적었다. 그러면
데몬 기동 경로(로컬 compose·prod compose·systemd 유닛)마다 변수를 넣어야 하고,
**하나라도 빠뜨리면 그 배포는 스케줄러가 0개**가 된다. 이 저장소는 `aotmcp`
에서 이미 "업그레이드 스크립트에서 빠뜨려 조용히 어긋난" 이력이 있다(6절).

그래서 판정을 코드로 옮겼다:

- `create_app(config, run_scheduler=False)` — **기본이 실행 안 함**
- 데몬만 `create_app(run_scheduler=True)` 로 부른다(호출부는 `DaemonController`
  하나뿐이라 구조적으로 하나가 보장된다)
- `AOT_SKIP_SCHEDULER` 는 기존 안전 스위치로 계속 존중한다

빠뜨렸을 때의 결과가 "두 번 발화" 가 아니라 "안 켜짐" 으로 바뀐다 — 둘 다
고장이지만 후자는 검증으로 잡히고 밸브를 두 번 열지 않는다.

### 7-3. 원안과 다른 점 ② — RPC 대신 '멈춘 스케줄러'

안 A 는 `approve_job` 의 등록을 RPC 로 데몬에 넘기라고 했다. 그런데 실행하지
않는 프로세스에서 스케줄러를 **아예 안 띄우면** APScheduler 는 `add_job` 을
잡스토어가 아니라 자기 메모리(`_pending_jobs`)에 담고 `start()` 때 비운다 —
웹이나 MCP 에서 승인한 예약이 **DB 에 닿지 못하고 조용히 사라진다**(APScheduler
가 남기는 `Adding job tentatively` 가 그 신호다).

그래서 실행하지 않는 프로세스도 **멈춘 채(paused)** 띄운다. `paused` 는
`STOPPED` 가 아니라서 등록·해제가 잡스토어로 곧장 가고, 실행만 하지 않는다.
호출부를 하나도 고치지 않아도 되고 RPC 경로를 새로 만들 필요도 없다.

대가는 **지연**이다. 데몬 스케줄러는 다음 잡의 시각까지 잠드는데 잡이 하나도
없으면 무기한 잠들므로, 다른 프로세스가 넣은 예약을 알아채지 못한다. 하는 일
없는 심박 잡(`scheduler_heartbeat`, 60초)으로 주기적으로 깨워 잡스토어를 다시
읽게 했다. 최악 60초 늦는데 `misfire_grace_time` 300초 안이라 발화 자체는
보장된다. 즉시성이 필요해지면 그때 RPC 를 얹는다 — **그때도 RPC 실패에
대비해 이 심박은 남겨야 한다.**

### 7-4. 함께 고친 것 — 등록 게이트가 계약과 어긋나 있었다

`init_app` 이 백그라운드 AI 잡을 `ai_enabled`(1단계, "메뉴 노출")만 보고
등록하고 있었다. 4-2 절이 지정한 정본은 `ai_runtime_state` 이고, 모델 주석은
백그라운드 작동을 2단계(`ai_running`)의 몫으로 못박는다. `ai_autonomy_enabled()`
로 바꾸고, 게이트가 닫히면 **영속 잡스토어에 남아 있던 잡을 지우도록** 했다 —
등록을 건너뛰는 것만으로는 예전에 저장된 잡이 계속 깨어났다(실측: 스위치를
끄고 재시작해도 10개 전부 생존).

### 7-5. 워커 증설 (2026-09-09)

`workers = 1` 하드코딩을 `resolve_gunicorn_workers()` 로 바꿨다
(`aot/utils/system_environment.py`). 산정은 **메모리가 먼저**다 — 워커마다 앱을
통째로 적재하므로(실측 RSS 404MB, 마스터 23MB) 코어 수와
`(가용메모리 − 예약분) ÷ 워커몫` 중 작은 쪽을 택하고 `WORKERS_MAX`(4)로 자른다.

| 환경 | 워커 |
|---|---|
| 라즈베리파이 (어떤 사양이든) | **1** — 늘려서 얻는 것보다 스왑으로 잃는 것이 크다 |
| 저메모리(`< LOW_MEMORY_GB`) | 1 |
| 로컬 도커 (4코어 3GB) | 2 |
| 일반 서버 (8코어 8GB) | 4 |

`GUNICORN_WORKERS` 로 덮어쓸 수 있다. 스레드와 달리 DB 설정은 두지 않았다 —
메모리를 직접 먹는 값이라 화면에서 바꾸다 기기를 재우기 쉽고, 바꾸려면 어차피
재시작이 필요하다.

**운영 배포(라즈베리파이)는 값이 바뀌지 않는다.** 이번 증설의 수혜는 도커·서버
설치뿐이고, 파이는 1 그대로다.
