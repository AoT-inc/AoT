    AI機能の概要~

    AoTは、MCP(Model Context Protocol)ベースのAIエージェントを使って、現場(温室、圃場、公園、建物など、機器が空間に配置された場所ならどこでも)の環境を観察・診断・制御します。AIはあくまでアドバイス役に徹し、機器を動かす操作はすべて実行前にユーザーの承認が必要です(設定だけを変更する編集は例外です。詳しくは「安全性と承認のモデル」の節を参照してください)。

    はじめに: スイッチは2つあります~

    AIを使うには、別々の場所にある2つのスイッチを入れる必要があります。あえて1つにまとめていません。

    スイッチ 場所 オンにすると起きること
    AIサービスを有効化 管理 > システム管理 > 一般設定 AIメニューがナビゲーションに現れ、AIページに入れるようになります。
    内蔵AIを動かす AI > 接続 > 内蔵AI 内蔵モデルそのものが動きます — チャットとアドバイス要求、そして誰も呼ばなくても動く作業(定期サマリー、コンテキストのブロードキャスト、天気サマリー、MCPヘルスチェック、リアルタイムアラート)。

    順序は 一般設定で有効化 → AI > 接続ページでモデル(エージェント)を登録 → 稼働を開始 です。

    Claude Desktop などの自分のAIアプリで接続する経路は、このスイッチとは別に動きます。管理 > システム管理 > 一般設定で外部MCPのアクセスを許可し、ユーザーごとのアクセスキーがあれば足ります。内蔵AIはオフのままで構いません。AI > 接続ページの上部で両方の状態を確認し、それぞれの画面へ移動できます。

    この「外部MCPアクセス」トグル(管理 > システム管理 > 一般設定 > 外部MCPサーバーを有効化、AIGlobalSettings.mcp_http_enabled)は、MCPサーバーへのリクエストのたびにキャッシュせず毎回確認されます — オフにすると、再起動なしでその場から外部MCP呼び出しがすべて503になり、オンに戻せば同じくらいすぐに復旧します。

    • モデルを1つも登録していないと稼働を開始できません。 尋ねる相手がいないままバックグラウンド処理だけが回ると、サイクルのたびにログにエラーが積み重なるだけです。このスイッチは、少なくとも1つのエージェントが有効化されている場合にのみ使えるようになります。
    • 最後のモデルを無効化または削除すると、稼働も止まります。 後でモデルを再度有効化しても、自律稼働は黙って再開しません — AIページであらためて開始してください。
    • 稼働をオフにすると、チャットとアドバイス要求も拒否されます。 このスイッチは「内蔵モデルが動いている」という意味なので、オフの間は尋ねる相手がいません — AIページの補足行もそう書かれています。ただし1つだけ開いたままです。すでに提出されたアドバイスを決定する操作は(自分のAIアプリがMCP経由で出したものも含めて)AI → リクエスト画面で引き続き行えるため、内蔵モデルを止めているせいで決定待ちの項目が消えることはありません。

    AIシステムのアーキテクチャ~

    AoTのAIは、2つの経路でツールを使用します。

    • アプリ内AIアシスタント — ダッシュボードのチャットアシスタントです。単一のエージェントループがツールカタログ全体を把握し、自らツールを選択・実行します。状態を変更する操作(デバイス制御、エンティティの作成・編集・削除など)は、チャットの承認カードでユーザーが確認したあとにのみ実行されます。
    • 外部MCPサーバー — aot/aot_mcp_server.py(標準MCPプロトコル、stdio/HTTP)。Claude Desktopなどの外部MCPクライアントがAoTのツールを直接呼び出せるように公開します。
    ユーザーチャット ─────────┐            外部MCPクライアント(Claude Desktopなど)
                         ↓                          ↓
            アプリ内エージェントループ       aot_mcp_server.py (stdio/HTTP)
                         └──────────┬───────────────┘
                                    ↓
               tool_execution.py — 承認ゲート + 監査ログ
                                    ↓
      ツールレジストリ (tool_registry.py) — ツール宣言の単一のソース。
      このディスパッチマップが呼び出しを実際のハンドラーに解決します
                                    ↓
                       AoTシステム (Daemon / InfluxDB / SQLite)

    どちらの経路も同じゲート(aot/tools/tool_execution.py)を通って実行され、同じ レジストリ(aot/tools/tool_registry.py)からツール定義を取得するため、アプリ内 アシスタントと外部MCPクライアントの間で承認ルールもツール一覧も決してずれません。

    MCPツール一覧~

    外部MCPサーバーと内部のmcp_aotエンジンが公開するツールです。読み取り系ツールと設定編集系ツールは即座に実行されます。制御・スケジューリング・有効化系ツールは、どちらの経路でも承認ゲートを通ります — アプリ内アシスタントのチャット承認カード、または外部MCPサーバーの承認キュー(pending_approval + respond_to_confirmation。詳しくは後述の「MCPサーバーの実行」を参照)です。

    ドロワーではなく14個のツール箱ひとつ~

    外部接続のツールカタログは既定で、機能が増えるたびに膨らむ一覧ではなく14個です。8個は読み取り専用です — overview、measure、weather、find、detail、records、screen_view、help。6個は何かを変更します — control、record、cultivate、configure、screen、そして削除だけを集めたremove(これにより、アプリの「常に許可」設定を削除以外にだけ適用できます)。

    各ツールはどの動作かを示すop引数を受け取ります(例: measureにop: "latest"なら今の値、op: "history"なら期間の値)。そして、すべての動作が同じ意味で使う共通の引数(target、period、at、measurement、value、query、limit、fieldsなど)を共有します。各ツールの説明にはその動作が「いつ使うか」が1行ずつ載るため、AIはツールを選んでいたのと同じやり方で動作を選びます — 使う前に別途「開く」手順はありません。

    ある動作の完全な引数・既定値・例が必要なときは、AIはtargetに"<ツール>.<動作>"の形を入れてhelpを呼びます — 別のタイムゾーンの場所の現地時刻が必要ならhelp(target: "weather.local_time")。引数なしでhelpを呼ぶと、この接続が使えるすべての動作が表示されます。

    どの動作が見えるかは、依然としてキーのツールセットと設定モジュール(次の節)に従います — その動作が担う作業がキーのツールセットに含まれていなければ表示されません。configure・cultivateは該当モジュールをオンにしたキーでのみ設定用の動作を表示します。オフの動作を求めると、ツールセット外の要求と同じ扱いで答えます。

    以前の表面。 これより前は機能ごとに名前付きのツールが1つあり、常時公開される小さなcore集合と、使う前に別途開く必要のある分野別ドロワー(デバイス・計測・関数・スケジュール・記録・空間・定義・システム)に分かれていました。その表面に戻すには、MCPコンテナ(とAIアシスタントを内蔵するアプリプロセス)にAOT_MCP_SURFACE=legacyを設定します。その後AOT_MCP_TOOL_TIERING=1にすると再びcore+ドロワーに分かれ、設定しなければ平らな一覧のままです。アプリ内AIアシスタントはこのスイッチの影響を受けず、常に上記のドメインツールを使います。

    APIキーごとのツールセット~

    APIキーごとに、外部のAIアプリが使える動作の範囲、つまりツールセットを選びます。キーの権限とは別の設定です — 権限はそのキーで何をしてよいかを、ツールセットは何を提供するかを決めます。

    ツールセットは運用(常にオン)に、チェックした設定モジュールを加えたものです。モジュールひとつが設定作業のひと分野を加え、チェックするとconfigure・cultivateなどのツールが提供する動作がその分増えるため、そのキーの用途に必要なモジュールだけをチェックしてください。

    • 運用(常にオン。新しいキーは既定でこれだけを受け取ります) — 日々の作業: デバイス・センサー・天気・スケジュール・ノート・区画の参照、住所・距離・近い場所の検索、デバイスと関数の制御、関数オプション・シーケンス運転時間・既存のシーケンスステップの調整、スケジュール登録、ノート・お知らせ・助言・区画ステージの記録とその編集・削除。
    モジュール 追加される作業
    plots — 区画と作期プログラム 区画の作成・編集・複製・分割、ステージの型と案内、作期プログラム
    map — 地図と位置 デバイスの配置、配管の口径、地図図形の削除
    automation — 自動化の作成 関数・シーケンスの作成・削除、シーケンスの1日の計画の一括設定
    devices — デバイス定義 デバイスの種類とオプション、入力・出力・GIS入力の作成・編集・削除、スロットの再割り当て
    dashboard — ダッシュボード ダッシュボード・ウィジェット・タブ
    library — 文書とライブラリ アーカイブ文書、調べた知識の保存、ライブラリソース
    admin — システムとAI設定 システム更新・ストレージ階層の状態、AIエージェント

    運用だけをオンにしたキーは約9,000トークンのツール一覧を受け取り、すべてのモジュールをチェックすると(設定)約15,000まで増えます。

    ライトが届く動作は運用と同じです — ツール一覧はすでに上記の固定された14個なので、ライトだからといってさらに縮むことはありません。ライトが今も制限しているのは応答ひとつのサイズです: それ以外の場合より低い約6,000トークン — 応答は会話に残り、以後のメッセージごとに再送されるためです。それより長い場合は先頭の項目だけを送り、質問を絞るよう案内を付けます。応答が積み重なるため、1日の上限が厳しい無料のAIプランには依然としてライトを選んでください。ライトには設定モジュールを追加できません。

    あとからツールセットを変える。 キーを再発行せずに3つの方法で変えられます: 管理 > システム管理 > ユーザーのキーの行(上記)、設定 > 一般 > AIツール一覧(ユーザーごとに自分のキーを見て、ライト・運用・設定から選ぶ)、またはAIに頼む — AIが今使っている接続のキーについてconfigureをop: "tool_profile_set"で呼びます(常に人の承認が必要で、ほかのキーは変えられません)。リモートMCP接続なら、接続アドレスに?tools=liteを付けることもできます(stdioはAOT_MCP_TOOLS=lite)。キーを変えずにその接続だけをライトに絞り、広げることはありません。新しい一覧と応答の上限は、アプリの再接続後に反映されます。

    すべてのモジュールをチェックすると以前の運用 + 設定と同じになり、そのように(configuration)保存されます — そのキーは今後追加されるモジュールも受け取ります。モジュール導入前に運用 + 設定だったキーはそれまでと同じ一覧のまま、運用のキーは運用のままです。変換は何も行いません。

    管理 > システム管理 > ユーザー一覧のAPIキー欄(AIツール)でキーの発行時にモジュールを選びます — 代わりにライト(小さいツール一覧)をチェックすると、そのキーをライトのツールセットとして直接発行し、モジュールのチェックボックスはオフになります。あとから同じ画面でキーを再発行せずに変更できます(キーの行のチェックボックス、またはその行のライトのチェックボックスを変えて変更)。変更にはキーの失効と同じ権限(ユーザー編集)が必要で、変更前後のツールセットとモジュール一覧が監査ログに記録されます。新しいキーの発行には、これに加えて直近のログインが必要です。接続済みのアプリは、再接続すると新しい一覧が表示されます。

    キーがオフのモジュールの動作を求めると、サーバーは拒否し(call_state: refused、reason_code: tool_profile、tool_module: <モジュール>)、そのモジュール名と、誰がどこでオンにするかをメッセージで伝えます。承認待ちには入りません。helpも、ツールセット外の動作を「不明な動作」ではなく同じメッセージで答えます。キーの権限でどのみち使えない動作(例: 読み取り専用キーの書き込み動作)の場合は、切り替えても意味がないため切り替えの案内を付けません。その他の拒否(助言専用モード・キーのロール・承認)でも切り替えは勧めません — 助言専用モードはどのツールセットでも変わらないサーバー全体の設定です。ツールセット外の動作の承認待ち項目はその動作が担う作業の名前を出さずに(中立の表示と分野のみ)表示され、そのキーで却下はできますが承認はできません。サーバーの案内文とoverviewのop: "brief"は、オンのモジュールと、オフのモジュールごとに何が加わるかを1行ずつAIに伝えるため、AIは「できない」と答える代わりに、どのモジュールをオンにしてもらうかを案内できます。

    • ツールセット導入前に発行されたキーは、アップグレード後の最初の起動時に一度だけ割り当てられます: 直近90日間にキーの所有者が設定動作を呼び出していれば運用 + 設定(全モジュール)、それ以外は運用です。監査ログにはどのキーで呼び出したかが残らないため、人単位で決めます — 同じ人のキーはすべて同じ値になります。割り当て後、キーごとに必要なモジュールへ絞ってください。
    • アプリ内のAIアシスタントはツールセットの制限を受けません。内蔵AI自身のサービスアカウントのキー(アプリ内のデバイス制御はこのキーを経由します)も同様で、画面ではこのアカウントのキーにモジュールの選択を表示しません。
    • 中央認証で接続した場合(claude.aiのリモートコネクターのようにキーを入れられないアプリ)は、キーの代わりに連携したアカウントにツールセットを置きます。設定 > 一般 > AIツール一覧の「サインイン接続のAIアプリ」の行、またはAIへの依頼(configureをop: "tool_profile_set"で)で選びます。選んでいなければ従来どおりaot.configスコープがあれば全モジュール、なければ運用です。選んだ値もトークンのスコープを超えません — ライトは常にライト、運用(+モジュール)・設定にはaot.configが必要です。
    • recordsのop: "knowledge_search"は、見つけた内容をrecordのop: "knowledge_shelve"で保存するよう促す案内を、それを使える接続(libraryモジュール、またはアプリ内のAIアシスタント — ノート編集権限がある場合)にだけ付けます。
    • AOT_MCP_TOOL_PROFILES=0でツールセットを無効にします(以前と同じく、すべてのキーがすべての動作を見ます)。AOT_MCP_DEFAULT_TOOL_PROFILEは認証なしで動くサーバーのツールセットです(既定operations。configurationやoperations+plots+mapのような値も使えます)。

    以前の表面(AOT_MCP_SURFACE=legacy)では、ツールセットは今も名前付きツールの平らな一覧を決め、ライトも自分だけの短い一覧(get_place_overview、get_sensor_reading、list_plots、get_control_state、get_weather、operate_device、respond_to_confirmation、get_screen)と、残りに届くread_tool・use_tool・get_tool_detailをそのまま使います。

    名前での指定、複数対象の一括指定、引数の事前確認~

    • IDの代わりに名前。 get_output_state・get_device_measurements・get_sensor_detail・get_sensor_readingはデバイス名を、get_zone_sensor_summary・list_plotsはゾーン・サイト名を、get_plotは栽培中の区画の名前・作物・品種を受け付けます。IDもそのまま使え、先に確認されます。名前が複数の対象に当たる場合は1つを選ばず、needs_disambiguationと、場所で見分けられる候補を返します。デバイスの引数にはsearch_devicesの応答をそのまま渡すこともできます — その応答に複数のデバイスが含まれる場合は1つを選ばず、候補を返します。1つの種類だけを受け取る引数に別の種類を渡すと、そのデバイスが実際にどの種類かを添えて拒否します。
    • 地図は場所ではありません。 ゾーン・サイトの引数(zone_id・zone_ids・loc_id・scope_id)に地図のIDは渡せません。その地図に描かれた図形の1つで黙って答えるのではなく、そのIDがどの地図かと、その地図にあるサイトの一覧(sites_on_this_map)を返します。場所だけを受け取る引数(zone_id・zone_ids・scope_id)にデバイス名を渡すと場所ではないと答えます(loc_idはデバイス名をまずそのデバイスとして読みます)。また、栽培中の区画の名前はその区画が入っているゾーンとして読みます。
    • 場所は区画ではありません。 区画の引数(plot_id・plot_ids)にサイト・ゾーン・施設は渡せません。その名前・IDがどれに当たるかを示し、その中の区画はlist_plotsで見るよう案内し、栽培中の区画の名前(growing_plots)も併せて返します — その名前の区画が無いとだけ答えることはありません。
    • 複数の対象を一度に(最大10個): device_ids(get_output_state・get_sensor_reading)、loc_ids(get_sensor_detail)、plot_ids(get_plot)、target_names(search_notes)、zone_ids(get_zone_sensor_summary)。応答は{count, results}で、項目ごとにどの対象への答えか(requested)が記され、形は対象ごとに1回呼んだときと同じです。単数の引数(device_id・plot_idなど)にリストを渡しても同じように読み、重複は除かれ、10個を超えると分けて呼ぶよう返します。
    • 引数を先に確認します。 書き込みツールは権限・承認の段階より前に引数を確認します。不足している引数、正しい名前の打ち間違いと思われる引数、modify_function_optionsの存在しないオプションキーや誤った値は、reason_code: invalid_argumentsと正しい名前の一覧で返ります(get_function_detailが関数のオプションキー・現在値・範囲を先に示します。temperatureのような範囲はキーではなく、その下限・上限のキーを使います) — 助言専用モードでも同じで、そのキーではどのみち実行できない呼び出しならその旨も伝えます。それ以外の不明な引数は無視され、_ignored_argumentsで知らせます。ただし照会ツールが受け付けない対象引数(target_name・zone_id・place・device_idなど)は無視しません — 捨てると農場全体がその対象の答えのように返るため、実行せずにunknown_scope_argumentとそのツールが受け付ける引数の一覧を返します。
    • 引数が原因で拒否されるときは、そのツールの詳細なschemaとhint(入れ子の項目の形・判断ルール・例)も一緒に返します。get_tool_detailも1つのツールについて同じ詳細な説明を返します。ツール一覧自体は軽いままで、これらは載せません。
    • 大きな結果は応答が大きくならないよう要約形で返します。list_plots・get_crop_statusは最初の10件のみ(truncated表示)、get_control_stateは画面専用の診断値を省き(detail=trueで戻せます)、get_plotは段階表の案内・目標を省きます。省いたものは_omittedに記します。
    • get_sensor_readingのスキーマにデバイスIDの一覧を載せなくなりました。デバイスが増えてもツール一覧は大きくなりません。
    • search_devicesは同じ名前のデバイスを示します(same_name_count・where・same_name_groups)。
    • get_spatial_treeをdepthなしで呼ぶと、すべての階層のサイト・ゾーン・施設と、場所ごとのデバイス数を返します。デバイスまで見るにはdepthを指定します。
    • 区画のステージ: すでに起きた切り替えはconfirm_plot_stage、まだ来ていない境界を動かすのはreschedule_plot_stageです。get_plotがそのステージを提案していなければ、confirm_plot_stageには日付(started_on)が必要です。MCPではステージ用の6ツール(確定・日程変更・取り消し、区画モジュールを有効にしたキーでは指針・追加・削除も)が1つのツールplot_stageとして表示され、operationにツール名を指定して選びます。各キーには使えるoperationだけが表示されます。承認と監査ログには選んだツール名が残ります。予定作成の2ツール(add_schedule・add_schedule_batch)も同じようにschedule_add1つとして、お知らせの書き込み3ツールはnotice1つとして表示されます。そのキーで使える操作が1つだけなら、元のツール名のまま表示されます。AOT_MCP_FACADES=0にすると以前どおり個別に表示されます。
    • ツールの説明は短くしました。結果の読み方は応答の_reading欄に載り、AIはそれに従います。

    シーケンス(設定編集には承認不要)~

    シーケンスは複数の出力を決まった順序で動かします — かんがいでよくある形で、バルブが順番に切り替わり、ポンプが運転全体にまたがって動きます。以下のツールはシーケンスを読み取り、組み立てます。この節のツール4つ(以下の3つとcreate_sequence_function)はいずれもfunctionドロワーにあります。

    ツール 説明
    configure_sequence_day ある曜日の実行計画全体を1回の呼び出しで設定 — どのデバイスを、どの順序で、どれだけの時間、どれをまとめて動かすか
    modify_sequence_step 1ステップのグループ・所要時間・単独/合計モード・合計ステップの先行/遅延マージン・実行順序・有効状態・ラベルを、全曜日一括または特定の曜日だけに設定
    modify_sequence_schedule 1日の実行時間帯、サイクル周期、シーケンスを実行する曜日

    シーケンスの設定編集は、承認なしで即座に反映されます。 上記の3つの ツールに加えてcreate_sequence_functionとmodify_function_optionsも、 設定を変更するだけで、機器を動かすことはありません。編集が現場で効果を持つのは activate_functionを経たあとだけで、有効化そのものは引き続き承認の対象です。 受け入れているトレードオフはこうです — すでに有効なシーケンスのスケジュールを 編集すると、承認なしで次回実行が変わります(2026-08-07に決定)。

    get_function_detailはシーケンスのステップに加えてweekly_plan(各曜日に実際に何が、実時刻でいつ動くか)を返します。変更を確認するときは、リクエストを繰り返すのではなく、これを読み返してください。

    シーケンスはIDの代わりに名前でも指定できます — まずIDが照合され、なければ名前で探します。関数の名前に重複の制限はないため、名前が2つ以上に当たる場合は何も変更されません。代わりに名前が曖昧である旨の応答と、候補(種別・有効かどうか・所属タブつき、最大10件と総件数)が返ります。意図したほうのIDで呼び直してください。

    使う前に知っておくとよいことが2つあります。

    • 同じスロットに並んだデバイスは同時に動きます。スロットは1つの所要時間を共有します。「この2つのバルブを40分間一緒に開ける」はこうやって表現します。
    • 曜日ごとに、どのステップを動かすか・そのグループ・所要時間を上書きできます。 そのため、たとえば木曜の夕方の運転と金曜の明け方の運転を1つのシーケンスでまかなえます。曜日が違うというだけの理由で2本目のシーケンスを作る必要はありません。

    modify_function_optionsはシーケンス(や他のトリガー)には効きません — それらの設定はcustom_optionsではなくデータベースの列だからです。呼び出すと、上記のツールを使うよう案内して拒否されます。

    呼び出し状態(call_state)~

    tools/callのすべてのレスポンスにはcall_stateが含まれます。各ツール固有の statusの語彙(modified、created、deleted、configured、successなど)を 知らなくても、その呼び出しが実際に実行されたかどうかをこれで判断できます。

    値 意味 クライアント側の対応
    executed この呼び出しで実行済み(読み取りツールも含む) 結果を報告する
    already_executed ユーザーが承認した時点でサーバーが既に実行済み 同梱のresultを報告する。再度呼び出さない
    pending_approval 未実行、人の承認待ち ユーザーを承認ページに案内して待つ
    queued ユーザーの画面に送ったが、画面がまだ実行を知らせていない(画面操作のみ) 「送った」と伝え「済んだ」とは言わない。もう一度送る前に画面を確認する
    approval_rejected ユーザーが却下した 実行しない。アドバイスに切り替える
    approval_expired 承認の有効期限が切れた あらためて承認を求める
    refused 別の理由で拒否された(レート制限、引数の不一致など) reason_codeを読んで説明する
    failed ツールがエラーで終了した エラーを報告する

    既存のstatusの値は変わりません — コードや稼働中の設定は既にそれで分岐しているため、これは軸を再定義するのではなく新たに1本追加するものです。

    状態を変える呼び出しが適用されなかった場合(executed・already_executed以外のすべて、または承認時の実行が失敗した場合)、レスポンスにはperformed: falseと短い_readingも含まれます。ユーザーに適用されていないこと(pending_approvalなら、まだ人の承認待ちであること)をはっきり伝え、対象はIDではなく名前で示す、という内容です。いくつかのツールはエラーではなく独自のstatusの語で「実行しなかった」ことを伝えます。状態を変えるツールでは、これらも適用されなかったものとして扱います: refused(呼び出し状態refused)、rejected・quota_exceeded・not_found・target_not_found・orphan_archive・needs_disambiguation・ambiguous・unavailable(呼び出し状態failed)。読み取りの照会が「どれか」を聞き返すレスポンスはfailedではなくexecutedです — 照会は実行され、候補の一覧がその答えです。それを「何も行われなかった」と読むのは状態を変えるツールだけです。そのため、呼び出し品質指標の拒否率は権限・ポリシー・人による拒否だけを数えます。

    ユーザーが見ている画面を変えるscreen_actionは、何も保存しないため権限上は読み取りに分類されますが、報告の仕方は同じです。端末で「AIによる画面操作を許可」をオンにし、直近30分以内に同期した画面は、同意を求めずにすぐ実行します。それ以外の画面は、見つけた画面でよいかユーザーの同意を待っている間(needs_confirmation)は呼び出し状態がpending_approvalで、時間内に誰も答えなければ(expired)failedになります — 画面の変更が実際に起きる前に、実行済みとして報告されることはありません。送ったものの画面がまだ実行を知らせていなければ(sent・queued)呼び出し状態はqueued、ユーザーが断れば(rejected)approval_rejectedです。画面が頼んだのと違うことをした場合(例: 項目にピンがなく地図全体を強調した)は状態がpartialになり、実際にしたことがdoneに入ります。その動作が使わない引数は黙って捨てずignoredに並べます。

    デバイス命令(operate_device・set_output_state・schedule_device_control)は例外です。命令がすでにデバイスに届いた可能性がある失敗(タイムアウト、通信エラー、送信後のコントローラーエラー)では、performedはfalseではなく"unknown"になります。タイムアウトは呼び出し側が待つのをやめたという意味にすぎないため、再実行の前に現在の状態を確認し(get_output_state、スケジュールならsearch_schedule)、確認できるまでは実行された・されなかったのどちらとも伝えません。何も送信する前に止まった失敗(存在しないデバイス、不正な引数、拒否)はperformed: falseのままです。アプリ内のAIも同じ結果を同じ意味で読み、Webの承認画面は単なる失敗ではなく「コマンドは送信しましたが、反映されたかは確認できませんでした — 機器の状態を確認してください」と表示します。

    関数・入力をオン/オフすると、まず設定を保存してから実行中のコントローラーに知らせます。コントローラーが確認を返さない場合(停止中や処理中の可能性があります)、レスポンスは保存された値をそのまま含み、呼び出し状態もexecutedのままですが、performedは"unknown"になります。今オンになった・オフになったとは伝えず、設定は保存されたが実際の動作に反映されたかはまだ確認できていないと伝えます。get_active_functions_summaryは保存された設定しか示さないため、これを確認する手段にはなりません。

    submit_adviceのレスポンスも、求められた変更ではなく提案だけが保存されたことを明示します。1つの名前が複数の場所やデバイスに当たる場合は、その候補ごとにwhereがあり、IDを使わずに区別できます(距離の照会の候補にはありません)。

    デバイスごとのAI対象トグル~

    設定 -> 入力 / 設定 -> 出力の各デバイス設定モーダルには、AI判断に含めるトグルがあります。

    • オン(既定): その入力/出力はAI判断・制御ツール(空間ツリー、デバイス照会、センサー/制御ツールなど)から見えます。
    • オフ: そのデバイスはこれらのツールの照会や制御対象から除外されます。機密性の高いデバイスや、AIに絶対に触らせたくないデバイスをデバイス単位で隠すのに使います。

    新規に作成した入力・出力は、この設定がデフォルトで有効になっています(is_ai_enabled=True)。

    安全性と承認のモデル~

    状態を変えない読み取りツールは即座に実行されます。書き込みツールは2つに分かれます。

    • 承認が必要(変更・物理制御): デバイス制御(operate_device、set_output_state、schedule_device_control)、入力/出力/Function/掲示板の作成・編集・削除、modify_gis_input・delete_gis_input・activate_gis_input、modify_ai_agent・delete_ai_agent、地図の配置変更(set_device_location、delete_geo_shape)、ノートの永久削除(delete_note)、デバイスの置き換え(rebind_device)、configure_library_sourceなど。
    • config-onlyな書き込み(承認免除): add_schedule、add_schedule_batch、create_gis_input、create_ai_agent、create_program、modify_program、create_sequence_function、modify_function_options、modify_sequence_schedule、modify_sequence_step、configure_sequence_day。これらはそれ自体では機器を動かさないため、承認なしで即座に保存されます — このうち大半(create_gis_input、create_ai_agent、シーケンス系ツールなど)は、作られるものが常に非有効の状態で、実際にそれを有効にする別の段階が用意されており、その段階は引き続き承認の対象です。たとえばcreate_gis_inputは即座に保存されますが、activate_gis_input(承認が必要)を経るまでオフのままですし、シーケンスのスケジュールは自由に編集できても、実際に現場で動くのはactivate_function(承認が必要)を経たあとだけです。create_note・modify_note・knowledge_shelveは記録の書き込みです — これらも承認なしで保存され、有効化の段階はなく、知識は人が確認するまで未確認・非正として扱われます(後述のAI知識の節を参照)。modify_noteは記録の書き込みのなかで唯一、呼び出しごとに承認の要否が変わります — ノートのタイトル・本文・タグを直し、アーカイブしたり戻したりしますが、それ自体でノートを永久に削除することはありません。呼び出した本人が書いたノート、またはユーザーの依頼でAIが作った作成者のないノートのときだけ即座に保存され、他人のノートや作成者が分からないノートは、ほかの変更系の呼び出しと同じく承認待ちになります。ノートを永久に削除すること — Webのノート画面の完全削除に相当するAI側の操作 — は別のツールdelete_noteが担います。上の3つの記録の書き込みとは異なり、これは常に承認待ちになり、記録の書き込みの免除ではなく地図編集と同じ設定編集の権限が必要で、承認カードにはそのノートのタイトル・付いている場所・最初の行・一緒に削除される添付の数が読み返されます — 削除は取り消せないためです。どちらの場合も変更前の値が監査ログに残るため、手で元に戻せます。それでも書き込みなので、Webのノート画面と同じ設定編集の権限が必要で、読み取り専用キーとアドバイス専用モードでは拒否され、グループの範囲に従います。承認免除は権限免除ではありません。アプリ内アシスタントでもMCPでも、config-onlyを含むすべての書き込みは、依頼した人にその権限がある場合にだけ実行され(ノート・知識・掲示板・知識ソースの設定(configure_library_source)と地図編集 — 地図の図形の削除・装置の配置、Webの地図編集と同じ — は設定編集の権限、区画・ステージ記録・区画の資源・作期プログラム・区画日誌はWebの区画画面と同じ区画編集の権限、それ以外は制御の権限(自分の接続のツールプロファイルを変えるset_tool_profileは例外で、特定の役割は不要で、読み取り専用でないキーでログインしていればよい) — 既定の役割ではMonitor・Guest・Kioskは不可)、対象をIDで指定しても名前で指定しても、その人のグループの範囲内でだけ実行されます。グループの判定は引数だけでなく、ツールが実際に変更する対象(解決された装置・関数・スケジュール・ステップ)に対して行われるため、名前で指定する、スケジュールやステップのIDを渡す、他グループのリソースを本文に書く、といった方法では回避できません。保留中のリクエストを承認するには、そのリクエストと同じ権限が必要です(区画のリクエストは区画編集、地図編集は設定編集、それ以外は制御 — Webでもrespond_to_confirmationでも同じ)。承認者が対象のグループ外であれば、リクエストは実行されず、判断できる別の人のために保留一覧へ戻ります。予約ジョブは実行のたびに、その責任者(作成した人、AIが提案した予約は承認した人)の権限とグループで改めて確認します — その間に権限やグループを失っていれば実行せず、失敗として記録します。背後に人がいないバックグラウンドのAI処理(定期要約など)は例外です。

    承認が必要な操作は即座には適用されません。アプリ内アシスタントでは、チャット上に承認カードとして提示され、ユーザーが承認してはじめて実行されます。外部MCPサーバー経由では、pending_approvalレスポンス(キューに入ったconfirmation_id)として返ってきますが、このレスポンスには、システムが依頼をどう解釈したかを人の言葉で読み返した一文(対象の名前と動作)も入っており、AIは実行する前にそれをそのままユーザーに伝えて確認を取ります — 承認として数えられるのは、元の依頼そのものではなく、この読み返しに対する明示的な「はい」だけなので、AIが別の装置や場所だと解釈していた場合でも、実行される前に食い止められます。先の依頼がまだ待機中のうちにAIが同じ依頼(同じツール、同じ引数)をもう一度送っても、2件目は作られず、既存のconfirmation_idが「確認済み」の印とともに返るため、ユーザーに二度尋ねることはありません。どちらの経路でも、ユーザーが却下すれば何も変わりません。

    承認ウィンドウ(画面下部のAIバーにある[承認待ち N]チップで開きます)で承認すると、その場で即座に実行されます。 AIが画面を変更しようとする際の確認(画面操作の許可・拒否)も同じウィンドウに表示され、判断が一か所に集まります。以前は、承認しても許可証が出るだけでした — 人がAIのところへ戻って伝え、AIがもう一度呼び出す必要があり、チャットモデルは話しかけられたときにしか動かないため、この往復をAI自身では完結できませんでした。現在はサーバーが、確認と一緒に保存された引数をそのまま使って実行するため、承認画面に表示された内容と実際に実行される内容がずれることはありません。AIが後で同じconfirmation_idで再度呼び出しても、二度目の実行にはならず、その保存済みの結果が返るだけです。1つの承認は1回だけ実行されます — すでに決定済みまたは実行中のリクエストを再度承認すると拒否され、同じ瞬間に2回承認しても実行は1回だけで、実行中に中断されたリクエストは再送されず実行中のまま残ります。機器の状態を確認してから改めて依頼してください。取り消せない物理制御(バルブ、ポンプ)だけは、承認画面でもう一段階の確認を求めます。

    承認ウィンドウでは、1件ずつ、またはまとめて承認・却下でき、修正してから承認(保存された引数を直してから実行)にも対応します。物理制御は項目内で、もう一段階の確認を求められます。AI → リクエスト画面とダッシュボードウィジェット(aot/widgets/widget_mcp_review.py)は承認待ちの件数と[表示]ボタンだけを示し、ボタンを押すと同じ承認ウィンドウが開きます。判断そのものはそこでは行いません。

    AIの記録~

    AI → 記録(/ai/manage)は、AIが行ったことを振り返る場所です。タブはツール呼び出し、会話、エラー報告、呼び出し品質の4つです。

    呼び出し品質~

    呼び出し品質タブは、接続されたAIがツールをどのように使ってきたかをまとめます。ツール呼び出しタブと同じ記録から計算するため、別に保存するものはなく、このシステムの外に送られるものもありません。

    期間(24時間・7日・30日)と、必要なら接続方式(HTTP経由のMCP、このコンピューター上のMCP、REST API、内蔵AI)を選びます。1行に1つの数字が表示されます。

    • 呼び出しのまとまり — 1つの会話の中で、90秒未満の間隔で続いた呼び出しです。サーバーには質問の区切りが見えないため、まとまりは質問の近似にすぎません。まとまりあたりの呼び出し数(中央値・90%)と、10回以上のまとまりの割合を合わせて示します。
    • 同じツールをすぐにもう一度呼んだ割合と最長の連続 — ツールがAIに必要なものを返せなかったことを示すサインです。
    • ツールや対象の検索から始まったまとまり、ツール一覧を開いて実際に使った割合。
    • 呼び出しの間隔(中央値・90%) — 呼び出しの合間にAIが考えている時間のおおよそです。
    • 照会時間(中央値・90%) — 実際に実行された読み取り呼び出しだけを数えます。
    • 失敗・拒否・承認待ちの呼び出し、空の結果(推定)、対象を聞き返した呼び出し、サイズ上限に合わせて短くした応答。「対象が見つからない」と答えた呼び出しや、どの対象かを聞き返した呼び出しは、失敗ではなく空の結果・聞き返しとして数え、その時間は照会時間に含めます。

    AI知識~

    AI -> 知識ページ(/ai/library)はAIの回答の根拠を集めておく場所で、タブが 2つあります。知識タブにはAIが引用できる項目がすべて並び、データソース タブにはその知識の入り口 — 文書(PDF/テキスト)、WebのURL、REST API、内部クエリ、 公共データフィード — が並びます。ソース行の2列目は同期状態(同期済み・同期失敗・ 未同期、その都度照会するソースなら「都度照会」)で、最終同期の時刻はその欄に マウスを乗せるか、ソースの設定で見ます。今すぐ同期も設定にあります。

    知識はどこから来るか~

    ライブラリには4種類のものが存在し、AIはそれぞれを異なる形で引用します。

    出どころ 何であるか AIの引用の仕方
    権威(Authoritative) 同期される公共データフィード(例: RDA、Nongsaro) ソース名を添えて事実として述べる
    人が入力したもの あなたが入力した、またはアップロードした文書 信頼できる — あなた自身がソース
    データから導いたもの このシステム自身の測定値から算出したもの 一般則としてではなく、ここでの観察として提示する
    AIが整理したもの AIが調べた、または導き出して保存したもの 人が確認するまで未確認のノートとして明示

    AIは自らライブラリに書き込むこともできます。何かを調べたときは要約を保存し、 次の質問がゼロから始まらないようにします。こうしたノートは常に未確認の状態で 入り、常にそうと明示されます — モデルが書き忘れても、サーバー側がその明示を 付け足します。ライブラリに登録されたソースから写したノートの場合は、引用に そのソース名も添えられます — 依然として未確認ですが、確かめに行く先がある ということです。

    AIが書いたものを確認する~

    AIが書いたノートのうち確認を待っているものがあると、知識タブの一番上に1行の お知らせが出ます。それだけ表示を押すと、一覧が「確認が必要なもの」に絞り 込まれます。項目を押して詳細を開き、ソースリンクがあれば開いて原文を確かめてから、 保存して確認(誤りがあれば直してから)または取り下げを押します。確認する ことがそのノートを「未確認」から引き上げる唯一の方法です。ソースリンクのない ノートにはリンクが出ません — 照らし合わせる原文がないということです。取り下げは やり直せます。取り下げたノートはよけた項目も含めるで一覧に再び現れ、 再有効化を押すと「確認が必要なもの」に戻ります — 取り下げを解くことは、 確認を済ませたことと同じではないからです。

    知識タブの下の知識の設定 → 確認済みの知識のみ引用(既定はオフ)は、AI自身の 未確認ノートをAIが引用しないようにします。権威ある知識と手入力の知識は影響を 受けません。

    閲覧と追加~

    知識タブの一覧は1行に1項目(タイトル・信頼度)で、既定では人とAIが書いたもの だけを載せます。ソースから同期した資料はタイトルがすべてソース名で、混ぜると見分け られないため、出典の絞り込みで別に選ぶか、データソースタブで管理します。タグは項目の 詳細で見ます — 検索し、出どころ・状態・タグで絞り込み、古くなったものは項目の 詳細から取り置きます(取り置いても行は残ります。AIの手が届かなくなるだけで、 状態の絞り込みで取り置いた項目も表示すれば戻せます)。

    知識を追加は、AIのやり取りやソース登録を経ずに、あなたが既に知っていることを 書き込みます。ここに書いた内容は確認済みとして扱われます — あなたが出典です。

    知識ダイジェスト・パイプライン~

    文書やWebのURLのような長い文章のソースは、登録時に一度だけ前処理されます。

    1. ソースをチャンクに分割します。
    2. 各チャンクをダイジェスト化(LLMによる要約 + キーワード抽出)し、ai_knowledge_chunkテーブルにキャッシュします。
    3. クエリ時にはLLM呼び出しは発生しません — 検索は純粋なDB照会と決定的な検索だけなので、回答は速く、コストもかかりません。

    範囲はサイトではなくタグで決まる~

    ここが変わりました — ライブラリは農場全体で共有です

    かつて知識はfacility_idで絞り込まれており、このページの旧版には、あるサイト 向けに登録した文書は別のサイトには決して出てこないと書かれていました。それは もう正しくありません。 ライブラリはフラットな、農場全体で共有するカタログです — どの項目もどの質問に対しても検索対象になり得て、関連性はタグとキーワード スコアリングで決まります。

    ライブラリを機密性の境界として扱わないでください。このAIを使う全員に見せたく ないものは、ライブラリに入れないでください。

    範囲は代わりにタグで決まります — 自由記述のテキスト(「大根」「北棟」 「橋A」など)で、実際に自分が管理している単位を使えます。AoTは農業専用では ないため、決まった語彙はありません。タグこそが、クエリを正しい主題へ絞り込む 手段です。

    地域を選ばない組み込みソース~

    組み込みソースのほとんどは韓国の公共データ(RDA、Nongsaro、NCPMS、 SmartFarmKorea)で、その提供元のAPIキーが必要です。それ以外の地域でも、 2つの組み込みソースはどこでもキーなしでそのまま使えます。

    ソース 何に答えるか
    FAO ECOCROP(EXT-GL-01) 2,500種以上の生育温度、降水量、土壌pH、標高の限界
    Open-Meteo(EXT-GL-02) 世界的な予報、深さ別の地温/土壌水分、基準蒸発散量(ET₀)、過去の気候

    Open-Meteoは予報ツールが動く土台でもあります。get_weatherはこの設置に 配線された天気センサーしか読まず、「今」しか答えません。 get_weather_forecastは指定した場所の座標でOpen-Meteoに問い合わせ、 どこでも最大14日先まで答えます — 最初の1日は1時間刻み、72時間までは3時間刻み、 それより先は日単位です。このソースを有効にしているか、座標の入ったOpen-Meteoの 予報入力があることが必要で、どちらもなければ予報の提供元がないと答え、 設定 > 入力で予報入力を追加するよう案内します。数値は最も近い格子点のモデル値で、 現場の実測ではありません。どの格子点が答えたか、そこまでの距離も レスポンスに含まれます。Open-Meteoに到達できない場合は6時間以内の過去の予報を そのまま使い、何時間前の値かを明示します。土壌の値とET₀は、どんなセンサーを 持っていてもここから供給されます。

    ソースの画面にも書かれている制約が2つあります。Open-Meteoのキーなしの経路は、 規約上は非商用の用途に限られます — 商用で使うなら、Open-Meteoのキーを取得して ソースに入力してください。そうすると商用のエンドポイントへ照会します(キー欄が 任意なのはこのためだけです)。そしてECOCROPの数値は「この種はこの気候で育つか」に 答える適合範囲であり、制御の目標値ではありません。どちらも出典の表示 (CC BY 4.0)が必要で、ソースに既定で入っています。

    それ以外は、ライブラリは逆方向に埋まっていきます — あなた自身の文書、 Webページ、REST API、そしてAIが作業中に調べて棚に上げたもの。

    データの出典表示~

    2つのグローバル組み込みソースはどちらもCC BY 4.0のデータです。このライセンス は、データを表示する場所に出典表示を添えることを求めているため、AoTは2か所で それを行います。

    • AI知識ページ — データソースタブの一覧の下に「データ出典」の行があり、 有効化しているソースを網羅します。
    • AIの回答 — クエリの応答には出典表示のテキストが含まれますが、画面に 既に表示されているという印が付いているため、AIは回答の中でそれを繰り返したり 引用したり読み上げたりしません。
    ソース ライセンス 出典表示
    Open-Meteo CC BY 4.0(無料枠は非商用限定) Weather data by Open-Meteo.com
    FAO ECOCROP CC BY 4.0 FAO ECOCROP

    商用利用について

    Open-Meteoの無料エンドポイントは、その利用規約により非商用利用に限定 されています(サブスクリプションや広告のあるサービス、商用製品への組み込みは 商用とみなされます)。商用の生産者・サービスは Open-Meteo APIキーを取得し、ソース設定に 入力してください — キーがあれば、AoTは商用のエンドポイントへ照会します。

    出典表示のテキストは、ソース設定(歯車アイコン)の出典表示欄で上書きできます。 空欄のままなら、組み込みの既定文が使われます。

    AIカード~

    AIカードは、接続したAI(自分のAIアプリなどのMCPクライアント)が、人が見ているAoTの画面に出す短いメッセージです。チャット画面とは別に、AoTの画面の上にそのまま表示されます。AIが調べ物を終え、結果を残しておく価値があるときに使う経路で、機器を動かしたり設定を変えたりすることはありません。カードは作成したアカウントのもので、同じアカウントでつながった画面にだけ表示されます。

    カードが表示される場所~

    • 字幕 — 新しいカードが届くと画面の下側に字幕として表示されます。同時に表示されるのは1枚で、新しいカードが来ると入れ替わります。閉じる(×)を押す、次のカードが届く、60秒たつと消えますが、未読のカードは受信箱に残ります。マウスを乗せている間、キーボードのフォーカスがある間、押している間は消えず、その間に届いたカードは最新の1枚だけが待機して後で表示されます。長いカードはもっと見る/たたむで開閉します。タブが隠れている間や、ビューアー・受信箱が開いている間は字幕を出さず、受信箱にだけたまります。
    • AI窓口 — 字幕のすぐ下の中央にある小さな面で、AIの接続状態、未読数、画面追従の設定(自動・確認・オフ)、オフにする操作を表示します。押すと受信箱が同じ場所から上に開きます。スマートフォンではアイコンと数だけが表示され、追従とオフは受信箱の上部の行に移ります。
    • 受信箱 — 受け取ったカードの一覧です(下の「受信箱」を参照)。

    AIが時間のかかる照会をしている間は、「照会中」のような一時的な字幕が短く出ることがあります。この字幕は受信箱には残りません。

    AIがカードに載せるもの~

    MCPのscreenツールのcardオペレーションがカードを作ります。カードはタイトル(80文字まで)、本文(2000文字まで、Markdown)、添付でできています。タイトルを省くと本文の最初の行がタイトルになります。

    • 天気や場所の要約の答えはサーバー自身がカードとして投稿するため、AIが重ねて投稿することはありません。それ以外の主要な結果(おすすめ・比較・計画・レポート・画像・リンク集)は、接続したAIが結論1行、最大5行、リンクは[文字](アドレス)、画像やファイルは添付として1回だけ出すよう案内されます。通常の会話の返答や途中経過はカードにしません。
    • 同じタイトル・同じ本文が2分以内にもう一度来ても、新しいカードは積まれません(添付がある場合を除く)。
    • 本文は見出し・リスト・チェックボックス・引用・水平線・表などのMarkdown書式で描かれます。表は字幕では1行の要約、開いたときや受信箱・ビューアーでは全体が表示されます。
    • 1人あたり1分に6枚、24時間に100枚までカードを受け取れます。
    • 設定 > 一般のAI結果カードをオン(初期値はオン)にしておくと、接続したAIが上記のルールを指示として受け取ります。サーバーの指示に従わないAI向けに、同じルールの文章をコピーできる欄もあります。オフにすると、その案内を送らなくなります。
    • 設定 > 一般のAIメッセージを隠すをオンにすると、字幕は表示されず、カードは受信箱にだけたまります。

    添付: 画像・ファイル・動画リンク~

    カード1枚には、添付を最大8個(ファイル・動画リンク・値タイルの合計)まで付けられます。1枚のカードのファイル合計は20 MiB、ファイル1つは5 MiBまでです。AIはファイルの中身を直接送るか、公開のhttpsアドレスを渡します。アドレスで渡した場合は、AoTサーバーがファイルを取得して保存します。

    種類 形式 表示のされ方
    画像 png, jpg, jpeg, gif, webp サムネイルのタイル。押すとビューアーで拡大
    ファイル pdf, csv, txt, md, json 名前と、形式・サイズの1行。テキスト系はビューアーでプレビュー、.mdは書式表示とソース表示を切り替え
    結果画面 html スクリプトも外部接続もない隔離されたフレームの中だけで表示。パスワードなどを入力しないよう案内が付く
    値タイル viz (ゲージ/ミニグラフ) カードの中に直接描かれます。タイルでもファイルでもありません — ゲージは1つの値を範囲の中で、ミニグラフは短い推移を表示します
    動画・Webリンク YouTube, Vimeo, mp4/webmの直接アドレス, 一般のWebページ 代表画像のタイルとタイトルのリンク
    • 本文に書いたMarkdown画像(![](https://…))や一般のリンクも、サーバーが取得してサムネイルのタイルにします(1枚のカードにつき本文の画像は最大4枚、Webページのリンクは最大3個、動画タイルは最大4個)。タイルになったアドレスは、字幕・ビューアー・受信箱の本文では隠されます。サーバーが取得できなかった場合は、タイルにならずリンクのまま残ります。
    • サーバーが取得するのは公開のhttpsアドレスだけです(プライベートネットワークや内部のアドレスは拒否)。ユーザーあたり1時間に30回、1日に100回までです。
    • 動画 — ビューアーでは16:9の枠(YouTubeショートのリンクは9:16の枠)とタイトルのリンクで表示されます。YouTubeはここで再生を押した後にだけビューアー内のプレーヤー(youtube-nocookie.com)が作られ、押す前に外部へのリクエストはありません。再生するとYouTubeがこの端末のIPアドレスを見られる旨の案内も出ます。mp4/webmの直接アドレスも、ビューアーで再生できる場合は同様にここで再生が表示されます。それ以外の動画(Vimeoなど)とWebページは、元のサイトで再生・元のページを開くで新しいタブに開きます。サーバーが自分で取得するのは代表画像(ポスター)だけです。
    • 添付が2つ以上あるとタイルの列が横にスクロールし、あふれた分は+Nで表示されます。ビューアーでは、◀ ▶ ボタン、左右の矢印キー、タッチのスワイプで前後の添付に移動でき、番号が表示されます。
    • 値タイル — 照会した値を文字の代わりに画像で見せたいときは、何か.viz という名前のファイルに小さなJSONスペックを入れて添付します。ゲージは{"viz":"gauge","label":…,"value":…,"valueText":…,"unit":…,"min":…,"max":…,"okMin":…,"okMax":…}(ok範囲は省略可)の形で、ミニグラフは{"viz":"spark","label":…,"valueText":…,"unit":…,"span":…,"points":[古い値…新しい値]}の形で、点は48個までです。valueTextを使うと、元の数字の代わりに短い文字(書式を整えたり四捨五入した値)を表示します。ミニグラフは線の下に点の観測された最小–最大の範囲も表示し、任意のspanはその横に付く短い期間ラベルです(例: "直近6時間")。ゲージは弧の下端にminとmaxを表示します — そのため、範囲を別の文で書かなくても絵から読み取れます。有限の数値と短い文字だけを受け付け、各タイルはカードと受信箱の中に直接描かれます — 上のタイルの列とは別で、ビューアーの添付一覧にも入りません。変化する数値を、数字の並びではなく一目で読めるようにするものです。値タイルもカード1枚の添付8個の上限には数えられますが、1日のファイル上限には数えられません。
    • 値を照会するとサーバーが値タイルを描きます。 外部接続が機器の現在値(measureのop: "latest")や短い履歴(measureのop: "history")を読むと、サーバーがその結果からゲージ/ミニグラフのタイルを作り、天気や場所の要約カードと同じようにカードを自分で投稿します。そのため接続したAIはそうした答えに.vizを付けず、チャットでカードを繰り返すこともなく、言葉だけで返答します。応答のcard項目に、投稿した旨(またはスキップした理由 — 画面オフ、自動カードオフ、基準範囲が不明な測定値、表示するものなし)が入ります。.vizは、そうした照会から出ていない数値にだけ自分で付けてください。値や推移を見せるためにHTMLやSVGのゲージ/グラフを自作しないでください — measure(現在値はlatest、短い推移はhistory)で読み、タイルはサーバーに描かせます。自作のグラフカードは遅く、見た目もばらつき、サーバーがすでに投稿するカードと重複します。
    • 1ユーザーにつき、1日にファイル20個、保存中のファイル合計100 MiBの上限があります。

    受信箱~

    AI窓口を押すと開きます(AIメニューの受信箱の項目からも入れます)。新しいカードには新着の印が付き、読んだカードは既読になります。すべて既読でまとめて処理もできます。古いカードは以前の分をもっと見るで続けて読み込みます。

    • 検索 — タイトルと本文からAIメッセージを探します。
    • 固定 — 固定したカードは自動整理の対象から外れます。固定できるのは1人あたり30枚までで、固定のみ表示で一覧を絞れます。固定を外しても最低7日は残ります。
    • カードを閉じる — 閉じたカードは受信箱から消えます。
    • ノートに保存 — カードの内容をAoTのノートとして保存します(ノートを作成する権限が必要です)。
    • お知らせとして投稿 — HTMLの結果画面カードを、ビューアーで確認の手順を経てお知らせとして投稿します。農場のすべてのユーザーに見え、添付も一緒に投稿するか選べます。お知らせを書く権限が必要です。人が自分で押したときだけ実行され、AIが代わりに投稿することはできません。

    カードは作成から30日間保管され(固定したカードを除く)、ユーザーあたり最新300枚を超えると古いものから整理されます。外部のAIが同じカードを読む方法は、下の「MCPサーバーの実行」にある読み取り専用リソースを参照してください。

    色~

    字幕・受信箱・ビューアーの面と文字の色は、カスタムUIのAIカードの面・AIカードの文字で変更します。面は画面が透けるよう不透明度0.8で描かれ、文字は常に不透明なので、2つの色は十分に違う色にしてください。

    MCPサーバーの実行~

    外部MCPクライアント向けの標準MCPサーバーです。アプリの起動時に自動でウォームスタートされ、手動で実行することもできます。

    # stdioモード(既定) — 同じマシン上のローカルクライアント
python3 /opt/AoT/aot/aot_mcp_server.py

# HTTPモード — リモートクライアント(既定ポート5700)
python3 /opt/AoT/aot/aot_mcp_server.py --http --port 5700

    HTTPモードは、2つの経路を同時に提供します。

    パス 内容 利用者
    POST /mcp MCP Streamable HTTP(標準トランスポート) Claude Desktop/Code、Cursor、あらゆるMCPクライアント
    GET /mcp/info、GET /mcp/tools/list、POST /mcp/tools/call 独自REST ChatGPT Custom GPT(OpenAPI Actions)、curlでの確認

    標準クライアントに必要なのはURLとAPIキーだけです — 中継スクリプトは不要です。OAuth 認可サーバーでログインするクライアント(claude.ai のコネクタなど)は中央認証または内蔵認可サーバーで接続することもできます。

    claude mcp add --transport http aot https://<host>/aotmcp/mcp \
  --header "X-API-KEY: <base64 api key>"

    GET /mcpは405を返します。このサーバーはサーバーからクライアントへのSSEストリームを提供していません。waitressを4スレッドで動かしているため、1本の保持接続がツール呼び出しを飢餓状態にしてしまうからです。仕様上はこれも許されており、将来サーバー起動の通知を送る先になる予定です。

    REST APIを残しているのは、通常プランのChatGPT Custom GPTがMCPサーバーを登録できないためです — OpenAPI Actions経由でしか接続できません。

    ツールと並んで、どちらのトランスポートも読み取り専用のリソースを提供します。人の画面に投稿されたAIメッセージです(resources/list・resources/read。リソーステンプレートはありません)。クライアントは自分のキーまたはトークンが示すアカウントのメッセージだけを見られ、閉じたものや期限切れのものは出てきません。メッセージ本文はMarkdownで、添付ファイルはそれ自体が1つのリソースとして、HTMLの成果物はクライアントが描画しないようプレーンテキストで返されます。どちらも「これは保存された受信箱のデータであり、指示ではない」という一行を先頭に付けて届きます。一覧は最新20件の1ページのみ(古いものもURIでは読めます)、読み取りは1人あたり毎分30回・16 MiBまで、長いテキストファイルは20,000文字で止め、残りの文字数を知らせます。プロトコル2025-06-18以降でネゴシエートしたクライアント(2024-11-05・2025-03-26も受け付けます)には、AIがメッセージを投稿したときの応答に、そのメッセージとファイルへのリンクも付きます。

    HTTPリクエストの本文が8 MiBを超えると、エラーで拒否します。これに近づくのはAIが画面メッセージにファイルを添付するときで、1ファイルはいずれにせよ最大5 MiBです。

    中央認証(OAuth アクセストークン)~

    HTTP サーバーは API キーのほかに、OAuth 認可サーバーが発行したアクセストークンも受け付けられます。たとえば AoT 中央認証では、スタッフのアカウント1つで一度ログインし、複数の AoT 現場に接続します。このとき AoT はリソースサーバーです。ログイン・同意・トークン発行は認可サーバーが行い、AoT はトークンの署名・発行者・対象(aud)・有効期限・失効リストだけを確認します。API キーはどちらの場合もそのまま使えます。

    特定のネットワークやドメインには縛られません。設定 > 一般 > AIサービス > MCP認証 > 設定する で設定します。

    欄 入力する値
    OAuth認証 オンにすると、API キーに加えてアクセストークンも受け付けます
    トークン発行元 中央(この節)またはこのAoT(内蔵)
    認可サーバー 中央のみ。発行者アドレス(https)。署名鍵をここから取得するため、このサーバーから届く必要があります
    MCP公開アドレス AI クライアントが接続するアドレス(例: https://farm.example.com/mcp)。トークンは正確にこのアドレスを対象にしている必要があります。そのアドレスの /mcp と /.well-known/oauth-protected-resource を MCP サーバー(ポート5700)へ転送してください
    Web公開アドレス AoT を開くアドレス。アカウント連携の後にここへ戻ります(Google 連携と共通の値)
    クライアントID・シークレット このサイトを認可サーバーに登録するときに発行されます。アカウント連携にだけ使います

    画面には認可サーバーに登録する値(リソース = MCP公開アドレス、リダイレクトURI、スコープ)が表示され、チェックする で保存前に認可サーバーと署名鍵に届くか確認できます。同じ配備テンプレートを複数台で使うときは、環境変数 AOT_MCP_CENTRAL・AOT_MCP_AUTH_MODE・AOT_MCP_CENTRAL_ISSUER・AOT_MCP_PUBLIC_URL・AOT_MCP_LINK_CLIENT_ID・AOT_MCP_LINK_CLIENT_SECRET が画面の値より優先されます。

    トークンの持ち主は認可サーバーのアカウントで、AoT のユーザーではないため、一人ずつ一度だけ連携します。AoT に本人としてログインし、同じ画面で自分のアカウントを連携を押してください。アカウントのロールが AI 接続を使えない場合は連携が拒否されるので、管理者に相談してください。連携するまでは AI は接続できますが、ツールを呼ぶと連携方法の案内だけが返ります。メールアドレスが同じでも自動では連携しません。連携すると、同じ画面がどのアカウントと連携しているかを示し、自分のアカウントの連携を解除を用意します。解除すると、そのアカウントでサインインした AI 接続はここで何もできなくなります。

    トークンでできることは、トークンのスコープを連携したユーザーのロールで絞った範囲です。aot.read(必須)は読み取り、aot.control は機器の操作、aot.config は設定の変更と全設定モジュール(設定ツールセット)です。連携アカウントでツールセットを選んである場合は — 設定 > 一般 > AIツール一覧 の「サインイン接続のAIアプリ」の行、または AI に頼んで — トークンのスコープが許す範囲でそちらが優先されます。状態を変える呼び出しは API キーと同じく承認を経ます。

    内蔵認可サーバー(このAoTがトークンを直接発行)~

    中央認証には別の認可サーバーとそこのスタッフアカウントが必要です。お客様が自分のAoTをclaude.aiのコネクターにそのまま接続したい場合は、このAoT自身が認可サーバーになれます。同じダイアログのトークン発行元でこのAoT(内蔵)を選んでください。利用者は普段のAoTログイン(TOTP含む)でサインインし、このAoTの名前が表示された同意画面で接続を許可します。トークンの持ち主がそのままAoTユーザーなので、アカウント連携の手順はありません。中央と内蔵は同時に1つだけ有効にでき、切り替えるともう一方の方式のトークンは使えなくなります。

    有効にする前に

    • コネクターはAI企業のクラウドから接続するため、AoTにはインターネットから到達できる公開httpsアドレスが必要です。その結果、AoTのログイン画面と/mcpが誰にでも見えます。強いパスワードを使い、機器を制御できるすべてのアカウントで二段階認証(TOTP)を有効にしてください。
    • プライベートネットワークやVPN内ではAIサービスがAoTに到達できません。その場合はどこでも使えるAPIキーを使ってください。
    • WebとMCPは同じオリジンである必要があります。そのアドレスを次のように振り分けてください。
    パス 送り先
    /mcp、/.well-known/oauth-protected-resource MCPサーバー(ポート5700)
    それ以外すべて — /authorize・/token・/register・/revoke・/.well-known/oauth-authorization-server・/.well-known/jwks.json を含む Webサーバー(ポート8084)

    Dockerでインストールした場合は分ける必要はありません。Webコンテナがこの2つのパスをMCPコンテナへ直接渡すので、アドレス全体をポート8084へ送ってください。直接インストールのnginxも同じことをします。

    設定: このAoT(内蔵)を選び、MCP公開アドレス(例: https://farm.example.com/mcp、発行者はこのアドレスからパスを除いたもの)を入力してOAuth認証をオンにし、保存して確認を押します。claude.aiではそのMCPアドレスでカスタムコネクターを追加するだけです。ほかに入力する値はありません。初めて保存するときにAoTが署名鍵を作成します。

    動作

    • ダイアログに表示されたリダイレクト先だけが登録できます。claude.ai・claude.comのコネクターと、Claude Codeのように利用者自身のコンピューターで動くツール用のhttp://localhost・http://127.0.0.1です。管理者は環境変数AOT_MCP_REDIRECT_ALLOWLIST(カンマ区切り)で一覧を置き換えられます。
    • 同意画面には、このAoTの名前(カスタムUI設定のブランドテキスト、なければアドレス)が最も大きく表示され、誰がログインしているかと3つのスコープが表示されます。利用者の役割で使えないスコープはオフになっています。アプリ名はそのアプリが自称したもので、検証されていません。ログインしたアカウントの役割がAI接続を使えない場合は、同意画面は表示されず、管理者に相談するよう案内するメッセージだけが表示され、トークンは発行されません。
    • アクセストークンは1時間、リフレッシュトークンは30日で、使うたびに新しいものに置き換わります。使用済みのリフレッシュトークンや認可コードが再び届くと、その接続全体を切断します。
    • 利用者がパスワードを変更したとき、無効化・削除されたとき、ダイアログの自分が接続したAIアプリで切断を押したとき、またはアプリ側が取り消したときに接続は閉じられます。
    • ログイン試行はWebログインと同じロックアウト規則に従い、/registerはアドレスあたり1時間30回、これらのパス全体は1時間600回に制限されます。
    • 署名鍵は、インストールごとにAoTデータフォルダー(databases/)にあるファイル(mcp_oauth_es256.pem、権限600)です。DB・ログ・バックアップには入りません。鍵なしでフォルダーだけが復元された場合は新しい鍵が作られ、すべてのAIアプリで再度許可が必要になります。

    トークンでできることは中央認証と同じで、トークンのスコープを利用者の役割で絞った範囲です。環境変数AOT_MCP_AUTH_MODE(centralまたはembedded)が画面の値より優先されます。

    ChatGPT Custom GPTを接続する~

    上記の3つのRESTパス(/mcp/info、/mcp/tools/list、/mcp/tools/call)を OpenAPI Actionとして登録します。ActionsつきのCustom GPTを作成するには 有料のChatGPTプラン(Plus/Team/Enterprise/Pro)が必要です — 無料アカウントは この経路をまったく使えません。

    1. APIキーを発行する — 管理 > システム管理 > ユーザー一覧で、自分のアカウント用に新しいAPI キーを生成します(「ChatGPT」のような名前にしておくと、あとでこの接続だけを 取り消せます)。このGPTが読み取り専用でよいなら、発行時にスコープ readonlyを選んでください — 書き込み系ツール呼び出し(ノート・知識を含む)はサーバー側で拒否 されるため、Custom GPTの設定ミスでデバイスに誤って触れることがなくなります。 複数人が使うなら、1人に1つずつキーを発行してください — 監査ログで誰が何を 呼び出したかがわかり、漏えいしたキーも他の全員を止めずに失効できます。 このGPTが設定作業をしないなら、AIツールは運用だけにし、するなら必要な モジュールだけをチェックしてください(ツールセット)。
    2. HTTPモードが有効で到達可能なことを確認する — サーバーは --http --port 5700で稼働している必要があり、ChatGPTがそのポート(または リバースプロキシが公開しているパス)に到達できる必要があります。まず認証なしで 確認してください(バージョンとツール数だけを返し、キーは不要です)。 
      curl https://<host>:5700/mcp/info
    3. GPTを作成する: ChatGPTでExplore GPTs → Create → Configureに進みます。 名前と説明を入力し、Instructionsには少なくとも以下を貼り付けてください — そのまま使うか、自分のサイトに合わせて調整します。
    You are an assistant for this AoT system: you observe status, advise, and
can register device-control requests when asked.

- Don't call listTools out of habit. The full tool catalog is a large
  response that eats into the conversation budget. Call it once early to
  learn tool names and arguments, then call only the tools you need.
- Prefer narrow tools. For a single device or zone, use a tool that
  targets just that instead of a broad summary tool.
- When calling callTool, always JSON-encode `arguments` into a string.
  E.g. not {"zone_name": "North Field"} but
  "{\"zone_name\": \"North Field\"}". Empty is "{}".
- Every tool response carries call_state. Judge success/failure from that
  field alone — each tool's own `status` field uses different words:
    executed / already_executed → done, relay the result
    pending_approval            → not yet run, tell the user to approve it
    approval_rejected           → rejected, don't retry — offer advice instead
    approval_expired            → approval window expired, ask again
    refused / failed            → refused or errored, relay the reason
- If a state-changing request comes back pending_approval, don't retry it
  yourself — tell the user to approve it on the web approval screen.
- Answer in plain language, without jargon.
    1. Actionを追加する: 同じ画面の下のほう、Actions → Create new action で、以下のスキーマを貼り付けます(<host>を実際のアドレスに置き換えて ください)。
    openapi: 3.1.0
info:
  title: AoT MCP
  version: "1.0.0"
servers:
  - url: https://<host>:5700
paths:
  /mcp/tools/list:
    get:
      operationId: listTools
      summary: List available tools and each tool's argument schema.
      responses:
        "200": { description: OK }
  /mcp/tools/call:
    post:
      operationId: callTool
      summary: Call one tool by name with arguments.
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [name]
              properties:
                name:
                  type: string
                  description: A tool name returned by listTools
                arguments:
                  type: string
                  description: >-
                    Tool arguments serialized as a JSON object string.
                    E.g. "{\"zone_name\": \"North Field\"}". Empty is "{}".
      responses:
        "200": { description: OK }
    1. 認証を設定する: Authentication → API Key → Auth Type Custom → Header name X-API-KEY → 値は手順1のAPIキー(base64)です。
    2. ⚠️ argumentsは文字列として宣言してください — オブジェクトにしては いけません。 ツールは100種類を超えるため、その引数の形をすべて1つの OpenAPIスキーマに宣言することはできません。argumentsを自由形式の オブジェクトのままにしておくと、ChatGPT Actionsは埋められないフィールドを 黙って落としてしまいます(実際に起きた事例、2026-08-09: list_devices_in_area 呼び出しにはarea_nameが必須でしたが、リクエスト本文にはargumentsキー自体が まったく入っていませんでした)。上記のように文字列として宣言しておけば、 これはすでに回避できます — 手順3のInstructionsも同じ理由から同じルールを 念押ししています。
    3. 保存して確認する: 共有するつもりがない限り、可視性はOnly meの ままにしておきます。チャットで「状況を教えて」のように尋ねてみて、 ツール呼び出しと応答が返ってくれば接続成功です。
    4. この経路でも、状態を変更するツールは即座には実行されません。 最初の 呼び出しはconfirmation_id付きのpending_approvalとして返り、ChatGPTは それをユーザーに提示し、ユーザーがWeb承認画面で承認します。その承認は たいていその場で要求を実行しますが、承認の応答がまだ実行されていないと 示す場合に限り、同じ呼び出しに_confirmation_idを加えて再試行し、実際に 実行します。Custom GPT の中で自動的に再承認される仕組みはありません。承認は AI → リクエスト(/ai)画面の一番上「承認待ちの制御リクエスト」で行います。 AIが出したスケジュールの提案とアドバイスも同じ画面で決定します。

    Claude Desktopを接続する~

    claude_desktop_config.jsonに追加します。

    {
  "mcpServers": {
    "aot": {
      "command": "python3",
      "args": ["/opt/AoT/aot/aot_mcp_server.py"],
      "env": { "AOT_MCP_API_KEY": "<base64 api key>" }
    }
  }
}

    stdioでも既定でAPIキーが必要です。管理 > システム管理 > ユーザー一覧で発行したキーをenvのAOT_MCP_API_KEYに入れてください — ないと接続直後に認証エラーで拒否されます(認証を無効にするにはAOT_MCP_REQUIRE_AUTH=0)。

    ここでも、状態を変更するツール呼び出しは即座には実行されません(aot/tools/mcp_safety_gate.py)。最初の呼び出しはconfirmation_id付きのpending_approvalとして返り、ユーザーは同じ会話の中、またはAI → リクエスト画面(/ai)上で明示的に承認または却下する必要があり、これはrespond_to_confirmationを通じて処理されます(/api/v1/mcp/review_pageは今も存在しますが、/aiへのリダイレクトになっただけです — ブックマーク互換のためです。監査ログ自体はAI → 記録(/ai/manage)の「ツール呼び出し」タブに移り、「会話」「エラー報告」「呼び出し品質」タブと並んでいます)。respond_to_confirmationで承認すると、その同じ呼び出しの中で要求を実行します — その結果を報告し、ツールを再び呼び出す必要はありません。その応答がまだ実行されていないと示す場合に限り、同じ引数に_confirmation_idを加えて再試行してください。呼び出し元のAIには、この承認を自分で決めたり偽装したりする手段がありません。AOT_MCP_WRITE_ENABLED=0を設定すると、書き込み系ツールを(ノート・知識も含めて)一律拒否します(アドバイス専用モード。submit_adviceは引き続き使えます)。締め切りは2段階あります — 既定で人が承認するまで15分(AOT_MCP_CONFIRM_TTL_SEC)、承認された瞬間からあらためて5分で実行(AOT_MCP_APPROVED_TTL_SEC)です。制御ツールを引き続き公開しているため、このサーバーは信頼できるクライアントにのみ接続してください。
