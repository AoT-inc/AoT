    セキュリティ~

    このページではログイン保護、APIキー、監査ログについて説明します。Web接続自体の 暗号化については、一般設定のHTTPS強制 を参照してください。

    パスワード要件~

    パスワードは8文字以上で、文字・数字・記号のみを使用できます。よく使われる パスワード(password、qwerty123 など、クレデンシャルスタッフィング攻撃で 使われるリストに含まれる値)は、長さの条件を満たしていても拒否されます。

    AoTは定期的なパスワード変更を強制しません。定期的な強制変更はもはや推奨される 方式ではありません — 実際に別のパスワードを使わせるというより、"Password1"、 "Password2" のような予測可能な小さな変化につながりがちで、ここでは要求しません。

    アカウントロック~

    1つのアカウントでログイン失敗が5回累積すると、どの端末・ブラウザから試行したか にかかわらず、そのアカウントが10分間ロックされます。カウンターはログインに 成功するとリセットされます。このルールはパスワードログイン、キーパッドログイン、 下記の2要素認証コードすべてに同じように適用されます — 誤った認証コードも誤った パスワードと同じ扱いでカウントされます。

    これらの値は固定値で、現在は設定画面に表示されていません。

    2要素認証(TOTP)~

    AoTはGoogle Authenticator、Authy、1Passwordなどのアプリが生成する標準的な 6桁・30秒のコード(RFC 6238 TOTP — これらのアプリが他のサービスですでに実装 しているものと同じ標準)を使った2段階目のログイン認証をサポートしています。

    特定のユーザーで有効になっている場合、ログイン時にはまずパスワードを入力し、 続いて認証アプリの現在のコードを入力する必要があります — どちらか一方だけでは ログインできません。

    まだセルフサービスの設定画面はありません

    現在AoTには、ユーザー自身がこの機能を有効にできる画面がありません — 計画はされていますが、まだ実装されていません。それまでは管理者が直接 設定する必要があります(aot.utils.totp.generate_secret() でシークレット を生成し、該当アカウントの totp_secret / totp_enabled = True を 設定)。一度有効にすると、追加設定なしで上記のログイン動作がすぐに 適用されます。

    APIキー~

    APIキーは、ブラウザセッションなしでHTTP APIへのリクエストを認証します。 管理 → システム管理 → ユーザー一覧でユーザーを編集し、APIキーを生成を 押すと発行されます。

    キーは生成されるその瞬間に一度だけ表示されます。 AoTはキー自体を保存せず、 一方向ハッシュのみを保存するため、設定画面で発行済みのキーを再度表示することは できません。生成直後にすぐ安全な場所にコピーしてください。紛失した場合は新しく 発行してください — 以前の値を復元する方法はなく、新しく発行すると同時に以前の キーは無効になります。

    キーは3つの方法で提示できます: X-API-KEY ヘッダー、HTTP Basic認証、または (廃止予定 — API.md参照)api_key クエリパラメータ。 キーを再発行すると以前のキーは即座に無効になるため、再発行前に古いキーを使う スクリプトや連携を先に更新してください。

    監査ログ~

    管理 → 監査ログ(システムログと同じ「ログを表示」権限が必要)には、 セキュリティに関わる操作が記録されます。

    • ログイン成功・失敗・アカウントロック
    • ログアウト
    • ユーザーの作成・変更・削除
    • 一般設定の変更
    • 出力/デバイスの手動制御
    • APIキーの発行
    • リモート管理トークンの発行

    操作・ユーザー・結果でフィルタリングでき、表示する行数も指定できます。 CSVエクスポートは現在のフィルタが適用された結果をダウンロードします。

    1年を超えた記録は自動的に削除されます。この期間は現在、設定画面から変更 できません。

    パスワード、パスワードハッシュ、APIキー自体は監査ログに一切記録されません — どの操作が行われたか、誰が行ったかのみが記録されます。

    リモート管理(Remote Admin)~

    リモート管理は、あるAoTインスタンスが他のAoTインスタンスのデータを表示できる ようにする機能です。/remote/setup に直接アクセスする必要があり、現在メイン メニューにはリンクされていません。

    リモートホストを追加する際、そのホストのユーザー名・パスワードの入力を求め られますが、これは最初の1回限りの認証用です。実際に保存されるのは、その目的 のためにリモートホストが発行した専用アクセストークンであり、アカウントの パスワードやそのハッシュではありません。保存されたトークンが漏洩しても、 影響を受けるのはそのホスト1台に対するリモート管理アクセスのみで、アカウント の実際のログイン資格情報には影響しません。

    この最初の1回限りのパスワードは、リモートの証明書で検証される接続でのみ送信 されます。資格情報を一切送らない状態で証明書を先に取得して固定し、 パスワードはその固定された証明書で検証される接続でのみ送出されます。以前の バージョンは順序が逆でした — パスワードが検証されない接続で先に送られ、 証明書は応答本文から受け取って固定していたため、中間者がパスワードをそのまま 読み取り、自分の証明書を固定させて以降のすべての接続を傍受できました。

    最初の接続の信頼は依然として利用者に委ねられます — 初めて見る証明書には 照合する基準がありません。そのため、ホストを追加する際に固定された証明書の SHA-256 指紋を表示します。接続を信頼する前に、別の経路で(リモート機器上で 直接)指紋を照合してください。

    その後、証明書が固定されたものと一致しなくなった場合、登録は中断され何も 送信されません。リモートが実際に証明書を更新した場合は、そのリモートホストを 削除してから再度追加してください — 削除時に古い固定も解除されます。

    アップグレード後は既存のリモートホストの再登録が必要です

    このトークン方式が導入される前のバージョンからアップグレードすると、 以前に追加したリモートホストが接続できなくなります。/remote/setup で 各ホストを削除して再度追加すると、新しいトークンで接続が再確立されます。
