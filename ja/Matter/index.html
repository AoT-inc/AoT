    Matter~

    実験的機能

    Matterのサポートは実験的機能です。仮想デバイスでは検証済みですが、さまざまな実機やスマートホームのエコシステムではまだ十分に検証されていません。接続が切れると被害が出る用途には、お手持ちのデバイスで十分にテストするまで使わないでください。

    AoTは、特定のメーカーやアプリのエコシステムに依存しないMatterコントローラーとして動作できます。Apple Home、Google Home、SmartThings、Alexaなど、ほかのMatterアプリにすでに設定済みのデバイスを、MatterのMulti-AdminでAoTと共有できます。ほかのアプリが短時間の共有ウィンドウを開き、そのコードをAoTに入力すると、AoTがデバイスを自分のMatterネットワーク(ファブリック)に参加させます。デバイスは2つのエコシステムに同時に属し、元のアプリでも引き続き動作します。

    AoTはこのデバイスを、入力と出力を持つ通常のAoTデバイスに変換します。そのため、グラフ、トリガー、PID制御、シーケンス、環境コーディネーター、AIアシスタントなど、AoTのほかの機能がそのまま使えます。

    読み取りと制御は、AoTとデバイスの間でローカルネットワークを通じて直接行われます。ほかのエコシステムのクラウドは経由しないため、そちらのAPI料金やリクエスト制限は適用されません。

    管理はすべて1つのページで行います: 管理 → システム管理 → Matter。

    画面の項目名のうち日本語に訳されていないものは、英語のまま表示されます。本書では画面上の表示を太字で示し、必要に応じて日本語の説明を添えます。

    AoTが行わないこと~

    • AoTは、デバイスがどのアプリから来たかを知りませんし、気にもしません。確認するのは「AoTのファブリックに追加できるデバイスか」だけです。
    • 同じデバイスを二重に取り込みません。すでにほかの経路(たとえばクラウド連携)でAoTに入っているデバイスをMatterでも追加すると、測定値が二重に保存されます。どちらか一方だけを使ってください。
    • AoTのAIアシスタントは、Matterデバイスの追加や削除を行えません。ペアリングコードは人だけが扱います。デバイスが作成された後は、その出力はほかの出力と同じように、アシスタントとその承認ステップを含めて制御されます。
    • AoTが扱うのは、IPで到達できるデバイスです。Wi-Fi、Ethernet、またはネットワーク上にすでにあるボーダールーター経由のThreadデバイスです。AoT自体はThreadボーダールーターではありません。

    要件と有効化~

    Matterは、ほかのAoT機能よりもネットワークに多くを求めます。失敗の大半はAoTではなくホストのネットワークが原因です。何よりも先に次を確認してください。

    • Linuxホスト。Docker構成、またはネイティブインストールでMatterサーバーだけをDockerで動かします(ネイティブインストール)。macOSやWindowsのDocker Desktopでは、Matterに必要なマルチキャスト通信を提供できません。Raspberry Pi 1台で足ります: Raspberry Piへのインストール。
    • ホストがMatterデバイスと同じネットワーク(同じVLAN)にあること。
    • Matterサーバーはマシンのホストネットワークで動作します。IPv6が有効で、IPv6ルーター広告を受け入れ、mDNSが動作している必要があります。マルチキャストを「最適化」する一部のメッシュWi-Fiやルーターはこれを壊します。
    • Bluetoothで新しいデバイスを追加するには、ホストにBluetoothアダプターとBlueZも必要です。これは任意です(下記参照)。

    1. ホストを点検する~

    点検スクリプトは、コンテナ内ではなくホストで実行してください。設定を読み取るだけで何も変更せず、見つかった問題ごとに修正コマンドを表示します。

    aot/scripts/check_matter_host.sh
    オプション 意味
    --iface <名前> このネットワークインターフェースを点検します。省略するとデフォルトルートのインターフェースを使います
    --ble 新規デバイス追加用のBluetoothも点検します: BlueZ、アダプターの有無、rfkillによるブロック、電源、D-Busソケット
    --json 結果をJSONで出力します

    各行はOK、WARN、FAILのいずれかで始まります。FAILがなければ終了コードは0です。まずすべてのFAILを直し、続いて該当する警告を直してください。

    2. Matterサーバーを起動する~

    MatterサーバーはDocker構成に含まれていますが、デフォルトではオフです。docker/.envに次を追加します。

    COMPOSE_PROFILES=matter

    その後、いつもどおりスタックを起動します。

    docker compose -f docker/docker-compose.prod.yml up -d

    コンテナが2つ追加で起動します。matter_server(Matterスタック)とmatter_socket(AoTがこのサーバーと通信するためのローカルソケットを用意する小さな中継)です。データボリュームmatter_dataにファブリックが保存されます。

    docker/.envのその他の設定:

    設定 意味
    MATTER_SERVER_TAG Matterサーバーイメージのバージョン。自動アップデーターはこのサービスを更新しません。新しいバージョンを使うにはタグを自分で上げてください
    MATTER_TEST_DCL デフォルトはfalse。開発・テスト用デバイス(ベンダーID 0xFFF1)を追加するときだけtrueにします。本番ではオフのままにしてください
    MATTER_LOG_LEVEL infoのままにしてください。debugではサーバーがWi-Fiパスワードを含むリクエストの生データをログに残します
    MATTER_BLUETOOTH_ADAPTER 下のBluetoothファイルを使うときのBluetoothアダプター番号(0 = hci0)

    AoTで管理 → システム管理 → 一般設定のMatterを使用(実験的)をオンにして保存します。すると設定メニューにMatterが表示されます(オフの間は表示されません)。

    管理 → システム管理 → Matterを開きます。Matter Serverカードに、Status(Connected / Not connected)、サーバーのバージョン、Fabric ID、デバイス数とそのうちReachable(応答中)の数が表示されます。接続されていない場合は、最後のエラーと同じ起動手順が表示されます。

    3. 任意: 新規デバイス用のBluetooth~

    箱から出したばかりのデバイスを追加するには、ホストにBluetoothが必要です。aot/scripts/check_matter_host.sh --bleを実行して報告された問題を直し、追加のcomposeファイルを付けてサーバーを起動します。

    docker compose -f docker/docker-compose.prod.yml -f docker/docker-compose.matter-ble.yml up -d

    以降のcomposeコマンドでは、必ず2つのファイルを一緒に指定してください。最初のファイルだけでup -dを実行すると、Bluetooth設定が抜けた状態でサーバーが作り直されます。コンテナは非特権のままで、ホストのD-Busを読み取り専用で受け取るだけです。

    Bluetoothが有効になっていない場合は、Add a new deviceの下にその旨が表示されます。共有デバイスの追加と、すでにネットワーク上にあるデバイスの追加は、そのまま使えます。

    4. ネイティブインストールで起動する~

    AoTをDockerではなくネイティブ(/opt/AoTのaot・aotflask・aotmcpサービス)でインストールした場合は、MatterサーバーだけをDockerで起動し、AoTのサービスにそのアドレスを伝えます。以下のコマンドはすべてホストの/opt/AoTで実行し、管理者権限が必要です。

    1. ホストを点検します(上の手順1)。Bluetoothを使う場合は--bleを付けます。
    2. Docker Engineをインストールします(すでにあれば省略します)。 
      curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
    3. Matterサーバーを起動します。Bluetoothで新規デバイスを追加する場合は、この後も常に-f docker/docker-compose.matter-ble.ymlを一緒に指定します。 
      sudo docker compose -f docker/docker-compose.matter-native.yml up -d
    4. AoTの3つのサービスにサーバーのアドレスを伝えて再起動します。 
      for s in aot aotflask aotmcp; do
  sudo install -D -m 644 install/aot-matter.conf /etc/systemd/system/$s.service.d/matter.conf
done
sudo systemctl daemon-reload
sudo systemctl restart aot aotflask aotmcp
    5. 管理 → システム管理 → 一般設定のMatterを使用(実験的)をオンにします。必要なパッケージがない場合はパッケージ管理画面へ案内されるので、インストールします。その後、Matterページでサーバーが接続済みと表示されるか確認します。

    Dockerインストールとの違い:

    • ソケット中継(matter_socket)はありません。AoTはホストで動作し、サーバーのループバックポート(127.0.0.1:5580)に直接接続します。このポートには認証がないため、このホストにログインできる人はMatterデバイスを操作できます。
    • Matterのデータ(Dockerボリュームaot_matter_matter_data)はAoTのバックアップに含まれません。FabricのルートCA鍵が入っているため、別にバックアップして秘密として扱ってください。 
      sudo docker run --rm -v aot_matter_matter_data:/data -v "$PWD":/backup alpine tar czf /backup/matter_data.tgz -C /data .
    • AoTをアップグレードしてもMatterサーバーは変わりません。バージョンはMATTER_SERVER_TAGで自分で上げます。

    ほかのアプリで共有されたデバイスを追加する~

    すでにほかのMatterアプリで設定済みのデバイスに使います。

    1. そのアプリでデバイスを開き、共有、ペアリングモード、リンクされたMatterアプリのオプションを選びます。表現はアプリによって異なり、「ペアリングモードをオンにする」や「ほかのハブ・アプリに接続」にあることが多いです。
    2. アプリが11桁のペアリングコード(とQRコード)を表示します。約15分間有効です。
    3. AoTでAdd a shared deviceを開き、Pairing codeにコードを入力して追加を押します。

    追加は通常1分以内に終わります。コードが間違っているか期限切れの場合は、AoTが諦めるまで数分かかることがあるので、ページを開いたままにしてください。

    AoTは、MatterデバイスごとにAoTデバイスを1つ作成して有効にします。その下に次が作られます。

    • デバイスが提供する測定値ごとにチャンネルを持つセンサー入力
    • 制御できるエンドポイントのための出力:スイッチ出力とディマー出力はそれぞれ1つで、エンドポイントごとにチャンネルが1つずつ。カーテンは1台ごとに出力1つ

    追加されたセンサーとスイッチの数が通知で表示されます。デバイスはMatter Devices一覧とデバイスページに表示されます。AoTはデバイスに自分を「AoT」という名前で登録するため、ほかのアプリの接続済みアプリ一覧にも「AoT」と表示されます。

    AoTはペアリングコードを保存も記録もしません。コードはMatterサーバーに直接渡され、短時間だけ有効ですが、期限が切れるまではデバイスの鍵と同じなので、ほかの場所に貼り付けないでください。

    デバイスを削除して後で再び共有した場合、AoTはメーカーが付けた固有IDでデバイスを見分け、新しく作る代わりに既存のAoTデバイスに再接続します。そのため測定履歴が途切れません。

    Bluetoothで新しいデバイスを追加する~

    箱から出したばかり、または工場出荷状態に戻したデバイスには、Add a new deviceを使います。AoTがBluetoothでデバイスを見つけ、ネットワークに参加させ、自分のファブリックに追加します。ほかのアプリは不要です。

    必要なもの:

    • デバイス本体または箱に印刷されたペアリングコード
    • MatterサーバーでBluetoothが有効(上記参照)で、デバイスをAoTサーバーの近くに置くこと
    • Networkとして次のいずれか:
      • Wi-Fi: Wi-Fi network nameとWi-Fi passwordを入力します。デバイスが2.4 GHzのみ対応なら、2.4 GHzのネットワークを選んでください。
      • Thread: お使いのThreadネットワークのThread dataset (hex)を貼り付けます。Threadボーダールーターがネットワーク上ですでに動作している必要があります。
      • Already on the network (Ethernet): デバイスがすでにネットワークに接続されているため、認証情報は不要です。

    追加を押します。ジョブはバックグラウンドで動作し、ページが数秒ごとに進行を確認します。デバイスの探索、ネットワークへの参加、ネットワーク上での再検出に数分かかることがあり、AoTは約12分で諦めます。デバイスが現れると、AoTデバイスが自動で作成されます。ページを閉じても構いません。ページを閉じている間に参加したデバイスは、一覧にNo AoT deviceと表示され、Create AoT deviceで作成できます(見つからないデバイスと孤立デバイス参照)。

    Wi-FiパスワードとThreadデータセットについて

    AoTはWi-FiパスワードやThreadデータセットを保管しません。デバイスを参加させるために一度だけMatterサーバーに渡し、ジョブが成功しても失敗しても、サーバーの認証情報リストから削除します。AoTのジョブファイルやログにも書き込みません。

    ただし、Matterサーバーはデータを追記専用の記録として保存するため、認証情報を削除した後や再起動後も、パスワードやデータセットがその記録に平文で残る可能性があります。現在のサーバーでは、AoTから消すことはできません。このデータはAoTのバックアップ(matter_data)に含まれます。そのため、

    • matter_dataを含むバックアップはすべて機密として扱い(アップグレード・バックアップ・復元)、
    • ネットワークのセキュリティが重要な場合は、デバイスを追加した後にWi-Fiパスワードを変更してください。

    作成されるもの~

    センサー~

    入力は、デバイスが自分で送る報告を読み取ります。値は、デバイスが変化を報告したときと、一定間隔のサンプル(デフォルトは60秒、入力のSample Interval (seconds)で設定)で記録されるため、安定した値が古い値に見えることはありません。応答しないデバイスは値が入らなくなり、デバイスに通信障害が表示されます。デバイスが「値なし」と報告した値はスキップされ、0として保存されることはありません。

    測定 保存される単位
    温度 °C
    相対湿度 %
    照度 lux
    接点(開/閉) オン/オフ
    バッテリー %
    圧力 kPa
    流量 L/min
    在室 オン/オフ
    CO₂ ppm
    PM2.5 µg/m³
    土壌水分 %
    電力・電圧・電流 W、V、A
    積算電力量 kWh
    ボタン 押した回数(長押しは−1として記録)

    CO₂とPM2.5は、デバイスがAoTの保存する単位で報告する場合にだけ追加されるため、別の単位の値を誤って換算して保存することはありません。AoTが認識しない値も同じ理由で無視されます。

    接点・在室・ボタンは、値が変わったときに入力に紐づくエッジトリガーも実行します(オン = rising、オフ = falling)。GPIO入力と同じ仕組みです。ボタンは押されたときだけ記録し、繰り返しのサンプルとしては書き込みません。

    スリープするバッテリーデバイスは、ポーリングで電池を消耗しないよう、直接読み取る代わりにデバイスの報告を受けて使います。

    出力~

    デバイス AoTの出力 動作
    スイッチ・プラグ・リレー オン/オフ出力 オンとオフを切り替えます
    調光できる照明 PWM出力、0–100 % デューティ1–100 %が明るさ、0 %またはオフが消灯、値なしの「オン」は前回の明るさで点灯です。調光可能と自己申告するデバイスだけをディマーとして扱います。通常のリレープラグを「30 %レベル」で駆動することはありません
    カーテン・遮光・換気窓 値出力、0–100 %の位置、100 = 開 下記参照

    スイッチとディマーはそれぞれ出力1つに、エンドポイントごとのチャンネルが作られます(2口プラグはチャンネル2つの出力1つ)。カーテンは1台ごとに出力が作られ、統合環境制御が個別に使えます。調光可能なエンドポイントは、スイッチのチャンネルではなくディマーのチャンネルになります。

    カーテンと窓カバー。 AoTは100 = 全開、0 = 全閉を使い、デバイス側の方式(Matter自体は0 = 開)への変換はAoTが行います。位置を報告するデバイスは正確なパーセントまで動きます。位置を報告できないデバイスは、50 %以上を「開く」、50 %未満を「閉じる」と解釈します。AoTは最後の位置を記憶する(移動中は約10秒ごと)ため、環境コーディネーターがカーテンを遮光や換気のアクチュエーターとして使えます。

    カーテンではオフは停止であり、閉じるではありません

    カーテンにオフを送ると動きが止まります。閉じるわけではありません。非常停止や終了時の動作など、「オフ」を「閉」の意味で使う機能にも同じことが当てはまります。カーテンはその場で止まるだけです。カーテンを閉じるには、値0を送ってください。(地図の閉じるボタンとAIアシスタントの閉じるコマンドはすでに0を送り、オフ・停止は止めます。)

    モジュール名はMATTER_NODE(入力)、MATTER_ON_OFF・MATTER_LEVEL・MATTER_COVERING(出力)です。オプションの一覧は対応する入力と対応する出力にあります。

    Matterデバイス一覧~

    Matter Devicesカードには、AoTのファブリックにあるすべてのデバイスが表示されます。

    列 意味
    Device 名前・メーカー・モデル(ファームウェアのバージョンまたはアップデートの進行状況)
    Sensors and switches AoTが作成したセンサーとスイッチの項目数
    Reachable Reachable(応答中)、またはサーバーがデバイスを見失うとNot reachable。サーバーは、デバイスが応答しなくなってから約5分後に応答なしと表示します
    AoT device このデバイスを包むAoTデバイス、またはNo AoT device

    各行のボタン: Read again、Share this device、Firmware、削除、そしてAoTデバイスのないデバイスにだけCreate AoT device。

    Read againは、デバイスを読み直して、追加時にはAoTが知らなかったが現在は対応しているセンサーや制御(たとえばAoTのアップデート後)を追加します。追加のみを行います。既存のチャンネルには触れず、スイッチとして登録された調光エンドポイントも自動では変換されません。そのスイッチ出力を削除してから読み直すと、ディマーになります。

    AoTのデバイスをほかのアプリと共有する~

    逆方向もできます。AoTがすでに制御しているデバイスを、Apple HomeやGoogle Homeなどのほかのアプリでも使えるように共有できます。

    1. Matter Devices一覧で、デバイスのShare this deviceを押します(Reachableである必要があります)。
    2. ダイアログに11桁のコードが表示され、コピーできます。これを要求するアプリ用にQRコードのテキストも出ます。コードは15分間有効です(共有ウィンドウは180〜900秒の範囲で開けます。画面は900秒で開きます)。
    3. ほかのアプリで「デバイスを追加」、Matterの順に選び、コードを入力します。多くのアプリは、スキャンの代わりに11桁のコードを受け付けます。
    4. ほかのアプリがデバイスを追加するまで、ダイアログを開いたままにしてください。 ダイアログを閉じる、またはClose sharingを押すと、共有ウィンドウが閉じてコードが無効になります。

    共有ウィンドウをもう一度開くと、前のコードは無効になります。AoTはコードを保存しません。デバイスにほかのエコシステム用の空きがない場合、AoTは開始前に拒否し、そのデバイスのほかの接続を1つ先に削除するよう案内します。

    接続中のエコシステム~

    同じダイアログのConnected ecosystemsに、デバイスが現在接続しているすべてのアプリとハブ(名前・メーカー、およびデバイスが対応する数のうちConnections used)が表示されます。AoT自身の行にはThis is AoTと表示されます。

    連携解除は、ほかのエコシステムをデバイスから外します。そのアプリはデバイスを制御できなくなり、再び使うにはデバイスを追加し直す必要があります。AoTはその後デバイスを読み直し、接続が本当になくなったことを確認します。AoT自身はここでは解除できません。デバイスからAoTを外すには、デバイスを削除してください。

    ほかのアプリがデバイスからAoTを削除した(「追い出した」)場合、デバイスが数分間Reachableのまま見えることがあります。AoTはセンサーをデバイスから直接読むため、失敗したサンプルは記録されず、デバイスに通信障害が表示され、コマンドはエラーになります。

    ファームウェアのアップデート~

    Firmwareは、現在のバージョンを表示するダイアログを開きます。Check for an updateは新しいバージョンがあるかを問い合わせます。AoTはファームウェアを自動ではインストールしません。アップデートは必ず人が開始します。

    AoTは次の条件を満たす場合にだけアップデートをインストールします。

    • 認証済みの提供元(CSAの本番用分散コンプライアンス台帳)のものであること。テスト用やローカルのイメージは認証されていないため拒否します。
    • デバイスが応答していること。
    • デバイスがアイドル状態で、すでにアップデート中でないこと。

    更新を押して確認します。デバイスが再起動し、数分間使えなくなることがあります。その時点で重要なもの(ポンプ・ヒーター・換気窓)を制御しているデバイスは更新しないでください。進行状況(ダウンロード、インストールなど)はデバイスの行に表示されます。

    見つからないデバイスと孤立デバイス~

    • Not on the Matter server — share it again to reconnect, or remove itは、AoTにはデバイスがあるが、Matterサーバーがそのデバイスをもう認識していないという意味です(たとえばサーバーのデータが初期化された場合)。ほかのアプリでデバイスを再び共有すると、AoTは同じAoTデバイスに再接続します。そうでなければ削除を押してください。
    • No AoT deviceは、デバイスがAoTのファブリックにはあるがAoTデバイスがないという意味です。たとえば追加している最中にページを閉じた場合です。Create AoT deviceを押してください。

    デバイスを削除する~

    行の削除を押す(またはデバイスページでAoTデバイスを削除する)と、確認が出ます。その後AoTは、

    1. デバイスから自分を削除して接続枠を空けます(必須の手順です。枠が残ると、いずれほかのアプリがデバイスを追加できなくなります)。
    2. AoTデバイスとその入力・出力を削除し、
    3. 記録された測定履歴はデータベースに残します。

    デバイスの電源が切れているか到達できない場合も削除は進みますが、AoTはデバイスから自分を外せないため、警告が表示されます。その場合は、ほかのアプリの接続済みアプリ一覧からAoTを削除してください。

    シーケンス・PID・ウィジェット・トリガーなどがその入力や出力をまだ使っている場合、削除は拒否され、何も変更されません。先にそちらから外してください。

    権限とグループ~

    操作 必要な権限
    ページを開く、一覧を見る 表示設定
    デバイスのConnected ecosystemsを見る 表示設定、かつ操作できるグループのデバイス
    追加(共有・新規)、Create AoT device、Read again、削除 設定を編集 および コントローラを編集
    Share this device、Close sharing、連携解除、ファームウェアの確認と更新 設定を編集 および コントローラを編集、かつ操作できるグループのデバイス

    グループを使っている場合、特定のデバイスに対する操作(接続の表示・共有・連携解除・ファームウェア)は、そのAoTデバイスのグループで検査されます。AoTデバイスのないデバイスはどのグループにも属さないため、グループに制限されないユーザー(「すべてのグループにアクセス」の役割)だけが扱えます。検査ができない場合、操作は拒否されます。

    バックアップ~

    Matterファブリックはmatter_dataボリュームにあり、AoTのバックアップに含まれます。ここにはファブリックのルートCA秘密鍵があります。これを持つ人は、同じネットワーク内からAoTに追加されたすべてのMatterデバイスを操作でき、失うとすべてのデバイスを共有し直す必要があります。アップグレード・バックアップ・復元を参照してください。バックアップファイルを保護し、Web画面からの復元はmatter_dataを復元しない点に注意してください。

    最初の起動後は、ベンダーIDとファブリックIDを変更しないでください。既存のデバイスがすべて孤立します。

    トラブルシューティング~

    追加に失敗すると、AoTが理由を表示します。原因は次のように分類されます。

    メッセージ 対処
    Matterサーバーに届かない matter_serverとmatter_socketのコンテナが動作しているか、COMPOSE_PROFILES=matterが設定されているかを確認
    ペアリングコードが正しくない 数字を確認してやり直す
    デバイスがコードを受け付けない 共有ウィンドウが閉じた可能性があります。もう一度共有して新しいコードを入力してください。新規デバイスなら、本体や箱のコードを確認
    ネットワークでデバイスが見つからない デバイスがAoTと同じネットワークにあり、共有ウィンドウが開いている必要があります。aot/scripts/check_matter_host.shを実行。新規デバイスなら、サーバーの近くでペアリングモードにし、--bleでBluetoothを点検
    デバイスが時間内に参加を完了しなかった ほかのアプリで再度共有(新規デバイスは再びペアリングモードに)してやり直す
    Matterサーバーがネットワーク情報を受け付けない (network_rejected) Wi-Fi名・パスワード、またはThreadデータセットを確認
    MatterサーバーがBluetoothを使えない (ble_unavailable) check_matter_host.sh --bleを実行し、docker-compose.matter-ble.ymlでサーバーを起動
    デバイスがWi-Fiに参加できない (wifi_failed) 名前とパスワードを確認し、デバイスが必要とするなら2.4 GHzのネットワークを使う
    デバイスがThreadネットワークに参加できない (thread_failed) Threadデータセットと、Threadボーダールーターの動作を確認
    デバイスにほかのエコシステム用の空きがない そのアプリでデバイスのほかの接続を1つ削除してから、再び共有
    デバイスが認証済みであることを証明できない AoTサーバーがCSAのデバイス台帳にインターネットで届く必要があります。開発・テスト用デバイスにはMATTER_TEST_DCL=trueが必要

    知っておくべきこと:

    • 値が入ってこないのにデバイスがReachableに見える場合は、接続中のエコシステムの追い出しのケースを参照してください。ほかのアプリでデバイスを確認します。
    • ThreadボーダールーターやメッシュWi-Fiを変更した後は、デバイスがしばらく応答しないことがあります。ホストの点検をもう一度実行してください。
